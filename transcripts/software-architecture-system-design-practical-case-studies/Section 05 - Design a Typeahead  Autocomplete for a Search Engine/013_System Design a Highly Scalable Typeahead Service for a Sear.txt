# System Design a Highly Scalable Typeahead Service for a Search Engine - Part 2

Welcome back. In the previous lecture, we started designing the type ahead system for a search engine. After capturing all the system requirements and defining our API, we had a first attempt at designing our system. In that attempt, we used a data structure called trie or lexical prefix tree, which is typically used for those type of use cases. However, after deeper analysis, we realized that that data structure would not fit our system. Due to our scale and performance requirements. However, on the positive note, we made two important observations that may give us a clue on how to proceed. The first observation was that although both of our rest API endpoints read and update the same data, they have entirely different performance requirements. So internally we can follow the pattern and have two completely different representations of the same data, each optimized for its own use case. The second observation was that we don't need to update our autocomplete suggestions immediately after a user sends us a search query and the suggestions we show our users can lag behind real time data by up to one hour. That gave us a clue that we could use the batch processing pattern for big data. So with those two important clues in mind, let's make a second attempt at our system design. Following a microservices architecture with the secure rest pattern, we will have two services. The first one is going to be called the Autocomplete Service. The service will take all the autocomplete requests whenever a user types in a character into the search box in their UI. Additionally, it will have a database where those autocomplete suggestions will be stored optimally so they can be quickly retrieved based on the given prefix. Now, what would be the most optimal way to store that data? Well, a simple mapping between a given prefix to a sorted list of ten autocomplete suggestions would be the easiest and most effective way to store this data. For instance, if the user wants to search for how to open a jar of olives, they will first type in the letter H. That will trigger a request to the Autocomplete service, which will search for that entry, for that prefix in the key value store. And once it finds that entry, it will simply read the list of ten suggestions and send it back to the user. Similarly, if the user types one more character, the letter O, it will result in another request for the h o prefix. The autocomplete service will then look up the prefix h o and return the sorted list of autocomplete suggestions based on their popularity in the last 24 hours. Of course this mapping is very big, but we don't need to store it all on one computer and we will see how we can distribute it in a way that can scale to meet our requirements a bit later. The bigger question is how we can get that data represented in such a nice way. So let's proceed to our second API endpoint, the search. In addition to going to the relevant search infrastructure, which is out of scope for our design, the request will go to a new service which we will call the Autocomplete Updater Service. The information that comes with each request to the service is a tuple containing the user's search query and the timestamp of when that search happened. So the first thing that we need to do is simply store each such tuple in a database or simply in a distributed file system for further processing. Now we can build a big data processing pipeline that can run on a schedule. The first step in this process is called map and it will iterate over all the tuples and perform the following logic. First, it will look at the timestamp and make sure that the search query was submitted within the last 24 hours. If the query is too old, it will be ignored. Then the map function will break the search query into all possible prefixes and for each prefix it will emit a key value pair where the key is the prefix and the value is the original query. So for example, after processing the search query for bat, it will emit the following key value pairs. Then after processing the query for bad, it will emit those two pairs and after processing the tuple containing the query better, we will get the following five key value pairs. Also notice that since the search query better was submitted twice, it will be processed twice. So at the end of this processing stage we'll have a big list of key value pairs corresponding to the search queries that happened in the last 24 hours. Now, to make the next stage in the pipeline easier, instead of placing all the key value pairs in random places will distribute them strategically so all the pairs with the same key will end up either in the same file or at least on the same computer. One way to do this is simply applying a hash function on each key. In the next step, which we will call reduce, will have a process that looks at the output of the previous step and aggregates it by key. So given a prefix and a list of original queries for that same prefix, this function will perform a top k sort where k is ten per our requirements and at the end we simply emit a new key value pair where the key is the prefix and the value is a sorted top ten search queries for the given prefix. So for example, after processing the prefix B, we'll get this output and similarly, after processing all the other key value pairs that were emitted by the map function, we get the following output. And since this is exactly what we need, we can store it inside a file system back database. Now the names map and reduce of course, are no coincidence. This pattern we just used is called MapReduce, which many big data processing technologies follow in one way or another, though their terminology may be a bit different. As a final step, we need to publish those results to the Autocomplete service. Efficiently, we can do it in many ways, but the most efficient way would be a technique called change data capture or CDC. With this model, we'll have a process that watches the logs of everything that happens to the target database that stores those mappings and every event in that log that indicates that a particular mapping from a prefix to a list of sorted suggestions has changed. This CDC process will read that data and publish it as an event to a message broker. The Autocomplete Service will then subscribe to events from that message broker and update its in-memory read optimized database with this new data. Now we can run this big data processing pipeline on a schedule every 30 minutes or every hour, depending on how long it takes to complete. But the important thing is at the end of this pipeline, execution will always end up with the mappings from prefixes to a sort of list of autocomplete suggestions available for the Autocomplete service to read. So now that we addressed our functional requirements and have a software architecture diagram for the autocomplete system, we are left with only one last step which is addressing our non-functional requirements. So in the next and last lecture of this section, we'll see how we can scale the system to billions of daily users and keep the autocomplete response time under the desired value.
