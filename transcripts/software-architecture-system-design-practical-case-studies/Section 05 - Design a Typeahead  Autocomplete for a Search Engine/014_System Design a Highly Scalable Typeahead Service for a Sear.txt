# System Design a Highly Scalable Typeahead Service for a Search Engine - Part 3

In the previous lecture we finished the architecture diagram for our type ahead system that addressed our functional requirements. As a reminder, we have two user facing services in the current architecture, one for each API endpoint. The first one is the auto complete service, which takes type ahead requests from the user's search box and sends back a sorted list of suggestions for common search queries that start with the given prefix. The second one is the auto complete Updater service. This service takes every search query intended for our search engine and updates our auto complete records through a big data processing pipeline. The batch process data thatrillionuns on a schedule then makes its way to the auto complete service through a change data capture process. The tales, the database logs and publishes an event only about the records that actually changed. The auto complete service subscribes to those events and updates its key value store with the new suggestions for the given prefix. So now let's go ahead and address our non-functional requirements. As a reminder, we have billions of daily users using our search engine. That means we have to process billions of search queries that go to our Autocomplete Updater service and at least that amount of traffic will go to the autocomplete service. But it will most probably be even higher because on average the user will need to type at least a few characters for every search query before getting a relevant autocomplete suggestion from our system. So let's start with placing the autocomplete service behind a load balancer and running it as a group of instances. Similarly, we'll add a load balancer for the Autocomplete Updater service and deploy it as a group of identical instances running on different computers. Now let's look at the Autocomplete Service Key Value Store. As we already noticed in the previous lecture, the number of mappings between a prefix and a list of suggestions is very high. So to scale this database, we'll first shard it so the data can fit in the memory of each database instance. It's important that it does fit in memory and not just on disk. Because of our performance requirements. The simplest approach would be to use a hash function with an even random distribution, so the keys are properly distributed across all the database instances. But storage is not our only problem, unfortunately. Sharding helps us with data distribution and not so much with load distribution. The problem in our case is that inevitably some prefixes will get more traffic than others. For example, one letter prefixes will probably be more popular than three letter prefixes. Certain one letter prefixes will be more popular than others, and certain three letter prefixes will also be more popular than others. So a database shard with one or multiple such popular keys may become a hotspot and as a result, a performance bottleneck. One way we can address it is by adding database replication. Besides the high availability benefit of using replication, we can now balance the load on each shard across multiple replicas. Instead of sending all the requests to a single instance. This is definitely an improvement, but it's still suboptimal. Generally an off the shelf key value store solution allows us to set a fixed replication factor for all the keys. This means the number of replicas will be the same regardless of the traffic load on a particular shard. This number may be too large for some shards, so we end up overpaying for storage and for some shards. This number may be too low, so we will still have a performance problem. Additionally, our traffic pattern may change depending on global events, time of the day or season. So a better approach would be to introduce a proxy between the Autocomplete service and the database instances which will call a shard manager. The shard manager is. Responsible for two things. The first one is for distributing the data across different shards for optimal storage, but also in addition, it will look at the traffic load on each shard and dynamically add or remove read replicas from each shard. We can do it by setting a lower and upper bound on either the average network traffic or CPU utilization per database instance in a given shard. That data can be collected by a background process that runs on each host and is sent periodically to the shard manager. Once a particular database shard gets close or exceeds the upper bound. The Shard Manager provisions a new replica instance for the given shard. The Shard manager then triggers a data sync from the Shard primary to the replica, and then adds that shard replica to the replication group. Similarly, if the average load on a particular shard drops below a certain level, the shard manager can save US costs by removing one of the replicas from that shard. This way we can balance the load across multiple read replicas on each shard. Depending on the load of its requests, which ultimately helps us meet our strict performance requirements because we no longer have any hotspots in our system. Obviously for high availability, we will never run a single shard with only one database instance. So the third role of the Shard manager will be to maintain a minimum of healthy nodes for every shard. Now let's move on to the second part of our system, which is updating the autocomplete suggestions based on real users search queries. Specifically, let's zoom in into our big data processing pipeline. The first observation is that while we get billions of search queries to our system, many of them will likely be repeated by different users. But notice that we only care about the frequency of each query relative to others, not the absolute number of times that query was repeated. So to reduce the amount of data we need to process, we can introduce sampling. For example, if we're getting about 10 billion search queries per day, that would be equivalent to roughly 400 million search queries per hour. If we throw away only 1% of those requests at random, our map function will have 4 million fewer queries to process. Since the map function breaks each input query into all its prefixes which the reduce function later needs to process. The performance impact of the sampling is multiplied. The next improvement we will make is instead of running a single map process on one computer, we will run map instances on different computers. Each map instance will take a portion of the input and process it in parallel to the other instances. Similarly, we can allocate our reduce instances running on different computers in parallel to each other and distribute the groups of intermediate key value pairs produced by the mappers across those instances with those two modifications. We can scale to a large amount of input data and cut the processing time significantly. Of course, the target database where the big data pipeline writes its data to will also be partitioned to store the results on multiple computers. Similarly, the CDC service will also run as a group of identical instances, and that's it. Our big data processing pipeline is now highly scalable and performant. As a final step, we can run our autocomplete system in multiple geographical locations, in different data centers. This will help us with high availability and also reduce the latency to our users. And that's it. We successfully addressed all of our requirements and we now have a fully functional, highly scalable and performant typeahead system that can save our users millions of typing hours when using our search. So before we conclude, let's quickly recap the highlights of our design. As a first attempt, which. Tried to apply the lexical prefix tree data structure to our typeahead system. However, we quickly realized that while this data structure is a perfect choice for this type of problem on a smaller scale, it did not meet our requirements on a larger scale. After that, we realized that we could instead apply the pattern and have two separate architecture paths and representations of our data, each one optimized for its purposes. We use the highly scalable distributed key value store for the autocomplete database, and we use the combination of sharding and dynamic replication using a shard manager. This way we could distribute the data across different shards and balance the traffic load on different replicas of each shard. When our auto complete updating path, we use sampling to reduce the volume of data we needed to process. And we also used the batch processing and MapReduce pattern to efficiently process the input search queries. Finally, to transfer the new data to the auto complete service without duplication. We used a change data capture service this way only database entries that change their content made their way to the message broker and were eventually read by the auto complete service.
