# System Design a Highly Scalable Typeahead Service for a Search Engine - Part 1

Welcome back. In this section, we will in this section, we will design a type ahead or autocomplete system for a search engine. Let's understand what exactly we need to design. In 2004, Google added a very cool feature to their search engine, which they called Google suggest. Interestingly, this feature started as a 20% side project by a software engineer named Kevin Gibbs, and by 2008 it became the default mode of Google search engine. With this feature, as soon as the user starts typing a search query in the UI, the search engine starts suggesting popular queries that start with the characters that the user already typed. A variation of this problem comes up a lot in system design interviews and for a good reason. Today, any platform that offers a search box in their UI has this feature which in the aggregate saves users millions of typing hours per year. So in this lecture we're going to design exactly that feature. As always, let's start with gathering the exact requirements for our system by asking some questions. The first important question is what criteria do we need to use for query suggestions? Some options include recent trending queries, most popular queries or suggestions based on the user's search history. The second question is whether we need to offer spell checking and correction of common typos. Also, we want to know how many suggestions we need to provide to the user. Then we want to know the languages that we want to support. And finally, it's important to know upfront the maximum length of a prefix that we need to provide suggestions for. So let's assume that we want to support only the English alphabet for the moment. Any time a user types a character, we want to provide ten suggestions. Those suggestions will be based on the most popular queries among all the users in the last 24 hours and the maximum prefix that we want to provide type ahead capabilities is 60 characters. It's also important to note that the actual search engine is out of scope for this design. All we need to focus on is the type ahead part of the search service, and we also don't need to support any spell checking. So if we don't find any suggestions for a given prefix, we simply don't show the user anything. Now let's move on to the non-functional requirements. The first important question we need to ask is the scale of users and queries we need to handle. And even more importantly, we need to understand the latency requirements to provide the autocomplete suggestions to the users. Finally, we need to know the consistency model of those suggestions. In other words, do we need to show all the users that type the same prefix, the exact same autocomplete suggestions in the same order or not? And do we need to provide the most up to date order of suggestions? Or can that data be a bit out of date? So let's assume that the answer to our questions is as follows. In terms of scale, let's assume we have billions of search queries daily. The performance requirements are pretty strict because if the suggestions come too late or are much slower than the typing speed of an average user, those autocomplete suggestions will not be helpful. A slightly above average typing speed is about 50 words per minute, which is equivalent to 250 characters per minute or four characters per second. So if each character the user types results in a new query suggestion, our system needs to have a maximum response time of 240 milliseconds. And let's say that our search query suggestions for a given prefix can be up to one hour out of date. Finally, eventual consistency is good enough for us and we don't have to provide all the users with the same suggestions or ranking order simultaneously. So now that we captured all of our functional and non-functional requirements, let's proceed to define our Systems API. In this case, we only have two types of calls from the user which we can represent using a rest API using HTTP. The first API endpoint we will define is the complete endpoint for search queries. So if a user wants to type the query, how do I open a jar of olives? Once they type the first letter h, the front end code will send a get request to the complete endpoint with the query parameter of the letter H. The response will simply be adjacent formatted array of autocomplete suggestions sorted by their popularity. If the user doesn't see anything helpful, they will proceed to type the second character in their query, which is the letter O. This will trigger another HTTP get request to our system to the same endpoint, but with the query parameter of h o. And this process will continue until the user either types the entire query themselves or picks a suggestion and clicks the search button. The second rest operation or endpoint is the actual search. In this case, the user already has the desired search query in their search box and they simply click the search button. The action will trigger an HTTP get request to be sent to the search endpoint of our system with the search query as the URL parameter. In response, our search engine will send back the search results for the given query. Notice that although this request internally will update our analytics about the most common search queries, the user doesn't need to know about it. And since getting a list of search results from a user perspective is an idempotent operation with no side effects, this is still an HTTP get method. The second thing to notice is the search query may contain special characters like spaces that are not URL friendly. So our front end will need to perform URL encoding on that query and our system will have to perform URL decoding when it receives that data. The third thing worth pointing out is that our user may type the search query in uppercase letters. However, our autocomplete service should not be case sensitive and internally we should convert all the uppercase letters to lowercase letters. So now that we finalized our API, let's make the first attempt at figuring out how to provide this functionality. Usually whenever we need to provide any type ahead or autocomplete system based on a prefix, there is one data structure that comes to mind. This data structure is called a lexical prefix tree, or sometimes it's just referred to as trie. So first let's see how this data structure works and if it can help us in our use case. A lexical prefix tree or trie is a tree data structure where the root represents an empty string. But instead of two children nodes, each node can have multiple children, one for each letter in the alphabet. Each path from the root to a terminal node represents a string so strings with the same prefix share the same path from the root, following the prefix until the two strings diverge into two different strings. For example, all the words bad, bad and better all start with the letter B, so they're all sharing the same path that goes through the node that represents the letter B, Then the B node has two edges to two additional children, one with the edge that corresponds to the letter A that leads to the word bat. The second leads to the prefix B through the edge corresponding to the letter E, and that node also has two edges that lead to two children nodes. One goes through the letter D and terminates, which means we have the word bad in our tree. Another goes through a series of nodes and edges and terminates with the word better, which means the word better is also in our tree. So using this data structure, if a user asks us for all the strings that start with the prefix. Of the letter B, All we need to do is go from the root to the B node and all its branches are strings that have the prefix of the letter B. Similarly, if the user types one more letter and asks us for the strings that have the prefix of B, then we need to take the b edge from the root and then take the edge and arrive at the prefix node that corresponds to the prefix B and now all the branches that stem from this node are valid autocomplete suggestions for the prefix B. Additionally, we can also augment this trie by adding a counter to each terminal node representing the frequency of this given string by users of our search engine. And now we have all the information that we need to provide the autocomplete functionality. This data structure would be a perfect choice if we were asked to design an autocomplete feature for something like a stand alone ID. All we need to store in that data structure are a few programming language keywords and a handful of variable names available to us in the given context and possibly also a few dozen of classes or modules. It would also be a great way to implement Autocomplete functionality to suggest email addresses or search queries we recently used. But unfortunately it will not be a good choice for our use case. And let's see why. The first reason is the size of this tree. If we revisit our functional requirements, we see that we need to provide Typeahead functionality for queries of up to 60 characters. That means that the potential height of our lexical tree is 60 with billions of search requests per day. This tree will most likely contain every combination of words and phrases in the English language. And if every node can have as many as 26 children, not even counting special characters like spaces, this tree can be really big way too big to store in a computer's memory. The second reason is performance. For a given prefix, we would have to traverse all its branches to find the strings that start with it and then sort them by their popularity. The number of branches for prefixes of 1 or 2 letters can be very big, which would take us way too long to traverse and sort on every autocomplete query. But fortunately we can find another solution if we make the following important observations. The first observation is our performance requirements are very different between our two API calls. In other words, while providing the autocomplete suggestion has to be very fast to be under the maximum of 240 milliseconds. The update to the ranking of our autocomplete suggestions doesn't have to be fast at all in this type of situation where we have essentially the same data for two API calls, one for read operations and another for data mutations while having completely different performance requirements are the perfect fit for the command and query responsibility Segregation pattern. This means we can have two completely different data representations instead of one. The second observation is around the fact that we don't need to provide the most up to date ranking for the most common autocomplete suggestions, and those results can lag by one hour behind real time data. This is a big indicator that we can use the batch processing model on the update side of our system. So with those two observations, we're now ready to make our second attempt at our design, which we will make in the following lecture. I'll see you guys soon.
