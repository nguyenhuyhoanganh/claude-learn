# Software Architecture & System Design of a Real-Time Instant Messaging - Part 1

Welcome back. In this section, we will design a highly scalable instant messaging platform where millions of users can communicate with each other in real time. By the end of this section, you will learn many important concepts for any type of real time messaging that can be applied to various systems. So let's start by narrowing down our scope and gathering our requirements, starting with the functional requirements. The first important question we should ask is whether we're talking about direct 1 to 1 messaging or some sort of group messaging. Then to narrow down our scope, we need to understand what type of media can be exchanged between different users. In other words, are we talking about text based communication or do we also want to support things like sharing images or even video calls? Another important question is whether we want to persist our chat history. In other words, if a particular user is offline at the time of receiving a message, do we need to allow them to get that message when they get back online? Finally, what other types of events do we need to exchange between users within a chat besides just the messages? For example, do we need other users connection statuses or do we need to show a user that another user is currently typing a message and so on. So after asking those questions, let's assume that we finalized the following functional requirements. We need to support three types of communication. The first one is direct 1 to 1 messaging. In this type of communication user, A can start a chat by sending a direct message to user B and only those two users can read and participate in that chat. The second is group messaging. In this type of communication, a user can create a group chat by sending a message to a group of users, and all those users can read and respond to messages within that group. The last type of communication is using a dedicated channel. In this type of communication, a user must first create a dedicated named channel for a particular topic. After its creation, other users can join the channel, leave the channel and also invite other users to that channel. You can imagine this type of communication being very useful in a company to discuss certain topics or share team or company announcements. In all of the above scenarios, users who are online should be immediately notified when a message is sent to them directly or as part of a group chat or channel that they're currently subscribed to. But if they go offline for a while and then go back online, they should be presented with all the messages they missed and also the ones that they've already read when it comes to data being exchanged for now, we're going to support only text messages, so we don't need to worry about sharing images or making video calls. Additionally, when a user clicks on another user's profile on their web based UI or mobile app, they should see whether or not the other user is currently online. However, other features like seeing if somebody is currently typing a message, editing a message or deleting a message are out of scope for the moment. Now let's talk about the non-functional requirements for this service, starting with scalability. In our platform, we have millions of daily active users. Most of those users will be connected to our platform for long periods of time throughout the day. So we're talking about six to even 12 hours of daily connection time. Those users will be exchanging lots of messages. So we should design for an average of hundreds of thousands of messages per second where each message is limited to 10,000 characters. Additionally, we can assume that our group chats and in particular our channels can easily grow to hundreds of thousands of participants. Now let's talk about high availability. If millions of users and dozens of organizations depend on our platform for communication, we definitely need to provide high availability. So let's aim for four nines of availability, at least for our paying customers. Finally, let's talk about performance. Of course, for instant messaging, we would like to provide the lowest latency possible. However, it's worth pointing out that getting a message from user A to user B is not as latency sensitive as, for example, showing a web page on the browser. And that's because user B doesn't know that a message has been sent to him and can continue going about his normal daily tasks until he gets that message notification. On the other hand, we don't want the latency to be too long, otherwise instant communication will be impossible. So let's aim for one second at the 99th percentile for message delivery when the user is online. And also let's aim for two seconds for an offline user to log in and get up to date with all the messages that they missed while being offline from the platform. So the next step in our process is to define our system's API and document some critical use cases using a sequence diagram. In our case, the API is going to be pretty simple. A new user to our system will first sign up by providing their name, email, password, public name or username and maybe even a profile image. And in response they can get an authentication token and their newly created user ID. Then they can send us a request for the home page with data about their recent 1 to 1 conversations, group chats and channels. On the other hand, a mobile user can simply log in using those credentials, using their mobile app and in return get an authentication token and their user ID as well. Then if a user wants to send a direct message, they can send us a search request first to find the user ID of a target user. Similarly, if a user wants to create a group chat, they can just repeat the search step until they have all the target. Get user IDs on their device. Once user A finds all those users, they can send us a message containing the target user IDs and the message text. Internally, our system will create a new chat ID or group ID for this new thread and send it back to the user so they can refer to it in the future. Additionally, it will persist that message and look up the users that need to get those messages. If the target user or one of the target users is online, that message will be delivered to their device or web browser instantaneously. Similarly, if a user wants to create a channel, they will send us a request which would send back a channel ID and a channel URL. That URL can be used to invite other users to that channel. And when another user navigates to that URL, they can join that channel. Once a user sends a message to this channel, it will go to our system, which will store it first. Then it will look up all the other users that are part of that channel and are also currently online and it will deliver that message to them one after another. And that's pretty much all the interactions that we need to support between the users and our system. So now, based on this sequence diagram, we can clearly define our system's API by capturing every interaction as well as the data passed to our system and returned to the user. And that's it. Now we have all the requirements as well as our system's API. So I'll see you guys in the next lecture where we'll continue our design by addressing our functional requirements.
