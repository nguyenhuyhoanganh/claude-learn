# Software Architecture & System Design of a Real-Time Instant Messaging - Part 3

Welcome back. In the previous lecture, we finished addressing the functional requirements for our highly scalable instant messaging platform. As a reminder, before creating this diagram, we made two important design decisions. One was to use our system to handle and broadcast all the communication between our users. The second was using a bidirectional communication protocol that every user that wants to receive instant messages needs to establish and maintain with our platform. So let's see how those two big decisions will impact our ability to scale to millions of users and keep our system highly available and performant. Let's start with the first non-functional requirement, which is scalability. Addressing scalability on our services side is going to be pretty straightforward. All we need to do is run each one of our services as a group of instances and place each service behind a load balancer. Since all of our services except for the messaging service are stateless and follow the client service model. This will work out of the box. However, we need to do a bit more thinking when it comes to the messaging service. If we use a simple round robin algorithm to send all our millions of customers to a group of a few, dozens or even hundreds of instances, the load of connections to our messaging servers will spread more or less evenly. However, now when user a connected to server, one wants to send a message to user B connected to server two, we have a problem. Server one will need to first of all know which server user B is connected to and secondly, be able to deliver that message to that server, which means that our instances will now be tightly coupled. So to address this issue, let's consider a few scenarios. The first scenario is our messaging platform is inherently partitioned. For example, if our customers are divided into separate companies and users of each company can communicate with each other, but not with users in other companies. Another example is if our system is partitioned by topics such as a computer game or some other topic that people are interested in. In that case, users of that product or game will communicate with each other directly through a group or different channels. But it doesn't make sense to connect users of different games or products. So if this is our case, then what we can do is at connection time, send all the users from the same organization or topic to a separate server. Each such server internally will maintain an in-memory mapping from a user ID to a connection to each user. This way, when user A sends a message to another user or entire channel within that organization, that server will be able to easily deliver that message to all the intended users that are currently online. And that's because they're all connected to the same server. Now the question is, can a single server maintain so many connections? Well, let's do the math. In this case, each server listens to incoming connections on one single port. In general, each incoming connection is identified by a pair of source IP address, which, if we're using IPV four, is a 32 bit number and a source port, which is a 16 bit number. So theoretically each server can accept up to two in the power of 48 connections, which is a huge number, definitely enough to support even the biggest organization. On the other hand, if a particular server needs to handle a big organization with frequent messages, we can use vertical scaling and upgrade that server, CPU and memory. So basically we scale our messaging service horizontally across different partitions and vertically for each partition as needed. Now let's talk about the second scenario, which is when our user base is not partitioned and every user can potentially communicate with any other user on the. Lot form. So in this case, the best approach would be to distribute the connection load among all the servers. Additionally, we can introduce another service which we will call the Connection Management Service with a highly performant in-memory key value database. That key value store will contain a mapping from a user ID to a messaging server address. Any time a new user connects to an instance of the messaging service, that instance will send a request to the Connection Management Service, which will add an entry with the newly connected user ID and the messaging service server address. Similarly, when a user disconnects from a server, that server will notify the Connection Management Service so it can delete the entry about that user from its key value store. Additionally, we will introduce a message broker between the messaging service and the Connection management service specifically for incoming messages. So now when user A connected to messaging server, one wants to send a message to a group or channel, that message will first arrive at server one. But now, instead of the server connecting to the groups and channel service and the chat history service, it will simply push that incoming message into the message broker. The Connection Management Service, which is subscribed to events from the incoming messages topic, will consume that message asynchronously. Then it will send that message to the Chat history service so it can store it in its database. After that, it will send a request to the groups and channels service to get the IDs of the users that are part of that group or channel. Finally, given those IDs, it will look up the messaging server addresses of all the target users and broadcast that message to those servers. And those messaging servers in turn will deliver the messages to the target users using the bidirectional communication between them and the users. Notice that with this approach we have a few important scalability benefits. First of all, by distributing the load of connections from users among the messaging service instances, our messaging service is fully horizontally scalable. In other words, we can dynamically add new servers if necessary. Also introducing the message broker between the messaging service and the Connection Management service allows us to absorb sudden traffic spikes into our system and buffer those messages. We also move the logic that requires talking to the chat history service and the groups and channel service away from the messaging service which is now executed asynchronously and doesn't hold the user. And finally, using this key value store in the Connection management service, we essentially implemented the publish subscribe pattern. In other words, each messaging service is subscribed to events about their connected users. So assuming that our system is in this second scenario, we now have a solution to scale our services. And the last thing we need to do is add database sharding to all our data stores to ensure that all of our data can be distributed among a group of instances. Finally, to decouple the clients, calling our API from the internal system that implements this API, we will also introduce an API gateway which comes with rate limiting to protect us from users that send us messages at an unreasonably high rate. And that's it. Now let's talk about high availability. To achieve high availability, first we'll need to have a high degree of redundancy, which we already have on our service layer, and we can easily achieve this in the data layer by using database replication. Finally, let's talk about performance. To improve the performance and reduce latency. There are a few things we can do. First, to improve the performance of user login and lookup, we can create an index on the username column in the users table. This will make it very fast for users to get their user ID based on their username when they log into our platform and also when. A user wants to send another user a message, they can quickly find the user ID based on the target username without having to scan through the entire table. Now let's take a look at the chat history database. Typically when a user logs in, they will try to load the latest messages from each group they're part of and channel that they're subscribed to. So to make those queries efficient, we can create two compound indexes. One that creates a hash over the group ID and assorted index on the message ID and another compound index on the hash of a channel ID and assorted index of the message ID. This way when a user looks up the latest messages for a group, for example, they will first query the group ID and then the latest message IDs in this query will be super efficient because of this compound index that we created. In addition, since the recent messages for each channel and group are frequently queried, we can also add an in-memory cache where we can store a subset of those messages for faster lookup. Now let's look at our data in the groups and channels service. The first two tables, the groups and channels don't actually require any indexes because they're mostly write only tables. However, in the group participants and channel subscribers, we need to add a hash index on the group ID and channel ID respectively. This way, looking up the users in a group or channel will be very fast and efficient and that's it. We addressed all the functional and non-functional requirements of our system and we now have a fully scalable, highly available and performant instant messaging platform. So before we conclude, let's quickly recap the highlights of designing the system to deliver messages to users. We use the bidirectional communication protocol instead of using the typical client server model that comes with HTTP to increase the scalability of our messaging service. We implemented the publish subscribe pattern in the Connection Management Service using an in-memory key value store that maps the user IDs to server IP addresses. We also introduced a message broker between the messaging service and the Connection Management Service to make publishing messages by users asynchronous while still maintaining consistency in the chat history database. In addition, we added an API gateway, but this time we also used its rate limiting capabilities to reduce the risk of a user, sending us too many messages in a short period of time. Finally, we also use techniques like caching and indexing to improve the query performance in our database and overall improve the user experience.
