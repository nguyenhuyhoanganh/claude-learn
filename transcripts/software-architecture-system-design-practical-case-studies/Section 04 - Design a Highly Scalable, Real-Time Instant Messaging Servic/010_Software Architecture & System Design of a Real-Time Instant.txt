# Software Architecture & System Design of a Real-Time Instant Messaging - Part 2

Welcome back. In the previous lecture, we completed the first three steps in designing a highly scalable instant messaging platform which was gathering our functional requirements. Non-functional requirements and defining our Systems API. Now let's pick up where we left off and start working on addressing the functional requirements. However, before that, let's have a short but very important design decision about the system we need to architect. The first thing we need to think about is how we're going to connect users to each other to exchange messages. Let's start with the simple case of user A initiating a chat with another user user. B The most natural approach would be a direct peer to peer communication in this topology. User A would first connect to our system and get the IP address of the device that user B is using. Then user A would send a request directly to user B, and if user B accepts the connection, they can continue the chat session independently without our systems involvement. The clear benefit of this peer to peer approach is our system can easily scale to millions of users chatting with each other one on one. And that's because our system will not be involved in passing messages only in the initial matching between pairs of users. It's also going to have the most efficient performance. The reason is that if the two users are both in the same building or country, the latency between them will be much lower than proxying every message through our system, especially if our system is deployed in a remote data center. On the other hand, this approach has one big downside, which is the fact that we also need to support group messaging and channels. For instance, if user A wants to send a message to a channel or a group of a thousand users, that user will have to open a thousand connections from their device and broadcast that message to all the users. This has a few implications. First of all, if the user is using a mobile device, is opening so many connections and transmitting so much data to so many users will quickly drain the mobile device's battery. The second implication is performance. Since the computing power of a single end user device is limited, broadcasting a message to a big group will simply be too slow. The last implication is that we won't be able to store those messages for users that were offline with the message was sent. So instead we're going to use the centralized approach where all the communication will go to the servers running in our system and our system that runs stationary and powerful servers will deliver those messages to the online users. Now the next thing we need to consider is how our servers will send messages to clients. If we look back to our sequence diagram, when we deliver a message, a server in our system is essentially the one initiating a request to the client. As a reminder, HTTP is a client server protocol. In other words, when we use HTTP, we always have one party that acts as the client, and only that party can initiate requests or send data to the server. The server can only respond to the client, but it cannot initiate requests or send data to the client directly without getting a request first. So if we take the centralized approach, how will we push those messages originating from our system to our connected users? So a naive approach is for the users to pull our system servers periodically by sending a request every few hundreds of milliseconds. Besides the fact that with millions of daily users, our system will be overwhelmed with such frequent requests. This approach is also very wasteful because some channels may not have any messages for hours or even days, but those requests will keep coming and cost our system CPU power and money. So to solve this problem, we will choose a different network protocol which allows for full duplex, bi directional communication between the client's browser or mobile app and our servers using a bi directional protocol. The users are still going to be the ones to initiate and establish the connection to our system. However, once the connection is open, the server can send messages directly to the user as they arrive and using that same connection, users can also send messages to our system. So now if we have a channel with, let's say, even a million online users, as long as those users are not sending any messages, those connections will remain idle. Those idle connections won't require any CPU power and they will need very little memory or bandwidth just to stay active. Now, an important side benefit of passing all those messages through our system is we can persist them internally for the benefit of the users that are currently offline. This way, if all or some of the recipients were not connected to our platform when the message was sent, they can still get them after they connect to our system. So with that discussion settled, let's start designing our system, starting with the first API item, which is the sign up of a new user. For that we will use the microservices architecture and add a user service with its own database. In that database, we'll have the users table which contains all the information about the user and their encrypted credentials. Additionally, to store the user's profile image will also use an object store. So for each user who uploads a profile image will have a separate column in the user's table, pointing to that location in the object store to serve web content to our web browser users. We'll also add the web application service. So now a web browser user will first send a request to our web application and get a sign up page that can load in their browser. After the sign up form is submitted, it will go to the user service where all the information about that user will be stored. The flow for a mobile user will be similar, except it won't need to load anything from the web application service, since the mobile app already has its own UI to log into our platform. The browser users will simply request the login page from the web application service and once they load the page in their browser and fill in their credentials, the client code will send a request to the user service. The user service will check if the passed in credentials are correct and if they are, the user will get an authentication token and their user ID. Now when the user is logged in, there is one more thing we need to do and that is the bidirectional connection with our system so they can send and receive messages. For that, we will create a separate service, which we will call the messaging service. And now after the user successfully logs in, they will establish a new bidirectional connection with the messaging service. As long as that connection is intact, the user is considered online. And we'll receive any messages intended for them either because it was sent directly to them or to a group or channel they are part of. Now let's think about what information we need to store and maintain in regards to the three types of communication we need to support on our platform. First of all, it's easy to notice that the first type of communication between two users is really just a particular case of a group chat where the group only consists of two users. So that already narrows down the scope of what we need to care about. Next for each group or channel, we need to store the information about who is part of that entity to deliver the messages. For that, we're going to create a new service, which we will call groups and channels. In the database of that service, we will store the following information. First of all, we'll have a group table in that table. We'll have the group ID and the time it was created. Similarly, we'll have a channels table which contains the channel ID, the channel name, the time it was created, the owner of the channel and the channel URL. Then we'll have another table called Group participants that connects the users and the groups that they are part of. Each row in this table contains a user ID and the group ID the user is part of. Notice that each user and each group can appear multiple times in this table. Similarly, we'll have a channel subscription table that connects users to the channels they subscribe to. So now the groups and channels service has all the information about the association between users, groups and channels. Now let's move on to storing the actual messages. For that, we'll create the Chat History service with its own database. In that database, we're going to store a table or collection that contains the following records a unique and monotonically increasing message ID, a group or channel ID, the sender ID, the timestamp of when the message was received by our system and the message text. And that's it. Now, when a user wants to send a direct message to another user first, they can send a search request to the user service with a given username and in response, get the user ID. Of course, if it's a group message, all they need to do is repeat this call until they get all the IDs of the users they're interested in. Then, since the group chat hasn't been created yet, it will send a message to the groups and channels service to store the information about the new group and its participants, and in response it will get the group ID. Now, given the group ID, the user can send a message to the messaging service with the message text and the group ID using the bidirectional connection they established when they logged in. Once the messaging service receives the message, it will first send a request to the Chat History service to store it in the Chat history database. Then it will send a request to the groups and channels service to get the list of users in that group. Once the messaging service has the list of all the users it needs to deliver, the message to it will deliver the message using the bidirectional communication to the users in that group who are currently online. A user in that group can later respond to the same group chat by following the exact same process. Now the flow of creating a channel is going to be very similar. First, a user that wants to create a new channel will make an API call to the groups and channels service containing the channel name. That service will update the relevant tables and in response, send back the channel ID and the channel URL. Once another user receives that URL, either using our group chat functionality or through another way, they can make an API call to our platform to join that channel. Now, whenever any user sends a message to a particular channel, that message will go to the messaging service. When the messaging service receives it, it will first send it to the Chat History Service to store that message in its database. Then it will make a request to the groups and channels service to get the list of users who subscribed to that channel. And it will broadcast that message to all the currently online users in that list, using the bidirectional connection established with those users as the final step in our design. When a user goes offline and then reconnects to our platform, they will first make a call to our web application. Our web application will first make a request to the groups and channels service to get all the groups and channels that the user is subscribed to. And finally, it will make a second call to the Chat History service to load a subset of the latest messages in each relevant group or channel. Now the user has caught up with all the latest correspondence and can simply connect to the messaging service to receive future instant messages. And that's it. We successfully addressed all the functional requirements and implemented all the paths for our Systems API. So in the next and final lecture, we will address some very important decisions that we need to make so our system can fulfill all the scalability, availability and performance requirements.
