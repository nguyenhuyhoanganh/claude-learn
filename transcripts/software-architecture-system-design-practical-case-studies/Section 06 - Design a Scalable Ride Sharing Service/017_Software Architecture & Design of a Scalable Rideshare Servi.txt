# Software Architecture & Design of a Scalable Rideshare Service - Part 3

Welcome back. In the previous lecture we mapped the API endpoint. We exposed to our users and drivers to a very detailed software architecture that addresses our functional requirements. However, we still need to address a very important part of our system, which is the actions we need to take after the trip is complete. So let's refer to the last part of our sequence diagram to see what steps we need to take after the trip. First of all, we need to calculate the trips fare and how much of that amount is the driver's pay. Given that our company takes a cut from the revenue to support its operations. Then we need to build a user, generate a trip map and send it along with the receipt to the user's email. And finally, we also need to pay the driver and send them the trip map as well as the payment confirmation. So going back to our architecture diagram, the trip service is the best place to calculate all those numbers since all the trip information such as the start time, end time and distance is stored in its database. Once all those numbers are calculated, it can send this as an event asynchronously to the payment service. This is a good fit for an asynchronous event driven architecture because the trip service doesn't really need to get any response back from the payment service. Once the payment service receives the event for billing the user and paying the driver, it can process those events by calling the third party APIs of the corresponding external services. As soon as the payment service receives a confirmation from one of those external services, it will send an event through a message broker to another service, which we will call the trip map generator service. This trip map generator service will use the event sourcing pattern and utilize the fact that we stored all the location update events as well as the trip start and trip end events inside the message broker between the driver service and the location service. This way it can consume all those events for that particular trip ID and generate an image with the map of the user's journey. After that process is complete, it will send another event containing that map and the receipt of the payment to the notification service. But it will also stash that map in its cache and set its expiration to some short duration, like an hour or so. The notification service will then consume that event and email the user all that information. Similarly, when the payment service gets a confirmation from the bank that the driver's account was successfully credited, it will send another event to the map generator service. This time, however, we don't have to regenerate that map from scratch. Instead, the trip map generator service can take that map it already generated for that trip from its cache and send it along the payment details to the Notification Service. The Notification service will send all that information as an email, as well as a push notification to the driver's app. Notice that it doesn't matter which one of those external services responds with the confirmation first. The first event will always be the one that triggers the generation of the map based on the trip and the location events. And the second event for the same trip will always find the map in the cache. After that map is used, it will be deleted from the cache since both the user and the driver received it as part of their email. For those of you who are curious, in the world of microservices, this pattern where a chain of services are passing events in a sequence to complete a transaction or operation is called choreography. In this case, we have four services that follow this pattern to perform the entire financial transaction and report on it to the driver and the user, and that's it. So now we successfully addressed all the functional requirements of our system, so I'll see you guys in the next lecture to finish this design and address the system's non-functional requirements so it can be scalable, highly available and performant.
