# Software Architecture & Design of a Scalable Rideshare Service - Part 2

Welcome back to the second lecture on our design of the ride sharing service. In the previous lecture, we captured all our functional and non-functional requirements. More importantly, we narrowed down what was in scope for our design and what was out of scope for our design. And we used a detailed sequence diagram that captured all the interactions between the actors and our system in three parts. The first part depicted the login of a driver as well as the registration and login of a user. The second part captured all the steps involving a ride on our platform, starting with the user requesting a ride. And the third part captured all the actions we need to take after a ride is complete. This diagram was also critically helpful in designing our system's API for both the drivers and the riders apps. We also use the state diagram to represent all the state transitions for the driver on our platform. So now let's use all that information and design our software architecture to fulfill the functional requirements. Let's start with addressing the user registration and login as well as the driver's login following a microservices architecture. We'll create the users and driver service. This service will contain two tables in a SQL database, one with all the user's information, such as the user's ID, name, credentials, age and the link to their profile image. And the second is for the drivers, which will contain their name, credentials, driver's license, vehicle information, and also link to their profile image. The profile images of the users and the drivers will be stored, as always, inside an object store. Additionally, we need a place to store the user's credit card and billing information to build them when they book a trip on our platform and also a place to store the driver's bank information to pay them for their work after the trip. We could store all that information within the users and drivers database. However, since the actual billing will be a separate process, we'll create a separate payment service with its own database. This service will integrate with the credit card processing company through its external API and with different banks through their external APIs. So now whenever a new user registers through their app or a new driver is registered by our team, after they pass an interview and a background check, that information will be stored within those two services. And when a user or driver logs into our system through their mobile app, that request will go to the users and driver service. If the user name and password they provided match our records, they will successfully log in and get an authentication token they can use for future API calls. Now let's move on to the next driver's API endpoints which are the driver join so they can be matched with a rider and the location update. For that, we will create a new service called the Driver Service. The connection will establish here will be long and bidirectional, which the driver's app will maintain for as long as they're logged in to our system. This will serve two purposes. The first is since the drivers will constantly send us location updates every 5 to 10 seconds by using a long and persistent connection will remove the overhead of re-establishing a new connection with every location update request. The second reason for this long and bidirectional connection is, as we mentioned in the previous lecture, when we find a rider to match with the driver, our system will need this bidirectional connection to push that data from our system to the driver's device. Now, for better separation of concerns, as will also add another service which will call the location service. This service will store and manage each driver's most up to date, location and state in between those services. We'll also add a message broker. This way all the location and status updates from the drivers go to the location service in an event driven model. This event driven approach gives us two benefits. The first one is we decouple the driver from the rest of our system, and the driver app doesn't need to wait until we store the drivers most up to date location in our database. The second benefit is we can use the event sourcing pattern to trace back the location of our driver at any given moment in the past. This will be very useful for us when we need to generate a map of a user's trip from point A to point B. The location service, however, only cares about the driver's most recent location update, so it will consume those location update events and store the current driver's location in its No sequel high performance database. Now let's look at the next API call on the rider side, which is requesting a ride. For that, we will introduce another service called the Rider Service. Similarly to the drivers, the connection between the rider and the service will also be long and bidirectional. This way we'll be able to push updates to the user once we find the driver to pick them up, as well as the location updates of that driver as they make their way to the user's location. Now to match a rider requesting a ride and a potential driver will add another service which will call the matching service. Now let's pause for a moment and think about what actually we need to do to match a driver and a rider. First of all, given the location of the user, which we can get in the form of their latitude and longitude coordinates, we need to find all the drivers that are physically close to the user. To do that, we can draw a circle around the user's location with a given radius like a mile or one kilometre and look for all the drivers in the area of this circle. We already have the location of all the drivers in the location service database, so performing the search is possible. However, just the physical distance is not enough. Consider a situation where we have the user and the driver very close by, but on two opposite sides of a river and the closest bridge is half a mile away. To make things worse, there is an accident or some construction on the way. So it would take the driver 40 minutes just to pick up the user. So for that we will need to use a real time service to get the actual estimated arrival time of the driver based on the drivers and user's location. Luckily, while gathering our functional requirements, we identified that we could use an external service to get that data by simply calling their API. So going back to our architecture diagram, when the user requests a ride, the matching service can send the user's location as part of the request to the location service. The location service will first find all the physically close by drivers in its database and then it will send a batch request to an external ETA service containing a list of pairs where each pair is the user's location and one of the driver's locations. In return, we will get a list of ETAs for each driver to the user. The location service will then send that data with additional data about each driver to the matching service to make the final decision. Now the logic in the matching service can be as simple as finding the first available driver with the lowest ETA to the user. But it can also be as complex as finding a driver that maybe is currently on a trip but is about to finish in a minute and is therefore going to be much closer to the user than any other driver. It can also enable features like allowing multiple riders to share a ride with the same driver only, of course, if it's going to be beneficial to the driver and cheaper for the riders. It can even perform more advanced logic like prioritizing drivers that may be slightly farther from the user than another driver, but have been driving for a while already and haven't gotten any rights. This will allow more drivers to make money on our platform, ultimately making both drivers and riders happy. Once the matching service makes its matching decision, we need to start recording the data about the upcoming trip. So for that we will create the trip service with its own database. Now, when the matching service finds the best driver for a rider, it will first create the trip entry in the trip service database. Then it will update the user about the driver's information through the rider service, and after that it will send that data to the location service. The location service will update its database that the current driver is now booked for a ride and will also add the details about the trips destination for the given driver. This data can later be used for matching purposes when the driver is close to finishing their trip. Finally, the location service will notify the driver about the upcoming trip through the driver service. And as the driver makes their way to the user, their location updates will still go to the location service. But since the location service knows that this driver is already booked for the trip, it will forward those updates to the user through the rider service and it will keep doing that all the way until the trip is complete. When the driver arrives at the user's pick up location, the driver must indicate that they picked up the user and are starting the ride, which they can do with the next API call. So when the driver starts the ride, that will be an event that goes to the location service first. The location service will update its database with the information that the driver started the trip. And also forward that to the trip service, which will add that trip start event to its database. Similarly, when the driver arrives at the drop of destination, that location update can be automatically matched by the location service to the trip's destination location. And if those two match, the trip will end automatically. However, in certain situations, the user may want to be dropped off in a slightly different location. So for that we have our final API call, which is the finished trip. Using this API, the driver can manually finish the trip by pressing a button on their mobile app. This event will make its way to the location service which will update its record of the driver, and it will also send an update to the trip service to indicate the trip's end time and the location. So now the trip service has all the necessary data for the trip, such as its start time, end time and distance and whatever formula we use to calculate the user's trip, fare and revenue model with the drivers. We have all that data in place and we also finished our software architecture to meet all the requirements of our API, both for the users and the drivers. However, we aren't done yet and we still need to take care of all the post trip activities such as billing the users, paying the drivers, generating the trip map, sending receipts and emails and so on. Luckily, we captured all of that in great detail in the last part of our sequence diagram. So in the next lecture, we'll continue and finish addressing our functional requirements for this design. I'll see you guys in the next lecture.
