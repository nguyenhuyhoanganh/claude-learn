# Software Architecture & Design of a Scalable Rideshare Service - Part 4

Welcome back. In the previous lectures, we finished addressing all the functional requirements and we now have a very detailed architecture diagram to work with to address all the non-functional requirements. So in this lecture, we're going to make all the necessary adjustments to make our system scalable, highly available, and meet all the performance requirements we captured at the beginning of the design. As always, let's start with the scalability. First, as a reminder, on average, we have millions of daily users and hundreds of thousands of drivers using our platform daily. Also, those numbers can go up as high as ten times the average during peak times, such as holidays and weekend evenings. And although we don't have that many drivers in total, the amount of data that we need to handle from them is very big. And that's because drivers send us location updates every 5 to 10 seconds. So going back to our diagram, we will first place our services that expose direct web API behind a load balancer and run them as a group of identical instances. On the other hand, the trip map generator service and the Notification service don't get direct web traffic, so they don't need a load balancer, but they will run as a group of instances with the ability to scale up and down depending on the traffic. Now let's focus on the driver service and the rider service since those two services maintain a bidirectional connection with the drivers and the users running them behind a load balancer is not enough. For instance, when a user requests a ride. Our matching service finds the best driver for that user and updates the location service that the driver is now booked for the trip. Then the location service needs to find the driver service host that the driver is connected to to inform the driver about the trip. Without that knowledge, the location service will not know which driver service instance it needs to talk to. Similarly, after the driver is informed about the trip, the driver starts driving to the user's pick up location. During this time, every location update from the driver must be forwarded to the user's app. And to achieve this, the location service also needs to know what rider Service host the user is connected to. So to take care of that, we will use the same technique we used in our instant messaging design and add the connection manager service with a high performance in Memory Key Value Store. Now, any time a user connects to one of the rider service hosts, that host will send an update to the Connection Manager service containing the user ID and the host IP address. The Connection Manager service will add that mapping into its key value store. Similarly, when a driver connects to one of the driver service hosts, that host will send that information to the Connection Manager service. And that service in turn will add that mapping to its own database. So now any time the location service needs to find the driver service instance, a particular driver is connected to it can do it by sending a request to the connection manager service and then it can use that address to send a trip update to the driver through the host to which the driver is connected to. And the same thing is true when the location service needs to send a driver location update the user. All it needs to do is send the user ID to the connection manager service and it will get the IP address of the rider service host that the user is connected to. Once the rider service host receives the update, it can push it to the user's app using their already established bi directional connection. So that takes care of the scalability and the functionality of those services. To scale our data stores, we will use partitioning and sharding as usual and to decouple the user's app and the driver's app from the internals of our system, we will add an API gateway. Now, to achieve high availability, we will add a replication to our databases and message brokers in addition to what we've already done. We won't spend too much time on this in this design since we've already done this part many times before. Instead, let's focus on more interesting stuff in this design, which is performance. The first thing we need to take care of is the fast user login. Specifically, as discussed in the first lecture of this section, we want to minimize the time. It takes for the user to get an error message if they accidentally type in their username incorrectly. In those situations, the login request will go all the way through the API, gateway load balancer, user service and user's database, only to find out that this user name doesn't exist. That's a lot of wasted time, especially in the last part that involves the database, which is generally the slowest part in our system. So one thing we can consider doing is reading all the user names in our database and putting them in a hash table inside the users and drivers service memory. And every time a user tries to log in, the user service instance will first look up that user name in its hash table. And if it is in the hash table, then the instance will continue the login process by querying the database to validate that the password the user provided actually matches the password for that user. And if the username is not in that in-memory hash table, the host will send back an error message immediately. Avoiding the costly trip to the database. However, there's one problem with this approach, and this is the amount of space we need to store all the millions of usernames in memory as our service scales to dozens or even hundreds of instances. And each host needs to store hundreds of millions or even billions of users. The in-memory hash map approach is too costly as each machine will need a lot of memory. So instead we're going to use another data structure which works similarly to a hash table but is much more space efficient. This data structure is called the bloom filter, just like the hash table. The bloom filter uses a hash function to find the right slot to add a new key. However, unlike the hash table, the bloom filter doesn't actually store the key, which is the username in our case. Instead, each slot is represented by a single bit, and when a new key is added to the bloom filter, all it does is it sets that bit for that slot to one. So after we add all the user names in our user table, all the slots that one of the user names maps to is set to one. The others remain zero. This is why the bloom filter takes far less space in memory than a hash table. All it really is is just a fixed size bitmap containing no keys. Now, because the bloom filter doesn't actually contain any of the keys themselves, if a user sends us a username, we can have only one of two answers. If after applying the hash function on that username, we get a slot that contains zero, that means that the username is definitely not in our database and we can immediately send an error to the user saving the expensive database query. If however, after applying the hash function on the username, we get to a slot with the value of one. We can only say that this username may be in our database, but we can't say for certain. And that's because the hash function may have collisions where different keys map to the same slot. And since we don't store those keys in the bloom filter, we cannot know what those keys are. But this is still a big performance improvement because we can avoid a trip to the database for at least some of the cases without the high memory cost. For perspective, a bloom filter with 128 hash slots takes only four bytes of memory and a bloom filter, with as many as 8000 hash slots will only take one kilobyte of memory, which is a huge difference from storing millions of usernames in memory. Now, to reduce the chances of collisions and improve the accuracy of the bloom filter, instead of using a single hash function, we would use k different hash functions, typically with K equals three. The benefit of using multiple hash functions is if we insert two different usernames that originally collided and mapped to the same slot with one hash function, they're much less likely to collide in all the three hash functions. So now when a user types in their username, we pass it through all the three hash functions and check the value of those three slots. If at least one of those slots is zero, that means that this username is definitely not in our database and we can confidently return an error to the user and only if all three hash functions point the username to slots with the value of one would we make the expensive operation of checking that username in the database with those three hash functions? We still may have false positives, but the chances of that are greatly reduced. One important thing to point out is we can only add new usernames to the bloom filter, but we cannot remove them. And this limitation comes from the obvious fact that multiple keys map to the same slot. However, this limitation is not a big problem for us because most of our operations in our users and driver service are either just read operations for login purposes or write operations for new user or driver registration. So deleting a user is a very rare operation in our system. And regardless, we can always simply recalculate the bloom filter from scratch. Every time a new users and driver service host is restarted, which will correct itself for those rare cases of deleted users. So now that we address the performance requirements for the user login, we have only one last super critical performance requirement to address and that is the fast matching between users and drivers. When a user requests a ride. So we will dedicate the next lecture to first understanding the challenge of this requirement and implementing a solution that will both be scalable and performant. But before we do that, let's quickly summarize the important improvements we made in this lecture. We first use the typical steps to address the system scalability and availability, such as load balancing, sharding and replication. The rider service and the driver service required us to add the Connection Manager service with its own key value storage. This service allowed us to map between a user and the host it's connected to. And finally, we use the statistical and space efficient data structure called a bloom filter. Using this data structure that we hold inside every users and driver service instance, we can reduce the number of database queries that wouldn't yield any useful data. This ultimately reduces our costs and improves the performance for our users while logging into our system. I'll see you guys in the next lecture where we'll finish our design.
