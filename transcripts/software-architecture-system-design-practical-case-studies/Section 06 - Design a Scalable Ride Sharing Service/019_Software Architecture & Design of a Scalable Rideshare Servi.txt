# Software Architecture & Design of a Scalable Rideshare Service - Part 5

Welcome back to the final lecture on designing a rideshare service. In the previous lecture, we almost finished addressing all the non-functional requirements. We updated our architecture to make our system highly scalable and available, and we also optimize the login operations by using a bloom filter to reduce the expensive database queries when a user mistypes their username. So now we have one last important part to address, and that is the performance of matching a user requesting a ride to a driver. But before we make any optimizations, let's first understand the problem or the challenge we're facing. As a reminder, when a user requests a ride, our job is to first create a virtual circle of a certain radius around the user and find all the drivers that are currently in that area. Then we need to make an external API call for that subset of drivers to calculate each driver's actual real time ETA to the user's location based on that ETA and potentially other factors. We decide which driver will be assigned for that trip. Now, there is not much we can optimize in the request to the external service to get the ETA for each driver since the service and API are outside of our control. And the third step is also pretty straightforward and just depends on our business logic. On the other hand, determining which drivers are one kilometer away from the user is not straightforward and is 100% under our control. And there's quite a bit that we can improve in this process. So let's see how we can calculate if a given driver is within that range of the user. Since each driver sends us their location in the form of their latitude and longitude every few seconds, we can retrieve that information from the location service. Similarly, when a user requests a ride, they also send us their coordinates. So given those coordinates, how do we calculate the distance between them? To answer this question, let's briefly discuss what those coordinates actually mean. If Earth was flat, those would be the X and Y coordinates in kilometers and we could simply calculate their distance using this very simple formula. However, Earth is not flat, so latitude is a coordinate that specifies the north south position in degrees relative to the equator, and it ranges from 0 to 90 degrees in the northern hemisphere and from 0 to -90 degrees in the southern hemisphere. Similarly, longitude specifies the east west position on the Earth's surface around the prime meridian and is also measured in degrees. So if we use the approximation that Earth is a perfect sphere, the formula we will use to calculate the distance in kilometers between two points would look like this. I won't prove this formula mathematically here, but we can spot the longitude and latitude of those two points where either can be used for the driver and the rider. We can also spot the R parameter which represents the earth's radius in kilometers or miles, all depending on how we want to calculate the distance between the two points. So now that we have this formula, we know that given the coordinates of the user and a driver, we can calculate the distance between them. If that distance is less than one kilometer. The driver is near the user in this virtual circle. And if the distance exceeds one kilometer, we don't consider this driver for the ride. Now, here's the problem. We have hundreds of thousands of drivers in our location service database. So to find the nearby drivers, we need to perform this calculation on every single driver. Any time a user requests a ride, well, this formula isn't the most complex. It's also not the easiest to calculate, especially given that the latitude and longitude are floating point numbers, which are the slowest for computers to do any type of math on. To make things even more difficult, those driver coordinates are constantly changing as drivers are not staying in one spot. So even if we found some clever way to speed things up with using some sort of indexing based on those coordinates, it wouldn't be very efficient. So to solve this problem, we will use a technique commonly used by many other location based services. The general idea is to divide Earth's surface into cells where each cell has its own unique ID, And any time a driver sends us a location update, we immediately calculate which cell they're located in and store that information in the location service database, along with their latitude and longitude coordinates. Now, whenever a user sends us a ride request, we only need to figure out which cells fall within that one kilometer radius. Typically, this would be a small number of cells, like 3 or 4 at most. Then giving the IDs of those cells, we can perform a very simple query for all the drivers that are currently in those cells. Notice that although our drivers are constantly moving and sending us new location updates, the cell in which they are located will not change very frequently. It will only change when they cross the boundaries of two different cells. Also, those cell IDs are not floating point numbers anymore. Instead, they can be a simple combination of letters and numbers. So putting a database hash index on those IDs will allow us to perform those search queries very quickly, eliminating the need to scan through all the drivers in the database. As an added benefit, we can use the cell ID of each driver to shard this table or collection across multiple location database instances. All we need to do is apply a hash based sharding strategy on the cell ID. This will help us scale this database and provide an even higher performance. Since the query load on each individual database instance will be a lot smaller. Now, once we find all the nearby drivers, we still need to calculate their ETA to the rider based on their precise location. So we still need to keep the latitude and longitude of each driver to send them to the ETA calculation External Service. But we no longer need to use this formula to find the nearby drivers. The next question you may be asking yourself is how specifically are we going to divide Earth into those cells? There are in fact many ways this can be done, and each technique has its benefits and drawbacks. Out of all those techniques, though, one algorithm particularly stands out due to its popularity. This algorithm is called the Geohash. The main benefits of the Geohash algorithm are its simplicity and flexibility. It's also in the public domain, which means anyone can use this system free of charge. Because of that, it is also supported by many libraries and even databases out of the box. In the Geohash system, we divide Earth into a grid of 32 rectangles. Each rectangle or cell is assigned a unique character using base 32. Then every such cell can be recursively divided into 32 sub cells whose character is concatenated to the previous character. And depending on the precision we need, we can keep zooming in and dividing each cell into 32 more subdivisions, which adds more characters to the string that uniquely identifies the cell. Theoretically, we can keep dividing each cell until the size of each cell is measured in square centimeters. But that type of precision is rarely used and requires a long string to represent each cell. If we only use a six character precision, we can divide Earth into cells of about 1.2km by about 600 meter, which is perfect for our use case. But if for whatever reason, we would like to increase that precision, either globally or only in certain densely populated regions, we can adjust the length of the geohash string accordingly. So now whenever we get a location update from the driver, we will immediately calculate there cell using geohash and update it in the location service database ready to be queried on demand. Also, any time a user requests a ride, we will first find the cells that cover the area of this virtual circle around the user and then query the database for all the drivers who are located in one of those cells. Once we have those drivers and their locations, we can send their coordinates as well as the user's coordinates to the external ETA service. And when we get the results back from the external service, the matching service can decide on the best driver for the job. And once that driver is selected, it will notify the user and the driver about each other and the details of the trip. And that's it. We successfully addressed all the non-functional requirements and we now have a scalable, highly available and performant ridesharing service. So let's quickly summarize the highlights of this lecture. First, we found a performance bottleneck in our system that came from the fact that calculating the distance between a driver and a user required us to make a complex calculation, and we need to perform that calculation on every driver in our database whenever a user requires a ride. After that, we devise the general solution, which is dividing Earth into cells and mapping each driver's location to a cell with a unique ID. Later, we specifically picked Geohash to divide Earth into 32 cells. Each is represented by a single character and we can recursively divide each such cell into more cells until we get the precision we need for our use case. This system allowed us to efficiently query nearby drivers since the geohash can be easily indexed and searched for in our database. All of that without the need for full table scans and complex mathematical calculations.
