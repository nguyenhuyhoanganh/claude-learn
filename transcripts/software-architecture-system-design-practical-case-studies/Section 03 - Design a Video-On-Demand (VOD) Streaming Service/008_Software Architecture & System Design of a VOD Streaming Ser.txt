# Software Architecture & System Design of a VOD Streaming Service - Part 3

Welcome back. In the previous lecture, we completed the first pass on our system diagram to address all the functional requirements and API. In particular, we use the pipes and filters architecture pattern to transcode and package our input video. This allowed us to save on storage costs using compression. Enable users to get the most optimal video quality based on their varying network conditions using adaptive bitrate streaming delivered the videos to different devices and platforms, using different streaming protocols and protect unauthorized users from accessing our video by using DRM encryption. Finally, we used an event driven microservices architecture for the rest of the system to enable efficient search and to notify our content creators when their video becomes available for streaming. However, we're not done yet, so let's go ahead and address all of our non-functional requirements, which are equally important. First of all, let's start with scalability for content creators. As we can see, the frequency of video uploads is not very high, so we can simply place a load balancer in front of our web application and video data services and run a few instances of each service. On the other hand, the volume of video we need to process in our system is massive. So let's see if we still have some bottlenecks that we need to address. If you recall from the previous lecture, our approach to uploading a video was as follows Once a content creator logs in and gets the video upload page, they send the video file through the API gateway to the web application on the web application then passes the video through to store it in our object store. However, with the large video files we are dealing with, we are wasting a lot of network and computing power on both the API, Gateway Service and the Web Application Service. This forces us to add a lot of instances of those services. Every time we have a new video or videos getting uploaded to our system. So to optimize this flow, we will use a feature called signed URL or sometimes also referred to as pre signed URL. A signed URL is a URL that provides limited permissions and time to make a request directly to the object store. So in our case, any time a content creator wants to upload a video, the request will go to the API gateway where the user will be authenticated and authorized. Then it will go to the web application, which, using its own permissions, will create a time limited signed URL for the object store which it returns to the content creators front end code. The front end will then prompt the content creator to upload the file using that pre signed URL directly to the object store, bypassing the API gateway and the web application services and saving us a lot of money and resources. And that's pretty much all we need to do to support the scale of content and requests we're getting from content creators. Now let's move on to high availability. By using redundancy in our services, we already provide a level of high availability in using a cloud managed object store and transcoding and packaging services. We also get high availability out of the box. As a final step, we need to add a replication on the video data service database. This way we guarantee that if one of our database instances crashes, we don't lose any data and that's it. Now when it comes to performance, our requirements for content creators are pretty modest. So besides what we already have in our system, there is only one thing that we need to address. If we look at the requirements, again, we see that on average, new videos are uploaded by content creators no more than once a week. However, if all of our content creators end up uploading new content on the same day or at the same time, we may not be able to process all of them within a reasonable enough time frame. So for that, all we need to do is provide enough. Parallelism in our video processing pipeline. This way if we need to process multiple videos simultaneously, we can do it in parallel keeping our service level agreement with the content creators. Finally, we need to provide content creators with consistency over availability regarding updates to video metadata. For that, all we need to do is either choose a database, technology or configuration for the video data service database to provide consistency and partition tolerance over availability and partition tolerance. And that's it. We successfully addressed all the requirements for the content creators. Now let's move on to our users or viewers. Unlike in the case of content creators, we now have millions of users visiting, searching and watching video content on our platform to address those scalability requirements. All we need to do is place the search service behind the load balancer, just like the rest of our services, and run it as a group of identical instances. Then we'll also replicate the search database so we can support many requests that can be spread across multiple database instances. Now, regarding high availability, we already pretty much did all the work, so the only thing we need to do is run our system across multiple isolation zones and geographical locations. Finally, to address performance, there is one big component that we need to add to our system, and that's a CDN to improve the video delivery to our users. We will use the CDN push model and add that as another step in our video processing pipeline. In other words, instead of updating our video data service with the video location in our object store, we will update it with the location in our CDN. This way when users request the video URL, they will get the URL that points to the CDN, and the CDN will fetch the content to the user's device from the closest edge server to the user, which results in the first three segments of video getting to the user a lot faster. And after that, adaptive bitrate streaming kicks in, keeping the buffering time on the user's video player virtually zero. And that's all we need to do to provide high performance for our users, since we already thought of everything during our initial design. Finally, there is not much we need to do to support availability over consistency for users. If we look back at our diagram, the search service gets its data from the video data service using the secure pattern, which is an event driven pattern that already guarantees only eventual consistency. So if we also configure the search database to prioritize availability over consistency, we pretty much get what we want. And that's it. We successfully addressed all the non-functional requirements for our highly scalable video on demand streaming platform, and now our content creators can upload any type of video to our system and get notified when their video becomes available to the users. And also our millions of users who are located in different geographical locations can search for videos based on various attributes and stream videos effectively to any type of device and under any network conditions.
