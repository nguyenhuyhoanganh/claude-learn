# Software Architecture & System Design of a VOD Streaming Service - Part 2

In this lecture, we will continue our design of a highly scalable video on demand streaming platform. And specifically, we'll focus on addressing the functional requirements that we captured in the previous lecture. But before we start drawing any diagrams, first we will focus on two of the most important functional requirements we gathered earlier. The first one is that content creators can upload any type of video format or codec to our system. And the second is that our users can watch those videos on any device using different web browsers or a dedicated app and under varying network conditions. So let's talk about what it takes to deliver an input video file that may come in different forms to various users, devices and networks. Let's start with the input video files can come in different formats or what is commonly referred to as containers. This container is like a box that can keep multiple streams of media inside a single file. For example, a typical container would have a video stream, an audio stream, and maybe even subtitles or some metadata about those streams, like their codec bitrate resolution frame rate and so on. So when we're asked to support multiple formats, we are essentially asked to support multiple types of containers. However, there is more to it. The binary representation of each video and audio stream within that container can vary depending on how those streams were encoded. The algorithm used to encode and decode those streams is called a codec. Typically a video that comes out of the camera is encoded using a lossless compression algorithm, which makes those videos suitable for professional video editing. But this type of encoding also makes them very big too big to store in our system at such a scale, and in particular too big to stream to our users. So the first step after ingesting a video file should be converting the video and potentially also the audio stream to another type of encoding, one that uses a lossy compression algorithm so we can reduce the amount of data that we need to store on each video. Substantially, this process of converting one encoded stream to another encoded stream is called transcoding. Now the size of the video file roughly equals the bitrate multiplied by the video length. So to minimize our storage and the amount of data we need to stream to our users, we want to minimize the number of bits that we need to represent every second of video while still providing our users with high enough video quality. But because of the second functional requirement where we need to support different users using different devices and under different network conditions, we can't come up with one such number. Instead, we're going to use the fact that the bitrate of the video is directly proportional to the product of the resolution of the video and the frame rate of the video and is inversely proportional to the efficiency of the codec. So instead of transcoding the original video file into one output, we will transcode it into multiple outputs. So for high end users with large screens and high bandwidth, we will keep the resolution and the frame rate as high as the original video. And for users with lower internet bandwidth or devices with limited computing power, we will produce output files with lower bitrates by reducing the resolution, the frame rate or a combination of the two. Additionally, we can also use different codec technologies with higher efficiency. For example, with devices that support newer codec technologies, we can produce output files with high video quality but the same or even lower bitrates. On the other hand, some devices may be too weak to decode certain codec technologies or just don't yet support them. So we will have to reduce the other parameters to keep the bitrate low. However, we're not done yet. Deciding up front on which one of those streams we will deliver to. The user is very tricky if we overestimate the user's bandwidth. The user's device won't be able to keep up with the input rate of data resulting in buffering poses to catch up. On the other hand, if we underestimate the user's bandwidth, we may send them poor quality video for no reason. Additionally, network conditions can change drastically over time. For example, a user may start watching a video while being alone at home and then halfway through the video, his kids or his spouse also start watching the video on the same network. So the bandwidth to each device on that network would drop by 50%. Another example is if the user is watching a video on a mobile device while traveling on a bus or train during that ride, the network conditions can change every few seconds. So to solve this problem, we will use a technique called adaptive bitrate or adaptive streaming. To achieve this, we will break our Transcoded video stream into small segments, typically 5 to 10 seconds long, and reference all those streams in a text file, which is called a manifest. This manifest file contains information about the bitrate resolution frame rate and codec of each stream. Now, when a user starts streaming a video, their video player first downloads that manifest. Then it picks the first stream in the list and buffers the first three segments so the user can start watching the video. Then the video player on the user's browser or app starts analyzing the time it takes to download each segment and the performance of the player and reevaluate where to download the next segment from. If the bandwidth drops, then it will start downloading segments from a lower bitrate version of the stream. And if the bandwidth improves, it can upgrade and start downloading the next segments from a high quality version of our video. Now, as the last step in connecting our users to the content, we need to package it to deliver over the network. The current reality in the industry is the different platforms, browsers and apps support different video streaming protocols, and each protocol has its own limitations and delivery format. So for us to support various devices, we need to package our Transcoded video into each one of those protocols. Additionally, at this stage we can use DRM to protect our video without DRM, a malicious user can potentially take one of our video URLs and play it without permission or without using our platform or app. So by using DRM encryption, we ensure that only authenticated and authorized users can play the video and only on our platform. And that's it. With that knowledge, let's proceed and start converting our functional requirements and API into a software architecture diagram. First, to consolidate the authentication and authorization. In one component, we will place an API gateway to provide our content creators with a web based UI to upload the videos. We will also add the web application service. So now when a content creator logs in, they send a request to our web application service through the API Gateway and get a video uploading web page to their browser. Now to store videos being uploaded to our system, we will use an object store and to store and manage the metadata about each video, such as its title, author, description, tags and location of the video. We're going to introduce the video data service with its own database. Now, when a content creator uploads the video, the request will go through the API gateway and the web application. The web application can pass the video into the object store, while the metadata about the video can go directly to the video data service. And once the video upload is complete, the content creator gets a confirmation. Now to prepare the video for delivery, we will use an architecture pattern called the pipes and Filters pattern, which is the most natural. For this type of workflow in this pattern, once the input video file is uploaded to the object store, the Object store will publish a notification to a message brokers, channel or topic on the receiving end of that event. We'll have our transcoding service. The service will consume the event that contains the input video file, URL and transcode that video into multiple bitrates in 10 to 15 second segments. The output of the transcoding includes the manifest file, which will go to another object store location and also a publish notification to another topic or channel. That notification will be consumed by the video packaging service, which will take the Transcoded videos, add DRM encryption to them and package them into different streaming protocols. Once it's done, it will store those files in their final location in the object store, which in turn publishes yet another event to another topic or channel indicating the final location for the packaged video files and their manifests for each type of streaming protocol. Now, on the receiving end of the final event, we have a video data service. The service will update its database about the given video that it is now available for streaming and also add all the data about its location. Additionally, to notify the content creator that their video is now available for streaming, we'll add the email Notification Service. That service will also subscribe to the same events from the video packaging service. And once the event is consumed, it will look up the content creators email address and send them the email. And that's it. We just finished addressing all the functional requirements for the content creators and we now have the full architecture path to ingest an input file and prepare it for delivery to users. So now let's move on to the users experience. To authenticate and authorize users, we can use the same API gateway that we already added and to serve our platform's homepage to the users who use the browser, we can use the same web application app. Now, as always, whenever there is a search involved, we want to have a dedicated service with a specialized NoSQL database optimized for search as always, to get the relevant data from each video from the video, data service will add a message broker between the two services and whenever the video data service finishes updating its database that a new video is ready to be streamed, it will also publish a notification to that topic. The search service will then consume that event and update its search optimized database, which will tokenize and index the title description and all the rest of the data that we get about each video. So now when a user sends us a search query, that request will be sent to the search service, which will send back the most relevant search results to the user, including their video IDs. Now, when the user is ready to start watching a particular video, that request will go to the video data service. The service will decide based on the user's device and platform which video stream URL to send back, knowing which streaming protocols are supported and the most optimal for that particular user. Finally, the user can use that streaming URL to download the video manifest and start streaming the video from the object store. And that's it. We completed the architecture diagram for the video on demand streaming platform.
