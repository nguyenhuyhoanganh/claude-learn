# System Design of a Highly Scalable Image Sharing Platform - Part 3

Welcome back. In the last lecture we completed the first pass on our software architecture that fulfills all the functional requirements for the scalable image sharing social media platform. Now we're going to focus on addressing the non-functional requirements and update this diagram to provide us with the desired quality attributes. As a reminder, these are the quality attribute requirements we gathered in the first lecture. So let's start with addressing the first requirement, which is scalability. In the first part, we see that we have billions of users with hundreds of millions visiting our platform daily. So let's go back to our architecture diagram and see what we need to change. To scale our web application service, we can simply run many identical instances and place them behind the load balancer. This way, no matter how many users we have visiting our platform, we can simply increase the number of those instances dynamically and completely transparently to the users. Similarly, to support many users logging in and registering to our platform, we will place the user service behind the load balancer and run multiple instances of that service. Now let's think about storage of our users As a reminder. We store our users data in a NoSQL document store where each user is represented by a separate record. However, we probably won't be able to store billions of such records on a single database instance. So we will use sharding and distribute this data across multiple physical instances. The simplest way to shard this data would be by using a hash strategy applied on the user ID. This will evenly distribute our users among as many shards as we want, and if we keep getting more users, we can add more shards and redistribute the users among all of them. Of course, we need to make sure that those IDs are randomly generated using a uniform distribution. Otherwise some shards may get overloaded with more data than others. Similarly, if we look at the followers collection, we can use the same hash sharding strategy on the follower user ID. This way when a user logs in and wants to get the list of all the users that are currently following this request will go to only one of our shards, which is very efficient. Now we will repeat the same step for all the other services by placing them behind a load balancer and running them as a group of identical instances. When it comes to scaling the timeline Key Value store, we can use the same sharding strategy of using a hash function to spread the entries across multiple shards, and also the post table can be partitioned by post ID across different database instances. Of course, granted that we chose a SQL database technology that provides this type of partitioning. Now let's look at the second part of our scalability requirement, which is storing hundreds of terabytes or even petabytes worth of data in a form of uploaded images. So first of all, by making the right decision up front and using an object store as the place to store those images, we already took care of the scalability for the most part. And that's because regardless of whether we use a cloud based object store or run it in our own data center, object stores are particularly optimized for a high volume of data due to the fact that they run a distributed system of multiple instances under the hood and also their model where each object is basically a key value pair, which allows for very easy partitioning of data across multiple machines internally. However, there is one more thing we can do. One thing we should notice is that users can upload images in different formats and resolutions. Some of them may come directly from their high end cameras or their mobile phones. However, those uploaded images are not necessarily optimized for storage and for viewing on mobile devices or web browsers. So what we can do is. Add an asynchronous pipeline component that can compress the images so they take less space, reduce their quality to an acceptable level, and even reduce the resolution of the image to something that would look good enough on an average computer or mobile screen. But no more than that. This way, while we're getting petabytes or hundreds of terabytes of data from users, we may only need to store terabytes or even only hundreds of gigabytes. And this technique can be applied to images that come as part of a post as well as profile images. Finally, we would like to increase our organizational scalability and decouple are front end code from the internal organization of our services. For that, we're going to add an API gateway. Now every request from the client side will go to the API Gateway Service first and then be directed to the appropriate service within our system. This way, if we need to add a new service or split an existing service, the client code will not have to be impacted. And that's all we need to do to provide high scalability. Now let's move to the next non-functional requirement, which is high availability and fault tolerance on the service side. We actually don't need to do anything. Just having multiple replicas of each service behind a load balancer is enough to provide our system with high availability in terms of services. However, on the database side, we do need to add replication in each one of our databases. This way, if one of the database shards crashes, we won't lose any data and read or write. Operations can simply go to the other replicas. Additionally, we will run our system in multiple isolation zones and different geographical regions or data centers and direct users to the closest region using a global load balancing service. This way a power or network outage in one part of our data center won't impact our users, and a complete failure of our data center in one location will simply trigger a redirect of all the traffic to another region. And that can easily be achieved because the load balancing service is constantly aware of every region's health and performance. And that's all we need to do to add high availability to our system in general. And the level of high availability depends on the number of additional replicas, regions or isolation zones that we add to our system. Now let's talk about performance for our users. And let's start with the first bullet point, which is a general requirement for a response time, lower than half a second at the 99th percentile to reduce the latency of loading the home page or getting the post images from our system to the users. We can use a CDN service by pushing our sites static content like HTML, CSS and JavaScript to the edge servers as well as the post images. We can significantly reduce the response time to our users. In fact, we could have even delegated the compression of the images to the CDN service if we wanted to. But performing the compression ourselves reduces our storage cost, which is why we prefer to do it ourselves. Regardless. The fact that the CDN servers need to send smaller images also reduces the latency and improves our users experience. Now let's talk about the performance of fetching our users timeline from the timeline service to the browser. Thanks to the architecture decision we made by creating the service and storing a cached materialized view of each user's timeline, we have already made a huge step in providing high performance. However, we can make a few additional critical optimizations. The first one would be in the case of a celebrity or an influencer that has hundreds of millions of followers and who posts very frequently, although there are very few such users compared to the total number of users on our platform, their impact on our performance can be significant. The reason for that is that every time such an influencer makes a post, our timeline service will have to insert that post into potentially hundreds of millions of timeline entries in its user timeline collection. This puts a very high load on that service and its database, which have to make billions of write operations just because of a few such posts made by a small number of users. So to address this issue, we will make the following changes to our system. First, we're going to establish a threshold of the number of followers that indicate if a particular user is a celebrity or influencer or not. That threshold can be a million users, 10 million users and so on. It all depends on the performance of our system. The second change is adding another field to the user's collection that marks that a particular user is an influencer. Now, when the timeline service consumes an event about a post, it will send a request to the user service just like before. However, now the user service will first check if the current user is an influencer. If they are, then instead of returning the list of followers it will return a message telling the timeline service that this user is an influencer so it should not update its followers timeline. Instead, the timeline service will store that post in a new key value collection, which we will call the influencer posts. In this collection, we will have a mapping between the influencers ID and their recent posts. So if we have a few thousand influencers in our platform, this collection will be relatively small. All. Now, whenever a user logs in and sends a request to the timeline service, it will also send a request to the user service to check if the current user is following any celebrities or influencers. If they do, the user service will return the short list of IDs of those influencers. Then the timeline service will merge the posts from the user's timeline collection that contains all the recent posts from the non influencer users that the current user is following. With the recent posts of the influencers that the user is following and return one single sorted list of posts based on their timestamps to the user. This merging can easily be achieved because every individual list is already sorted by timestamp and the timestamp of each post is present in each post entry. So after the timeline service creates user B's timeline, it will send back only a subset of this list since we use API pagination. So now we have an optimal solution for efficient read operations for user's timeline and for influencers posting new images to our platform. And that's it. We successfully fulfilled all the functional and non-functional requirements for our system and we have a highly scalable, available and performant image sharing social media platform. So before we move on to the next design problem, let's quickly summarize what we did in this lecture to improve our system scalability. We introduced a load balancer in front of each service and ran each service as a group of identical application instances. On the database side, we use the sharding technique with the hash based sharding strategy so we can store more data that could effectively fit on one single database instance. Additionally, we post-processed the user uploaded images to save on storage space and costs associated with it. Finally, we added an API gateway to decouple our front end code from the rest of the system to provide high availability. We added database replication and also ran our system in multiple isolation zones and geographical locations. And last but not least, we improve the performance of our system by first introducing a CDN and publishing our images as well as other static content to its edge servers. As the final step, we optimized our timeline service and introduced another collection where we can store the posts of popular users such as celebrities or influencers. And then whenever the user wanted to get their most up to date timeline, we merge the data from the user's timeline collection and the influencers post collection. And that's it. So I'll see you guys in the next lecture with a new exciting system design problem.
