# System Design of a Highly Scalable Image Sharing Platform - Part 2

Welcome back. In this lecture, we will continue our design process for the large scale image sharing social media platform. Now, after we gathered the functional requirements and define the Systems API, we are ready to sketch our software architecture diagram. Focusing primarily on the functional aspect of the system. So let's take a quick look at our sequence diagram. As we can see, the first step of a user coming to our system is getting our home page and registering to our platform. So let's start with creating the Web application service, where a user can send the initial request and depending on whether the user is already registered or not, we will send back either a login page or a registration page for both scenarios. We need another service which we will call the user service. That service will store all the users in its own database. Now each record inside the user's database includes the unique user ID, public information that includes the user's username, first name, last name and profile image, and then private information such as the password, email and maybe even phone number for two factor authentication. And additionally, it also includes a bunch of optional attributes such as location, age, interests and many others that we may want to add in the future. Now we could try to store the image inside the database. However, this is not going to be a good approach. The reason for that is databases are not optimized to store binary objects, and even those that do support them set a pretty low size limit on such objects. So instead we're going to add an object store and we will store the profile image in it instead of in a database. And that profile image in the database will be replaced by a profile image URL entry pointing to that image location in the object store. Now, as we can see, the schema of the user record is pretty fluid because of all those optional fields that we already have and may have more in the future. So we will choose a NoSQL document store for storing the user's data. So now a user registration request will first go to the user service, which in turn will store the image in the object store and return the image URL. Then the user service can add a new entry to the user's collection and return its newly created user ID and an authentication token. Using those two pieces of information, the user can continue interacting with our platform and call our API. Now let's move on to the next API call, which is the login request. The login request will authenticate the user given their username and password by sending a request to the user service and looking up that user inside the database. If the user name exists and the password correctly matches, the user service will also return the user ID and the authentication token, just like in the case of user registration. Now let's move on to the next API call, which is posting and sharing a new image. For that, we'll create another service called the Post Service. This way, if we want to extend our platform to other types of posts beyond just images, we can keep using the same service. And of course this service will have its own database inside that database. For each post, we will store the unique post ID, the user ID, which refers to the user who shared that image, the URL that points to the location of the image and the timestamp that indicates when the image was uploaded. Now to support other types of posts in the future, we can also add a post type column, which for now will always be of type image. To store this kind of information, we can use both a SQL and the NoSQL database, but since the schema here is pretty well defined and fits very naturally into a table structure, we will stick with a. Database for now. So when a user uploads an image, that request will go to the post service. The service will upload the image to the object store and add an entry for that post in its database. Once the insertion is successful, the user will get a confirmation. Now let's move on to the next functional requirement and API, which is searching for a user by username, first name, last name or any other type of attribute. We could simply send that request to the user service. However, a better approach would be to have a dedicated search service with its own NoSQL database that comes with a highly optimized text search engine. This way we can support faster and more advanced search capabilities with system provided suggestions and so on to keep the user's database and search database in sync. We will use an event driven architecture and the access pattern. Using this pattern, any update to an existing user or any registration of a new user will be published as an event to a message broker by the user service and the search service will subscribe to those events to consume them and update its database with the new data. So now every search request will go to the search service, which will in turn pull data from its own database. This way we can quickly return search results and even show potential matches to the user as they're typing their search. Now let's move on to the next requirement, which is the ability for the users to follow or unfollow other users. If we want to be very granular in our microservices architecture, we could create a new follower service with its own database. However, this isn't necessary because the following can be easily represented with a simple mapping inside the user service database. All we need to do is create another database collection. Each entry in this collection contains the follower user ID, which is just the user ID of the follower and the target user ID, which is the user being followed. So if user A follows, user B and user C, then we would have two entries that look like this. And if user C also follows user A in return, then we would have the following additional entry and that's it. So now the follow user request will go to the user's database and we'll add the appropriate entry to the followers collection if that entry doesn't already exist. Similarly, if a user changes their mind and wants to unfollow a user, they can also do it very easily. Now let's move on to the last requirement, which is the personalized timeline or. Newsfeed of the latest posts of all the users that the given user is following. For example, if user A is following user B and user C, then when user A logs in, we will show the latest posts from both user B and user C. So what would be the best way to achieve this? Well, here is one way we can do this. Any time a user opens the home page, we can send a request to the user service first to look up all the users that user A is following. Then, given that list, we can send a second request to the post service. The Post service will then have to perform a complex SQL query that filters all the target users that user A is following and sort them by timestamp in a descending order. Of course, this query returns way too many results, so we should add a limit to use it with pagination. And now after this complex query completes, we send those post URLs back to the client. And finally, the client side would have to issue another batch of requests to the image object store to actually load those images into the browser. As we can already see, this approach is very inefficient and simply won't work if we have hundreds of millions of such requests coming to our system daily, especially given the strict performance requirements we received in the previous lecture. So while we can certainly improve the performance of the last operation, we can't completely eliminate it. However, we can certainly do something about the first two parts. In particular, we can definitely eliminate the negative performance impact of this complex SQL query. So we will use two patterns to improve the performance of this operation. The seekers pattern and the materialized view pattern. First we will introduce another service, which we will call the timeline service. The service will store the timeline for each user in our system. In other words, every user will have an entry that maps from the user ID to a sorted list of image posts coming from all the users that the given user is following. For example, if user A follows, user B and user C, then we will have an entry for user A that contains all the posts from user B and user C in a sorted order. Similarly, if user C also follows user A, then user C will have only posts that user A shared recently. And of course, since user B is not following anyone, his timeline will remain empty. Every post record contains the post image URL, the ID of the user who posted it and its timestamp. Since all we need is a simple mapping, we will use a highly performant in-memory key value store to store this data. Of course we're not done yet, so we will also introduce a message broker which the timeline service subscribes to. And now any time a user posts a new image, the post service will produce an event that includes the user ID, the post URL and the timestamp for that image. The timeline service in turn will consume that event a synchronously, which means the user will not be impacted and it will send a request to the user service to get the followers of the current user. Once the timeline service has the IDs of all the followers of the current user, it will update the entries of those followers with the new post and place it in front of the list. The reason it goes to the front of the list of each follower is that this post is now the most recent, and since the number of recent posts in each user's timeline is constant, it will also push off the least recent post out of this list. This way we always keep the timeline posts chronologically ordered, and now when a user sends a get timeline request, that request needs to go only to the timeline service, which already has the timeline posts ready and sorted in the right order. Once the client code receives this list of URLs, it can immediately go and fetch those images directly from the object store. While we still have many things we can optimize, this is a huge improvement to the timeline experience for our users. Of course, the clear downside of this approach is new image posts by users will show up on their followers timelines. Not immediately, since now we have only eventual consistency, but that's completely acceptable for our purposes. And that's it. We now completed our software architecture diagram, which fulfills all our functional requirements and maps every API call to a path within our system. In particular, we place the profile images and post images in an object store, which is a much better type of storage solution for this type of data. We also use the pattern to separate the user registration and the user update operations, which now go only to the user service from the search operations that now go only to the search service. And the service has a more optimized data store for this use case. And finally, we use the seekers and the materialized view patterns together to optimize getting the timeline for our users. In this case, we avoided performing multiple requests to different services and in addition, a complex SQL query against our post database. Instead, by using those patterns, we have a cached view of each user's timeline in the timeline service database ordered in a way that is ready to be used by the front end code. So in the next lecture we will make another iteration of this diagram and make all the necessary updates to provide our system with high performance availability and scalability. I'll see you guys in the next lecture.
