# System Design of a Highly Scalable Image Sharing Platform - Part 1

Welcome to our first system design lecture. In this lecture, we will design a highly scalable image sharing social media platform. We will start with narrowing down our scope by gathering the system requirements. Then we'll define our system's API. After that, we will define our software architecture by first designing to fulfill our functional requirements, and then we'll refine it to deliver on the non-functional requirements. So first, let's start with understanding what exactly we need to design by asking a few important questions. For example, what kind of information do we need to store about each registered user? What type of media can the user share? The title says it's an image sharing platform, but it's worth clarifying if it's always going to remain only images or maybe at some point we will want to expand our platform to text, video or other types of posts. Another important question is what type of relationship do we have between users? Is it a bidirectional relationship like friendship? Where you are my friend and I am your friend automatically? Or maybe we have a unidirectional relationship like a follower and a publisher. Finally, what kind of operations can a user perform on our platform? So let's assume that when users register to our platform, they must provide their first name, last name, email, username, password and a profile image. And optionally, they can also provide their age, location and maybe some other fields that we haven't decided yet. When it comes to the media that a user can share, let's assume that we indeed allow only images at this point. However, we need to design our system so that adding new types of posts like text, video or music wouldn't require too many changes. The relationship between the users on our platform is going to be unidirectional, so every user can follow as many other users as they want. But following someone back is optional. And for the last question, let's assume that a registered user can perform the following operations. A user can post a new image. A user can search for other users by name, last name, username, or other attributes. Once they find that user, they can see their public information and look at their shared images. Then we have the follow and unfollow functionality meaning any user can follow as many other users as they want and they can also unfollow them. Finally, when a user logs into their account, they should see a personalized timeline or news feed of the latest images posted by the people they follow. And those images should be sorted so that the most recently posted images show up first. Let's also assume that other activities like leaving a like commenting or sharing are out of scope for the moment. Okay, so it looks like we have a pretty decent number of features that we need to design for. But before we jump into the next stage of the design now it's important for us to capture the quality attributes or what we call the non-functional requirements of the system. With all those requirements, we may design a system that is functionally correct, but becomes completely useless for the workload we intend to use this system for. So let's start with scalability. Let's assume that we are designing for a global scale with billions of active users and hundreds of millions of those users visit the platform every day. Also, each user on average shares one image per day. So given that images typically take a few megabytes at most, we are talking about the order of magnitude of terabytes or even petabytes of new data that we need to process daily. Now let's talk about availability and fault tolerance. We're definitely aiming at high availability here. While it may seem like nothing terrible can happen if an image sharing platform goes down, but let's not. Or get that At some point we may want to start monetizing this platform through ads or maybe even by paying people to share photos of important events in real time. So if our system becomes unavailable to all or some of our users, we risk losing a lot of money. So in this case, we will aim for four nines of availability at the very least. Now let's talk about performance. Since end users interact with our system directly, we absolutely have to reduce the response time and the page load time for every interaction with our platform. Otherwise users will get bored or frustrated and move on to something else. So let's aim at around 500 milliseconds of end to end latency at the 99th percentile. Now loading the personalized news feed or timeline that includes the recent posts from all the users that the current user is following is a much heavier task. So for that we will set the response time SLA to under 1000 milliseconds at the 99th percentile. So now that we narrow down the scope of our design and captured the functional and non-functional requirements, let's move on to the next part of the design, which is the definition of our system's API. Since we have a lot of features that we need to implement, it's going to be helpful to put them in a sequence diagram. This way we ensure that we don't miss any important details and as a side benefit, the API definition will be much easier. So for simplicity, the actors in our system are two different users user A and user B and of course our system is in the middle. When a new user comes in the first, make a request to our system to load the registration page. After they get the registration page to their browser, they can fill in their information and also upload their profile photo as part of the process. Once our system receives the registration data and ensures that the user name is not already taken, it stores the user information and logs them into our platform. At the same time, a registered user user B can simply log into our platform by providing their username and password. Now user A can post as many images as they want and in each case we will store that image and send back a confirmation. Then user B can look for user A by name, last name or username. And if a match is found, we send back a page with user A's information and all the images that user A has already uploaded. Notice that this number of images can be very big. Too big to send all at once. So we will implement this call using API pagination. Now user B can start following user A, which would be another API call to our system. Finally, when user B comes back and logs into our system, they should see a newsfeed of all the images that user A and all the other users that user B is following sorted by the timestamp on their home page. Of course we will need to use API pagination here as well, otherwise we may return way too many results that can slow down the loading of the page. Now if we take every interaction between the user and our system as well as the data that passes in each call, we have our systems API fully defined. Now we can use this API and move on to the next step of our design, which is the functional diagram of our system. It's worth pointing out that this is an abstract representation of our API, and if we want to implement the system we can easily translate it to a rest API or any type of specific API very easily. But we're not going to spend time on this in this lecture, So let's have a quick recap. We started with a very ambiguous and high level description of our system, which is just an image sharing social media platform that can mean different things. And now, after following the three steps of our system design process, we have a very well defined set of features that we need to deliver, quality attributes that we need to guarantee and an API that we can use to start the architecture of our system. So in the next lecture we're going to move on to the next step, which is our software architecture diagram that fulfills the functional requirements. I'll see you guys in the next lecture.
