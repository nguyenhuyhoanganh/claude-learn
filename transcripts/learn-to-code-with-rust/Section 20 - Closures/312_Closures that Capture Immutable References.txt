# Closures that Capture Immutable References

In the previous lesson, we mentioned that a closure can capture values from the scope in which it is defined. Capturing means saving data for later use. A closure can capture values in three ways, all of which align with the ownership principles that we've learned previously. So a closure can take ownership, it can borrow a mutable reference, or it can borrow an immutable reference. These three ways all correspond to the three closure traits: FnOnce, FnMut, and Fn. So here is our old 'multiply_by' example and it captures the 'multiplier' value from above. Now in this case, 'multiplier' is a u8 type and integers implement the Copy trait. So technically the closure defines a procedure that has a copy of the original value of 5. So there is no technical movement of ownership here at all, and thus Rust infers the closure's type to be something that implements the Fn trait, some kind of callable procedure, right? Now where these differences matter is, as always, with types that do not implement the Copy trait, then the Rust compiler has to decide the capture strategy of the closure, which is how it's going to infer the closure's type. And it's going to judge that based on what the closure does in its body. In this case, the closure doesn't take ownership over anything at all. And thus, technically speaking, it's implementing the Fn trait. But let's take a look at some of these variations throughout this lesson and the next few. So I've declared a vector of numbers here. Vectors of course do not implement the Copy trait. So here I am printing out 'numbers' after its declaration and we can see it right here. So what I'm going to do on the next line is declare a new variable called 'print_numbers'. And I'm going to set this equal to a closure. So two pipes and then my curly braces and then my semicolon because I'm assigning the whole closure to the 'print_numbers' variable. And all I'm going to do in the body of this closure is print_ln! and output 'numbers' once again in Debug format. So there we have it. Now, because I'm only having one line of logic in this closure, it's likely that rust-analyzer will remove the curly braces when I save. And indeed it does. And that's totally fine. Now I want to be clear. We have defined a closure here, but we have not yet invoked it, so nothing is going to run yet. We're not actually going to see 'numbers' being output here from this logic executing. The only reason we see it in the first place is coming from this line number 8. But if I comment it out, you can see we declare the 'print_numbers' closure, but we haven't run it yet. So take a look at the inferred type right here. It's once again impl Fn. The Fn trait indicates that the type is a closure. It's some kind of invocable procedure that can be called. The empty parentheses indicates that the closure accepts no parameters, and the absence of an arrow indicates that the closure does not return a value. Now remember the Fn trait, this one, is for closures that either borrow immutable references or capture nothing at all. So the compiler observes that the 'print_number's closure right here uses the vector in Debug format simply for the purposes of the print_ln! macro. The print_ln! macro itself receives an immutable reference to 'numbers'. The key takeaway is that Rust can observe that the closure is not doing anything that's going to mutate the vector, so it does not need to borrow a mutable reference. It can get away with just reading, and thus an immutable reference is sufficient. For closures that either borrow immutable references or do not borrow anything at all, the compiler will infer the Fn trait. The closure implementing the Fn trait is the most logical inference. There is no need to move ownership away from 'numbers'. There's also no need for immutable reference, because the closure does not change the vector in any way, and thus the closure is going to capture an immutable reference, and the type of the closure itself will be a callable procedure, i.e. something that implements Fn. So because we are borrowing an immutable reference, we can also invoke 'print_numbers' as many times as we want. So here I am invoking it three times. Each time we're going to see the exact same vector output. And I can also bring back my print_ln! after and use my original 'numbers' owner, which proves that ownership was also not moved when this closure was either declared or executed. It's just borrowing an immutable reference at the point of declaration. We are able to use the 'numbers' vector before and after the closure's declaration and multiple invocations because there is no transfer of ownership. We can have any number of immutable references to the same piece of data, i.e. the vector throughout the program, and thus we are able to invoke the 'print_numbers' closure multiple times because there is no risk to doing so. The data is read-only. So this is an example of where the compiler will infer the implementation of the Fn trait. It's going to choose to infer that one compared to the other two trait options, once again based on what the logic is doing in the actual body of the closure itself. We're going to see examples of closures in the upcoming lessons, where the compiler is going to infer the other traits, FnMut and FnOnce, once again, based on what is happening in the body of the closure itself. So I'll see you there.
