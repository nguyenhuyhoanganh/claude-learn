# Closures with Ownership

So at this point, we've seen how closures can capture an immutable reference or a mutable reference based on the logic in their body. The third way that a closure can capture a value is through ownership. The first way that we can move ownership of a value into a closure is to have the closure's logic return that value. And that value, by the way, must be heap allocated. So I want to show you two closure examples side by side. The first closure is going to return an integer which does implement the 'Copy' trait and lives on the stack. And the second closure is going to return a heap 'String' instead, which of course lives on the heap and does not implement the 'Copy' trait. So let's start with our first example. I'll declare a 'number' variable set to an arbitrary value like 13. Then on the line below, I'll declare a variable called 'capture_number' and assign this to be a closure. So two vertical pipes and my curly braces and my semicolon. And in here all I'm going to do is return 'number' from above. And since there's only one line of logic here, you'll notice that 'rust-analyzer' will remove my curly braces. But that's totally fine. So what's happening here in this situation? An 'i32' type. This 13 right here does implement the 'Copy' trait. So what the closure will do is it's going to create a copy of the value 13 for future use. Notice the type of the closure is 'impl Fn'. The 'Fn' trait indicates that this closure can be executed multiple times. And that's because each time the closure runs, it's going to be able to produce and return a fresh copy of the value 13. I can prove this to you by, in fact, invoking the closure multiple times and assigning its return value, which is going to be 'number' right here. This, remember, is just an implicit return of whatever 'number' happens to be. So I'll invoke 'capture_number' and collect its return value in an 'a' variable. And then I'll do the exact same thing on the line below, invoking the closure one more time and assigning its return value to a 'b' variable, and then print out both 'a' and 'b'. And we of course are going to see the value 13 printed twice. But that proves that on every invocation of the closure, we are creating a full copy of the value 13. Furthermore, after the declaration of the closure, we also have access to 'number' because the original data was never moved. The integer implements the 'Copy' trait, so we did not need to transfer ownership away from the 'number' owner. We just created a copy of it for the purposes of the closure declaration, and then each time the closure runs, it returns that copy back to the new owner, in this case 'a' and 'b'. Next up, let's compare this example with a different one that does the exact same thing, but with a heap allocated 'String' type. So here I'll declare a 'first_name' variable set to a 'String'. So I'll use the 'String::from' function and provide an arbitrary string like "Alice". Then I'll declare a 'capture_string' variable. That will be the exact same idea. A closure. So here are two pipes and I can omit the curly braces since they're going to be removed anyway. And here this closure is going to return the 'first_name' variable from above. Notice immediately that the type of the closure is completely different. The type is inferred to be a closure that implements the 'FnOnce' trait. Totally different from 'Fn' up here. And we'll talk more about this trait in just a moment. But for now, the first thing I want to point out is after the declaration of the closure, not the invocation, but just the declaration, the 'first_name' variable is no longer valid because 'first_name' is no longer the owner. So here if I, for example, try to output 'first_name', you'll notice we get a compiler error. And you can see "borrow of moved value 'first_name'". 'first_name' is no longer the owner. So when we have our 'capture_string' closure return the 'first_name' 'String', this is an operation that requires the closure to capture the value by ownership. We're not just borrowing the string immutably to read it or mutably through a reference to update it. We're actually capturing it in order to have to return it to whatever is going to invoke the 'capture_string' closure. The compiler understands that the invoked closure will return the string to its new owner, say another variable. Say for example, here we have an 'owner' variable assigned to the return value of 'capture_string'. The compiler understands that the invoked closure will return the string to its new owner. Thus, after the closure declaration, 'first_name' will no longer be the owner. I want to mention again that that movement of ownership happens at closure declaration, not invocation. The closure cannot redeclare itself, and that's because there will be no more 'first_name' owner. The owner of the string will be whatever variable or owner receives the returned string that is the result of the first closure invocation. This closure cannot run more than once. It cannot repeat the logic of taking ownership from 'first_name' again, because after the first invocation, 'first_name' will no longer be the owner. You can't take ownership again from something that is no longer the owner. So you can imagine if there was no 'FnOnce' restriction here, which means if we allowed this closure to run multiple times, how would that work? How would that work if the closure could be invoked a second time? How would it get the string of "Alice" to take ownership from 'first_name'? The owner would no longer be 'first_name' after the invocation. It would be 'owner' right here, right? So we can't just repeat the logic of taking this from an owner that is no longer the owner after the invocation. That's why the closure declares its type as 'FnOnce', which means it's a type of closure that cannot execute more than once. So I want to show you here that if I bring back 'first_name' and execute my code, I want to show you the compiler error. Notice here it says move occurs because 'first_name' has type 'String' which does not implement the 'Copy' trait. That is expected. But here it shows where that happens. Right here. "Variable moved due to use in closure". It happens at the declaration of the closure itself, not the invocation. We're not actually invoking 'capture_string' in this example. All right. Here's another very similar example. The same principle of the movement of ownership will happen if we assign a heap data type to a variable inside the closure. So for example, if I expand this to be a pair of curly braces. And here I create a local variable called 'person', let's say and assign it to be 'first_name'. And then let's say I don't even return anything. I just 'println!' and output the value of 'person'. This is another example of a closure that will implement the 'FnOnce' trait. Let's think about why. Well, imagine that this line existed outside of the closure. That would move ownership of the 'first_name' 'String' from 'first_name' to 'person'. That logic could only happen once, right? After this line exists, we would not be able to take ownership again away from 'first_name', because it would no longer be the owner. It's the same principle here, except it's being captured in this invocable procedure called a closure that just hasn't ran yet. The 'first_name' variable is invalid after this closure declaration because this closure is almost taking ownership for a future use case, which prevents anything else from being able to take ownership from 'first_name', because 'first_name' is going to become invalid after the closure declaration. It's almost like the 'capture_string' closure has captured ownership of 'first_name', so we cannot have anything else take it. So in this example, the closure does not return the string. So it's actually going to be deallocated after the first invocation of the closure when 'person', the new owner, goes out of scope. Regardless, the key takeaway is we cannot logically run the closure again. It's impossible to run it multiple times because we can't take ownership from 'first_name' away to assign it to the 'person' variable multiple times. It's a one time operation, and that's exactly why the compiler infers the closure type of the 'Fn' trait. Movement of ownership is a one time operation, A closure with 'FnOnce' cannot be called multiple times. That is because the closure with an 'FnOnce' designation will take ownership of some value, in this case 'person', and that's an operation that cannot logically happen multiple times. So we cannot logically call the closure multiple times either, right? In fact, if you try to run it twice, let's take a look at what we see here. Right here. It's going to tell us closure cannot be invoked more than once because it moves the variable 'first_name' out of its environment. That's exactly what the compiler is trying to tell us about the example that I was signing. Now, again, you don't need to worry about the complexity here. The important thing, as always, is that the compiler will catch you, but hopefully it serves to demonstrate the kinds of situations where the compiler can intuitively understand that a closure is capable of being invoked multiple times if, for example, it simply has a copied type, or for example, if it borrows an immutable reference or even a mutable reference, there's no risk to the closure running multiple times. It just needs to make sure that it's either reading the data or writing an updated reference to the data, right? But it's not an operation that logically can't execute multiple times. That is, in comparison to a closure that implements the 'FnOnce' trait, which indicates a closure that can only run a maximum of one time due to the logic in its body, such as the capture or the movement of ownership of a heap based data type like a 'String', and that can occur, as we saw in these examples, through the closure, returning that heap based data type, or something like moving ownership to a local variable. And there's many other examples that we've seen throughout the course of how ownership can move from an owned value to another. And if that logic of movement happens in the body of the closure, that is a movement of ownership, and the closure is going to have that 'FnOnce' trait designation, hopefully that makes sense and more on this in the next lesson.
