# Passing in a Function to Fn Trait Parameter

A function is an invocable procedure. If the function's logic does not involve capturing a value from the external environment, the outer scope in other words, we can actually pass a function in as an argument where an 'Fn' trait type is expected. A closure is a totally valid argument there as well, and the most common example we've seen. But I want to demonstrate that function arguments are valid as well. That's why the most accurate statement to make is to state that the 'Fn' trait is not really mandating a closure, it's more so that it is mandating some kind of procedure that can be invoked with parentheses. A closure is satisfactory, and sometimes a function can be as well. To show you this, what I'll do is define a very simple function with my 'fn' keyword called 'bake_cake'. And in here I'll just do a simple 'println' and output something like "Hello chocolate cake". And in the body of main, I'm going to invoke 'execute_thrice', which expects a procedure argument that has a trait bound of being something of type 'FnMut', some kind of invocable procedure. And what I'm going to pass in here is 'bake_cake' uninvoked. Right. Because we are passing in a procedure, and the 'bake_cake' function is going to satisfy this requirement of being an invocable procedure and thus give us the function being invoked three times. A function and a closure are two distinct entities, but they are similar in that they can both be called, which is what the 'Fn' trait or the 'FnMut' trait captures. So here's an example from the real world. Let's say that I have an Option. I'll declare an option variable, and I will make its type an Option whose T generic will be a vector of strings and on the right hand side, I'll provide the None variant. Now as you may recall, we have our 'unwrap_or_else' method that we explored earlier on in the course. And this expects some kind of invocable procedure. And we previously passed in a closure. As an alternate option, we can pass in a function. For example, think about the new constructor function on the vector type. Right here I'm going to access my 'Vec' type. And as a reminder we have the 'new' constructor function which returns an empty vector. So how is this going to work? Well, Rust is going to run the 'unwrap_or_else' method. It's going to see the None variant. So it's going to match on that. And remember what it does in the body of 'unwrap_or_else' is it invokes the procedure that it gets. In this case, the procedure that it gets is not a closure but the 'new' constructor function which will be invoked, which will return back an empty new vector, which then will become the return value of the 'unwrap_or_else' method. So here if I assign this return value to 'collection', we're going to see that 'unwrap_or_else' will give us a vector of strings. We pass in the cooking recipe, the uninvoked procedure, which in this case is the 'new' associated function living inside the vector or the 'Vec' namespace. And that's totally valid. So here I can show you, for example, that if I output this in Debug format, we do indeed have a valid vector. And we were able to get the code to compile without strictly passing in a closure type, but rather a function. That just goes to demonstrate that functions can still serve the same purpose as closures do. Typically, again, you're going to see closures because you're going to want a one-off quick procedure that you can declare inline, where you don't have to worry about giving it an explicit name. And you'll also get some of those benefits, like not always having to write out the parameter types or the return types. That's kind of the advantage of closures is they can be a nice quick throw away option, but it just goes to show that functions can be valid as well.
