# The Fn Trait

So very quickly, let's review the 'Fn' trait. The 'Fn' trait is a sub trait of the 'FnMut' supertrait, and it represents a closure that captures immutable references or doesn't capture any state at all. Many of the inline closures that we defined implemented the 'Fn' trait, but you'll find it to be pretty rare to define a closure parameter that mandates the 'Fn' trait. It is the strictest one of the three because it cannot accept an 'FnOnce' closure or an 'FnMut' closure. So it's actually pretty uncommon to find the 'Fn' trait being mandated for a parameter, even in the Rust standard library and its code. I do want to show you a basic example of an 'Fn' constraint in action, so I will just declare a very simple function here called 'execute_thrice', and all it's going to do is accept a closure and execute it three times in a row. So here I'll define a 'procedure' parameter. And I'm going to make it of type F. I will define that F generic right here. And here I will use my 'where' keyword to add my trait bound. And I will mandate that the type of F be some type that implement the 'Fn' trait. Here it is again, the strictest one. And for now I can say that the closure will accept no parameters and return nothing at all. And then in the body of my function, I can take my 'procedure' and just invoke it three times in a row. We are more than welcome to invoke our closure multiple times if it is 'Fn'. So now in the body of main, let's try invoking the 'execute_thrice' function with a variety of different closures. So here I'll just declare a separate variable so we can take a look at the inferred type of each closure. So here is my first closure. Here's my two pipes. Let's just do a basic 'println!' right here. And I will output something like "I'm the boss" and here I will invoke 'execute_thrice' passing in my invoked closure, and we're going to get this closure invoked three times, which is going to print this content three times right here. The important takeaway here, though, is notice the type of the inferred closure parameter. It is indeed 'impl Fn' because there is no state being captured. There are no immutable references, but even more generally, there are no outside variables or names that are being pulled into this scope of the closure. There's no borrows, there's no ownership transfers. So the closure implements 'Fn'. Next up, we can declare a closure that implements the 'FnOnce' trait. So as a simple example we can have the closure take ownership of some heap data type. So here for example I can declare a 'bosses' variable set to a vector in here. Let me just populate a single string of "Boris". And one way that we can force the transfer of ownership inside a closure body is we can simply assign that owned data type to a local variable. So if I have, say, an 'employees' variable and I assign it to 'bosses', that forces a movement of ownership from 'bosses' to 'employees'. And that kind of happens when we declare the closure itself. But because that transfer of ownership is an one time operation, Rust will infer a type of FnOnce for this closure, and now it is illegitimate to pass into 'execute_thrice'. Because remember, 'Fn' is the strictest possible closure type. You can pass in an 'Fn' closure type where a 'FnOnce' closure is expected, but not the inverse. FnOnce is at the very top of the hierarchy, and we cannot pass it in to a place that expects 'Fn'. The same rules are going to apply for a closure of type 'FnMut'. We cannot pass in an 'FnMut' closure into a parameter that expects an 'Fn' closure. 'Fn' is the strictest one. So to show you that variation, all I can do here is make my 'bosses' vector mutable and borrow a mutable reference to it by calling the 'push' method to append a name like "Alexandra" right here. So now notice in order to mutate the vector, the closure will borrow a mutable reference in order to call the 'push' method. And thus the inference is going to be 'FnMut', right? 'FnMut' is invalid to pass in to a parameter that expects an 'Fn' closure. Now I want to note that there is nothing technical preventing this closure from being passed to the 'execute_thrice' function, besides the strict 'Fn' requirement right here. Unlike the previous ownership example, this closure can be invoked multiple times. It can just keep borrowing a new mutable reference to the updated vector each time, and just keep appending the same "Alexandra" string over and over again. In other words, it's not really this closure's fault, it's the strict requirements of this trait bound mandating 'Fn', which makes 'FnMut' an illegitimate closure type to pass in to 'execute_thrice' so we can make the 'execute_thrice' function more flexible by reducing this trait to be 'FnMut' instead of 'Fn'. The 'FnOnce' trait becomes too flexible because we intend to invoke the procedure closure three times. So 'FnOnce' is insufficient, but 'FnMut' is a little bit more of an upgrade over the stricter 'Fn' because it enables us to pass in stuff like this as well. The only thing that we need to update here is we need to make sure we mark the 'procedure' parameter as mutable, because it's going to own that closure, and the closure state that it's going to be changing after every execution. In this case, that captured state refers to the mutable reference to the 'bosses' vector. The 'bosses' vector will be changing each time the 'push' method is called. It adds one more element to the end. So the mutable reference that the closure is capturing needs to update each time it executes the closure. Right? This time it's going to be operating with a 'bosses' vector that already has an additional string of "Alexandra", and here it's going to be operating one more time with a vector that has two strings of "Alexandra". So the underlying vector state is changing, and thus the mutable reference to it has to be changing as well. And that is captured or enclosed within the 'procedure' parameter right here. So that closure state itself is changing the kind of closure logic, the redeclaration of that closure body. And thus we need to mark this as mutable with the 'mut' parameter. All right. So now we can see that this example would work as well as our original 'Fn' closure that simply printed out content. And it's for this reason that you're typically not going to see a lot of methods or functions define a closure parameter of 'Fn', because it tends to be very strict, and usually you're going to be able to have more flexibility simply for making it an 'FnMut' instead, where you can still pass in an 'Fn' closure, but also pass in an 'FnMut' closure, just like we saw in this example.
