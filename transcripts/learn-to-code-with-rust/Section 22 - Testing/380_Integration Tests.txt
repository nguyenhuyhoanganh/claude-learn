# Integration Tests

The tests that we've written so far can be described as unit tests. A unit is a small, independent chunk of code or functionality. Now there's some discussion and debate on what exactly constitutes a unit. I like to view it as one small building block of a larger application. So to me, testing an individual method is an example of a unit test. We're not testing, for example, the struct's interaction with other pieces in the application or other structs. Rather, we are zooming the lens in on one single isolated functionality. And that's the beauty of the dependency injection pattern. From the previous lesson. We were able to test venue management more in isolation. We also made it more flexible for future venues that may not exist yet. So the rust community adds unit tests like the ones we've written directly within the implementation files that we have, just like we had here, we declare a tests module within the implementation file. And that's where we write the tests for the constructs declared within that file. The unit tests live alongside the implementation code. We followed this pattern for the tests within our attractions module and our management module. Now the complement to unit tests is integration tests. Integration tests are larger in scope than unit tests. Integration tests may test a feature as a whole. It may test a feature that will require, for example, the communication or interaction of multiple structs, multiple types or functions working together. So if you're building a library for consumption by others, integration tests can test the code as a whole, much like any external code would use your library. We are looking to test the bigger picture, so integration tests are not going to need this special configuration annotation. Rather, rust is going to look for our integration tests based on their location in the code base, and the convention is to store them within a top level tests directory.
