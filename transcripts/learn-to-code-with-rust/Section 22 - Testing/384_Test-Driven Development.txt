# Test-Driven Development

In this lesson, I want to introduce test driven development, which often goes by the acronym TDD. Test driven development is a paradigm that encourages you to write your tests first. Of course, you might be curious if you write your test first. Doesn't that mean that the test will automatically fail because the implementation does not yet exist? And the answer is absolutely, and that is the intent. This is part of the cycle of TDD, which is also called the red green refactor cycle. The red phase indicates a failing test. The test is validating some assertion of value that does not yet exist in the program. You then move on to the green phase, where you get your tests to pass by writing the actual code. Finally, in the refactor phase, you improve your implementation to make it the best one possible, while continually running your tests in the background to ensure that you haven't broken any functionality, then the process or the loop begins all over again, right? A failing test. Get it to pass, then improve your code. So what are the advantages of TDD? There's actually several of them. First up, test driven development will actually guarantee that you have tests for your code. Tests are often neglected, especially after a feature is complete. TDD guarantees that you will have a well-tested code base, because you will not have permission effectively to write your implementation code unless there's already a test for it. Another benefit is that you will avoid over testing if you write a test with test driven development and it automatically passes, that means that that functionality already exists in your code and your test is not testing anything new. That means that test is excessive because its functionality has already been covered. So a failing test in the beginning guarantees that the functionality you're going to add in your source code is actually brand new. Right. Adding additional value. The second advantage of TDD is that it forces you to define your contract. Before you start rushing to write your code. It often allows you to simplify and break down a problem into smaller pieces. You have to think about questions like what is the name of the next function that I want to write? What arguments should it accept? What return value should it produce? You don't have to worry about the implementation just yet, but you can define the battle plan, so to speak, the basic outline of what some functionality should do and how the tests are going to validate that it does. When you write your tests first, you're much more likely to avoid testing specific implementation details because those are not yet going to exist, and you're more likely to focus on testing the core functionality of the eventual code, even without knowing the exact function body that you're going to write, you can ask, what should this function produce as a return value? What is its single responsibility? How do I validate that single responsibility in my test before I even start writing the actual code? A third advantage of TDD is that it will likely simplify not just the complexity of your tests, but the complexity of your code, and also improve the quality of the code itself. That is perhaps the biggest benefit. It's not just about better tests, it's about better design in your code. TDD will typically allow you to think about how to break up functionality into smaller units of value. It's much more likely to lead to good design patterns in your code. That's perhaps the biggest advantage of TDD is that I argue that it will actually lead to better code, not just better test.
