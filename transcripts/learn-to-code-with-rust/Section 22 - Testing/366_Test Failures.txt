Next up, let's take a look at a failing test. Or in other words, a test in which the assertion fails. The assertion is not met. So I'll add another test within our 'tests' module here. It's going to be again a plain Rust function. I'm going to call this one 'museum_can_sell_multiple_tickets'. And here is the key component. Very important. I'm going to annotate this test with my 'test' attribute. And that is critical to establish this as a test function and not just a general helper function. In the body of this test function, I'm going to perform some logic that is very similar to what I have above. In fact, I can just copy and paste the first two lines from the test above, but this time around I'm going to sell another ticket. And since each ticket generates $25 in revenue, the museum's total revenue should be $50. But this time around, I want to show you what a failure will look like. And when a test fails, it could be because you set up the test incorrectly or because something could be broken within your code. So I'm going to once again use my assert_eq! macro. And let's say I compare the value of the 'revenue' field on the museum with the value 25. This is a mistake and it is a mistake on the test side. All right. So I'm going to run 'cargo test' once again. And now you'll notice we're going to have both of our tests listed. Because we added our 'tests' module, we're also going to have this 'tests' prefix before the double colons. And then once again the name of the function as we wrote it is listed. And for each individual test, we're going to see whether it passed with 'ok' or whether it failed with 'FAILED'. Failed means the assertion has not been met. So the test runner will execute each of these tests in a separate thread. And when a thread sees that its test has failed, the thread and its test will be marked as failed, but the other ones will continue running. In other words, a test failure will not stop the remainder of the test suite from executing. Rust is going to run all of the of the available tests as quickly as they can, and then aggregate and summarize the results in your terminal. Now, for every successful test, you're just going to see its name and 'ok'. For every failure, you're going to see a more detailed section that's going to describe exactly what went wrong. So it's going to tell you again the exact file, the exact thread, the exact line number where the failure occurred. So this is line #44 which is exactly where our assertion was written. assert_eq!, right? That means that nothing went wrong here. It was actually in the assertion that things went wrong. Now, you'll notice immediately below that we're going to have left and right, and left and right simply refer to the first and second arguments to the assert_eq! macro. And it actually doesn't matter which order you pass them in. You could reverse the order of these two and the results would be the same. So left is telling us that 'museum.revenue', the very first argument to assert_eq! the value of that 'revenue' field was actually 50, while the value we provided for the second argument represented by right, is 25. That is not equal and thus there is a test failure. Now, in some other test frameworks in other programming languages, the order of these arguments matter. One argument typically represents the intended result of the operation that is being tested. The other represents the hardcoded expected value that we know. Rust and its test runner don't really care about the order of the two arguments. They're just using left and right to represent the first and second arguments. So again, you're more than welcome to swap the order of these two, if that makes more sense to you. I generally like to have the operation first, but regardless they're both going to yield the exact same result, failure, but now you can see left is 25 and right is 50. I'm going to bring this back to our original implementation. All right. And once you have a failure, that tells you that something is wrong. In this case, it's obviously our test. So we can go ahead and fix this by changing this to 50, which is correct. And now our test suite is running. But the value of tests is usually finding bugs in your implementation code. So maybe for example you have the test here verifying this logic. And maybe you have something as simple as a typo. You accidentally type 24 here when you're writing the code. Well, the test is keeping you honest because it is verifying the code is working as it is expected. This test doesn't know technically about the internal working details or the implementation of 'sell_ticket'. Obviously it does know that because it's going to execute that, but the point is it's verifying that this method when it's executed is going to lead to this result. So we could in fact write this test before the method even exists. That is in fact a specific paradigm of testing called test driven development, which we'll explore a little bit later in the section. But regardless of whether you write the test first or after your implementation, it's keeping you honest so that if you make a mistake, whether it be a typo or a bug, let's say you're changing this method a year later, the test will keep you honest and say "Hey, actually, it was supposed to be 25 here for the museum revenue, but I'm getting 24, right?" And in this case, since the 'sell_ticket' method is broken or not delivering on the expected functionality, both of our tests are now actually failing. We're going to see both of them listed right here. You can even see that the order we have them declared within our file is not necessarily the order they're going to be printed because again, remember they are running in separate threads. They are totally independent. So it looks like this test failure was declared first. We can see 'test::museum_can_sell_multiple_tickets', its respective failure and the comparison of the two values, left and right, once again representing the two arguments to the assert_eq! macro. And then for each test failure, such as the other one, the individual ticket one, we can see the exact same failure listed. And then at the bottom of the list we have all of our failures aggregated as well. For each individual test we have the failed text right here. And then the summary output says 0 tests passed and 2 failed, offering you a nice aggregated view. All right. So I'm going to switch this back to the original design.
