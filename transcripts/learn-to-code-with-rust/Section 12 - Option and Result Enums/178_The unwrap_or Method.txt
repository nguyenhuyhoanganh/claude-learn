# The unwrap_or Method

In this lesson, I want to introduce you to another method that is available on the 'Option' enum, and it is 'unwrap_or'. This method is similar to 'unwrap'. It attempts to extract the value stored in the 'Some' variant. However, this method mandates an argument which represents the fallback value. The fallback value is the default value to return in the case that we have a 'None' variant, so this offers a more error prone way to extract a value, because we'll either pull out the value from the 'Some' variant or provide a backup value in case we have a 'None' variant. So let's declare two variables here. I'm going to call the first one 'present_value'. And I'm going to use 'Option::Some'. And this time around let's have the type be an i32 and I'll store a value of 13. Then, on the line below, I'll declare a 'missing_value' variable and this will be the 'None' variant like so. Once again, if you want to, you are welcome to just write it like this. 'Some' and 'None'. Notice that if I change the syntax, the Rust compiler still correctly infers that the type of these variables is an 'Option'. The only reason we have an error here is because we are starting out with 'None', we need to provide the concrete type for the generic 'T' parameter explicitly. So here I can say something like 'Option'. And let's say this will store an i32 in the 'Some' variant in case it has one. But other than that, this code is perfectly fine. The compiler is happy and it will understand the type to be an 'Option' simply from 'Some' and 'None' right here. So below I can take println! and let's interpolate a dynamic value. I'm going to take my 'Option' in the 'present_value' variable. And I'm going to invoke the 'unwrap_or' method. This method requires a parameter called 'default' which is the fallback value. It's the backup. You can think of this as the value to provide in case of emergency. So here I can provide an arbitrary value like 0. Now in this scenario, 'present_value' is the 'Some' variant. So there is an associated piece of data to unwrap and it is the number 13. So now the backup value of zero basically is pointless. We are able to successfully extract 13 just like we would with the regular 'unwrap' method or the 'expect' method. The advantage of 'unwrap_or' is in the this scenario where we might have a 'None' variant. So here I can provide 'missing_value'. And normally if we tried to call 'unwrap' on a 'None' variant, we would get a panic. We would get a runtime error. Now we provide a fallback value which says if you have an 'Option' and it happens to be the 'None' variant and there is no associated piece of data to extract, give back 0 instead or whatever argument we pass here. So I can run this. And now we're going to get 0. And here as another example, if I provide 100 once again we're going to get 100. Now this is where our original type annotation becomes so handy because it is based on our declaration of an i32 here, that Rust knows that the fallback value to 'unwrap_or' must also be an integer, right? Either we're going to have an integer in the 'Some' variant, or we're going to fall back to a value of the same data type from the 'unwrap_or' method. So, for example, if I try to return a true, we're going to get a compiler violation. We declared that the specific type for the generic type 'T' was an i32. But we're trying to fall back to a bool, right? So there's two ways to fix this problem. The first is just to return a actual integer here. Or if we actually want this 'Option' to store a concrete type of bool, we can provide a 'bool' here. And that will similarly fix the problem, because now our default fallback value is of the same type as the concrete type for generic 'T', right? So that's the 'unwrap_or' method. Hopefully, the method name makes sense as well. It literally is 'unwrap_or' provide this value. That's why the method is called 'unwrap_or'. All right, that's all there is to cover here.
