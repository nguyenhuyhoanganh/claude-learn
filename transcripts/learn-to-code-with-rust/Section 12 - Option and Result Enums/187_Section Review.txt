Congratulations on reaching the end of another course section. As always, let's take a few moments to review everything that we learned. In this section, we focused on perhaps the two most widely used enums built into the Rust language, and they are Option and Result. So first up the Option enum. It models a scenario where a type could be either a present value or an absent one. It consists of two variants. The Some variant holds an associated piece of data of generic type T, so it can hold data of essentially any type but that represents the present data, and then the complementary None variant holds no associated data and represents the absence of data or data being missing in other words. There are certain situations that can yield either some data or no data. So the way I like to remind myself of this is I like to think of the word optional, which is where Option comes from. It's optional because it may or it may not contain some data of value. So once we have that Option enum, we can have either variant. And there are a wide variety of methods available that are going to target or extract that nested data if the variant happens to contain it. So for example, the 'unwrap' method attempts to extract the value from the Some variant. The reason I use the word attempts to here is because if the variant happens to be the None variant, there is no associated data. So the 'unwrap' method will cause a panic at runtime. The 'unwrap' method will give you that value of type T from the Some variant, but only if it happens to be the Some variant. And for that reason, the 'unwrap' method is a bit optimistic and a bit relatively underused. Sometimes it's just an easy developer thing to add, because you are certain that you're going to have the Some variant, but usually you're going to find more comprehensive solutions like, say, a match statement or the if let statement to make sure that you cover all possible bases, because it is possible that 'unwrap' will lead to an error at runtime. The 'expect' method is identical to unwrap, but it allows the customization of the error message that is printed to the console. And then finally, we have the 'unwrap_or' method which returns a fallback value. That's the argument you provide to the method, but only in the case of a None variant. So if we have a Some variant, we get its data, or we fall back to the argument you provide here. And there's many other methods available for extraction as well. All right. So the second enum we covered was the Result enum which models the outcome of an evaluation that can produce either a success or an error. There are many things that can go wrong. And usually you don't want your Rust program to panic and crash. Rather, you want to handle those errors gracefully, and the Result enum is the Rust idiomatic way to do so. So it consists of two variants: Ok and Err which is abbreviated E-R-R, and both of those contain a piece of associated data. The Ok variant has an associated piece of data that is associated with generic type T, and the Err variant has an associated piece of data associated with generic type E. Remember, those types T and E are just generics. They are placeholders, so the concrete type that fills in or plays the role of T and E can differ. But the reason there are two generics declared is so that we have the ability to have Ok and Err be two totally different types, or they can be the same type as well. It's all going to vary depending on which Result enum you're working with, from which function or method as written, by which developer, etc. it's up to you how you want to define your interface, and if you want to return a Result, it's up to you to choose what you want the Ok data to be and what you want the Err message to be, and the corresponding types for those. The Result enum implements the Debug trait. So as with all other other types, we can use our format specifier symbol, the colon, followed by the question mark to get the Debug string representation of a variant. All right. And just like with the Option enum, the Result enum has the exact same family of methods. The 'unwrap' method attempts to extract the value from the Ok variant. The Ok variant indicates a success, and once again, if the Result variant happens to hold an Err variant, there is no success data to extract, so to speak. So that method will cause a panic at runtime. So will the 'expect' method, which is identical to 'unwrap', but it allows the customization of the printed error message. And once again, the 'unwrap_or' method allows you to have a little bit more of a safer approach because you can provide a default value, a fallback value to give back in the case of the Err variant. If you have the Ok variant and you call the 'unwrap_or' method on that, then you're just going to get the associated data from the Ok variant. And finally, some extra tidbits. We talked about the notion of the Rust prelude, which is just a collection of names that are automatically imported into every Rust program. The Rust prelude includes the top level enums of Option and Result, but also all of their variants. So you can use Some, None, Ok, and Err at the top level of your program without specifying their enum prefix before. You're welcome to write it out fully. It's whatever you prefer. You're going to see both options in the real world. And finally, as I mentioned, the match keyword as well as if let are popular combinations to mix with Result and Option enums because the match keyword will use the compiler to validate that every possible scenario is covered in the match statements' arms.
