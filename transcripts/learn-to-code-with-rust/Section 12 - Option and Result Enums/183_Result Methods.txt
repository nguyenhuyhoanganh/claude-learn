# Result Methods

Using a match statement is a common solution for handling a Result enum, but the Result enum also has various methods to assist with extraction, very similar to our Option enum. For example, methods like 'unwrap', like 'expect', 'unwrap_or'. All of those methods are available and they operate very similarly. So for example, let me get rid of my match here and let's return back to a invocation that will return the 'Ok' variant. So I will change this back to 2.0. So I have my 'result' variable. Let's go ahead on the next line and provide a dynamic value to println! And on a Result enum. Just like on an Option enum, I'm going to have an 'unwrap' method. As you might guess, this is going to extract the associated data from the 'Ok' variant. So in case of success, remember you can think of 'unwrap' as unwrapping the present. We're getting the good thing that's inside. In this case, it's going to be this 'Ok' variant's associated data, which is going to be 5. Just like with the Option enum, if we have the incorrect variant, in this case the 'Err' variant, if I tried to divide by zero, then the 'unwrap' method will trigger a runtime panic and error because we cannot unwrap the kind of success value represented by the 'Ok' variant because there is no 'Ok' variant. All right. As you may recall, there is a complementary 'expect' method. It works the exact same way as 'unwrap', but it allows us to provide a custom error message. So here I can say something like "Unable to parse calculation". And so when we have this 'Err' variant and we try to call 'expect' on the enum, we're still going to get a runtime panic. But now we have this custom error message. And of course there is also the 'unwrap_or' method. And what this will do is allow us to provide a fallback value. So in the case that we have the 'Err' variant, what do we provide instead when we unwrap. So let's say we arbitrarily decide that if we cannot divide by zero, we're just going to give you back a 0.0 floating point value. So here I can just write that. This type again must be of the same type as the success type, the 'T' type in our Result. So if I try to do something like five, this is not going to work because Rust sees it like an integer and we need an actual float. So this is now going to give us a 5.0 because this 'divide' function returned a Result enum with the 'Err' variant. So 'unwrap_or' fell back to the argument that we have here. Finally, I want to show you two more methods that are available. And they are going to give you back Booleans. And they can be helpful if you simply want to figure out the kind of Result that you have, the specific variant that it happens to be. There is a method called 'is_ok' As you might guess, what that will do is give you whether you have the 'Ok' variant. And there is also a complementary one called 'is_err'. Just like the variant names, it matches 1 to 1. So these will all always return the inverse of one another. In this case we have the 'Err' variant. So it is false that it is 'Ok', and it is true that it is the 'Err' variant. If I invert this to a valid calculation like this, now the return values are going to be reversed. It is true that the Result on line #10 has the 'Ok' variant, and it is false that it has the 'Err' variant. So sometimes combining these Boolean return values with something like an if statement can once again allow you to take a branching path of logic should you only want to handle one of the possible variants. There's many ways to deal with these ideas in Rust. There is match. There is 'if let'.  There is checking manually for a specific variant. Lots of different ways to solve these problems, but all of these helpful constructs and methods are available on Result enums as well as Option enums.
