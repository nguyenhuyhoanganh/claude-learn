# The unwrap and expect Methods

Once again, it's important to understand that the Option type is a wrapper around a core value. In other words, a reference to a string ( &String ) is a different type from an Option enum with a 'Some' variant that holds the reference to a String. The Option is its own separate enum type. So once we have this Option, we need to actually get the actual value, retrieve the actual value out of the variant or the 'Some' variant to be more precise. And there are several ways to accomplish this. And in this lesson, I'll start with the more naive approach, which is the 'unwrap' method. The 'unwrap' method attempts to extract the associated data out of the enum. So if you think about the word 'unwrap' in the real world, think of it like unwrapping a present, you're retrieving something that is hidden by the wrapping paper, right? It's the same principle here. This Option enum is sort of like the present, and we're trying to unwrap it to get the core value out of it. Now if the variant is 'Some', then the 'unwrap' method will extract the value. But if the variant is 'None', we're going to run into a runtime error because there is nothing to extract. So let's take a look at both of those scenarios. And then in the next lesson, I'll show you the more idiomatic way to deal with options in Rust, which is using the 'match' keyword. But for now, what I can do is I'll create a variable, let's call it 'valid_instrument', and I'm going to take my 'bass' variable, which is an Option, and call the 'unwrap' method on it. So once again if we have the 'Some' variant then that 'Some' variant's associated data is what the 'unwrap' method will retrieve. So in this case it's technically going to be a String reference ( &String ). Right? Now I can output the value of 'valid_instrument'. This is a string reference. But as always that's not a problem because Rust will dereference it. It's going to follow the address to the location and output the core String there which is "Bass". So we started with our Option enum. We called the 'unwrap' method. It was successful because our variant was 'Some', and we got out the String reference ( &String ) that the 'Some' variant was storing. The problem with 'unwrap' is if we're dealing with a 'None' variant. So for example here I don't even need to assign it to a variable. If I simply do 'invalid_instrument' and call 'unwrap'. We're going to run into a runtime problem right here. We're going to panic. And the output says we called 'unwrap' on a 'None' value. There is nothing to unwrap. There is nothing inside the present, so to speak, because we have the 'None' variant and that has no associated data. So we can see even the Option by itself, if we start using some of these more risky methods is not perfect, because we're not handling all of the ways that the program can go wrong. The Option was a great beginning point for something like the 'get' method, but then we can't just assume that we have the value that we want. We have to be a bit more safe in the code we write, to make sure we handle all of the possibilities and 'unwrap', it's problem is that it always assumes that you have something to extract. Now, the reason that we have the 'unwrap' method, despite its risk, is sometimes you're going to know with full certainty that you have the 'Some' variant, and you just don't want to go through the more complicated process of handling all possible scenarios. So 'unwrap' still exists mostly as a developer tool to help you write faster, easier code. We just call a method. We get the value, but it's not always the idiomatic Rust way because it's not the safest approach. All right. And I do want to show you one other method that is very similar to 'unwrap'. And it is called 'expect'. 'expect' is basically identical to 'unwrap', but it allows us to customize the error message. So once again if you have the 'Some' variant, the 'expect' method will extract it. If you have the 'None' variant, the program will fail at runtime, but it's going to display the error message that you provide to 'epxect'. So for example here, instead of 'unwrap', I can do 'expect' and write something like an error message that says "Unable to retrieve element". And I'm just going to comment out this code right here. So we're going to see we're still going to get "Bass" because in this case it was successfully able to unwrap or retrieve the associated data for the 'Some' variant. However, here I'll replace this 'unwrap' with 'expect' as well, and I'll write something like "Unable to retrieve musical instrument". So we're still going to get a runtime error, just like the 'unwrap' method. But now the string that we pass to 'expect' is the custom error message that is going to be displayed in the output. So it's a little bit better than 'unwrap' because we can provide more context that is specific to our program to explain what went wrong. But regardless, both 'expect' or 'unwrap' suffer from the same problem, which is that they are optimistic. They are only going to work in the hopeful scenario that you have a 'Some' variant with data to unwrap, with data to pull out.
