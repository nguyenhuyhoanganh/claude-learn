# Returning a Result Enum from a Function

Next up, let's define our own custom function that will return a Result type. This will give us more practice with both returning a Result variant as well as handling it wherever the function is called. So let's define a simple function called 'divide' And this function is going to divide one float by another float. So I will define a parameter called 'numerator'. And I will declare its type to be a 64-bit float, a f64, and then a second parameter of 'denominator'. And that will also be a 64-bit float. Then I'm going to specify my return value as being a Result. This syntax requires me to provide two concrete types for my generics. So if we successfully divide a float by a float, we're going to get back a float. And that will be my type for the 'T' generic in the 'Ok' variant. And then for my 'Err' variant, it's type I can declare to be something like a String. All right. So here's an example of how something like this could fail. In mathematics, it is impossible to divide by zero. It is an invalid operation. So what we can do is if our denominator is zero, we can return the 'Err' variant. We're going to avoid any kind of panic. We're just going to return an 'Err' variant holding a String that describes the error. And if our denominator is not zero, then we'll perform the division and return it in the 'Ok' variant. So I'll begin with an if statement. And I'll check if my denominator is equal to 0.0. I need to make sure I compare with a float here, and I use the equality operator, which is two equal signs ( == ). If this is the case, I'm going to return here implicitly the 'Err' variant. Once again we can write this. But this is the equivalent of writing 'Result::Err'. Same thing. So 'Err' here. And we specified that the type is going to hold within itself is going to be a String. So I can either do 'String::from' here or call the 'to_string' method on a string literal. Let's go with that second approach. So I'll provide an error message like "Cannot divide by zero". Call the 'to_string' method on this string literal. This will give me back a heap allocated String. And I'm going to store that as the associated data in my 'Err' variant and return that. Then I'll provide my else clause. Here I'm going to take my 'numerator' and divide it by my 'denominator'. This is a float 64. But that is not a valid return value, rught? Because it is not wrapped in a Result. More specifically a variant of the Result. So this will be our other variant which is 'Ok'. So here I'll provide 'Ok'. And then I'm going to store the associated data of the actual calculation within that 'Ok' variant. And now in the case of either a failure or a success, the beautiful design here is that we have a consistent return type and the program will not break. We are gracefully handling the possibility of an error and then delegating the responsibility for handling it to the caller, to the part of the code that is actually going to invoke our 'divide' function. So now in main, let's handle both of those possibilities. So here I'll define a 'result' variable and I'll invoke my 'divide' function. Let's start with a valid division. So I'll provide a numerator of 10.0 and a denominator of 2.0. Now once again notice the inferred type for the Result variable. This is not a type of a float 64. It is not a type of a String. It is a Result enum and more specifically a Result enum that has an 'Ok' variant type of a float 64 and an 'Err' variant type of a String. So if we, for example, declared a Result type with different concrete types here that did not match what we are returning from 'divide', we would have a type mismatch. So the type checking doesn't just stop at the enum, it goes into the specific concrete types that are filling in for the generics of the respective variants. All right. So now we have a Result. How can we gracefully deal with it? Well as you might guess, just like with Option a really popular solution is the 'match' keyword, right? So here I'm going to do 'match' and 'result'. And now the compiler will only compile if I handle both possibilities in 'match' arms. What to do if the operation was successful and what to do if the operation failed. So let's start with our 'Ok' variant. This will have a piece of associated data. I can call that something like 'calculation'. And Rust will know that the type of calculation from the 'Ok' variant is a float 64. So here I can output something with println! like "Result: " and then provide the value of 'calculation'. Then for my other arm, we're going to cover our 'Err' variant which is just "e-r-r". And that is also going to have its own piece of associated data, which I can call 'message'. But the type of message is this type right here. It is a String. We have customized what this is returning right here and right here. So now we have a String. And we can output something totally different like "Error". And then interpolate that String right here in line. It's represented by the message. So now the compiler is wonderful because it's forcing us to respond to the possibility of failure. That is one of the reasons why Rust is such a safe language is because it always models these situations that can go wrong with an elegant design, like the Result enum type. There is no way that this code will compile if we don't tell Rust how to treat the unhappy scenario. The failure scenario. The error scenario. And that's why Rust tends to be so safe, is because it forces us to account for all possibilities. So now we can run this and we're going to get a Result of 5. That is exactly what we expect when we divide ten by two. Let's now look at a opposite situation. Let's return this thing right here. So let's provide a denominator of 0.0. This is not going to lead to our program crashing. This is instead going to lead to a very elegant reality where we still get back the exact same type. It's still a Result. Now the only thing that's different is we're going to hit this arm right here in our match statement, the 'Err' arm. And we're going to output "Error" And then here we have this String that we provided right here from the 'Err' variant. So both of these arms are doing the same thing. They are extracting the respective piece of associated data within each variant. But that piece of data happens to be of different types. And we're just gracefully handling either scenario with different logic. So in this case: "Error: Cannot divide by zero". All right. So once again this Result type is a wrapper around whatever underlying value we have captured. So it's important to note again we cannot just simply use float methods or string methods here. This is a Result. This is a separate type. It's kind of like a protective shell or wrapper or container around one of these two types of values. So we need to handle both of those scenarios. And the match keyword is a very elegant, very common solution here, just like it is with the Option enum.
