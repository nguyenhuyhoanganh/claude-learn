# The use Keyword II (Name Conflicts)

When we create a shortcut with the 'use' keyword, we bring a name into the current file's scope. There can only be one example of any given name within a file. Otherwise, there's going to be a name conflict or a name collision, which is when Rust doesn't know which name we are referring to. For example, I can spot something like line #11 and think to myself, "Oh, wouldn't it be great to bring in this 'MANAGER' name directly into the 'main.rs' file? Well, if I try to add something like 'use orders::MANAGER', the compiler is not going to be happy. That's a bit of good news because the compiler will warn us about the errors. The issue here is that we already have a 'MANAGER' name in this namespace, in this file from line #5. So if we have two 'MANAGER' names that we are trying to provide a shortcut to, and we reference 'MANAGER' like we do on line #11, and similarly if I remove 'orders' like this, Rust doesn't know which 'MANAGER' name we are referring to. Is it coming from the 'inventory' module's 'MANAGER' or the 'order' module's 'MANAGER'? So the Rust community generally does recommend importing names with the 'use' keyword for simplicity. However, there are always exceptions, and one example of an exception is what we have here. When the same name is shared between different modules, many Rust developers will recommend keeping the original module name present, providing the more longer path. While this code, if I remove this is not technically wrong, it's inconsistent. The 'orders' 'MANAGER' name is module-scoped, while the 'inventory' 'MANAGER' name is available at the top level. It's inconsistent. If we add that consistency, number #1), we'll know which module the names are coming from. And number #2, that provides additional clarity, right? In the sense of who does this 'MANAGER' belong to? Is this the 'inventory' 'MANAGER' or is this the 'orders' 'MANAGER'? As we scroll down in the file and we separate ourselves from the top level 'use' keywords at the top, it's actually harder to understand that detail, right? We've basically followed one rule for this name and a different rule for this name. So now, let's give them a consistent format. So here, I'm going to remove this 'MANAGER'. This means Rust doesn't know where this top-level 'MANAGER' name is coming from. We can specify it is the 'MANAGER' constant within the 'inventory' module. Now there is both consistency and clarity between lines 10 and 11. And obviously as you can see, we can also have a mix and match style. So we can import a certain names from a module like 'FLOOR_SPACE' and 'talk_to_manager' while still providing the full path to other names within the same module. This is totally normal and common within Rust code. It's all about providing clarity and avoiding conflicts like these.
