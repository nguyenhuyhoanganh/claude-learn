# Section Review

Congratulations on reaching the end of another course section. As always, let's take a few moments to review everything that we learned. This section focused on project structure, which is: How can we build larger, more scalable Rust projects that are contained in multiple files and folders? So let's begin with projects, packages, and crates. These are all common pieces of terminology in the Rust ecosystem. A project is just a folder on your computer with a 'Cargo.toml' file. That 'Cargo.toml' file contains the project's name as well as dependencies, and it's what the rust-analyzer tool, as well as the compiler, use to identify that you have a Rust project. Another piece of terminology is a package, which I generally think of as the same thing. And in technical terms, a package is a collection of one or more crates. A package must have at least one crate. A crate is a collection of Rust code that produces either an executable, which means an independent running program, or a library, which means a collection of code for other crates to pull in to reutilize to reuse. So, as I mentioned, there are two types of crates: binary and library. A binary crate is a program that compiles to an executable, and Rust will infer that the current package has a binary crate if it locates a 'main.rs' file in the 'src' directory. A library crate exports functionality for other Rust programs, in other words, other binary crates to use and Rust will infer that the package has a library crate if it locates a 'lib.rs' file. 'lib' is short for library, so as we talked about, a package can have both a library crate and a binary crate. It can have either one, but it cannot have neither. So a package must have at least one crate, which means at least a 'main.rs' file or a 'lib.rs' file within 'src'. Both of those crates, if you have both, will have the same name, and that will be determined from the name value in your 'Cargo.toml' project configuration file. So for us we had a name key set to "warehouse". So the name of our library crate was "warehouse", and the name of our binary crate was also "warehouse". Once again you do not need both, but you can have both if you want to. All right. Now that's all kind of at a higher level. Now we move on to constructs within the code. The most important one is perhaps the module. A module is an organizational container that encapsulates or collects related pieces of code. So that can be various Rust constructs, constants, functions, structs, enums, and submodules which are just nested modules within the parent. That module serves as a namespace. You can almost think of it like a directory or folder that exists for the benefit of the compiler, and the advantage there is that different modules can hold items with the same name. It's up to you how many modules you want to declare and how big or how small they are. It's your choice how you want to organize the concepts and constructs in your program so that it makes sense to you and to other future developers. Now, all module items are private by default. That means that no code outside of the module can access them and use them. So we need to make each individual item or name public, assuming that we want that item to be exposed. Not everything has to be made public. Some internal name, like a struct or a function, can simply be used by other constructs within the module. Not everything has to be made public. It all depends on what you want to expose to other parts of your program. When we want to make something public, we use the 'pub' keyword in front, and that allows external code to reach into the module and access that item, that name. If we use the 'pub' keyword with an enum, for example, all of its variants will be public. If we use the 'pub' keyword with a function, the function is invocable outside of that module. Now the struct is kind of interesting because if we use the 'pub' keyword with a struct, its fields will still be private. So we're going to be able to access the struct name but not actually instantiate it. So we can actually designate certain struct fields to be public and others private. If you want the complete struct to be capable of being instantiated outside of the module, you need to make every field public. If you don't want that, if you have one or more private fields, then the struct must support an alternate mechanism for instantiation, which is usually going to be some associated function that you can make public and invoke to create that struct instance. It's various different design patterns depending on what you want other parts of the program to customize or have access to or modify. So there's three different ways that we can declare a module. They're all going to start with the same syntax, which is the 'mod' keyword followed by a name. And then we have three possible options. The first one is to declare the module's contents directly in an inline block. So you provide the curly braces and you simply nest everything within there, and that's all associated and nested within that module's namespace. The second option is to declare the module's contents in a Rust file, ending in a '.rs' extension with the module's name. So if you declare a module like 'books', then you need a 'books.rs' file. Those names must match because Rust will locate the 'mod' keyword, see its name, and look for a file with that same name in the current folder. The third option is to declare the module's contents in a 'mod.rs' file. That name must stay 'mod.rs', but the module's name will be a folder that you create at the same level that's going to contain that 'mod.rs' file. So once again, if you have a module called books, you'll have a 'books' directory containing a 'mod.rs' file. All right. We can also have submodules. A submodule is simply one module nested within another. To access any module item, including a submodule, we use the scope resolution operator ( :: ). That's the double colons, and that navigates us downwards into the next module so that we can access a name. Submodules, when we are declaring them, will require the creation of a folder for the parent module that is declaring the submodule. Right. So you can't just create all of your module files at the top level of 'src', unless all of those are declared within 'main.rs' and serve as top level modules. Once you have a submodule, which means nested within another, you need to create a folder for the parent module, and it is that parent module folder that's going to store either the submodule's name as a file name, or as a separate directory with its own 'mod.rs' file. So it's the same naming principles. It can get pretty confusing. So what I recommend is just declaring several nested submodules. In fact, go 2 or 3 levels deep and practice creating the necessary files until you kind of get the hang of it. All right. We also have this notion of the 'crate' prefix, which refers to the top level of the crate, the crate root. And for a library crate, that's going to be our 'main.rs' file. This all relates to this concept of the path, which is the location. Or another way to think about it is the navigation instructions to get to a name in your program so we can use an absolute path, which means the full, complete, absolute path from the top of the crate, from the crate root to your intended name or construct. And so if you want to start at the very top, you can use the 'crate' keyword to get there, to start from there and then navigate downwards to wherever the name is located in whatever module or submodule. In comparison, a relative path is a path from the current location, relative to where you are right now. So you start from where you are. You don't have to worry about any parent modules, you just navigate downwards to wherever you want to go. All right. So now we have these modules declared. Let's say that we want to bring them in at a higher level in order to use them within our program. So 'mod' by itself will work to declare a module. And then we can provide the full prefix or the full path to get to a name. But more often than not, you'll use the 'use' keyword because that will bring a name into your current scope, which will simplify all the future paths that you have to write in the code. So if you have, say, a struct within two nested submodules, you can use the 'use' keyword, refer to that struct location once, and then just simply use the struct name in your code without having to provide that location each time. So you write your 'use' keyword, and then you provide the complete path to the name. The last name that is referenced is what is going to be available in that file scope. If you want multiple values from the same location, you can provide curly braces and then separate the names with commas. All right. When we are importing, we can also designate a module itself to be included by using the 'self' keyword. Usually that's going to be when you're combining both the module name as well as some name that is found within that module and you want to declare those imports on the same line. So the module name alongside an item that is nested within that module. Remember, there is always the possibility of name conflicts, which means there might be two things with the same name across different modules, and the compiler will be unable to work with that because it will be unsure what the name is referring to. So one solution to that is to use the 'as' keyword, which creates an alias or a nickname for that import in that given file. It doesn't change anything about the module structure or the name declarations, it's just how you refer to that item in that current scope, in that current file. We also discussed the glob operator, which is the asterisk symbol ( * ). That imports all public items, all public names from a given module. That's generally not recommended because it's a little bit implicit. You're not always sure what it is that you're bringing in. It could be 1 item, could be 10, could be 100. And then it might become more difficult to understand where a name is coming from. But still this pattern is used in certain situations, such as the Rust Prelude, which again brings in a lot of common top level names like your enums, Option, Result, etc. into your program when it initializes for the first time. All right. We also talked about the 'super' keyword. That is how we navigate upwards. So from a submodule, we can reference the parent module. We can navigate upwards. And that can sometimes be useful if for example you want to go into a sibling module. In other words, another submodule belonging to the same parent to get one of its names. So with 'super', you don't even need to know the parent's name. You can just navigate upwards in order to then go somewhere else. All right. So we also talked about the 'pu use' keywords being used in combination with one another. That re-exports an imported name from the current module. So usually the advantage of this is say you have a complex module hierarchy, maybe you have 5 nested submodules and they're all small and contained and descriptive, and they work really well to model some domain in the real world. But that can also create complexity for people trying to use your code, say, your library, because then they need to know all of these nested module structures. So what you can do is simplify that complexity by, for example, exporting all of the most commonly used items, say, the most popular structs and enums and functions from the top level, say the crate root. And now somebody can pull in those names without having to know how you've structured all of that complexity, because all of those names are simply available at the top level. They're not defined there. They're defined within those nested submodules, but they are available from the top because you're sort of making a shortcut to them by re-exporting them with 'pub use'. All right. So we talked about creating these library crates within our own project. And we utilize the 'use' keyword. And the same exact syntax is going to apply for external crates and Rust's standard library. An external crate is just a library crate, a dependency that you pull into your current project. It's code that somebody else has written so that you don't have to write. We declare those dependencies in the 'Cargo.toml' file, and when we run our program, it's going to fetch those dependencies from the web, compile them alongside your code, and store all of that in the final executable. The standard library, in comparison, is a collection of modules built into Rust. There's nothing more that we have to install or download to use it. We just have to utilize the 'use' keyword to declare the submodules and the named constructs that we want to bring into our code. So the same use syntax applies to our library crates, as well as external crates and the standard library. It's a single consistent syntax. So once again, a library crate in comparison to a binary crate is meant to store reusable code that other binary crates can use. So a library crate does not need a 'main' function. There's nothing automatic to run. There is no entry point. Rather, it just gives you the tools, the building tools, or the toolbox that other programs can use. Your project's binary crate in your 'src/main.rs' file can pull in the library crate's content, and you simply reference the library crate's name, which in our case was 'warehouse', and that was coming from the package name in 'Cargo.toml'. It's important that you mark your top level modules in 'lib.rs' as public with the 'pub' keyword. They are a name like any other, and thus since they are declared within that library crate, in its own kind of nameless top level module, you need to make sure that outside code such as your binary crate, has permission to access it because it's private by default. The modules, just like anything else, are names, and they are private by default, so you need to add the 'pub' specifier to make them public so that code outside of that crate or outside of that namespace can reach in and have permission to use it. Finally, we talked about this idea of having multiple binary crates. You can create a 'bin' folder in 'src', and every Rust file that you create in there will be its own binary crate, just like 'main.rs'. So in these binary crates, you need a 'main' function. You need the main entry point that is going to be run automatically when the program launches. And these binary crates can coexist alongside the primary binary crate in 'main.rs'. Maybe your program is meant to do 5 things. Maybe they have equal importance, but maybe the one in 'main.rs' is the primary one and the other four are kind of helpers. Well, now you can have multiple programs and you can specify which one you want to run from the command line. And all of them can utilize the shared exported functionality that you define in your library crate. Remember, if you have a library crate, you don't even need a single binary crate. You don't need a 'main.rs' file, you don't need a 'bin' folder. But at the same time, if you want to have all of these crates in your project, the compiler will support that as well. So from the command line you run 'cargo run', then you provide that setting '--bin' and then the name of the program. And that's going to come from the file name directly within the 'bin' directory. The one exception is the main program in 'main.rs'. And that name again will be determined from the setting in the 'Cargo.toml' file. All right. That's all there is to cover in this section.
