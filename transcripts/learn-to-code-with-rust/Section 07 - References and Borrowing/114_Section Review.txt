# Section Review

Congratulations on reaching the end of another course section. As always, let's take a few moments to review everything that we learned. This section focused on references and borrows. A reference stores the memory address of an existing value in your program. Borrowing is the act of creating a reference. We do so with the ampersand symbol ( & ). That is the borrow operator. The advantage of references is they enable the reuse of a piece of data without moving its ownership. Another advantage is that we avoid duplicating the original data, which can be pretty costly. So a real world analogy looks something like this. Imagine a famous national landmark like the Eiffel Tower. A lot of people want to experience or see the Eiffel Tower, but imagine how costly it would be to create a full copy of the Eiffel Tower for every person who wanted to see it. So we don't do that, right? Instead, what do we give people or tourists? We give them the address. The address on a piece of paper is a lot easier to replicate and create multiple copies of than creating a full copy of the Eiffel Tower. It's the exact same principle in code. Heap data can be pretty costly to copy because it requires generally more memory than your simple stack- based data types like integers and floats. So rather than creating a full copy of the heap data, the String is just one example, but there are many. Rather, we can create a reference to that data. We can just ask for its existing address so that we can visit that address and reuse that same piece of data over and over again, without creating a full copy. That tends to lead to faster programs because it reduces data duplication on the heap. So there's two types of references in Rust: immutable and mutable. References are immutable by default. Rust is always going to play it safe and make everything very protective. And it's going to require us, the developers, to be explicit any time we want to allow for mutation. So an immutable reference does not have permission to modify the original value at that memory address that it is storing. It can visit that memory address, it can read the data, it can use it, but it cannot replace it or override it or change it in any way. A value can have any number of immutable references because there is no risk to doing so. Every reference does not have permission to change the original value, so it doesn't matter how many there are. It doesn't matter if the Eiffel Tower has one address or 100 addresses that are shared among people because the original data point, the Eiffel Tower in this example, doesn't have permission to change. All we are creating is an address that's going to lead us there. Immutable references, for that reason, implement the Copy trait, so Rust will create a full copy in situations where one is needed. For example, assigning to a variable or passing a immutable reference in as a argument to a function parameter. It's easy to copy these references. They're just addresses, and thus they implement the Copy trait. There's no risk to doing so. We also have mutable references. They also have permission to access the original value at the address, but they also have permission to mutate it or change it. Now, in order to play it safe here, the compiler mandates that a value can only have one mutable reference at a time. So once your program declares a single mutable reference, we cannot have any kind of second reference, mutable or immutable. And that is because that first mutable reference has the potential to update the data, which means a hypothetical second reference could be referring to something that it does not expect, right? So you can have multiple mutable references as long as they are not co-existing or overlapping each other's timelines of existence, which are called lifetimes. So for that reason, mutable references do not implement the Copy trait. They follow the rules of ownership. If you have a variable that is a mutable reference and you assign it to another variable, that second variable will take over the ownership. Ownership will move so that we do not create a duplicate copy of a mutable reference, which creates that potential for error and bugs that I just described. So as I mentioned, the compiler understands what's called the reference's lifetime, which is the time or the region of code that it is being utilized in the program, and a lifetime can end before the function scope. So a few lessons ago, we saw those interesting examples where we were able to declare multiple mutable references within the body of the main function, as long as we did not use them together, and Rust could understand that the first use of the first mutable reference ended before we asked for the second one. In fact, it's not even fully correct to call it a second one because they never coexist. It's just creating one mutable reference, letting its lifetime end, and then creating a separate mutable reference after that. All right. We also talked about dangling references. That is, a reference or a pointer, more specifically, to a memory address that has been deallocated. It's like getting an address to a house that is no longer standing. In other programming languages, dangling references can create bugs and unpredictable behavior. Luckily, the Rust compiler prevents dangling references. It guarantees that if you have a reference in your program and if you were to follow the memory address that it stores, that memory address is going to hold the expected valid data. There's no way for a reference to outlive the data that it is providing an address to. Now we usually express this as the thought "the referent must outlive the reference". The referent is the original data. It is the source that you are saving the address of to the reference. So the original data must outlive all of its addresses. Once again, in real world terms, a house must live longer than any addresses to the house, because that validates that the address will always lead you to a standing, valid house. All right. Finally, we talked about ownership with composite types. Composite types like arrays, tuples and other ones that we're going to be introducing in future sections are capable of storing multiple elements. Right. And those composite types have ownership over those elements. So what's going to happen if we index, for example, into an array or a tuple? The answer is it depends on whether the type of that nested element implements the Copy trait or not. If that value implements the Copy trait, it's easy and safe to make a copy, and not expensive from a memory perspective. So Rust will create a full copy of it when we index into the type. If a value does not implement the Copy trait like a String, ownership will move from the composite type to the new owner. We saw that with a variable example a lesson or two ago where we had a array of Strings. A String is a heap allocated type, so if we were to move ownership from the array to a variable, that would create this weird situation where the array would remain the owner of its other elements, but lose ownership over the element that was moved to a new variable owner. So for that kind of reason, Rust prohibits that kind of weird behavior. So you can either create a full copy of that heap data that does not implement the Copy trait, or you can borrow a reference which avoids that data duplication and is the proper Rust way of doing things. All right. That's all there is to cover in this lesson and in this section. So I will see you in the next one.
