# Multiple Immutable References

The benefit of a reference is that it allows our program to access and reuse a piece of data without duplicating it. The problem occurs when there are multiple references with different expectations about what the data is. For example, the first reference may expect the value at the memory address to be one thing, but if a second reference changes the value at that address to be another thing, well then the program will have bugs and unpredictable behavior. That is a possibility in other programming languages. But once again, Rust works its hardest to prevent it. But let me give you an analogy from the real world to put this into perspective. Say that you are the owner of a blue car. Say that two of your friends want to borrow your blue car. You are going to remain the owner, but you're going to be borrowing out your car to two people so you can provide both of your friends with the equivalent of a reference, which is probably the address of the garage where your car is stored. Say that your first friend asks for the equivalent of an immutable reference or an immutable borrow. In other words, they will borrow your car and they promise not to change any aspect about it. So they expect that they will be borrowing a blue car and they will be giving back a blue car. Now imagine that your second friend asks for the equivalent of a mutable reference or a mutable borrow. They will also borrow your car. You will remain the owner, but in their time with it, they will have permission to mutate it, to change some aspect about it. For example, painting it a different color like red. So your first friend expects to borrow a blue car, but your second friend may borrow the car and change it to be red. And as you might expect, your first friend is probably not going to be happy because their original expectation is not going to be met. Basically, the same principle applies in programming languages. A reference has an expectation about what data is being stored at the memory address that it is representing, but there exists a potential that another reference will change what that value is after that first reference has been declared. For example, maybe the first reference expects a memory location where there is a String with five specific characters or 5 specific bytes, but a second reference may mutate the String at that memory location to remove the characters or replace the characters, or add one to the end, so the first reference thus becomes invalid because it won't point to what it expects to point to. It's like your first friend showing up to the garage to find an unexpected red car. So how does String solve these kinds of problems? We're going to talk about it step by step over the next couple lessons. In this lesson, I want to show you the first thing to know, and that is that String permits any number of immutable references to the same value at the same time. You can create as many immutable borrows as you want and use them alongside each other in the code. The reason that any number of immutable references is allowed is because there is no risk involved. There is no opportunity for the data to change because there is no mutable reference that can change the data. Therefore, it is safe to have multiple immutable borrowers at the same time. Another way to describe this is we can have any number of readers, but only one writer at a time. So going back to the friend and car analogy, if you have one friend or five friends or 100 friends who ask to borrow your blue car, and all of them promise not to change it or mutate it. All of them expect a blue car. All of them are going to give back a blue car. Well, then all of them are going to have their original expectations met. There are no surprises because the underlying data or the car in this case is not going to be changing. So similarly, in Rust, if we have an owned piece of data like a String, we can declare any number of immutable references to it at the same time in the code. So as a quick example, let me begin by declaring a variable called 'car', and I can set this equal to a String like let's say "Red". And here I'll declare a reference. I'm just going to use a simple variable name of 'ref1'. And on the right hand side, I'll take a reference to my car with the borrow operator ( & ). This is a immutable reference because I am omitting the 'mut' keyword, right? So I do not have permission to update this String on the heap, but I can read it by following the reference to the memory address on the heap where this is being stored. 'car' remains the owner throughout this entire example, and if I declare another variable like 'ref2' and create another immutable reference, another "ref String" by doing '&car', this is totally valid and I can furthermore use both of these at the same time. For example, right here in a println!, I can reference 'ref1' and 'ref2'. And just to make things even more interesting, let's take another immutable borrow in line. So I'll provide another pair of curly braces. And for my dynamic value, I'll just take another inline, immutable borrow. None of these borrows involve the 'mut' keyword, so none of them are mutable references. They're all immutable references. They can all reuse the same data on the heap, but none of them can change it, so there is no risk. So Rust knows that this line is going to be safe. All of the expectations that these references have about the original text being read are going to be upheld, because there's no chance for that data to change while these references exist to the data. At the point of declaration, RUST knows that this is a reference to this piece of memory containing "Red", and there's no chance for that to change. So 'ref1' and 'ref2' and this inline reference can all coexist at the same time without any compiler issues. All right, that's all there is to cover in this lesson.
