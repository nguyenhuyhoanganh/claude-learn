# Ownership with Arrays and Tuples

So far, we've covered ownership with scalar types, types that hold a single value. Rust also has collection types such as arrays and tuples that can contain multiple elements within themselves. In this lesson, we'll learn more about the nuances of ownership with these collection types. Ownership is not strictly limited to a name like a variable or a parameter. Ownership is answering the question: who is responsible for cleaning this data up? Collection types own their values, and that means ownership can extend many levels down, resembling a hierarchy. For example, a variable can be the owner of a collection type like an array, and then the collection type in turn owns its values. So for example, here I'll declare a variable called 'registrations' and I'll assign it to a array of Booleans. Let's do true, false, and true. So the same principles of ownership apply. 'registrations' is a name that is responsible for cleaning up this piece of data. An array. But the array is the owner of its internal elements, in this case booleans. All right. Now let's discuss an interesting scenario. Let's say I want to use my indexing syntax to access and extract the first element within my 'registrations' array. So here I'll declare my variable called 'first'. And as a reminder to extract an element by its index, we reference the array, then provide square brackets and then the index position of the element. The index starts counting from 0. So if I want this true right here that is index 0. Now this is completely valid code. But I want to talk about what is going on here. A Boolean implements the Copy trait. Therefore, whenever we extract the first element, what happens is Rust creates a full copy of the Boolean and assigns it to the 'first' variable. It's very similar to the examples we've seen previously, with one variable being assigned to another. Rust has to figure out what is going to happen to this data when something else wants to access it, right? 'registrations' is the owner of the array, which is the owner of these three elements, and it remains the owner of the three booleans even after we extract 'first' out, because 'first' is a full copy of this true value. And thus, for example, I can output the value of 'first' and output the value of my 'registrations' array. That will require me to use my Debug formatting, and you can see both of those names remain valid after my extraction, but let's take a look at what's going to happen if we instead have an array of heap owned data like Strings. So here I'll declare a 'languages' array, and here I'll declare two Strings. The first one will be "Rust" and the second one will be "JavaScript". I still have an array, but an array of owned values. The same principles apply. 'languages', the variable, is the owner of the array, and the array owns its nested internal elements, these two Strings. What's going to happen if I declare a 'first' variable again and assign it to index position 0 of my 'languages' array? Notice we get a totally different result. Let's talk about why. In this scenario, the String type on the heap does not implement the Copy trait. That would mean that ownership would move from the array owner to the 'first' variable becoming the owner. And that would create a really weird state where the array would have kind of partial ownership. It would still own this String because this string hasn't been moved. But then the former "Rust" String has been moved to a new owner of 'first'. It's kind of weird, right? Because the array is in this kind of partial state of ownership of some of its elements, but not the other ones. And thus Rust is going to prohibit this behavior. If we take a look at the compiler output, it says "cannot move out of here". Here is in reference to the 'languages' array. A move will occur because this array has type String. That is the type of its internal elements, and that type does not implement the Copy trait. And so here we can see two possible solutions, both of which are valid. The first one is creating a full clone or copy of the String. And that looks like this. We simply just call the 'clone' method. That does not move ownership of the String. Rather, it just creates a full copy. Remember, we have to manually explicitly tell Rust when we want to create a copy of heap data because Rust is trying to reduce total memory, so it doesn't want to make copies, and we have to explicitly tell it to do so. The problem with this approach is now we are duplicating this Rust text on the heap. Right. So this solution right here I would argue is the most idiomatic Rust approach. Idiomatic simply meaning "the one that's most likely to be found in code". We want to borrow a reference to this element contained and owned within the 'languages' array. So instead, what we can do is borrow a reference the exact same way: by providing our borrow operator ( & ). So now, 'languages' is the owner of the array. The array remains the owner of its two Strings. And we're going to borrow a reference. In other words, ask for the memory address of just the very first element within the array, thereby preventing the movement of ownership. The borrow operator by creating a memory address does not take ownership away. So now you'll notice the exact same rules will apply. With this syntax, I can now reference both 'first' and 'languages', and both of them are going to be valid names in our program. Once again, the array requires Debug syntax. And there you have it. So this is yet another example of where the Copy trait becomes really important because it affects what's going to happen in situations where Rust needs to figure out how data is going to be moved. Is it going to be moved by creating a full copy, or is it going to be moved by moving ownership away from the original owner? And it will depend on what your types are that you're dealing with. So this is an example with arrays. I want to show you very quickly the exact same rules apply to tuples. So as a reminder, tuples are declared with a pair of parentheses instead of square brackets and tuples allow the data to be of different types. So, in this case, we'll just allow it to remain of the same type. I'm just going to swap the square brackets here with parentheses. So now we have a three element tuple. And then whenever we access an element inside a tuple, we have to switch to using dot syntax. The index positions continue to apply. So 'registrations.' Then the first element is position 0. And that is totally fine. Here I'll similarly update the 'languages' array to be a 'languages' tuple holding two heap Strings. So the tuple is the owner of these two String elements. And thus if we try to do this with dot syntax, once again the code is invalid because we are attempting to move ownership of one element from this composite type that is the owner of all of its elements. So once again, the first solution is to simply 'clone' that heap string. That solves the problem. There is our code. And the second solution, and the one that prevents the additional use of memory to copy the "Rust" String, is to simply borrow a reference using the borrow operator ( & ). 'first' is thus a ref string ( &String ). It is a memory address pointing to this String on the heap. It is not duplicating the original text data, it's simply borrowing it by creating a memory address to it, and the code remains the exact same with the alternate tuple type. And in general, when you're going to be seeing various composite types throughout the course moving on -- so any kind of types that are holding multiple things within themselves, that composite type will continue to be the owner of anything that is nested inside it. And whether those nested elements implement the Copy trait or not is going to play a significant role in how we interact with that composite type.
