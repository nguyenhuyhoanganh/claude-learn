# Ownership with Immutable and Mutable References

In the previous section of the course, we learned that immutable references implement the Copy trait. That means in specific situations, such as a value being assigned to a variable or a value being passed into a function, Rust will automatically create a full copy of the value if its type implements the Copy trait. Because we can have any number of immutable references to the same value at the same time, it's safe to create a full copy of the reference each time. A reference is also cheap to copy, it's just a single memory address. Thus, an immutable reference implements the Copy trait. And I want to show that to you to kick this lesson off. So here in main I have a String assigned to a variable called 'coffee'. I'll declare an 'a' variable and this will be an immutable reference to my 'coffee' String. On the next line, I'm going to do what we've done many times before in the course, I'm going to assign my variable to a new one, so I'll declare a second variable called 'b' and make it equal to 'a'. So what's going to happen here? An immutable reference implements the Copy trait. So Rust will create a full copy of this immutable reference and assign it to 'b'. So 'a', the name, the variable, remains valid and it remains the owner of its own immutable reference. 'b' represents a copy, a separate entry on the stack, a separate immutable reference that it is the owner of, and thus we are welcome to use both 'b' and 'a' after the assignment. Here I am running the code. We can see "Mocha and Mocha" So you can think of this line. 'let b = a' as being functionally equivalent to. 'let b' be another immutable reference to 'coffee'. That's exactly what's going on behind the scenes. We are creating a second independent, immutable reference to the same piece of text on the heap. That is totally valid because we can have any number of immutable references coexist at the same time because there is no risk of mutation, and thus there is no risk that one reference is surprised by referencing data that has the capacity to change. So this code is totally valid. In comparison, mutable references do not implement the Copy trait, and this feature exists to follow the rule introduced in the previous lesson, which is that we can only have a single mutable reference to a value at a time, right? So, for example, if I return back to this code and I make this reference mutable, which also requires me to make my original 'coffee' owner mutable, what's going to happen here? Now on line #4, a mutable reference does not implement the Copy trait, which means principles of ownership start to apply. So 'coffee' is the owner of the original String, but variable 'a' is the owner of this mutable reference on line #3 and on line #4, ownership of that single mutable reference moves from its owner of 'a' to its new owner of 'b', and that move of of ownership invalidates variable 'a'. Owner 'a'. Therefore, we are not able to reference 'a' in this String. You can see here. If I try to output it, it's invalid. "Move occurs because 'a' has type &mut String which does not implement the Copy trait'. So the issue on line #5 is not even that we're trying to use 'a' and 'b' together, it's simply that we're trying to use 'a' by itself because that name is invalid. It no longer exists because that owner has been replaced by owner 'b' owning that mutable reference. Right? The reason that a mutable reference cannot implement the Copy trait is because if it did, then it would create a full copy and you would have two mutable references to the same piece of data coexist in the program, or have the capacity to coexist, and following the rules from the previous lesson, the compiler will prohibit that. Then, once again, same principles apply. If I want to use 'a' right here and I want to use 'b' right here, that is totally valid, because on line #4 'a' is still the owner of the immutable reference. Ownership does not move until line #5, so we are welcome to use 'a' before that point occurs. On line #5 is when ownership of the immutable reference moves, and thus we are no longer able to use it here. All right. So very important to keep these things in mind because now this Copy trait which we've introduced before with things like integers and Booleans, now it's going to vary depending on whether or not you have a immutable reference or a mutable reference. There's a lot of these nuances and specifics in Rust that makes it kind of more complex to reason about, but hopefully the basic gist of why these rules exist makes sense. Once again, the compiler will tell you if you're doing anything wrong.
