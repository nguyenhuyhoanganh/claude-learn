# Dangling References

In this lesson, we'll learn about dangling references. A dangling reference is a pointer to an address in memory that has been deallocated or cleared. This creates a bug in other programming languages. The word "dangle" means to hang loosely or unreliably, so a dangling reference literally means an unreliable reference. A reference to a memory address where the value is no longer present. The good news, once again, is that the Rust compiler will keep us safe, and it will do so by validating that any reference to data cannot be used after the data that it references has been deallocated. So let me show you an example of a dangling reference violation. I'm going to define a 'create_city' function. What this function will do is create a String. So here I can declare a 'city' variable assigned to a heap allocated string. I'll create it with my 'from' function. And I'll provide some text of "New York". And then what I will attempt to do is return not the String itself. So not 'city', but an immutable reference to the String ( &String ). So I'm going to try to return a reference. I'll create it in line with my ampersand symbol ( & ). Remember, we can think of a reference just like any other type. It's a value. It just happens to be a value that is a memory address pointing to another value, just like an address on a piece of paper. So this means that I have to specify my return value here. And my return value of this function is not a String, it is trying to be a reference to a String ( &String ). Notice that we're going to see a violation as soon as I save the file. Notice as well that we haven't even invoked the 'create_city' function in the body of the main function. This definition by itself is unsatisfactory to the Rust compiler. The reason is because the return value here represents a dangling reference, a reference to data that will no longer exist. Let's talk about why this is the case. On line #4, we have a String and 'city' becomes the owner of that String. 'city' is the name that is responsible for deallocating that heap memory. When does that happen? That happens when the 'city' variable goes out of scope, which is at the end of the block on line #6. So when the scope ends and the 'create_city' function ends, the 'city' owner will deallocate this String. It's going to go to the heap. And you can think of it just like clearing a whiteboard, right? Using an eraser, just wiping away the value at that memory location. The problem is we are returning that memory address. We are returning a reference to that spot in the heap memory that will no longer be holding the String after this function ends. So this is a dangling reference. It's an unreliable reference. It's an address to data that is no longer existing. In analogous terms, It's like giving your friend an address to a house that is no longer standing, to a building that is no longer there. Well, now the address is useless, right? It's pointing to somewhere where we expect one thing to exist, but it no longer will. So when I try to run this program, even without invoking the 'create_city' function, we're going to see the error message. So notice this helpful message here. "This function's return type contains a borrowed value". That is true. An immutable reference is a borrowed value, "but there is no value for it to be borrowed from". In this case, the value that we are borrowing from is this String right here. There will be no value anymore at the end of 'create_city', so that there cannot be a reference to it. There cannot be an address to something that will no longer exist, but we're trying to return that address to use it. So even if I try to save this here, like 'let reference' equals the return value of 'create_city', right? Here, it's going to think it's a reference to a String ( &String ), which is what we've annotated. But this String will no longer exist and therefore the reference to it, mutable or immutable, will be invalid. So notice now what the compiler recommends us to do is this. Instead, you are more likely to want to return the owned value directly. So rather than returning a reference to a String which will be deallocated as soon as the function ends. Rust recommends we return the String itself, and that will indeed solve the problem. So right here I can change my return type to be a String. Now there's a mismatch because Rust is expecting us to return a String. We're now returning a reference to a String ( &String ). We're going to update this to 'city'. And so now here the type is updated to be a String as well. It is no longer a reference. We can say it's a 'city' instead. And there we have it. If we want to simplify things even further, again, we can refactor this code to avoid the 'city' variable entirely so we can get rid of this code, get rid of 'city' and get rid of the semicolon to make sure it's an implicit return. And now, once again, this is totally valid code. I can println! right here and observe that the 'city' variable will be equal to "New York". So hopefully that makes sense. This avoids the issue of dangling references. The compiler is keeping us safe. A dangling reference is a reference or a pointer to an address in memory that has been deallocated. The value at that memory address no longer exists, so we cannot use it, and the compiler is going to try its hardest to ensure that this always holds true, that if we have a reference, it must die out, so to speak, before the value that it references. We cannot have a reference outlive the data that it is providing the address for. All right. Hopefully that makes sense. And with that I will see you in the next lesson.
