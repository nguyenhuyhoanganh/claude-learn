# Passing Structs into a Function

Next up, let's discuss the different ways that we can pass a struct into a function as an argument. A struct is a great function argument because it's a bundle of data. Instead of having to define multiple parameters, we can just define one parameter, one input for the struct, and the struct will arrive as a single type, but as a composite value that contains many different fields, many different pieces of data stored within it. So a function can receive a struct in 4 possible ways, and I want to review them all in this lesson. The first option we have is defining a parameter that receives the struct as an immutable value. That looks like this. I'm going to define a function called 'drink_coffee' It will accept a 'coffee' parameter. And I'm going to define the type of the parameter as being a 'Coffee' struct instance. Here I can println! and write something like "Drinking my delicious {}", and I can provide the value of 'coffee.name'. And then in main I can invoke my 'drink_coffee' function and pass in 'mocha'. So let's pause and talk about what's going on here. In this first example, the 'coffee' parameter takes an immutable 'Coffee' struct instance and it also takes ownership. In this example, ownership of the instance moves from the 'mocha' variable to the 'coffee' parameter. We are literally passing in the 'cofee' value. The instance itself to 'drink_coffee' The 'coffee' parameter is the new owner. When 'coffee' goes out of scope at the end of 'drink_coffee', it as the owner is responsible for clearing this struct instance. That means after 'drink_coffee' is done running, 'mocha' is no longer the owner of the 'Coffee'. In fact, that 'Coffee' no longer even exists in memory because it's been cleared right here. So afterwards, we are not going to be able to access any field on 'mocha'. It doesn't matter which one, because 'mocha' is no longer the owner and thus we cannot access any of its fields. Now in this example, by default parameters are immutable. So while we take ownership and while we are able to read the instance's fields, we are not able to mutate the struct. We are not able to change any of its fields. So for example, if I try to do 'coffee.is_hot' and I set that to false, that is invalid. We cannot mutate it because our parameter of 'coffee' is immutable. So our second option is to make it mutable, and we can do that by adding the 'mut' keyword in front of the parameter, like so. 'mut coffee' So this example is very similar. We are still moving ownership from the 'mocha' variable to the 'coffee' parameter, but the 'coffee' parameter is now a mutable 'Coffee' struct instance. It has permission to mutate the state, to change the fields. So we can read from our instance. And we can write a new value to any one of our struct instance's fields. Once again, after 'drink_coffee' is done running, 'mocha' is no longer the owner, so we can't do anything with the 'coffee' here. And furthermore, unless we return the 'coffee' back to the caller and save it to a variable, this 'coffee' parameter as the owner will go out of scope and clean up the instance memory. So 'coffee' will be gone at the end of the 'drink_coffee' function. So in both of these examples we are passing the instance by value either immutably or in this example mutably. All right. So our third option is passing in a reference instead of the actual 'coffee' instance itself. Remember a reference is just an address. It's an address that we can follow to get to the original value. So here I'm going to remove my 'mut' keyword. And I'm going to define 'coffee' not as a 'Coffee' instance but as a reference to a 'Coffee' ( &Coffee ). In other words, as an address in memory that I can follow to get to some 'Coffee' in memory. Once again, this type, which is called ref coffee ( &Coffee ) or a reference to a 'Coffee', is a different type than a 'Coffee', just like a String is a different type from a 'ref String' ( &String ), right? One is a piece of text. One is an address in memory. Same situation here. A 'Coffee' is an instance. A 'ref Coffee' is an address to a 'Coffee' instance. Now, by default, our parameters and our references are immutable. So that means that I will have permission to read a field, but I will not have permission to write it. The only reason we're not seeing that violation yet is because Rust is complaining about this one here. This is a type mismatch because we are passing in a 'Coffee' instance, whereas the 'drink_coffee' function expects a 'Coffee' reference. So I'll provide my ampersand symbol ( & ) here. Now 'mocha' is the owner. We're passing in a reference to the 'Coffee', an immutable reference. We can read from that struct, we cannot write to it. So I'm going to remove this line here. In this example with references, ownership is never moved. 'mocha' continues to be the owner throughout the entire program. We do not transfer or move ownership of the instance. We pass in a reference. So when the 'coffee' parameter goes out of scope, it does not clean up the 'Coffee'. It only cleans up the reference. The 'mocha' variable remains the owner, and thus I can access any of its properties or fields after the invocation of 'drink_coffee'. So here we can see. Here is our content from 'drink_coffee': "Drinking my delicious Mocha". And then I'm able to access the 'mocha' fields here because 'mocha' is still a legitimate valid name. It's still the owner of the struct. The second thing worth remembering is that you might be curious how are we able to do '.name' even though 'coffee' the parameter is not a 'Coffee', but rather a reference to a 'Coffee' ( &Coffee ), right? This is an address. The answer is whenever we have a reference and we use the dot syntax either to access a field or to invoke a method, Rust automatically dereferences. That means it takes the address. It follows the address to the original value, in this case the struct, and then treats it just like we were accessing this field on the struct itself. This is a good design because it means that no matter what our parameter is, whether our parameter is a 'Coffee' or a reference to a Coffee ( &Coffee ), this code stays the same. It's dynamic and flexible, right? You may recall there is a manual way to do this in Rust, which looks like this. Whenever we put a star in front of a reference that means dereference. Follow that address to the value. So this is what's going on behind the scenes. Rust is automatically dereferencing. It's automatically getting the original struct on which we want to access the 'name' field. But it does that automatically for us whenever we use a dot. So this syntax, while valid, is not necessary. Rust is trying to help us by making it identical to access a field on a struct, or to attempt to access a field on a reference, which is what 'Coffee' is in this example. Rust will take care of that. For us, it's a little bit of its convenience, right. So this is our third example. Our fourth possibility is a mutable reference. So now here I'll provide the 'mut' keyword after my ampersand ( & ). This is different from the example we saw earlier where we put 'mut' in front of the parameter. Right here. 'coffee' is a parameter that represents a mutable reference to a 'Coffee' instance. It's an address that we can follow, but also this parameter has permission to mutate or modify the 'Coffee'. 'mocha' will still be the owner throughout the entire process, but the 'coffee' parameter has permission to modify. So I can do something like 'coffee.is_hot = false`. 'coffee.price = 10.99' and all of this is valid. Okay. Now we're going to see a couple compilation errors. So let's fix them. Number one this is a type mismatch. We are passing in an immutable reference to a 'Coffee'. while the 'coffee' parameter should be a mutable reference to a 'Coffee'. That is a mismatch. We have to worry both about a mismatch between value versus reference and also a mismatch in mutability expectations. So this needs to be a mutable reference. So I can add a 'mut' right here, right? Secondly, if we're passing in a mutable reference, which means that the reference can be followed to the address and the value can be modified, that means that this must be made mutable as well. 'mocha' is the owner, and 'mocha' right now is immutable, so it's not expecting its 'coffee' instance that it is the owner of to change. But a mutable reference creates the possibility of change, and thus the owner has to be made aware. So we have to make the original 'mocha' variable mutable. And there you have it. So now the 'mocha' variable remains the owner. I can output the value of something like 'coffee.price' We can see that 'drink_coffee' -- rather, 'mocha.price' My apologies. We're going to see that 'drink_coffee' is going to accept a mutable reference. It's going to read data. It's going to write data. Ownership will never move. 'coffee' the parameter goes out of scope, cleans up the mutable reference. 'mocha' remains the owner throughout the entire process. We can thus access a field like price and see 10.99, which means we correctly modified that value, but indirectly through a mutable reference. We did not have to pass in a mutable 'Coffee' instance. We did not have to pass in the value. We got away with passing in a reference. Right? So the strategy or the approach that you want to take depends on what you want to do. Again, the advantage of references is that we avoid dealing with ownership, and we also avoid the problem of creating duplicates. Right? A struct by default will not make duplicates, but that means if we pass it into a function by value, we're going to have to deal with ownership. If we want to mutate it within a function and transfer ownership, we have to keep returning it back to the original caller to make sure the parameter going out of scope doesn't deallocate that struct. That's not an advantageous design, because we then have to keep returning the struct back. If we have five functions that are each going to take mutable ownership over the struct, all five of them have to keep returning the struct back. That's a pretty annoying design. So the more common practice you'll see is what we have here. If we want a function to be able to modify the struct instance, we pass in a mutable reference, and that allows the original owner to maintain ownership. If you just want a function to read something from the struct and use it for something, but you don't need to modify it, then stick with a immutable reference. And finally, if you do want your function to take ownership once again, there's the first two options. Pass it in by value immutably or pass it in by value mutably. All right. So hopefully those distinctions make sense. And with that I will see you in the next lesson.
