Save that. And now we have a nice sentence of "My mocha this morning cost 4.99. It is false that it was hot". Let's take a second to talk about ownership. A struct is the owner of its fields. A field in turn owns its value. So the 'mocha' variable is the owner of this 'Coffee' struct. This instance, to be more specific. The struct in turn owns the fields like 'name', 'price' and 'is_hot'. And then the field like 'name' is the owner of this corresponding String of "Mocha". So a field can be an owner just like a variable can. And just like a parameter can. A field, if you think about it, is another name in our program corresponding to a value, and as the owner, the field is responsible for cleaning up the associated memory, whether it be on the stack like a value like this or this, or whether it be on the heap like a String. So I know I mentioned this kind of concept of a hierarchy of ownership, and that's kind of how it works. When the 'mocha' variable goes out of scope at the end of the main function, 'mocha', the owner, is responsible for cleaning up the struct, and that creates almost like a cascade of cleanups, a waterfall of cleanups, right? It's like this hierarchy of nodes, starting with a parent node that then has its child nodes, that then has its own child nodes. The 'mocha' variable, the 'mocha' owner cleans up the struct. The struct in turn cleans up its fields, and the fields in turn clean up their associated values. Now you may recall the issues we saw earlier in the course when we accessed heap allocated data like strings that existed within a larger type, like an array or a tuple. When we try to access an array element that was a String and assign it to a variable, that created this weird situation where we had a partial movement of ownership because a variable became the new owner of one element from that collection, like the array, but the other elements were still stuck within the array, with the array as the owner. And so the Rust compiler wasn't happy. Well, the same principles are going to apply to structs and more specifically, fields that have types that do not implement the Copy trait. For example, say that I declare a 'favorite_coffee' variable and I assign it to 'mocha.name'. This is an assignment. Right. So what's going to happen here? This syntax is going to move ownership of this String from the 'name' field inside the struct, from the 'name' field to the new owner which is the 'favorite_coffee' variable. A String on the heap does not implement the Copy trait, so it is not copied. Rather, ownership of it is moved. The same rules do not apply to floats and Booleans because they are stored on the stack. So if we were to do something like 'favorite_price' and assign it to 'mocha.price', that would be a full copy. Not a problem. But here, a String does not implement the Copy trait. So this represents a movement of ownership, right? We are totally able to output the value of 'favorite_coffee'. It's the new owner of this string. And so here we can see "Mocha". But take a look at what happens if we try to output the value of 'mocha.name'. The 'name' field is no longer the owner of that String. 'favorite_coffee', the variable, is now the owner of that String and we're going to run into a compiler problem. The value is moved right here. Ownership was moved with our 'favorite_coffee' variable assignment. So what we're trying to do here is whenever we use a field in a println! we are borrowing it in order to print it, in order to print out the text representation of it, but we can't borrow the 'name' field from the owner because 'name' the field is no longer the owner. We can't borrow something from a non-existent owner anymore, and thus the compiler complains. This is one more example of the complexities of ownership in Rust. You have to be careful. The good news is it's going to be a source of frustration. But the compiler will always catch you when you're doing something wrong. Right. So the key takeaway at the end of the day, a struct is the owner of its fields. And each field, each name like 'name', 'price' and 'is_hot' is the owner of its respective corresponding value. Ownership, just like with any other owner, can transfer right? Ownership can move from a variable to a parameter when we invoke a function, we saw that earlier. Similarly, ownership of a heap allocated type like a String that does not implement the Copy trait, ownership for that can move from a struct field to something like a variable, or to something like a parameter as well.
