# Tuple Structs

Earlier in this section, I mentioned that Rust has three kinds of structs: named field, tuple-like and unit-like. We've been playing around with the most common one, which is a named field struct, which assigns each piece of data a name. Let's now explore the other options, starting with a tuple-like struct, also called a tuple struct. A tuple struct is similar to a tuple. It's a struct that stores multiple pieces of data that can be of different types, but each piece of data is not given a name. Rather, it is given a position in line. And just like with a tuple, the count or the index as it's called, starts counting from 0, so the first element is assigned position 0, the second element is assigned position 1, and so on. Let's declare a tuple struct right above main. It's going to be slightly similar syntax and slightly different syntax. So we again begin with the 'struct' keyword. Then our name. Let's choose a name of 'ShortDuration' And now instead of curly braces, I'm going to provide parentheses. And this is the exact same syntax that we usually use to declare a tuple. But now we have the struct keyword and the struct name. And then in here we declare the types of the elements in their respective order. So let's say that this 'ShortDuration' is going to model some passage of time, some length of time. It's going to represent hours and minutes. And I'm going to model both of those as unsigned integers. So right here I'm going to add u32, then a comma and a space and another u32. So this is going to be 2 pieces of data in order. But I can have as many as I want and they can be of different types. So if I wanted to have a Boolean in here and then a String, I totally could. It's just up to me to declare them. Let's stick with this example. And here I'll provide my semicolon and above, I'll leave myself a comment to remind us that this is representing hours and minutes. And just for a future example, I want to also declare another tuple on the line below. And this one is going to be called 'LongDuration' And let's assume that in modeling this longer passage of time, we're going to use slightly bigger units of years and months, but we're still going to represent them with the same two data types, two unsigned integers. So I'll do a u32 and a u32 here as well, and then leave another comment that this 'LongDuration' represents years and months. Now notice that they have the exact same two types of data in the exact same order, but I have given each struct its own unique name, which declares its own distinct, separate independent type. And that's going to play an important role in explaining the benefits of a tuple struct over a plain tuple in just a moment. For now, let's practice creating or instantiating an instance of these tuple structs. So in here I'll declare a variable called 'work_shift' and then I'll refer to my tuple struct above. Let's do 'ShortDuration'. And once again the syntax is going to differ. The syntax is always going to mirror what the declaration syntax was. So for a named field struct, we provide curly braces. And thus when we create an instance we provide curly braces as well. With a tuple struct we use parentheses, and thus we also use parentheses in the instance. So here I'll provide my parentheses. And now as you might have guessed, we'll provide concrete values to fill in for these two expected types, these two expected unsigned integers. Provide 'era', access position 0, access position 1, and everything is going great. Now what is the advantage of the tuple struct? Hopefully the syntax is easy to understand, but why not just use a regular tuple? Well, it's a totally different type from a regular tuple. First things first. So we cannot use a regular tuple in places where a tuple struct is expected and vice versa. But the primary advantage is that the name of the struct serves as an identifier for that type of data. That means it is less likely to avoid type conflicts. For example, let's say that you were trying to model the same idea of a short duration versus a long duration, but using a plain tuple. So you might do something like this. You might declare a 'work_shift' variable and use regular parentheses to represent a tuple, and do '(8, 0)', and then also represent an era. And that would be also something like '(5, 3)'. The problem is from the Rust compiler's perspective, this type and this type are exactly equal, right? It's a tuple consisting of two integers in a row. And these are signed integers. These are unsigned. But let's ignore that difference for now. From the compiler's perspective, these are the exact same, and thus there's a greater probability or chance that you might accidentally pass in the wrong type and not have the compiler catch it. For example, let's say you have a function called 'go_to_work' and you define that function to take some length of time. And rather than using a tuple struct, you use a regular tuple. So the type would look something like this. It's going to be a tuple consisting of an integer followed by an integer. And for my body I can do something like "Passing time, {} hours and {} minutes". And I'm going to pass in 'length.0' and 'length.1'. And so somewhere in main, I can invoke 'go_to_work' and let's pass in something like 'work_shift'. And this is going to operate just fine. "Passing time eight hours zero minutes". But notice there's no compiler error if I pass in 'era'. Even though 'era' is supposed to represent a time of several years and months, it's a different concept of duration in our business context, right? In our domain. But from the compiler's perspective, it's the exact same type. So now we're passing in something that really shouldn't be valid for this function. But the compiler sees no type mismatch and thus it allows it. And we get into a weird state where invalid data that we do not want to pass in may get passed in, say, through developer error, and the compiler is not going to catch it. Now let me show you how the tuple struct solution will solve this problem. So let me comment out this code and bring our old code back in. Well now if I define 'go_to_work's' 'length' parameter as being of type 'ShortDuration'... Well, 'ShortDuration' is a tuple struct and its own unique tuple struct, a unique name, a unique identifier. It's a different type from a 'LongDuration', even though the two have the exact same elements of the same type in order. The tuple struct gives us a name, and that name brings uniqueness, and thus, if I try to pass in 'work_shift' into 'go_to_work', that is totally valid because we are passing in a 'ShortDuration' tuple struct, where a 'ShortDuration' tuple struct is expected. But if I pass an 'era'... in our tuple example right here, the compiler was happy. Here, the compiler will prohibit the behavior. That is invalid because a 'LongDuration' tuple struct is not equal to a 'ShortDuration' tuple struct. It's a type mismatch, and thus we reduce the chance of that kind of error happening because we've created a unique identifier. Right. So these are different types. And furthermore they're also different from a regular tuple. So if for example I have some arbitrary function like 'accept_ tuple' and I'll provide a length, let's just say '(u32, u32)' here I can't provide either one of my duration tuple structs into here, neither 'work_shift' nor 'era' because they are completely different types. So both of these are different from a tuple and they're different from one another. The same cannot be said for two tuples that have the exact same data and the exact same order, because from the compiler's perspective, a tuple is just a composite type that stores elements in order, and as long as they are of the same type in the same order, they're considered equal. So the advantage of tuple structs is that we get a little bit more preciseness with our types, and the ability to distinguish and create difference between them to help aid in situations like this and reduce various compiler errors. But the key takeaway is that a tuple struct uses the exact same struct keyword syntax. We give it a name, but instead of curly braces, we provide positional elements in order, and the data is stored not by name, but by position, but by order, and then, otherwise, the syntax is very similar. For the instantiation, we use parentheses very similar to a tuple instantiation, but we provide the actual tuple struct name. And then it's the exact same dot access syntax to access any one of the tuple structs elements by its position.
