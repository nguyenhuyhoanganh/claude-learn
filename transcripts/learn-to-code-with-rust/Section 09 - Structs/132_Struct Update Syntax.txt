# Struct Update Syntax

So here's our next scenario. Let's say I wanted to create a new 'Coffee' based on some of the values from my 'mocha' 'Coffee'. Say I wanted a new 'Coffee' with a different name, but the same values for 'price' and 'is_hot'. How can I accomplish this? Well, the first option is we can manually assign values to fields in the new struct by accessing another instance's fields. So for example, I can declare a variable like 'caramel_macchiato'. And this will be my new 'Coffee' instance. And I'll provide my three fields. For example, 'name' will be something new and distinct, so I'll create a new String. Let's call this 'Coffee' "Caramel Macchiato". But for my other two fields like 'price', I can simply reference the variable above, 'mocha', and access its 'price' field. I can do the exact same thing for my 'is_hot' field. So 'is_hot: ' Where am I going to get the value from? I'm not going to define it inline. Rather I'll get it from 'mocha'. So this is totally valid and safe to do as well because floating point values and Booleans implement the Copy trait. So when we do this, we're going to create a full copy of the float for this 'Coffee' instance and a full copy of the Boolean for this 'caramel_macchiato' 'Coffee' instance. So this is a valid solution, but you can imagine it can get pretty verbose if we have a lot of fields. Imagine our 'Coffee' struct had 10 fields instead of 3. It's a lot of manual work to write out all of those fields are one by one, so we can accomplish this exact same result of copying one struct's values to another by spreading one instance's fields to another. So Rust calls the syntax we're about to see the struct update syntax. What we do is when we create a new struct, we provide two dots in a row, followed by the struct that we'd like to copy the fields from. So here I'm going to specify '..mocha'. So this double dot syntax must be written last in the list of fields. That is a requirement. Furthermore, we can remove these two values right here. And we want to leave 'name' for now. And I want to talk about what's going to happen here. So Rust is going to parse this code. And it's going to see that we are referencing the 'name' field before our double dot syntax. Because it sees a specific field definition for the 'name' field, It will not copy the 'name' field from 'mocha'. So any field that Rust sees before the double dots, it will not copy from this struct. For example, if I bring back 'price' and do 'price' like 10.99, that means Rust will not copy either the 'name' or the 'price' field from 'mocha'. So the only thing that will be copied is the 'is_hot' field. So these are the values that we want our own independent definitions for. And anything that remains is what's going to be copied over with the double dot syntax. This syntax works differently from language to language. Sometimes in other languages like JavaScript, this kind of syntax automatically replaces every field that came before it. Rust is different. It will be cognizant of what has been declared beforehand. All right. So if I remove this, we're going to define 'name' with a separate String. And we're going to copy 'price' and 'is_hot' over. Now I want to clarify that these two structs are independent instances. So if we make changes to 'mocha' after this struct update syntax, the 'caramel_macchiato' struct will not be affected. They have full copies of these values, the floats and the Booleans. So they can now exist as two totally independent structs. Now as always, we have to be careful because we may run into ownership issues. This struct update syntax is equivalent to assignment. We saw an example of manual assignment at the beginning of the lesson. This double dot syntax works just like an assignment. It's just like 'mocha.price' and 'mocha.is_hot' being applied to the respective fields in 'caramel_ macchiato'. So what's going to happen if I do code like this? If I just write out '..mocha', I do not have any preceding fields being declared here, so this is equivalent to doing 'mocha.price', 'mocha.is_hot' and 'mocha.name'. The problem with that is 'mocha.name' is a String and String types do not implement the Copy trait. So what this syntax is the equivalent of is: 'name: mocha.name' This is the equivalent of what this is now doing behind the scenes. This means that ownership will move from the 'name' field in the 'mocha' 'Coffee' struct to the 'name' field of the 'caramel_macchiato'. 'Coffee' struct. I can prove this to you. I can, for example, just go back to '..mocha' to copy those fields from 'mocha' to 'caramel_macchiato'. And of course, I can access my 'name' on 'caramel_macchiato'. That's not going to be a problem, but if I try to access the 'name' field on my 'mocha', take a look at what's going to happen. We're going to have a violation. The compiler is unhappy. Take a look at what it tells us. Value was moved here. This syntax, the struct update syntax with the two dots caused a move: "value was moved here". It's potentially a little bit harder to see, because we don't see that explicit field of 'name' being written out, but rest assured, this is still a move. So now the 'mocha' struct no longer has essentially a valid 'name' field. That 'name' field was invalidated because it moved ownership to another 'name' field. The 'name' field in the 'caramel_macchiato' struct. So then when we tried to access the 'mocha' struct's 'name' field to borrow it, to print it out, we're trying to borrow something from an owner that no longer exists. We can't borrow something from an owner that no longer has the original thing to give us. So even simple syntax like this can cause a little bit of a problem in Rust. So if we want to create a effectively a full copy of this struct and keep this 'mocha' struct functional, we need to make sure we create a copy of the 'name' field and any other field that does not implement the Copy trait. So the way we can do that is like this. We can write 'name', then reference 'mocha.name' By itself, this syntax accomplishes the exact same result. So we're no better off. But what we can do here is take this String and invoke the 'clone' method. We're not invoking 'clone' on the 'mocha' struct. We are invoking 'clone' on the String that the 'name' field in the 'mocha' struct gives us access to. This gives us a String. We clone this String, which means we create a duplicate of the data on the heap. Twice as much data for these two Strings. That's totally fine for now. And now we avoid the issues of the movement of ownership. 'caramel_macchiato' is going to have its own String, and 'mocha' is going to retain ownership over its String. 'caramel_macchiato' at this point doesn't really make sense as a variable name, because the name here is still 'mocha', but hopefully the example makes sense. So now the program will compile and you're going to see the name for both is "Mocha". All right. That's just one more example of how ownership can lead to some pretty complex and tricky situations in Rust.
