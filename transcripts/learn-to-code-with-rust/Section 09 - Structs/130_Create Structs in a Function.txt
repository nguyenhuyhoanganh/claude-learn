# Create Structs in a Function

In this lesson, I want to define a new function called 'make_ coffee', and this function will create and return a 'Coffee' instance. Later on in the section, we'll learn about associated functions, which is the more idiomatic way to create structs in Rust. But for now, this example will demonstrate that structs can serve as return values. They are a valid type just like any other. So the first thing we'll need to do is move this 'Coffee' struct definition outside of the main function. I'm going to move it to the very top of the file. If we kept it inside the main function, its scope would be limited to main and we would not be able to create 'Coffee' instances anywhere besides the body of main. Now that the struct definition is outside, it exists at the file level or also called the module level. This means we can now refer to this struct within any function in this file. It is more global in a sense, more available. So below main I'll define a new function with 'fn' called 'make_coffee'. And what this function will accept is three parameters that are going to represent my eventual field values for a newly created 'Coffee' instance. So I'll accept a 'name' parameter that will be a String. I'll accept a 'price' parameter that will be a 64-bit float, f64, and then an 'is_hot' parameter. That will be a Boolean. Remember that the way that we can specify the type of a return value is with this arrow syntax. So here I can specify that 'make_coffee' is expected to return a 'Coffee' instance. This can be any type in Rust. And now we have a valid new type in Rust, which is this custom type of ours: 'Coffee'. So here I can provide my curly braces. And furthermore, I can utilize Rust's implicit return syntax, where I can simply write an expression that then becomes the final return value of the function, as long as I do not provide a semicolon. So here I will instantiate or create a new 'Coffee' instance. I'll provide my curly braces. I need three fields, and all of those three fields correspond to these parameters. So what I'm going to write is 'name: name'. So to explain this, 'name' here is still the struct field. This is directly connected to these field declarations right here. This 'name' on the right hand side is our 'name' parameter. It is whatever dynamic argument that is flowing into 'make_coffee'. That is going to be the value that is going to be supplied to the 'name' field. Right. This will be something dynamic. Each time we can call 'make_coffee' ten different times and pass in ten different Strings for the coffee's name each time. Those Strings will be assigned to the 'name' field. So similarly for my 'price' field, I'll assign the 'price' parameter, and for my 'is_hot' field, I'll assign the 'is_hot' parameter. We don't need to do anything more. We are correctly implicitly returning a 'Coffee' instance. So now in the body of main I can invoke this function. 'make_coffee' It needs three parameters, so let's supply them. I can begin with an inline String. Let's do a String. Let's do something like "Latte". Let's do a price of 4.99 and 'is_hot' of true. And if I assign this to a variable like 'coffee'. Notice that rust-analyzer will correctly infer that it is a 'Coffee'. It looks at the definition of 'make_coffee', sees that we promise to return a 'Coffee' instance, and can then infer correctly that this variable will be of type 'Coffee'. I forgot to mention this earlier, but of course with structs we can annotate the type just like any other. So if I wanted to explicitly write out the type, it's going to be a colon after my variable name and then 'Coffee' like so. This is totally valid syntax if we want to be explicit, right? Usually, if Rust will infer correctly there's no need for this. But this is the syntax just in case you wanted to know. So down below I can use println! and just verify once again that my 'coffee' instance holds the respective fields which are these values right here. So I can do "My {} this morning. cost {}. It is {} that it was hot" and once again provide my 'coffee' fields. So 'coffee.name', 'coffee.price' and 'coffee.is_hot'. Provide my semicolon. Let's run main and we're going to see "My latte this morning cost 4.99. It is true that it was hot." So the 'coffee' instance is created here. And if it wasn't returned, it would be forever lost and the memory would be cleared. But because we are returning it, 'coffee', the variable here becomes the owner of this new struct instance and then is able to use it moving on in the function. I want to try something special here, which is let's extract this "Latte" String to a separate variable. So right here I'll declare a variable called 'name' and define my String here, and then pass in 'name' like so. And we're still going to get the exact same result. But I do want to talk about the transfer of ownership throughout this example, just to reinforce these ideas that we've been talking about. Ownership is actually going to move quite a few times in this example. So on line number #8, we create our String on the heap and the 'name' variable becomes the first owner of it. When we invoke 'make_coffee' we pass in that String. We do not pass in a reference. We pass in the String itself. That means ownership moves from the 'name' variable to the 'name' parameter. They happen to be named the same, but they don't have to be. If this was 'first_name', then ownership would move from the 'first_name' variable to the 'name' parameter. So this is the first transfer of ownership. Then ownership transfers once again, because we use the 'name' parameter and its value as the assignment for the 'name' field. When this happens, the 'name' field inside the 'Coffee' instance becomes the new owner. Ownership moves from the parameter to the 'name' field, and all these three fields are captured within the 'Coffee' instance. So when it is returned, the String here that 'name is the owner of, is kept. It is maintained. It is not lost, right? At this point, the 'name parameter is invalid. That parameter goes out of scope, but it's no longer the owner of the String, so we don't worry about it. 'Coffee', the instance, is returned back. The 'coffee' variable becomes the owner of the 'Coffee' instance. And then, as we talked about in the previous lessons, it's a hierarchy. The variable is the owner of the struct. The struct in turn is the owner of its fields, and the field like 'name' continues to be the owner of the String. That is a quick explanation of how ownership works in this situation. And with that, I will see you in the next lesson.
