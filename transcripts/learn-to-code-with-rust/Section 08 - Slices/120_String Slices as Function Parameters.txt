# String Slices as Function Parameters

Next up, let's explore the difference between string slices and string references as function parameters. So above main, I'll begin by defining a new function called 'do_hero_stuff', and I'm going to provide one parameter called 'hero_name'. And here we have an option. What is the type that we want to declare for our 'hero_name' parameter? So of course if I declare it to be a String, then this parameter will take ownership of the String. So instead, we can also define the parameter type as a string reference (&String). That's going to be this syntax: &String. And in here I can println! and say something like "{hero_name} saves the day". So we have defined 'hero_name' as having to be a String reference, and that is not going to include a string slice. It is limited in that it can only accept a 'ref String' (&String). So for example here I can invoke 'do_hero_stuff' And if I want to pass in 'action_hero'', that is a String. So if I want a reference to it from above, I can do '&action_hero'/ This is going to work. We're going to pass in a reference to a String. This will work. However, if I have a string slice which I can easily create with a string literal, for example, I'll declare a variable called 'another_action_hero'. And I'm going to set this to "Sylvester Stallone". This is automatically a string slice. As an alternative, we can use our square bracket syntax to extract a slice from 'action_hero' above. That would accomplish the same result. We have a string slice here, a 'ref str' (&str). A 'ref str' (&str)  is not the same type as a 'ref String' (&String) , right? This is a slice, which is a reference to a portion. This is a reference to a full String. So if I try to invoke 'do_hero_stuff' and pass in 'another_action_hero', which I think is a reference to a String, it's not actually the same type. We can see the mismatch right here. The function is expecting a reference to a full String: &String. We're passing in a string slice. This is a mismatch and the code will not compile. So let's try the alternative. Let's now update the type of the 'hero_name' parameter to be a string slice. So that's going to be '&str', and this is going to be significantly more versatile. As it turns out, the 'do_hero_stuff' function will now support both options, argument of a string slice like 'another_action_hero' and a string reference like &action_hero. All right, so here I can run this code and we're going to see it works. So you might be curious: why is this code compiling? Isn't it the exact same issue but in reverse with the opposite type? And the answer is Rust is actually flexible enough to support this. This feature is called deref coercion. And that is when Rust sees a reference and it keeps dereferencing it until it gets to the original value. Basically, to explain this kind of quickly at a high level, when Rust sees an input of a &String, a string reference, such as '&action_hero' It will automatically convert it into a string slice behind the scenes, and that will support the 'hero_name' parameter's expected type. But the same is not done in reverse, which is why our first example did not work. Rust will not convert a string slice to a 'ref String' ( &String ), but it will convert a 'ref string' ( &String ) to a 'ref str' ( &str ), to a string slice. Hopefully that should make sense. And the reason is because if we have a 'ref String' ( &String ) right, we know that we have a reference to a full piece of content, which means we can represent it as a. 'ref str' ( &str ). This is what Rust does behind the scenes. When we pass in our reference to 'action_hero', it cannot do the same thing in reverse, because there's no guarantee that a slice or a portion of a string is guaranteed to be the full reference to the String, right? This can be a chunk or a portion or fragment that sometimes can be equivalent to this, but not always. And thus Rust prefers to play it safe. It can't guarantee that this slice represents the same byte sequence as a reference to the full String, but it can guarantee the reverse, which is that a reference to a full string can be represented as an equivalent string slice that happens to be a reference to the complete portion of the string. So that's why this syntax is more versatile, because it supports both parameter types, both reference to a string ( &String ) and a string slice ( &str ) , which is 'ref str'. So it's generally more advantageous to define your string parameters as being string slices as their types ('ref str', &str) because they are versatile enough to accept either type of input.
