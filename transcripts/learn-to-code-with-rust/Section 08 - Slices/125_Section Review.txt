Congratulations on reaching the end of another course section. As always, let's take a few moments to review everything that we learned. This section focused on slices. A slice is a reference to a sequential portion of some collection type. Could be a string. Could be an array. Some type that can contain multiple values. Now usually a slice is going to target a chunk or fragment of the collection. And that slice is fundamentally a reference to that portion. Now the portion can technically be the complete collection as well. We use the borrow operator, the ampersand symbol ( & ), before the collection, and then a pair of square brackets with a range. The range consists of a lower bound and an upper bound. When we are creating a string slice from some text source, we are targeting positions by bytes. And when we are targeting a slice of an array, we are targeting elements by their index positions. So a range again consists of the lower bound and upper bound separated by two dots. There's also a secondary syntax that is '..=' that will make the upper bound inclusive. But this is the one that you're going to see more often because you can subtract the lower bound from the upper bound to easily get a count of the number of bytes, or the number of elements that that slice will represent. So with this syntax, the upper bound is exclusive. Rust will go up to that point, but not include its value. So we can provide two numbers, but there's also a couple shorthand options available. Some shortcuts. For example, we can omit the lower bound to start from the beginning of the collection, from position 0, and similarly we can omit the upper bound to progress to the end of the collection from some point. So a string slice is a reference to a portion of a string, to a portion of some piece of text living somewhere else. A string literal that we declare with double quotes is itself a string slice. Its type is not a 'str'. It's always a 'ref str', so it's portion, so to speak, its chunk happens to be the complete text that is hard coded into the binary executable. More specifically, a reference to your computer's memory that has read in your binary executable and has that content saved somewhere in memory. If we use our regular slice syntax with either an existing string slice or applied to a heap allocated String, we're just going to get another string slice, and that will exist as an independent reference. The length of a string slice is its count of bytes, not its count of characters. And it's important to make that distinction because as we saw certain characters that we human beings see as just a singular character, like an emoji, under the hood can occupy 2 bytes or 4 bytes of memory. So it's important to note that when we are slicing strings, or when we are targeting a subset or portion of that text as a reference, we are targeting by bytes, not by characters. Finally, we talked about deref coercion, which is a cool feature and one that you're going to see often when you're going to be defining functions that accept parameters. We can choose to define the types of those parameters, and certain design decisions will lead to more flexible and versatile code. So for example, if a function defines a parameters type as a string slice, which is a 'ref str' type ( &str ) '&str', then that function can accept either a string slice argument which is a 'ref str', but it can also expect or accept a string reference, a 'ref String' ( &String ), and that is because Rust will coerce that string reference, that 'ref string' ( &String ), to a 'ref str' ( &str ), to a slice. It is possible to do that, but deref coercion does not apply in reverse. Rust cannot coerce a string slice or a 'ref str' ( &str ) to a String reference ( &String ), because there is no guarantee that that string slice is coming from a heap allocated String in the first place. In comparison, if we have a reference to a String ( &String ), we can represent that as a string slice. It is an immutable reference to some piece of data somewhere, so it's easy to convert one type to another. But the inverse does not apply because we cannot guarantee that a string slice is always going to be coming from a String reference ( &String ). The same rules are going to apply to array slices. We saw that if we used the second type option here, and we declared the actual length of the array in our reference definition. Well then, we would bind our parameter to only be a reference to a specific array with a specific length. But if we instead define the parameters type as being an array slice, which is just ampersand ( & ), and then the square brackets containing the array elements' types, that was versatile enough to accept both array slices as well as a full array reference, because that array reference can be coerced or represented or thought as a array slice itself.
