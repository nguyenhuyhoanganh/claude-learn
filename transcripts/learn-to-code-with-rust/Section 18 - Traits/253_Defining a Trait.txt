# Defining a Trait

So here I am back in VSCode. Let's say that we are building a Rust program for a travel website like Expedia, Kayak, or Skyscanner. Users will use our program to search for different options for nightly stays, places where they can book lodging like hotels and Airbnbs. So what I'm going to do is define a new trait called Accommodation, and the Accommodation trait will represent the characteristic of being a place a person can book for a night. We don't know all of the types that will implement this trait eventually, but we don't have to at this point. We are just defining the trait, the contract, the list of requirements that any type must honor should it choose to implement this Accommodation trait. So outside of main, I'm going to begin with a new keyword, which is "trait". "t r a i t" in lowercase. This is not up to me. This is a keyword built into Rust. I follow that with a space and then the name of the trait, which is up to my choosing. So I'm going to call this "Accommodation" - a c c o m m o d a t i o n. Accommodation has two c's and two m's. Trait names should follow PascalCase naming conventions, which means we capitalize the first letter of every word and then no spaces, no underscores. Just separate with a capital letter at the beginning of every subsequent word and the first one as well. Then, I'm going to provide a space and a pair of curly braces, and it is inside the braces that we're going to define the trait's requirements. Let's decide that the Accommodation trait will require two methods: 'get_description' and 'book'. The intention of the 'get_description' method will be to return a string summary of the place, and the intention of the 'book' method will be to make the booking to reserve the place. So if we define these methods inside this trait block, then we are mandating that these methods must then exist on any type that chooses to implement the Accommodation trait. So we're going to start with our 'get_description' method. And the syntax is going to look very similar to declaring a method. We're going to start with the 'fn' keyword, then a space, then our method name which will be 'get_description'. Then I'll provide my pair of parentheses for my parameters and here I'm going to define an immutable reference to 'self'. So this will be an immutable reference to an instance of whatever type happens to be implementing the Accommodation trait, and whatever type the 'get_description' method is invoked on. So we do not know all of the possibilities of what that type that is implementing Accommodation will be. But as we'll come to see, that is the good part. That is the brilliance of this design. We don't need to know all of the types or any of the types in advance. We are just defining the desired behaviors that that type should be able to do. We are saying that if a type honors the Accommodation trait, it should have a 'get_description' method that should receive an immutable reference to the instance. As always, we can specify how the method should receive 'self', and we have all of the familiar options. So we can mark this as being an immutable reference. We can also do a mutable reference with '&mut self'. We can also take mutable ownership with 'mut self', and we can take immutable ownership with just 'self'. It's totally up to us. It's whatever we want to define as the terms of the contract. So here I'm going to choose to go with our original option of an immutable reference. Then, I'll provide my regular return value syntax. So I'll do my arrow and then decide that this method should return say a heap allocated String. And then I'm going to provide my semicolon. So we're not going to provide curly braces for the definition. So notice that we are not writing any method code yet. This is not a method implementation. This is just a contract. It's a list of requirements for any type that is implementing the Accommodation trait to honor. What we are saying is if a type chooses to implement the Accommodation trait, it must define a 'get_description' method that accepts an immutable reference to 'self', and that method must return a String. And if the implementation that the type attempts fails to do that, then the type will not correctly implement the Accommodation trait and the compiler will not compile the program. We are mandating consistency across all future types that choose to implement the Accommodation trait. So let's define another method. I'm going to call it 'book' on the very next line. Once again 'fn book'. And we can vary things up here. We can say that this method will accept a mutable reference to the instance. So I'll annotate the type here to be '&mut self', and say that this method will be responsible for the actual booking, for making a purchase for a night, So I know that this method will mutate some part of the type of the eventual type. And that's going to be storing the actual booking information. So we don't know all of the possible ways that a future type could implement the exact specifics of the 'book' method, but that's the point. We just know that it's going to be mutating the eventual type somehow, which is why I'm defining this parameter to be a mutable reference to self. This trait just says: "You must honor this promise. You must have a 'book' method that will receive a mutable reference to whatever instance you're working with so that you can update your internal state, but the actual details of the implementation, these specifics are left up to the specific type". We don't know all of the possible ways that different types will honor the 'book' method. We are just mandating the existence of a method called 'book' with this set of parameters and return values. So we're going to receive a mutable reference to the instance. Let's also define a 'name' parameter that's going to be a string slice. That's going to be the name of the person making the booking. And then a 'nights' parameter representing how many nights they're booking. And this can be an unsigned 32-bit integer. So a u32. I don't want the 'book' method to return anything of value, it's just going to mutate the type's internal states. So I can either explicitly specify a return value of a unit which is just an empty tuple, an empty pair of parentheses. The unit is Rust's default return value for a method anyway, so if I want to, I can also remove this unit type annotation and accomplish the same result by adding a semicolon right here. All right. And that's all there is to a trait definition. So in summary we've defined an Accommodation trait that requires or mandates two methods for any type that chooses to implement this trait. Any type that wants to honor Accommodation, that wants to present itself as something that is capable of serving as an accommodation, of having that distinguishing quality or characteristic of being an accommodation, any type that wants to honor this trait must promise that it's going to implement these two methods exactly as they are defined. The body of the method, the implementation, the actual logic can vary and should vary honestly from type to type. We are just defining this contract so a type cannot implement, for example just this method and ignore this one. Rather, we are mandating both of these two must be defined for any type that implements the Accommodation trait. We're going to see how to actually create that connection between type and trait in the upcoming lessons.
