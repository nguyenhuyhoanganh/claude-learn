# Intro to Traits

Welcome to the next section of the course. In these lessons, we'll dive deeper into the concept of traits. Now the word trait is defined as a distinguishing quality or characteristic. Distinguishing means serving to identify something. So a trait is a quality or detail that a thing has that allows us to identify it and categorize it in the real world. Different types of things can have the same trait, even if they represent different entities. For example, consider a trait like flight. Flight describes the quality or the characteristic of being able to fly. We can say that both a bird and a plane have the trait of flight, even though they are different types, right? Here's another example. Consider a trait like storage. Storage describes the quality of being able to be kept or stored. So we can say that a USB stick, a garage, and a bookshelf all have a trait of storage or a characteristic of storage. Consider a trait like illumination: the quality of being able to provide light. Well, a candle, a computer screen, and a sun are all different things, but they all have that common characteristic, that illumination trait in common. So traits are not a type of thing. Rather, they describe an ability, a functionality, a capacity to serve some defined purpose. It's a similar idea in Rust. In Rust, a trait can be thought of as a contract that describes functionality that a type with that trait should have. We use the word "implement" to describe when a type honors that traits requirements. So if we were modeling the previous slide in Rust, we could say that a candle, a computer screen, and the sun implement the 'Illumination' trait. Now, from a more technical perspective, we start out with the trait definition in Rust. That is us defining the contract, the hypothetical contract that one or more types can opt into honoring. So in that trait definition we define one or more methods. And those are methods that we mandate that any type implementing the trait must have. A type does not have to implement the trait, but if it chooses to do so, it must define whatever methods we declare in the trait definition. So the trait definition will include the method names as well as the methods' parameters and their corresponding types, and then the methods return value type as well. So the trait can be thought of as the more abstract definition of requirements. There does not have to be any types to define a trait, so a trait can exist by itself. It's just an abstract contract. But once we define the contract, one or more types can opt into implementing the trait, which means those types, should they choose to do so, must honor all of those trait definition's requirements. It must have those methods with those names, with the exact parameters, with the exact types and the exact return value types as well. And if there are any violations when a type tries to implement a trait, then the compiler will not compile the program. We've encountered traits many times throughout the course. We began with the Display and Debug traits. These two traits require that a type defines methods for formatting itself in a string representation. So these traits are contracts. They define the intended functionality. And then a concrete type like String chooses to implement a trait like Display, which means it promises that it will define the required method or methods that will then allow Rust to convert it to a string representation. Similarly, if a type implements the Debug trait, rust promises that it can interpolate that type within a string using the colon question mark ( :? ). Debug syntax. As another example, we have a Clone trait, and that Clone trait requires a type to define a 'clone' method that will return a duplicate of itself of the original value. So if a type implements the Clone trait, it promises that it is capable of being cloned or being copied. So the advantage of traits is that they enforce consistency across different types. Imagine that there was a different Debug symbol for every type, or a different method for cloning, depending on the type you were working with. Imagine a situation where the method was 'clone' on one type versus 'create_clone' on another versus 'duplicate' on another one. That inconsistency would be exhausting. So traits by having these contracts, which are just enforcements of method names and parameter types and the like, they enable us to standardize and formalize shared behavior across different types. The types will be different, but they will all implement the traits that they choose to and will have the same method names and same expected behaviors for those traits, for those behaviors like being able to be cloned. So we first begin with a trait definition. And once we have defined the trait, we then choose to implement it on our own types like our own structs and enums. And then those types promise to honor the trait's contract. So for example, a type implementing a Flight trait promises that it can fly. Or another way of thinking about it is it promises that it supports a method called 'fly'. Whatever happens to be the method name that is mandated by the trait definition, that's what the type implementing the trait promises to be able to to do. Multiple types can implement the same trait. That is the intent: to have shared consistency. So a bird and a plane type can both implement a trait called 'Flight', and thus both promise that they can fly, or perhaps both promise that they have a method called 'fly' available on those two types, even though they are different things, right? And finally, a type can implement multiple traits. It can support multiple behaviors. It can be capable of doing multiple things, having multiple defining characteristics. For example, a Plane can implement both the 'Flight' and 'Storage' traits, which indicates that it can both fly and store items. All right. So that has been a very high level definition. As always. It'll make more sense when we get deeper into the code. But in this section we're going to be discovering more about traits in much greater depth, both understanding more about Rust's built in traits as well as defining our own custom ones.
