# Implementing the Display Trait on a Struct

A custom struct that we define will not implement either the Display trait or the Debug trait by default. As a reminder, these two traits serve a similar purpose. They indicate that we can convert a type into a string. Now, the Debug trait string is meant to be a technical string representation for the benefit of developers, and we can derive a kind of fallback or default implementation by using the 'derive' attribute. That's what we've seen throughout the course, and it looks like this. The Rust development team chose a reasonable default or standard for how to convert certain types into a string. For example, if we apply this to a struct, this Debug implementation will print out a string that will include the struct's fields and the corresponding values, once again for the benefit of developers reading the code. Now, the Display trait is similarly meant to convert a type to a string, but it's meant to be a human readable string. A user-facing string. Your program's audience may not necessarily be Rust developers or technical people, so it's up to you, the developer, to decide how you want to represent your custom types as user-facing strings. We get to decide what the Display trait implementation should look like. What output do we think is going to provide value for the user if we convert our custom type to a string? So in this lesson, we're going to define a custom struct. And then we're going to implement the Display trait on it, and that will allow us to utilize that type just like many other built in types. So first things first, let's define a new struct. Up top, I'm going to call it Apple. And Apple is going to have two fields. The first will be 'kind' which will describe the kind or type of apple we have. This will be a String and then a 'price' which will be a 64-bit float. So in the body of main, I can create an instance of the Apple struct. I'll assign it to a variable of 'lunch_snack' And this Apple can have a 'kind', let's say, of Granny Smith. And it will have a price of 1.04. So we have a valid struct instance. Right now, it does not implement either Display or Debug. We could choose to derive Debug up top, but let's skip that for now. And what I'd like to try to do is to simply output my Apple struct. So here I'm going to provide my usual set of curly braces and then provide 'lunch_snack'. This code is not going to compile. We're going to see... the error message says "The Apple type does not implement the Display trait". The Display trait is found within the 'fmt' or formatting submodule. Our type does not implement that and thus Rust is unhappy. So here's what actually goes on behind the scenes. The Display trait requires a method to be defined called 'fmt', which is short for format, and that method defines how to format that type as a string. Now, whenever we use this syntax of the curly braces and provide a type, what actually happens behind the scenes is that Rust takes the type and calls the 'fmt' method on it to get that string, which it then outputs. And the way that Rust knows that a type will have that 'fmt' or format method is if it implements the Display trait. It's the exact same principles we've talked about throughout the section. Because our Apple struct does not implement the Display trait, Rust cannot guarantee the existence of an 'fmt' or format method, and thus it does not have a method to call when we use these curly braces. So every time we've used this syntax throughout the course, we've actually been secretly invoking methods behind the scenes that have been required by the Display trait. So in order to allow the syntax to work, we just need to implement the Display trait, and that will allow us to use our Apple struct like any other type. Now we could define some custom method on our struct directly that will output our type as a string, but that will break the convention. The convention is to make our type as similar to Rust's built in types as possible. So in order to use, for example, this interpolation syntax, it's better to just opt in to Rust's standards and implement the Display trait rather than coming up with our own custom solution. So at this point, let's take a look at the definition of the Display trait from the Rust standard library. The Display trait requires that single method called 'fmt' or format, and it will first accept an immutable borrow of the instance of the type. That should all be familiar. And then the method will also accept a mutable borrow of this Formatter type, which is actually a struct defined within the 'fmt' submodule. This Formatter struct includes helper methods to assist with formatting the final string. Now Rust will create the Formatter struct instance and pass its mutable reference to the 'fmt' method automatically, so we don't have to worry where we're going to get this instance from. Just know that the 'fmt' method will receive it automatically when we use, for example, 'lunch_snack' right here and we use the curly braces. Rust will call the 'fmt' method required by the Display trait, and it will pass in the type and the instantiated Formatter struct. We don't have to worry about it. In addition, this 'fmt' method must return a Result enum with the Ok variant storing a unit which is an empty tuple, and the Err variant storing an error type. All right. So remember, Result has two variants: Ok and Err. Each one has a piece of associated data. And these concrete types for the generics define the type of that associated data. So specifically the Ok variant must have a unit, an empty tuple, and the Err variant, the 'E-r-r' variant must have this type of error. Now you might be curious why is the Ok variant's associated data an empty tuple? That is basically no data, right? And the reason we don't return the actual formatted string itself in the Ok variant is because we're going to actually write it directly to the Formatter struct. It's not actually going to be part of the return value. Rather, it's going to be written in the actual body of the 'fmt' method, which you'll see in just a moment. Now, as you might recall from earlier, there are multiple Result types in Rust, but often they are redeclaration of the base Result enum type with specific concrete types substituted for the generics. We saw this with the Result type within the input/output submodule, and similarly the Result type here is actually the Result type inside the formatting module, and that is an alias or kind of an alternate type based off the original Result type in Rust, and the difference is that it hard codes the concrete types for the generics T and E from the original Result to be specifically the concrete type of an empty tuple for T and the 'fmt::Error' type for E, and that just allows the definition of the 'fmt' method to simply write Result like so.
