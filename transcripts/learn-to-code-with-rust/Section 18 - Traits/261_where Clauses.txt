# where Clauses

In this lesson, I want to introduce you to where clauses, which are yet another syntax option that we have available for generic types that we want to bind to implement one or more traits. To get there, let's update our 'mix_and_match' function to use the trait bound syntax. So instead of the manual declarations for the implementations of given traits per parameter, I'm going to define two generics instead. So here after 'mix_and_match', I'll provide my angle brackets and declare two generics: T and U. Once again the names are up to us. And again, the reason I'm declaring two generics is so that we have the possibility of passing in two different types for the 'first' and 'second' parameter if we wanted to. If we stuck with a single type T, and we declared that T to be the type of 'first' and 'second', that would be totally fine, but then we would be mandating that 'first' and 'second' must be of the same type. So we would not be able to do code like this, where we pass in a reference to a Hotel type and to an Airbnb type. There's no right or wrong answer. It depends on what you want your function to do. So if I want two values of two different types to be passed in, I can't represent that by a single generic type T. So I need at least two generics, T and U. And then of course, as you may recall from the previous lessons, to enforce that those types implement traits, I can declare them here in line. So I can say type T will be a type that implements both Accommodation and Description, while U will be a type that only accommodates Accommodation. Pardon the pun. And then I can replace this with a mutable reference to type T and the second parameter to be a mutable reference to type U. So this should hopefully be more of the same. And basically these are two possible options for how we can declare this kind of logic. One is defining the trait implementations per parameter. The second is defining generics and then enforcing trait bounds on those generics, which means mandating that the compiler check that the given generic types live up to one or more traits, right? Now here's the third option, and it is called where clauses. And the reason for this is because we are using a new keyword called 'where'. What we're going to do is after the closing of the parentheses with the parameter list, but before the opening curly brace, we're going to write the word 'where', and you're going to see how this is going to be a replacement very soon for the code in here. So I'm going to do a line break which is just for convention. And then I'm going to write out both of my generic types T and U. And it is here where I'm going to provide the list of traits that they must implement. Basically what this 'where' syntax does is it simplifies things so that you can declare your generic types here without any specific trait declarations. And those trait declarations move to being right here in the 'where' clause. It's just a different way to accomplish the same code. So what I'm going to do here is write where T is a generic type that implements Accommodation and the Description trait, then a comma. Then my second type is U, and that is a type that is going to only implement Accommodation. And obviously we wouldn't have it in both of these locations. It's one or the other. So if we go with the 'where' approach, we can simply declare our generics inline without any trait annotations or bounds here. And this is the alternate syntax. All right. So it accomplishes the exact same thing. It defines two generic types called T and U. T, the generic type, must be some type that implements Accommodation and Description. So when we pass in a concrete type for T, like for example a Hotel struct, here the compiler will validate that any given type that is filling in for generic T must implement both of these two traits, and any concrete type filling in for generic U must implement the Accommodation trait and that will be of course the type of the 'second' parameter. But what this accomplishes is the exact same thing. It's basically another way to simplify the code by declaring our generics without a lot of additional code. So it's much easier to parse this first line and understand that we have two generics, and then afterwards is where we add the trait constraints or the requirements. A lot of times if you have many generics and they all implement multiple traits, and you start adding the plus sign here with a lot of different generics, it just becomes harder to parse what all your generics are. So this syntax allows you to separate the two: the declaration of the generic types and the enforcement of the traits that they must implement. But the code is basically accomplishing one and the same. The compiler sees them as as identical.
