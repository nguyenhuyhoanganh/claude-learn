# Implementing the Eq Trait

So let's come back to our Flight struct from a lesson ago. It is currently deriving the PartialEq trait and as you can see, all of these examples are evaluating to true. I have two Flights with the exact same origin, destination and time, and the default implementation of the PartialEq trait checks for the equality of all of the struct's fields. Now there is an additional trait to introduce in this lesson, and it is the Eq trait or the equality trait. So there is PartialEq or partial equality. And then there is Eq for equality. A little bit confusing. So the equality trait, 'Eq', is a subtrait of the 'PartialEq' super trait. Remember what that means is if a type chooses to implement the Eq subtrait, it must implement the PartialEq supertrait or parent trait as well. That relationship does not apply in reverse, so a type can choose to implement PartialEq but not be obligated to implement Eq. Now, the more fascinating thing is that the Eq trait does not actually require any methods, so you can think of it more like a compiler flag. You simply opt into it, and as long as you define PartialEq, which is a requirement anyway, everything works. All right, so what the equality or Eq trait declares is that three additional principles are going to apply. The first of those principles is the reflexivity principle which means a equals a. What that means is that it is okay to compare an instance against itself, and it should be found equal in that scenario when it is compared with itself. And you can also reverse the order of the values around the equal sign and get the exact same result. So what we're doing here on line #22 is one of the first principles that the Eq trait promises to uphold. If you choose to implement that subtrait, you are saying that a type is equal to itself. And I know that that is a little bit confusing because you might think to yourself, isn't that always going to be the case? Isn't some value always equal to the exact same value? We're going to come back to that in just a moment, and that will help explain why we have two of these equality traits in Rust. But the first principle of anything that implements the Eq trait is that it must follow this principle of reflexivity. The second is symmetric equality. What that means is if a value 'a' is equal to a value 'b', that also means that value 'b' must be equal to 'a'. So if 'a' is equal to 'b', like we have in line #23, then 'b' must be equal to 'b'a, and we are promising that if a type chooses to implement the Eq subtrait. All right. The final principle that is required by any type implementing the Eq trait is the transitive rule of equality. That basically means if value 'a' is equal to value 'b' and value 'b' is equal to value 'c', then value 'a' must be equal to value 'c' as well. So as another example here I'll create another Flight. Let's assign this to variable 'c' right here. And let me show you that variable 'b' is equal to variable 'c'. We're going to get a bunch of trues. So if 'a' is equal to 'b' like on line #24 and 'b' is equal to 'c' like on line #26, then 'a' must be equal to 'c'. Right. And that principle is upheld here. So because our Flight struct honors all of these requirement,s we can opt in to the Eq subtrait as well by writing it here within our 'derive' attribute. Nothing will change in our code, but now we are telling the compiler you can be confident and sure that our Flight struct is upholding those three additional principles that we talked about. Now, these two traits might seem not just confusing, but like overkill, right? It's two things that seemingly are accomplishing the exact same result. So most of the time you're going to derive both the Eq and PartialEq traits simultaneously, because the additional requirements of Eq will apply most of the time to your own custom types. The reason the Rust team declared two separate traits in this parent trait/subtrait hierarchy is because there are rare exceptions where a type may implement only the PartialEq supertrait. For example, the float type, both float 32 and float 64. These types will implement the PartialEq supertrait, but they do not implement the Eq subtrait, and that is because the floats can't promise that they fulfill the reflexivity principle of the equality or Eq subtrait. Now, that might also be confusing, because the reflexivity principle would seem like it would always apply to a float. For example, isn't a value of 5.14 always equal to a value of 5.14 right in either direction? How could it possibly be anything otherwise? How could a value not be equal to itself? Well, it turns out that floats also support a special value called 'NaN', which is short for not a number. Let me show you that in action. I'm going to delete all of my former code here just to buy some space. I'll declare a variable called 'division', and I will divide 0.0 by 0.0. Take a look at what the inferred type is of the division. Rust is looking at this division, and it assumes, since we're dividing a float by float, that we're going to get a float as well. But this is an invalid mathematical evaluation. It's not a number, right. It's a kind of a chaos, if you will. There's no defined behavior for what this is. It's mathematically undefined. So if you output the value of 'division' right here, take a look at what we're going to get. We're going to get 'NaN'. That is a special designation which is short for "not a number". But notice that the type is still technically a float 64. So Rust still classifies a NaN, a not a number, as a float technically, under the hood. It's like a value underneath the possible parent type of a float64, or rather a possible value underneath that parent type. Now, technically speaking, an NaN is not equal to an NaN. It's not equal to itself because an NaN represents an invalid or irregular value. It's like comparing the equality of chaos with chaos, or comparing the equality of something invalid with something else that is invalid. We can't necessarily say that that's always true, right? Because it doesn't really represent something concrete, even that we can measure the equality of. So let's declare a 'value' variable below and I'll assign it to 3.4. But if I compare 'division' with 'division'...they're both the same value. And they are both of the type 64-bit float. This is going to give us a false because an NaN is not equal to an NaN. In fact, an NaN cannot be considered equal to itself. 'division' is not considered equal to 'division' because once again, it's like comparing the equality of two undefined things. Two chaotic things, two nonsensical things, two impossible things, right? I know it starts to sound a little bit like science fiction, but hopefully it makes sense in the sense that this is a hypothetical, right? It doesn't really exist. It's not a possible operation. So if you take that evaluation of the impossible and you compare it with the impossible, what do you get? Is that a true, right? Doesn't really make sense. So Rust goes to false. So for that reason the float 64 type and the other float type of a 32-bit, they implement the PartialEq trait because they do promise a certain amount of partial equality. For example, in comparisons of actual, concrete floating point numbers like 3.4, but they do not promise to uphold the three principles of the Eq subtrait, because they cannot make that promise for the possible value of NaN, right? Now, you don't have to remember all these details about the NaN type. It just goes to show why the Rust team chose to develop these two traits. And that is again because there are these rare situations where a type may only want to implement PartialEq because it can't promise to fulfill all of the more stricter requirements of the Eq subtrait. For most of your custom types, like the custom structs and enums you'll declare, most of them will be able to opt in to both trait implementations, but there are some types that do not really fit that perfectly, and that is why the Rust team had to break it up into this two trait, parent trait/subtrait hierarchy.
