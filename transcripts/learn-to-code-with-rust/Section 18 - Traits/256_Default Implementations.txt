# Default Implementations

Previously, our Accommodation trait had no code. So this definition right here just defines a contract that mandates the presence of these two methods. However, we can actually define a default implementation for any trait method. So in other words, we can actually write a method body for any method that we mandate in a trait definition. The way this is going to work is that Rust will utilize the method definition from the trait declaration, but only if we do not declare that method when implementing the trait for a given type. So you can think of the methods that we declare here as fallbacks. They are default methods to run in case a type chooses not to individually implement that method. So for example, let's say that we want 'book' to always be declared for every single type that implements the Accommodation trait, but 'get_description', we can afford to be a little bit more generic and standard. So I'm going to provide a default method implementation here. So rather than the semicolon, I'm actually going to define a method body. And this is going to be what 'get_description' does or returns if a given type implements the Accommodation trait but does not define a 'get_description' method. So here I can return a String using the 'String::from' function. And let's just do something very general and standard like "A wonderful place to stay". So notice that if I change nothing else and I run the code from the previous lesson, we are calling 'get_description' on both a Hotel and Airbnb. Nothing will change here. We have the 'get_description' from the Hotel. Here we have the 'get_description' from an Airbnb. And the reason nothing changed is because each one of the implementations of Accommodation define their own 'get_description' method, and that is what Rust will rely on. However, if we choose to remove that definition from the implementation block, for example, for Hotel, I'm going to remove 'get_description' right here. The code now will compile. It wouldn't in the previous lesson, but it can compile now because if we call 'get_description' on a Hotel struct, because we no longer have a 'get_description' method, Rust will fall back or rely on the definition of that method in the trait declaration. So we don't have to follow this pattern if we do not want to define a default implementation and just allow each type to have to declare it. That's totally fine as well. It depends on whether you have a kind of general thing that the method can do in the case that a specific type does not want to implement it. So now notice our code will compile. This implementation block for Hotel is only defining a 'book' method because in a sense we have made the 'get_description' method optional. There's always a default fallback to fall back upon. So now when I run this code, we are calling 'get_description' on line #59. We're now going to get the implementation from the trait definition. "A wonderful place to stay" is not coming from anything defined in the Hotel. It is coming from this definition right here. And as we can see with 'get_description' and 'book', we can mix and match. So some of your trait methods can have a default definition, while others can mandate an explicit declaration for the future type that will implement that trait.
