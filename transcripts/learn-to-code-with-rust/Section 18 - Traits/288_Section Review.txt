A trait is a technical contract that requires that a type support a certain functionality. The advantage of traits is that they enable similar behavior between different types. Two types can represent two distinct entities, but can be capable of uniform, similar behavior through, for example, the same method names. It would be a lot more complicated if we had the same functionality, but have different method names on one type versus another versus a third type, so traits help to add that consistency when there is a similar operation being performed on many different types. A type opts into implementing a trait. So the word implement describes the situation where a type says "Yes, I'm going to support these methods and thus support these behaviors". A type can implement multiple traits, and a trait can be implemented by multiple types. So if we are defining our own custom trait, we have a trait definition. And that begins with the 'trait' keyword, the trait name and then a block. And within there, we define the required methods and their signatures. That means we define the parameters and their types, as well as the return values of those functions and their types. The trait definition can also define a default implementation for any of its methods. It doesn't have to, but it can, and Rust will use that fallback method if a type does not define that method when it implements that trait. Another important note: a trait must be in scope in order to invoke any of its methods on a type. That is true for Rust's built-in traits, as well as any custom ones that we define. So once we have our definition, the next step is implementing that trait for one or more types. So we use the 'impl' keyword, then the trait name, then the 'for' keyword, and then the type that's going to opt in to supporting that behavior. So for each trait, we need one implementation block. So if you have, for example, ten traits, you will need to define ten separate 'impl' blocks. So we do 'impl Trait for' the type, curly braces. In there, we provide the concrete implementations for any required methods. Those are the ones without a default implementation. And the compiler is going to hold us responsible. It's going to raise an error if there are not enough methods, too many of them, or if there are any type mismatches in parameters or return values. For any independent methods, such as your own custom methods or associated functions that you want in your custom type, those will live in a separate 'impl' block because they're not directly connected to a specific trait implementation. They are just functionalities available on that type. We can also define an associated constant within a trait definition. So we once again use the 'const' keyword, a name. And we do need a concrete type written inline. And then the initial assignment of the value with an equal sign. Constants cannot change. They are immutable, and then trait methods can utilize that constant value. It's supposed to represent some kind of fixed, hard coded data that can be reused across perhaps many different methods and trait implementations for a type can overwrite the constant for for their own benefit. If there is some slight variation in the data that it would like to use for a given method and its implementation. You're looking for the right balance of reuse versus customization. If every single implementation of a trait requires a value to be different, then probably each one should use its own data. If there is a consistent piece of data that is valued or reusable by every implementing type, then it makes sense to extract it to a constant defined in the trait definition. We also talked about trait bounds or trait constraints. So that means that we can require that generics live up to a trait, that they implement that trait or support a given functionality. So for example, a function can accept a generic which by itself is just any type for let's say a parameter. But we can get more specific and demand that that generic parameter implement a given trait. So the first option to accomplish that is to use the 'impl' keyword followed by the trait, and that is done in the parameter definition. The second option is to define a generic in your angle brackets, and then add trait bounds within the angle brackets. So you do the colon, and then you write the trait or multiple traits that that type must implement. It's still a generic, so the concrete type can vary at the invocation point, but we are requiring those traits be lived up to. That the type, whatever it is, implement those traits. So we are limiting the set of possible types that will be accepted and then within the body of the actual function or method, because Rust has the guarantee of a trait being implemented, it knows that that type will support a given method, even if it doesn't know what the exact type will be until the actual invocation. The third option is to define your generic by itself, and then you add the 'where' keyword, where you specify the generic again, a colon, and then the similar traits that it is required to implement. And the reason you might use this alternate syntax is simply if you have a lot of generics and they each are requiring specific traits, sometimes it can get pretty verbose to put that all within the original angle brackets. This just allows you to break up the declaration of the generics and the declaration of their trait requirements, but the technical result is the exact same as the previous option. We also talked briefly about trait objects. A trait object is an instance of a type that implements a trait, and those methods will be called at runtime using a feature called dynamic dispatch. Basically, trait objects allow a little bit of dynamism. They enable our code to store different types within collections like vectors. And there are other use cases. But the key benefit is that we are not coupling ourselves to just a single specific type. We have the flexibility to rely on multiple different distinct types that all share a commonality of implementing the same trait. So in our example, we had a vector of different types, and we declared the type of the entries inside the vector as being references to something dynamic, some dynamic type or any number of dynamic types that all implemented a given trait. And that's exactly the benefit. We have a vector that can store changing different types as long as they all implement the same trait. We also talked about defining getter and setter methods within our trait definition. A getter is a trait method whose purpose is to read or get a piece of data. The complementary setter is a trait method whose purpose is to write a piece of data or set it. So getters and setters allow us to solve the problem that traits can only mandate methods, they cannot mandate data and state. They, for example, cannot know what fields a struct will have. In fact, a trait can be implemented for both, say, a struct and an enum, and something else, so there's no guarantee of the exact type it's going to be working with and how it's storing its data or what data it is storing. All right. Let's talk about super traits. A super trait is a trait from which another trait inherits its functionality, its requirements. It is also called the parent trait because it sits higher up in that hierarchy. The subtrait is the trait that is going to be inheriting functionality from the super trait, and that is also called the child trait, right? Just like a parent-child relationship. So we use the colon syntax to establish that relationship between subtrait and supertrait. Remember, types that implement the subtrait are obligated to implement the supertrait as well. So if you are implementing the subtrait, you must implement the methods of the super trait as well in your own separate 'impl' block. The reverse does not apply, so a type can opt in to implementing the parent trait, the super trait, in which case it is only responsible for implementing those required methods. It does not have to opt in to implementing the child traits requirements, and that again allows you to build up certain real world situations where certain types may fill one obligation but not others, while another type may implement even more functionality, including that shared functionality that is defined in the parent. We also talked about the 'PartialEq', or partial equality trait. That indicates that a type is comparable, that its equality can be compared with something else, and so familiar operators like the double equal sign ( == ) for equality or inequality, which is the exclamation mark and the equal sign ( != ) can now be used with your custom types. And then there is the more stricter Eq trait, which is a sub trait of PartialEq, and that adds three more requirements to a type. There's the reflexivity aspect, which means a type is equal to itself, or a value of that type is equal to itself. There's the symmetric requirement, which is if a value 'a' is equal to a value 'b', then the reverse must also hold true, that the values are equal to each other in either direction of equality comparison. And finally, the transitive property, which is that if value 'a' is equal to 'b' and 'b' is equal to 'c', then 'a' must be equal to 'c', and this is again a stricter set of requirements.
