# Associated Types II

Whenever we use a trait with an associated type, we need to provide the concrete type for that associated type. So as another example, let's say that we want to define a function that returns the sum of two numbers. But we want this function to be reusable so that it can accept, for example both integers and floats. So for that we can use a generic type parameter. For example, I can declare my function here. Let's call it 'add_two_numbers'. Pretty simple function. I'm going to define one generic type T and then define two parameters both of type T. So parameter 'a' will be my first number of type T, and parameter 'b' will be my second number of type T. I plan to add them together and return a value of type T as well. And so in the body of the function I can just take 'a' and add it with 'b'. So as it turns out, this code will not compile. And the reason the compiler isn't happy is because it cannot guarantee that the T type is some type that supports addition with the plus operator. Not all types support addition using the plus symbol ( + ). The only way that Rust can guarantee that a type supports addition is if it implements the Add trait. So what we can do is we can add a constraint and mandate that the generic type T be some type that implements the Add trait. As a reminder, the way we can do that is. First up, we need to bring in the Add trait into scope. So once again use std::ops::Add. And then as a reminder, after our generic type T, we add the colon and specify the Add trait. So we're saying some type T can be any type T as long as it is a type that implements the Add trait. But notice once again that the compiler is unhappy because remember like we saw in the previous lesson, the Add trait cannot operate by itself. It needs the developer or the implementation to clarify what is going to be the type for the Output associated type. The way we provide that is right here, after the Add trait, we're going to add a pair of angle brackets, almost like its own generic. And in here we're going to explicitly write that associated type which is Output. Then an equal sign surrounded on both sides by a space. And then the type that we want to be the type for the Output. Well, in this case it's actually going to be our generic type T. So I'm going to write it in here. And let's talk more about what we're saying here. So what we're saying here is we're defining a generic type T that can be any type that implements the Add trait. And in addition the Add trait's Output associated type is set to T as well. So Rust knows that the add method for whatever type T is provided that implements the Add trait is going to be something that returns Output, which is going to be T itself, whatever that type happens to be. So knowing those details, Rust knows that 'a' plus 'b' is going to be resulting in a value of T, which is whatever the concrete type is here. So if we pass in two i32s, now the compiler knows we're going to get back a sum of an i32 type. If we add two floats, we're going to get a sum of a float again. Right. So whenever a type T is, both of the parameters are of the type, the return value of the type, and we promise Rust that that type T can implement the Add trait such that when type T is added to type T, the resulting return value of the required 'add' method will also be of type T. So down below I can show you two variations. Here I can create a variable called 'integer_sum' and invoke 'add_two_numbers' and pass in two i32s. Let's do 1 and 2. So now the concrete type of T here filling in for the generic T is i32. i32 is a type that implements the Add trait. More specifically, it implements the Add trait with the Output associated type set to i32, which means Rust knows that it can call the 'add' method as mandated by the implementation of the Add trait, and also know that that 'add' method is going to return type T, which it knows to be an i32 here. So it just validates all of those checks for parameters and return values, and the trait requirements for type T all in one line. And similarly, I can do 'float_sum' and add two numbers and provide two floats like 1.5 and 2.4 once again. Now the concrete type of float 64 (f64) fills in for T. The float 64 type is a type that implements the Add trait, so that is valid. We tell Rust that the Output associated type will be equal to float 64. So when you add two type T's together you're going to get back a type T. So add two floats together. Get back a float. 'a' and 'b' are indeed of the same type. The return value is indeed of type T. Everything is satisfied. And now you can see we can reuse the exact same function for operations with different types. So here is 'integer_sum'. And here is 'float_sum'. And they're going to be the correct respective values. All right. And that's how you write a generic function with something like addition. Once again, the parameter of generic type T is insufficient because Rust needs to make sure that whatever operations you're doing in the body of the function or method are possible. not every type can be added. Not every type can be subtracted. Not every type can be ordered. Right? So Rust needs guarantees. And the way it knows that a behavior is available is if a specific trait is implemented. That's why we need to bind our generic type T to a specific trait. In this case Add, which enables the 'add' method for addition. But the Add trait itself requires an associated type of Output, which is what we need to provide here and then be a little bit more creative as far as what Output is going to be, which also represents the return value of the 'add' method. Pretty complex stuff. This is where Rust really gets, you know, really gnarly and complicated, but it does serve to make your code more resilient and more battle-tested. It allows the compiler to do a lot of that extra checking for you to prevent a whole category of errors.
