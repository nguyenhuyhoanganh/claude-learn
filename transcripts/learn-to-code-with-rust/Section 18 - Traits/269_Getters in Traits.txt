# Getters in Traits

At this point we have two structs, Income and Bonus, both of which implement the Taxable trait. Notice as well that the implementation of the 'tax_bill' method is identical for both of the structs. That makes the 'tax_bill' method a good candidate to move to the Taxable trait as a default method implementation. We can already see some shared behavior. Let's take a look at what happens if we do that. So I'm going to copy and paste this definition right here. And within any implementation, we can still override the 'tax_bill' method if we want to. However, what this allows us to do is here in Income, we can now remove this former code because it's automatically going to be the default implementation that the Income struct will receive from the Taxable trait, and the same rules are going to apply here. We can remove this, and we're going to keep our TAX_RATE constant to overwrite the one in the trait definition. So this cleans up the code quite a bit. Unfortunately, we run into a bit of a problem with the compiler. The Rust compiler is unhappy because it cannot guarantee the existence of an 'amount' field, right? Traits do not have access to hypothetical fields of some future types. In fact, the idea of a field is something that will only exist on a struct. What if we, for example, tried to implement a trait on an enum which doesn't even have this field-based syntax of a dot and the field name. So traits are meant to define shared behavior through common methods. They are not meant to define shared data. So this Taxable trait and the Rust compiler cannot guarantee that you're going to have some type that has to have an 'amount' field. There's no way to guarantee that. So this code will not compile. So how can we solve this problem? One solution is defining what is called a getter method. A getter method is a method that we define or mandate in the trait definition, whose responsibility will be to fetch or get or retrieve some piece of data or state from the type. Remember, traits cannot guarantee fields, but they can guarantee the existence of methods. And that's going to be a little bit of a hack that's going to allow us to solve this problem very elegantly. Here's what I'm going to do. Within the Taxable trait, I'm going to mandate the existence of an amount method on any type that chooses to implement the Taxable trait. I'm going to say that this 'amount' method is going to accept an immutable reference to the instance, and it's going to return a float 64. Now, within the 'tax_bill' method, I cannot access an 'amount' field as we just saw. But the Taxable trait does know that the type, whatever it happens to be, will support an 'amount' method. So what I can do here is let's invoke the 'amount' method that the trait will guarantee the existence of through line #4, and assume that the 'amount' method will give us the data that we need, some float that we can then multiply against the TAX_RATE constant. So now all we have to do is in both of these implementation blocks, we have to define that 'amount' method. So right here I can define my 'amount' method. And I need to return a given float64. Where am I going to get that from? Well, I'm going to say just give back the value in the 'amount' field. And similarly right here I'm going to define an 'amount' method as mandated by the Taxable trait. And all this will do is expose the value of the Bonus struct's 'amount' field. All right. So now everything should work as expected. And this is a pretty beautiful and elegant design because we have once again relied on a trait's advantages, which is that it can mandate or guarantee the existence of a method. And so rather than accessing a piece of state on some type, we have said we're going to invoke a method on that type called 'amount'. And that is going to give us the piece of state that we need for the 'tax_bill' method. And here's the beautiful part about this design. Let's say tomorrow for some technical or business reason, Say we have to change the name of this field to 'value'. Well, remember, all that the Taxable trait requires is it needs some 'amount' method that gives you back a float. So now all we have to do is keep the same exact 'amount' method. But say that the 'amount' that is going to be getting or where it's going to be getting the float value to multiply the tax rate by is now going to be 'value'. So notice we maintain the same method. We maintain the same interface, the same commonality or consistency between the Income struct and the Bonus struct in that they both guarantee an 'amount' method as mandated by the trait, but their internal implementation can vary. In fact, this does not even have to access a float. It can get a float from some other internal nested data structure. It can maybe be storing a HashMap or a vector. As long as we define an 'amount' method that gives us back a float, Rust will be happy because it's going to live up to this promise of an 'amount' method that returns a float, which means 'tax_bill' can guarantee a float from here, from this method that must exist that it will in turn multiply by TAX_RATE. So the code remains type safe. So the only thing that we need to do now is in 'main', we can update 'amount' to be 'value'. So now our Income and Bonus structs are indeed distinct. They have differences in how they store their internal data. And tomorrow they could be radically different. One can have five fields, another can have ten fields. Tomorrow, we can have a third struct with 15 fields. The day after that we can have an enum field. But the beautiful part is by using the benefit of traits, we have enforced the consistency of having an 'amount' method, and that is all that the compiler needs to ensure safety. If it has an 'amount' method, then it knows that it can invoke 'tax_bill' and have it work as expected. So now we're going to get our expected result. All right. So what this is right here is what we call a getter. It's just a regular method mandate that we can declare in a trait. But the purpose of this method, the kind of category that it falls into, is a getter. And it's called a getter because its purpose is to get a value or read a value, or access or retrieve some piece of data from a given type. But the type in the definition of the 'amount' method in its implementation block will specify how to get that value. And so we're not bound to a field on a struct or any kind of specific type of data. We have the abstraction of just requiring a method. And as long as it returns a float 64 as we do in these examples, the compiler is happy. All right. Hopefully you see the advantage of this design. And with that, I will see you in the next lesson.
