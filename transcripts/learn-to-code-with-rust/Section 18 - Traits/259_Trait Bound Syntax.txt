# Trait Bound Syntax

In the previous lesson, we defined a 'book_for_one_night' function that accepted an 'entity' parameter whose type had to implement the Accommodation trait. Hopefully this design reminded you of another Rust topic, which is generics. Generics help us solve pretty much the same problem, which is avoiding having to define multiple functions because we want the ability to pass in multiple types. So with generics, we define a generic type that is a stand-in for a future concrete type. And then we can use that generic within our function declaration to annotate the type of parameters and or return values to be of that generic type. So the syntax that we currently have is what's called syntactic sugar, which means it is a shortcut for a longer alternative declaration form that uses generics. And that alternative declaration form is known as a trait bound. And I want to show you that trait bound syntax in this lesson. The trait bound syntax uses a generic, but it then limits the generic type to only types that implement a given trait. So a regular generic type allows any type whatsoever, while a trait bound allows us to limit the generic type to only those that implement a trait. The reason it's called a trait bound is because it creates a boundary, a constraint, a limitation. The generic type is bound by the constraint that the generic type must implement a given trait. So here's how we define a trait bound. The alternate syntax. We're going to begin by adding a generic type. That happens, as a reminder, right after the function name. I'll provide my angle brackets, and then I'll define one generic type and call it T. As a reminder, the name 'T' is up to us. We're just declaring one future type that we can then utilize anywhere throughout our function definition. Here's the difference. And this is the trait bound syntax. After T, I'm going to add a colon and then write the trait that the generic type must implement. And for us this will be Accommodation. So T is a generic. It is a stand in for a future concrete type that I cannot predict in advance. However, I am adding a boundary, a constraint, and that is that generic type T is not just any type in Rust whatsoever. It has to be some type that implements the Accommodation trait. Now I use my generic type T the way I would normally use generics. So here for 'entity', I'm going to say a mutable reference to some type T. So we are combining generics with this trait bound syntax to constrain the possible options that type T can be. Can't just be any type, it has to be a type that is capable of some behavior which is enforced by the compiler. Validating that type T be some type that implements the Accommodation trait. So now notice my code from the previous lesson in 'main' will run the exact same way. So this trait bound syntax is an alternate way that we can accomplish the exact same result as from the previous lesson. 'entity' is now going to be a mutable reference to some type T, but Rust will validate that that type T implement the Accommodation trait. So when we pass in, for example, a mutable reference to a Hotel struct on line 67, Rust says "What is the concrete type that you are providing for generic type T?" It understands this to be a Hotel, and then it validates that that type, a Hotel struct, implements the Accommodation trait. It does, so the code compiles. Same principle on line 71. We pass in a mutable reference to an Airbnb struct. So Rust knows the concrete type that is filling in for T in this invocation is going to be an Airbnb type, but then Rust says "I can't just allow any type to fill in for generic T, I need a type that implements Accommodation". Does an Airbnb struct implement Accommodation? It does, so the compiler is happy and the code works as expected.
