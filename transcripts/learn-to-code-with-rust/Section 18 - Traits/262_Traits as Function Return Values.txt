# Traits as Function Return Values

So at this point, we've seen how we can define function parameters that are not bound to a specific type, but rather any type as long as it implements one or more traits. Similarly, we can annotate the return type of a function as being one that implements a specific trait rather than a concrete type. This allows us to write more abstract functions. So, for example, let's define a function here called 'choose_best_place_to_stay'. This function will accept no parameters, and I'll provide my arrow syntax here to annotate the return type. But rather than a concrete type like Hotel or Airbnb which would box us in, I'm going to be a little bit more abstract and say it can be any return type, as long as that type implements the Accommodation trait. So the syntax looks like this. As you might expect, not a concrete type, but rather the 'impl' keyword followed by the required trait, which is Accommodation. So here in the body of this function I can return any type that implements Accommodation. Now there are some nuances to this that we'll explore in just a moment. But for now realize that this can be either a Hotel or an Airbnb, as long as it is one or the other. So just to pick one, let's create a Hotel. Here in line, I'll instantiate a new Hotel with the 'new' constructor function. Choose a name of "The Luxe". I will omit my semicolon, so this will be the return value of the function, and a Hotel struct type does implement the Accommodation trait, so the compiler is happy. Down below I'm going to remove this line. The last one to avoid some complexity. And here, instead of instantiating Hotel inline, I'm simply going to invoke the 'choose_best_place_to_stay' function from above and close the semicolon. And there we have it. Now a couple of things to note here. First up, notice that Rust infers the type of the Hotel variable no longer to be a Hotel type, but rather some type that implements the Accommodation trait. And that's because Rust is not looking at our concrete implementation. It's looking at the definition of the function, particularly the return type. So when we see this line right here, the compiler is not happy. And the reason for this is even though it doesn't know the exact type of what Hotel is, it's trying to make sure that all trait requirements are met, so it sees the invocation of 'mix_and_match' where we are passing in a mutable reference to Hotel. So Rust knows that 'hotel' is something that implements the Accommodation trait, some type. Unfortunately, the requirements of the first parameter to 'mix_and_match' are to be of type T, and type T must be a type that implements both Accommodation and Description. So this is insufficient because some type that implements Accommodation is not the same thing as some type that implements both Accommodation and Description. Rust has no guarantee that whatever hotel's type is is implementing Description and thus the compiler is not happy. So if we want to continue using 'mix_and_match', we have to tell it that the return type of this function will be some type that implements both Accommodation and Description. Same syntax. 'impl' keyword followed by each one of the traits we want to mandate, separated by a plus ( + ). The plus is additive, which means add them together. So when I save this, now our code is going to work. And similarly I can replace this with something else. Like I can create an Airbnb here and let's give it a host like Peter. So we can return either different Hotel instances or different Airbnb instances. But we cannot return either a Hotel or an Airbnb. And that is what the compiler is unhappy about. It says if and else have incompatible types: expected Hotel. Rust is inferring the generic type that is going to implement Accommodation and Description to be a Hotel type. And we're trying to return some kind of different type. So this may seem to defeat the purpose of the more abstract return value here that is only bound to traits, but this 'impl' syntax still has advantages in other Rust domains.
