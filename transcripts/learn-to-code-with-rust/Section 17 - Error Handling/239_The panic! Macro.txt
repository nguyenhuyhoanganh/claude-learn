# The panic! Macro

Welcome to the next section of the course, which is all about error handling. Error handling revolves around how Rust and its developers handle errors or operations that may go wrong. The Rust compiler is renowned for its ability to catch errors at compile time, but there are also issues that we have to identify and prevent that occur at runtime. So we can group errors into two general categories: recoverable and unrecoverable. Recoverable errors are ones that we can deal with, that we can recover from, that we can define code to handle. One example is asking the user for input. If the user gives us an invalid input, that is recoverable. We can identify that circumstance and recover by, say, asking the user to provide the input again. Unrecoverable errors are ones that cause the program to be unable to proceed, to terminate. An example that we've seen is accessing a non-existent index inside a vector, and there's no way to recover from it. The program will simply panic or crash. So those are examples of runtime errors. And so they occur after the program has successfully compiled and is actually running or executing. We have to be careful with these kinds of errors because the compiler will not catch them. Now when the program runs into an error at runtime, we call that situation a panic. One simple example of a panic I can show you is if we have our Option enum, we have a None variant on it. If I take that variant and I call the 'unwrap' method on it, remember that 'unwrap' works if you have the 'Some' variant of an Option enum. The 'unwrap' method will extract the associated data that lives on that 'Some' variant, but the 'None' variant has no associated data to unwrap or extract, and thus we run into a panic and it looks just like this. So what we're going to see is the file where the error occurred, as well as the line number in this case line #2. And then the position within the line, which is the number of characters within the line where the error occurred. So the reason this says "10" is because it wasn't actually the 'None' variant itself that caused the problem. It was the invocation of the 'unwrap' method on it. Then what we see afterwards here is what's called the backtrace. And a backtrace is just a technical term for the complete list of files and functions that were running at the point that the error occurred. So this is actually going to show us parts of Rust's standard library, parts of the core Rust language itself. You can see this is actually within Rust and its compiler, specifically with the files that deal with panicking, that deal with the definition of the Option enum, etc., basically giving you a track record of everything that was running in sequence. Perhaps the nested function calls or nested method calls, etc. that led to the actual problem. And you can use this usually to Debug, if you want to see the complete sequential chain of events that led to a panic. Now we can actually force a panic manually with a macro called panic! So for example here say I have a program, I'll declare a basic variable called 'a' assigned to 1. And then down below I'll use this panic! macro. And it looks like this. Like all macros, it ends with an exclamation point. And it accepts a message as a string that it will output to your console, to your terminal. So here I can do something like "Something went wrong". And this will force the program to panic, to terminate. So you can see right here we're going to get pretty much the exact same thing we just saw with the 'unwrap' method. Here is our custom error message. "Something went wrong" and here is the backtrace. So all of these panics whether they are from some invalid operation or with the use of the panic! macro. It's a very similar output that just describes what happened and where it went wrong. Now the good news is that Rust is actually going to clean up the stack entries in any kind of data that has been created within the program, and that just ensures that there is no data corruption or memory corruption from leftover data. So even if the program panics, things like this 1 that exists somewhere in your computer's memory will be cleaned up when the program panics. So Rust is actually going to traverse all of the stack entries and the heap data and clean it all up. And that process is called unwinding. Okay, so some Rust developers even argue that the word "panic" is a little bit over-exaggerated. It's a little bit misleading because it's actually a pretty orderly cleanup process. It's not a crash in the in the kind of traditional computer science sense where there's undefined behavior and there may be consequences elsewhere in memory. It's actually a very safe cleanup, so you shouldn't be too scared of the word "panic". It basically just means something went wrong at runtime. Rust will clean everything up and give you the error message on the right hand side. Now, in practice, it is really rare to call this panic! macro directly in your own code. There's no reason to force a crash of your program, but I want to show you it explicitly, just so you understand that this is what happens behind the scenes when you run into a runtime error. Rust is just going to panic, which basically means give you this output describing the error or the thing that went wrong that forced the program to terminate and be able or be unable, rather, to continue operating further.
