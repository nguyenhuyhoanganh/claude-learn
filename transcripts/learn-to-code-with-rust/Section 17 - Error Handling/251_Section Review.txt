Congratulations on reaching the end of another course section. As always, let's take a few moments to review everything that we learned. In this section, we focused on error handling in Rust. An error is an operation that goes wrong and there are two categories of error: recoverable and unrecoverable. A recoverable error is one that we can react to and handle in our code gracefully. We can recover from that mistake. An unrecoverable error is one that prevents the program from progressing or proceeding. If you run into that unrecoverable error at runtime, which means something goes wrong, that is called a panic. So a panic is a runtime error that occurs because of some logical error that prevents the program from being able to continue. And whenever that happens, the output will include what's called the backtrace, which is a list of all of the functions that we're running at the point that the error occurred. So you can track down where the call chain began, and then all of the pieces that were involved up until the point that you ran into the actual problem. So if you want to gracefully exit a program, you can use the 'exit' function, which is found within the 'process' submodule in the standard library. It terminates a program. Now the function accepts a 'code' parameter that must be an integer, and the long-held tradition in many different programming languages and technical ecosystems is that a value of zero indicates that the program exited without an error, and any number greater than zero, usually one, indicates that the program did encounter an error, and then whatever is picking up from that point, say the terminal, can react to either one of those error codes depending on what it wants to do in each scenario. All right. We also talked about standard error. So if we use the eprintln! macro, we output a message to standard error. Standard error is another output stream or channel that you can send messages to. It's very similar to a TV channel in the sense that it's a separate location or destination where you can send specific messages. So if you use println!, that macro, that outputs a message to the standard output, which is one channel, one option. The eprintln! macro outputs a message to standard error instead, and code can log to these different streams or channels to segment and categorize your messages. So for example, you can save all of your success messages to a file while logging all of your standard error messages to the terminal. That is one option. The key takeaway is that you have the ability for that segmentation. The eprintln! macro accepts all of the exact same formatting options as println!, so you're welcome to interpolate values, structure them positionally. All of that is supported. Okay, so whenever you run into a recoverable error in Rust, it's usually going to be modeled as a Result enum. That models an operation that could be successful or erroneous. Now this is not going to lead to a panic. The program is not crashing. It's just going to give you that type that could represent either scenario. And then we have to figure out what to do for each possibility. So two examples of functions or methods that return Result included the 'read_line' method on our standard input struct, as well as the 'open' constructor function on a File. So those two examples, accepting input from the user or opening a file are examples of operations that can go wrong, and we don't want the program to crash. We want rather this wonderful design standard of Rust in that those functions will give us this enum representing either a success or a failure, and we then figure out what to do with that Result. So that Result enum has two variants: Ok and Err. And each one of them stores an associated piece of data that is represented by a generic type so it can be whatever you want. The Ok variant stores the success data, whatever the function developer chose that to be, and the Err variant stores the error data or the error message, whatever the function developer determined that that should be. So once we have that Result, one very common pattern is to combine it with the 'match' statement, which forces you to write a pattern or an arm for every enum variant. So we decide what to do in every circumstance. Sometimes that's not what you want simply because you only care about, say, one variant out of ten. For those situations, the 'if let' statement is also popular. That allows you to declare conditional logic if you have a specific enum variant. In other words, to declare what to do if you have this single variant that you care about, and then you're also going to be able to extract its associated data in the 'if let' declaration as well. We also talked about propagating errors, which basically means sending errors back up to the caller. So a common pattern is to define a function with some small responsibility, and it's going to send a Result back to the caller at any point that it encounters an error, and that 'Err' variant can store different error messages based on what went wrong. Now, truth be told, you probably don't want that much variation, because if there's that much variation, it's a good sign that the function is doing too much. Your function should ideally focus on a single responsibility, and then either represent that success in the 'Ok' variant or give you back the error message in the 'Err' variant. But as we saw with the operation of opening a file, we kind of started moving in a simplified direction by getting that function to have less and less of a responsibility. The benefit of propagating an error up is that the caller can then customize how to react to the error. So two different programs can rely on, say, a library crate that defines a function that returns a Result. And both of those programs can react differently to that error. It's not hard coded in the actual helper function, right? In addition, that removes part of the responsibility of the helper function because it focuses on the success path or what we call the happy path, and then says, well, something else can figure out how to handle the error. So you're splitting up responsibilities, which makes the function easier to reason about. The caller that the error is going to be propagated to, will handle the error in whichever way it sees fit. In fact, that pattern is so common in Rust that Rust has the question mark operator ( ? ) to perform the exact same logic, so that operator will either extract the data from the Ok variant in the Result enum and continue the execution of the function, or it's going to stop the function and return the Err variant with the contained error message. In fact, code can method chain the question mark in sequence if you have a sequence of methods all of which return a Result. So rather than writing a match statement which is totally valid but pretty verbose, if you simply want to continue on in the case of success, or propagate an error in the case of an error, this question mark operator is a really elegant way to accomplish that. We saw as well that with the Option enum, we have a very similar design where the question mark operator returns the value from the Some variant. And when I say returns, I really mean it extracts that value and it allows the function to continue running, progressing. And if you have the None variant, then the question mark operator returns at that point. So even though Result represents success and failure, an Option represents the presence or absence of a value, they are similar in the sense of you usually have something that you want to progress with and keep going with. Otherwise, the other case represents a scenario where you cannot progress, whether it be an error or an absent value. And at that point, it makes sense to just terminate the function early and send your error or absent value back up to let the caller deal with it.
