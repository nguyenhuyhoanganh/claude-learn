Congratulations on reaching the end of another course section. As always, let's take a few moments to review everything that we learned. This section was focused on control flow, and the term control flow refers to how a program will execute. We are able to control the flow, or in other words, to alter the execution of the program's logic. That begins with constructs like the if statement. The if statement executes the associated block when its condition evaluates to true. So now we have code that is conditional, that may or may not execute. The complementary else if statement executes a block when its condition evaluates to true and the original if statement's condition evaluates to false. So now we are able to declare multiple potential pathways of execution. Usually that is going to be connected to some bit of dynamic data, so that when the program runs over and over again, it may take a different pathway of execution each time. With the if and the else if, Rust will check until it finds the first match, the first condition that evaluates to true, and it is that associated block that it is going to execute. We also have the complementary 'else' keyword and that executes a block if no previous if or else if statements have evaluated to true. So the else serves as a fallback because its associated block is guaranteed to execute, assuming that no previous condition has been met. It's important to note that these blocks can produce a value. So within the curly braces, you can declare something like an integer or a boolean, and you can assign the entire if/else, if and else construct to a variable. The variable will then store the value from the block belonging to the condition that has been met. Now if and else if are wonderful, but Rust also supports something called a match statement, which is done with the 'match' keyword. That is able to compare a value with all of its possible variations. This is a little bit more exhaustive because with an if statement, the responsibility falls on the developer to check for a certain condition. With a match statement, Rust and the compiler are going to validate that every possible variant of a value is met. For example, if you have a boolean after the match keyword, Rust will require that you specify what to do in the case of true and in the case of false. Same thing with an integer. Rust will require you to specify what to do with every integer in the world. So it's more comprehensive. So within the curly braces or the block that you give to 'match', we declare what are called patterns or arms. A pattern or arm matches a value against the value after the match statement. And if they are a match, then it executes the corresponding block. So you define the logic to execute for each possible variation of the value. When an arm is met, Rust evaluates the corresponding block of code. We also saw an alternate syntax where we can associate each pattern with a value, and then the value becomes the final output or product of the entire arm, and then also of the entire 'match' statement. So for example, you can assign the 'match' statement to a variable as well. That is why it is important that every arm produces a value of the same type. Evaluation proceeds from top to bottom, and then it stops when Rust identifies an arm that matches. Now of course, when we're dealing with, say, numbers or strings, there are an infinite number of possible values. For that we have to use something like the underscore, which is a special character that serves as a catch all. It will always match. So it's critical that you place that pattern at the very end. It's like the final fallback to rely on assuming no previous arm has been matched. So the underscore is like the match equivalent of an else clause. All right. iteration is the process of repeating an action over and over again. And there's a couple of ways to accomplish this. The simplest, you could even say the most crudest way is the loop keyword, which declares a block. And Rust is going to continue executing that code in that block over and over again. By default, there is no end point. It will run indefinitely. So in order to prevent an infinite loop, we have to force a breakage. We have to force a termination. We do that with the 'break' keyword which terminates the iteration. And that is usually going to be connected to a conditional. So some criteria has to be met that will force the loop to stop its execution. We also have the 'continue' keyword which stops the current loop and starts again at the beginning of the next one, at the beginning of the next iteration. All right. There's also the complimentary 'while' loop, which executes as long as its condition continues to be met. It's called while because it executes the block while something is true. The nice part about this design is that we do not have to manually manage termination with the 'break' keyword. We just need to make sure that we stop at some point. So when that some point is is going to be determined by when the while condition evaluates to false. So the block that is attached to while should be mutating some state. When I use the word state, I'm simply referring to data that changes over time. So the block should be mutating some data that will affect a future termination and enable the loop to to conclude, right? Otherwise, a while loop still has the potential to continue forever and have an infinite loop if the while condition continues to be true forever, alright? Now, the 'break' and 'continue' keywords work with a while loop the exact same way as they do with the loop keyword. Finally, we talked about recursion. Very complex topic. Recursion is when a function calls itself. Within the function body, within the declaration of the procedural logic that a function contains, we invoke that same function itself. Each recursion represents a separate independent execution of the function, so the original caller or the original starting invocation remains in this pending state until the next recursion is complete. The problem here, very much like with the loop keyword, is we have the potential to create a program that runs forever, for the recursion to never stop. So we have to terminate it at some point, and we do that with a base case. A base case is a terminating condition that forces the recursion to stop, allowing all of those nested invocations to conclude and bubble up to the original caller that started it all. So the base case will involve some kind of conditional, some kind of if statement that will not involve a recursion, and that will indicate that the end has been reached. And then the entire thing can conclude. All right. That is a quick introduction to control flow, how we alter the execution and conditional flow of how a program executes. Hope you had fun.
