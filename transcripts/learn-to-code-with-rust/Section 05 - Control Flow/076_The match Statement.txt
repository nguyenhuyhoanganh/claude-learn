# The match Statement

In this lesson, we'll introduce the match statement. The match statement works like a switch case in other programming languages, if you're familiar with that idea. If not, no worries. The match statement enables us to react to multiple possible variants of a value. That means covering all of the possibilities that a value could be, and describing what code to run in each situation. A match allows us to consolidate many if and else if statements into this simpler syntactical structure. So I'll begin by defining an 'evaluation' variable and I'll set it equal to true. Right now this Boolean value is hard coded. But let's assume that the boolean will be dynamically calculated at runtime. Next, let's introduce the match statement. We'll begin with a new keyword called match, followed by the value that we want to match against, or in other words, the value we want to compare with. In this case, it's going to be our 'evaluation' Boolean from above. The value that follows after match can be pretty much any type. It can be a boolean, an integer, an array, a tuple. The beautiful part about it is that Rust will understand that type, that this is and will validate that every possible value that that type could be will be accounted for. So what I mean by this, and why a Boolean is a nice value to start with, is because a Boolean has a finite set of two possible values: true and false. So that means the match keyword will demand that we describe the course of action or the code to run for both the possibility of evaluation being true and the possibility of evaluation being false. So this value represents what we're going to be comparing with or matching against. Let me show you how that's going to work. After the value, we're going to do a space and provide a pair of curly braces. And inside the curly braces, we're going to list what are called patterns or arms. A pattern or an arm represents one option to compare the initial evaluation value with. Each pattern comes with an associated block that represents the code to run in the situation that the value matches the match value. So let me give you a example. What I'm going to do is write true here. And true represents one possible value that evaluation could be. After true, I'm going to add a space and provide this rocket like ( => ) syntax, which is an equal sign and the greater than sign. And then after another space, I'll provide a pair of curly braces. And this represents a block. This represents the block of code to run if evaluation happens to be true. You can think of this as being the equivalent of writing an if statement that says "if evaluation is true", then run this block. So here I can do a println! and say something like "The value is true". So what's super cool here is we're going to see a compiler violation. And if we hover our mouse over, it's going to tell us. "missing match arm: false is not covered". Rust is going to perform an exhaustive check to validate that we have covered every possible variant of what 'evaluation' could be. As a Boolean, 'evaluation'  can be either true or false, but we only have one arm or one pattern covered and that is the situation of a true. This code will not compile, and that's a good thing. It means that Rust is forcing us to write code that promises to react to every possible scenario. So what we need to do is add a pattern or an arm. That's one of these things for the false situation. We do not need to do anything to separate our arms, not even a comma. I'm just going to write my next value on the next line, and the other one that we need to cover, the other possibility that 'evaluation'  could be is a false. Similarly, I'll provide this rocket syntax ( => ) and a block of code to run if 'evaluation'  is false. So here, I could output something totally different. The value is false. So you can think of this as equivalent to writing an if and else if statement. If evaluation is true, run this code. Else if evaluation is false, run this code. This is not necessarily any cleaner than an if and else if. But you can imagine if we have a type that has, let's say 6 possible variations or 6 possibilities, very quickly, this will become a lot cleaner, because that match construct is going to capture every single possibility, along with every possible block of code to run for each scenario. So let me show you here that if I run this file, we're going to see the value is true. And if I flip 'evaluation'  to false, we're going to match this arm instead and run this block instead to get "The value is false". One cool feature of a match statement is that each arm can return a value. So let's say I arbitrarily decide that a value of true for my 'evaluation'  Boolean should map to an integer value of 20, and the value of false for 'evaluation'  should map to an integer value of 40. What I can do here is write the value 20. In fact, if I'm returning something, I can completely get rid of these curly braces since I'm not executing any block of code, but just mapping my variant here to a corresponding value. In this case, I'm just going to remove the curly braces entirely and write 20. With this scenario, where we are mapping each variant or each arm to a corresponding value. We do need commas right here. So this is going to be 20 and false I'm going to map to 40. All right. Now, right now this is giving us a error. And that's simply because Rust thinks that we are returning the evaluation of the match statement as the return value of the 'mai'n function. But the cool thing here is that this is going to produce a value, and we can actually assign it once again to a variable. So here I can say something like 'let value ='. And once again, whenever we have a variable assignment on the right hand side, we need to close that expression off with a semicolon. So once I add that and save, the compiler warning will go away. But now take a look at what we're doing. We're using a match statement to say check for whatever 'evaluation'  is. If it happens to be true, get a value of 20 and assign it to the 'value' variable. If 'evaluation'  is false, get a value of 40 and assign it to the 'value' variable. Once again, if we forget to include an option, the compiler will warn us. So it's a little bit more extensive than a simple if/else if because an if/else if is not going to hold you responsible. If you only check for true, there's no compiler warning. The else if is something you, the developer, needs to remember to add. With a match statement, we are getting the benefit of the Rust compiler validating that every possible variant is exhausted, that we have a pattern or an arm for every possibility. And this is just one example, with 'evaluation'  being a boolean. But there's a lot of different values that we can provide here. And for each different type, Rust will perform the same validations to make sure every possible value that this could be is covered. So now I can print out the value of 'value'. We can see right now 'evaluation'  is false. That's going to lead to a return of 40 being assigned to 'value'. And we're going to output the value 40. If I swap 'evaluation'  to be true, then the match statement will match on true returning a value of 20 and assigning it to 'value'. And we're going to output 20. All right. So hopefully, the match statement makes sense. It's very similar to an if and else if or even multiple else ifs in that it allows us to either run a block of code based on some variation of a value or produce a corresponding value, once again, based on the variations of a value. We took a look at the Boolean variations, which can only be true or false, but there's a lot more that a match statement can do, and we're going to explore that in the upcoming lessons.
