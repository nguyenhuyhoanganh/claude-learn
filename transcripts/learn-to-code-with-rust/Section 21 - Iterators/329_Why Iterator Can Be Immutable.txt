# Why Iterator Can Be Immutable

So just one more thing that I wanted to mention about the code in the previous lesson. Say that I made the my iterator variable right here mutable with the mute keyword. Doesn't it seem logical to do so? After all, the iterator must be mutable, so that the iteration with the for loop can modify its internal state that keeps track of what elements have been accessed. Well, as it turns out, if I try to run this code, we're going to see a warning right here and it's going to appear right here as well. Variable does not need to be made mutable. Why is that? Does an iterator have to be declared mutable as we iterate over it? Something has to be keeping track of that internal state, right? Well, recall from earlier in the course in the ownership section that we mentioned that when ownership changes, so can the mutability permissions. The new owner of a variable or a value can rebind that original data and its ownership as mutable. For example, say we ignore everything below line number two. Say I declared a new owner variable assigned to my vector. This would transfer ownership from my vector to new owner. But what I could also do is make new owner mutable right here. So what that would do is new owner would become the new owner of the vector, but also declare its ownership as mutable at the same time. So when my vector was the owner, it did not have permission to mutate the vector's data. But when ownership moved to new owner, the new owner declared itself as a mutable owner with permission to mutate. And that's totally legitimate, right? Well, what we see here explicitly is exactly what's happening implicitly behind the scenes with a for loop. So the for loop right here takes ownership over the iterator. And when it takes ownership it rebinds that iterator as mutable. Behind the scenes technically speaking, it calls into iter first to get the iterator itself, but then it transfers ownership and declares its new ownership in the for loop as mutable. So we are technically transferring ownership from a mutable iterator to another mutable owner who makes its ownership mutable, implicitly behind the scenes. Therefore, the original mutable my iterator variable is never actually mutated before its ownership changes to the for loop, and thus, because it's not modifying the iterator in any way, it does not need the mute keyword. It's technically useless because this thing is not performing any mutation. That's why rust is unhappy. So if I change my iterator back to being immutable, then ownership will correctly transfer from the immutable my iterator owner to the mutable owner right here that we don't really see, but it's the one behind the scenes handling the for loop logic. That mutable iterator is where the data is actually changed and updated over the course of the iteration. Again, we don't see that owner directly in our code with a name, which is why it becomes a little bit confusing, but that's what's going on behind the scenes. The for loop takes ownership of the iterator and declares its ownership as mutable, allowing that internal state to be modified.
