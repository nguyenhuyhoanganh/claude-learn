# The Stack and Heap

In order to understand more about memory, we need to distinguish between the stack and the heap. The stack and the heap are two different parts, or regions of the computer's memory, that are available to a Rust program when it runs. At runtime, when the program needs to store a value in memory, it will choose between the stack and the heap. The reason that there are two options is because each one has its own advantages and disadvantages. The stack is generally faster, but it only supports data of a fixed, predictable constant size, and also that size must be known at compile time. The heap is generally slower, but it supports dynamic data that can change in size over the program's execution. So first up, let's talk about the stack. A stack is a structure that stores values in the sequential order that it receives them, and it removes the values in the opposite order that it receives them. A stack is often called last in, first out, or LIFO, because the last item in is the first one out. In other words, the last item that is added is the first one removed. The most common analogy that you'll hear is a stack of lunch trays. So say there's a bunch of people eating in a cafeteria. When lunch is over, they stack their trays in a pile, and we can see a visualization of this on the right. The first person arrives and they add the blue tray on the very bottom. The next person stacks their tray on top of the previous tray, and then the third person stacks their tray on top of the second one, and so on. When the next person arrives at the cafeteria to eat, they're going to take their tray from the top. So in the image on the right, the red tray at the top, which was the last one added in, will be the first one removed. And that process of removal will continue until the stack is empty. The last tray added is the first one taken out, and you can only add or remove a lunch tray from the top of the stack. Nowhere else. So the technical terminology for adding a value to the stack is called pushing onto the stack, and the terminology for removing a value is called popping off the stack. The advantage of the stack is that it's speedy and efficient. And the reason is because there's only one possible place to push or pop the next piece of data from, and that is at the top of the stack. All stack data must have a fixed, consistent size that is known at compile time. Remember, fixed means unchanging. Constant. Predictable. Think, for example, of an i32. It will always be 32 bits or 4 bytes, and the compiler knows this when it compiles the program. So data types like integers, floating points, booleans, characters, and arrays have a fixed size that is known at compile time. And thus Rust is going to store them on the stack at runtime. That is the region of memory that it will use for those types of values. So we can pretend that each one of the lunch trays on the right represents a value declared in our Rust program and, say, assigned to a variable. So the first value declared in our program can be the blue lunch tray at the bottom. Then the second value declared will be the tray above that one. And then the third value declared will be the tray above that one. And then when the function ends, the variables go out of scope and their stack values are cleared in last in first out order. So in analogous terms, the lunch trays are popped off from the top of the stack one by one until we get to an empty stack. So let's compare the stack to the heap. The heap is a large area of storage space. You can think of it like a warehouse or a parking lot. When a Rust program needs dynamic space, it requests it from the heap at runtime. And what do we mean by the word dynamic? We mean unpredictable, not fixed, unknown at compile time, or perhaps capable of changing during the program's execution. Rust will store those types of values on the heap. So two examples I can give you are user input and a file's content. If we ask the user for something like their address, we don't know how many characters they're going to provide. It could be 5 or it can be 100. Similarly, if we ask the user to choose which file on their file system to open and read, we don't know how much content that file will have. It could be one kilobyte, it can be one megabyte. That data size is unpredictable, and thus it cannot be stored on the stack and must be stored on the heap. Now, how does this process happen? Well, it begins with a program called a memory allocator, and that program finds an empty spot in the heap in the warehouse, so to speak, that is large enough to store the data. The memory allocator returns a reference, which is just a memory address. Think of an address like in the real world. It's a designation for a location. An address is a different idea from the value itself. An address is what we can follow to get to the value. So let's think of a house in the real world. The house is a concrete structure that occupies space. We can think of the house as the heap data. In comparison, the address is what we follow to get to the house to arrive at the house. So similarly in Rust, the heap data is the actual content that is being stored, but what the memory allocator gives us is the address, which is just the address or location of that data. Another analogy is a parking lot. Say you park your car in the lot. The car, once again, is the concrete structure that occupies space. The address like spot "H25" in the image on the right is the address. It is the designation or location for where you can find your car later. So often the reference is also called a pointer because it points to the data. In the real world, an address is a pointer to a house. Think of it like an arrow navigating you or pointing you to the value. So when we get that reference, we are not getting the value. We are getting an address we can follow to the value. And we can assign that reference, that address, to a variable in our Rust program. The reference itself is stored on the stack because it is a fixed size. The original data is stored on the heap, but the reference can be stored on the stack. So in real world terms, think of writing down an address for a house on a piece of paper. The house may vary in size, and that's why it has to be stored on the heap. But the piece of paper can be the same size each time, because it just needs enough room to store the address and then follow it to get to the original data. So a reference size or a pointer size is fixed and constant, and thus it is valid for the reference to live on the stack. So let's talk about speed. Pushing to the stack is faster than allocating on the heap. In a heap, the allocator has to spend time searching for an open spot in a stack. The program always adds the data to the top. We can think of these as the writing operations when data is being added. Now, when it comes to reading data, which means accessing data that is already been written, while reading data is also faster on the stack than on the heap, because within a heap the program has to follow the reference to the memory address to find the original data, the original value. So for each piece of data, the computer has to move around the heap to a different location following the correct address. So you can think of it like navigating a warehouse to find a package, or navigating a parking lot to find a car. In comparison, a stack has the data in sequence, so there is less jumping around from area to area like the heap. Computer processors work faster when the data is stored closer together, so that's why the stack is faster. So once again, if your question is: If the stack is faster for both reading and writing, why not use the stack for everything? And the answer is because the stack only supports data of a fixed size. When your data is dynamic, it must be stored on the heap. This section of the course is focused on the concept of ownership, and the purpose of ownership is to assign responsibility for deallocating memory, particularly heap memory. Remember, to deallocate means to remove a value from memory so that that memory slot can store something else. Ownership is a compiler feature that primarily exists to reduce duplicate heap data. It is that heap data that can be dynamic, that is usually going to be larger in size, and thus it's important to clean up that data when it is no longer needed. All right.
