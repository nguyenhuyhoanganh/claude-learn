# Ownership and Function Parameters

At this point, we've explored the concepts of copying versus moving when dealing with variables as owners. The same ownership rules are going to apply to functions and their parameters. A parameter is like a variable. It's a name inside the function that represents a value, and whether a value is going to be copied or moved to a function parameter will once again depend on the type of data it is and whether or not it implements the Copy trait. So it's the same rules when dealing with static data like integers, floats, or Booleans, all of which implement the Copy trait. Then, Rust will create a copy of the data for a function's argument, and thus there is no movement or transfer of ownership when a value is passed into a function, and similarly, when dealing with heap data like strings, Rust will instead move ownership to the function parameter. That's when the type does not implement the Copy trait. So let's see this in action. What I'll do here is I'll declare a function called 'print_my_value'. And all this function is going to do is accept a value and interpolate it in a printed string. So for now I'll declare my parameter. I'll call it 'value'. And we'll assume this function will will receive an integer. So an i32. And here I'll output the value of that argument. I'll say "Your value is {value}". Then, in the main function, I'll declare a variable. Let's call it 'apples' and I'll assign it to a value like 6. And then I'll invoke 'print_my_value' and pass in 'apples'. So what's going to happen here? When this 'print_my_value' function runs, it will receive a copy of the integer value 6. So 'apples' is never going to transfer ownership of the value to the 'value' parameter. You can almost think of this as being equivalent to 'let value = apples', where 'value' is the parameter right here in the 'print_my_value' function. An i32 implements the Copy trait. So 'print_my_value' will receive a copy of the integer value 6. It's going to print it out. Then, 'value' is going to go out of scope and it's going to clear its stack entry consisting of the value 6. But that is a duplicate copy of 6 anyway. And thus when we return back to the main function, 'apples' is still going to be valid. So I can println! right here and show you that 'apples' is still valid. We never lost ownership because 'apples' remained the owner throughout the entire main function, and it created a copy to pass in to 'print_my_value'. So here we're going to see "Your value is 6". That's coming from 'print_my_value' And then 'apples' is still valid to be used on line #4. So next, let's switch it up and pass a String to the 'print_my_value' function instead. So here, I'm going to update 'value' to be a String. And in my main function, I can change this variable. Let's call it 'oranges' just for a little bit of variety. And this will be a String with the text "oranges". And I'm going to pass in 'oranges' right here. I'm going to update the text right here. And once again: let's talk through what's going to happen here. So when we pass 'oranges' to 'print_my_value', we are passing a String. A String does not implement the Copy trait, so a copy will not be made. And thus we're going to have a movement of ownership. Ownership will move from the 'oranges' name right here to the value 'name' right here. So think of this 'value' as doing the equivalent of this. If we wrote this line of code in main, then 'value' would now be the owner of the String and 'oranges' would be an invalid variable. The exact same principle applies here. 'value' becomes the owner of the String. 'value' uses that String. Then, 'print_my_value' ends and we reach the end of its scope. The 'value' parameter goes out of scope and it deallocates its String. It's the owner of this piece of text on the heap so it deallocates that piece of text. And then that's cleared, and then we arrive back at main. But after the conclusion of the 'print_my_value' function, this 'oranges' name, this variable, is no longer the owner of the String. In fact, this entire String is now gone from memory and thus we are unable to use it on line #4 . Right? So right here we're going to see some familiar error messages. You can see right here: "move is going to occur because 'oranges' is of typeSstring which does not implement the Copy trait". When is the value moved? In other words, when is ownership transferred? Right here. Right. It says "value moved here" when we pass 'oranges' in. And here, looking at it from the other side, from 'print_my_value''s side, Rust says "this parameter takes ownership of the value in this function". So 'value' is now the new owner of that text. You'll notice what it's offering us here as an idea in 'main' is to call 'clone' on 'oranges', which would indeed solve the problem because that would pass 'print_my_value' a duplicate copy of the original String, and thus prevent the transfer of ownership. But we're not doing that. So ownership is moving to the 'value' parameter. It's once again the exact same principles that we dealt with when we just had two variables in the same function. But you have to be careful, because this can be a very common point of confusion in Rust, in that you can pass in some heap data to a function, and then all of a sudden when the function ends, you can no longer use the original variable, right? Remember, this can be annoying, but it exists to keep you safe. It exists to make sure that we clean up heap data properly. That there's only one owner who's going to be the one responsible for deallocating memory, right? So Rust is trying to help us, but we have to be careful and follow the compiler's rules and recommendations to arrive at this better, safer code.
