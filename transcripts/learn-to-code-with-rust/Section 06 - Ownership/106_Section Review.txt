Congratulations on reaching the end of another course section. As always, let's take a few moments to review everything that we learned. This section focused on ownership. Ownership is a Rust compiler feature that prevents memory errors that are found in other programming languages. The basic gist is that every value in our program, which means every piece of data, is assigned one owner at a time. The owner is who is responsible for cleaning up that value's data from memory. Now, the interesting caveat is that a value's owner can change over the course of the program. There is always one owner for any given piece of data, but who that one owner is can change when ownership moves from one owner to another. We call that a move. A move is the transfer of ownership from one owner to another. Now, in order to understand ownership, it's important to understand that we are usually trying to avoid creating duplicate data on the heap. In order to understand the heap, we have to understand the stack. They are two different complementary parts, or regions of the computer's memory, that are available to a Rust program when it runs. The stack is generally faster, both for reading and for writing data, but it only supports data of a fixed size that is known at compile time. For example, integers, floats, and Booleans are all stored on the stack. Any time you declare an i32, its size is fixed. It's always 32 bits or 4 bytes. That is not going to vary, and thus the compiler knows the type and its size at compile time and can store it on the stack at runtime. The stack follows what's called a last in or first out, or LIFO strategy, which means that the last item that is pushed onto the stack is the first one that is popped off the stack. Now, that kind of understanding is not critically important to understand what happens in a Rust program. It's just a little bit of the behind-the-scenes computer science ideas that are at play here whenever Rust is compiling and then executing your binary program. So the heap in comparison, you can think of that like a warehouse floor or a parking lot. It's this big open area of space, and the advantage is that it can store data of a dynamic size as needed at runtime. Dynamic means unpredictable, not fixed, or capable of changing. So whenever your program runs, the program says: "Hey, I need something of this size". And then a program called the memory allocator finds an empty spot in the heap that is large enough to store that data. You can imagine a crate arriving at a warehouse, and the warehouse manager has to decide what spot in the warehouse is big enough to fit that crate and its size. It's the exact same principle with the memory allocator. So the memory allocator finds a place to store this data that can be of a dynamic size, and then it returns back a reference which is just an address to get to that heap value. An address or a reference is a different idea from the value itself. An address is like an instruction that we can follow to get to the original value. It's two different ideas, and that idea is important to understand because references play a very important part in our Rust code. All right. Every value has its scope. It's the area within which it exists. A scope ends when a block concludes. A block is the region of code created by a pair of curly braces. For example, when you declare any function, you involve a block which intrinsically creates a scope. It creates a designated area or region. So variables declared in that region in that scope within that boundary will only live as long as that scope is valid, which is within that block. The owner is who is responsible for cleaning up its data when its name goes out of scope. For example, a variable is the owner of a value, so when the variable reaches the end of the scope, when it is the end of the block, it is that variable as the owner who is responsible for cleaning up the associated data on either the stack or the heap. We also talked about the Copy trait. As a reminder, a trait is a contract that requires that a type supports a specific functionality. A type can implement a trait called Copy to indicate that it can produce a duplicate of itself automatically in specific situations. One example we explored is assigning one variable to another, and that is just one example of when the Copy trait can matter. If a type implements the Copy trait, Rust will make a full copy of the value in that scenario. Right? So primitive values like integers, floats, and Booleans, all stack data, implement the Copy trait. So when you assign one variable to another, as one example of the kind of operation that can rely on the Copy trait.  In those types of situations, Rust creates a full copy because it's generally cheap to do so. Integers don't occupy a lot of space in memory, so it's easier to create a full copy than it is to create, let's say, a reference or an address to the original value. There's no point of doing so because it's just not expensive to create a full copy. The issue is that not all types implement the Copy trait, and nowhere is there is that more clearer than in the two different types of strings that we're dealing with in Rust. So Rust has two core string types. The first one is the 'str' type, and we call that the string literal, sometimes also called a string slice. It's not dynamic because the compiler knows the exact size, the exact characters at compile time, and thus it can embed those strings directly into the binary. This string is for dynamic data, so it can collect a value of any size when the program runs. For example, the user's name or the user's address, or the contents of a file whose size we may not know in advance when the program starts running. Now, this String type on the heap, this "String" does not implement the Copy trait. Rust wants to work its hardest to ensure that we don't duplicate data unless we have to. That's why we have to be explicit with calls to methods like 'clone'. We have to specify when we want to create a copy. We have to acknowledge that we are aware that we are duplicating data and thus requiring more memory. So with types like this, by default, Rust is going to assume that we do not want to duplicate the data. And thus if we do something like variable assignment, ownership will move from the first variable to the the other one, the new one. So ownership moves from one owner to another when we assign a string to another variable, or in other contextual situations, like passing a string into a function. A reference is the address of a value in memory. In other languages, it's often called a pointer. There is a slight distinction in that a reference in Rust is guaranteed to point to valid memory. In other words, that address will lead you to some valid existing data that is guaranteed to be legitimate or still present. In other words, it has not been deallocated yet. There are issues in other programming languages where you may accidentally have a pointer that leads you to a memory location that has accidentally been cleared or deallocated before, and that leads to bugs in your code. Those come from developer error. These types of situations are not possible in Rust. Now, a reference allows a program to use a value without transferring ownership because we do not assign new ownership. Rather, we simply ask for the address of something where something lives, so that we can access that address and refer to the original value without having to either create a duplicate of it or taking ownership away from the original owner. So we describe that action of creating a reference as borrowing. The reference is the noun and borrow is the verb. To borrow means to create a reference. We create that reference with the borrow operator, which is that ampersand symbol ( & ) in front of any value in Rust. As we saw, we can absolutely create references to stack data like integers, but usually that's not done because the default is just to let Rust create copies. Usually, where you're going to see borrowing is with heap data, because that is precisely where you do not want to increase memory by duplication. And you also may not want to deal with the complexities of ownership. So now you can reuse the same data. It will maintain the same owner. But now you can have other references rely on the same data, on the same piece of information, without dealing with ownership or unnecessary data duplication. The dereference operator, which is the asterisk ( * ), follows a reference to the original value. It's like saying "Take this address, go to that address and get me the value that is found there". So in common operations like printing out a value or invoking a method, Rust will automatically dereference the address. When we tried printing out the reference variable, as you may recall, Rust said: "Hey, you probably don't want to see the address itself. You probably want to see the value at that address" so it automatically dereferences it. It follows the address, gets the value at the original location, and shows you that output. Immutable references implement the Copy trait. That means you can create as many of them as you want. Rust will create a copy of the reference so the original one will remain valid. Finally, we talked about the principles of ownership in regard to function parameters. They follow the exact same rules of ownership as far as copying versus moving. So if a type does not implement the Copy trait, ownership will move to the parameter. If a type does implement the Copy trait, Rust will create a full copy of that value for the parameter. So if we pass an integer or a float or a Boolean into a function, those types do implement the Copy trait, and thus the function will receive a full copy of the value for the parameter. If a type does not implement the Copy trait like a String, ownership will move. The challenge there is that the function then has to return the value back to the caller to prevent the memory from being deallocated. Because the parameter becomes the new owner and the parameter goes out of scope at the end of the function body, and then going out of scope, it is responsible for cleaning up the data.
