# Moves and Ownership

In this lesson, we'll introduce the concept of moves, which are a key feature of ownership. A move refers to the transfer of ownership from one owner to another. A value in our program can only have one owner at a time, but who that owner is can change. Who is responsible for cleaning up that piece of data can change over the course of the program. All right, so a few lessons ago we wrote this code where we assigned one variable to another. In this case, the variable was an integer. And because integers implement the Copy trait, Rust created a full copy of the integer value on the stack. So thus, this second variable of 'year' has a complete duplicate of the original integer value 2025, and the first variable of 'time' was unaffected. Now we were dealing here with stack data. Let's take a look at what happens when we're working with data on the heap. So what if we replicated this code but changed it to use a String type instead? So we're going to reassign a variable. But our original value is going to be a heap allocated String. So right here, I'll begin with a variable called 'person'. And I'll assign it to a String. I'm going to use the 'from' function and pass in my string of "Boris". Once again this is a string literal, also called a string slice. This itself will be hard coded into the executable, but we're using that as a basis for creating a String on the heap at runtime. So we have our 'person' variable. And then we're going to create another variable called 'genius' and assign it the value of 'person'. So what's going to happen here? As it turns out, this code will operate completely differently from the integer example. A heap allocated String does not implement the Copy trait, and therefore Rust will not make a copy of this heap data when 'person' is reassigned to 'genius'. That would create a duplicate of the heap's text data, which we can generally assume is going to occupy more memory than something on the stack, right? Heap data is for data that can expand, that can grow. Typically, the data there will be larger than a simple integer or character or Boolean which is stored on the stack. Rust wants to reduce those heap copies as often as possible because they tend to be more memory expensive. If Rust operated this way the same way as it did with integers, there would be a String copy each time we assigned one String variable to another. So what happens here is, when we assign 'genius' to 'person', Rust copies the previous stack entry, so it copies the reference to the heap data, the length and the capacity from the 'person' stack entry to a new 'genius' stack entry. But Rust does not actually copy the String's text content on the heap. There is still one piece of heap data, but now we have two references to it on the stack. So let's come back to the idea of ownership. Given that there is one piece of data on the heap, who is responsible for cleaning it up for deallocating it? Is it the 'person' variable or is it the 'genius' variable? As it turns out, it's going to be 'genius'. When we assign 'person' to 'genius', Rust moves ownership from the 'person' variable to the 'genius' variable. 'genius' becomes the owner, which means that 'person' actually becomes invalid. It goes out of scope. We cannot use the 'person' variable after line 3, so it's going to be the 'genius' variable that is responsible for deallocating the String's. heap memory. When the 'genius' variable goes out of scope, there can only be one variable owning a String at a time. We can't have multiple owners, so when ownership moves from one variable to another, like from 'person' to 'genius', it's as if the original variable never existed. So at the end of the function scope, Rust only has to drop the 'genius' variable out of scope, and it will clean up the corresponding heap text. Imagine that it didn't work this way. For example, in other programming languages, without the concept of ownership, there could be two references pointing to the same heap data with this kind of code. So then when the function scope would end, the program would remove the 'person' variable, it would become out of scope, and it would try to remove the contents on the heap. But then that program would also have the 'genius' variable going out of scope, and that would attempt to clear the location and memory that was already cleared by the previous variable going out of scope. So when the language tries to free available memory on the heap twice, it actually runs into an error because that heap allocation will technically no longer have a value. This is called a double free error in other programming languages, and it can lead to memory corruption and security vulnerabilities. But it's not possible within Rust. We can't have two variables, two owners, attempting to clean up the same heap data because we can't have two owners. And the reason we can't have two owners is because in situations like this, ownership simply moves. Ownership moves from 'person' to 'genius'. 'genius' is the new owner, 'genius' is responsible. And now we don't have two owners for the same heap data. We only have one. So Rust solves that double free error by invalidating the first variable on the second one's assignment.
