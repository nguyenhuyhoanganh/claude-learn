# Return Values I

Next up, let's discuss the principles of ownership in a different direction, which is a function returning an owned value to a calling function. So we'll kick this lesson off by defining a 'bake_cake' function. And I want this function to create and return a String. So we'll use our arrow syntax to note that the return value will be of type String. And here I'll define a 'cake' variable and set it equal to a heap allocated String, which I'll create with my 'from' function. Let's call our cake "Chocolate Mousse". And then I'm going to explicitly return the value with the 'return' keyword and 'cake', providing my semicolon. And then, in the main function, I can invoke the 'bake_cake' function, which should give me back that String. I'll assign the return value to a variable called 'cake'. 'cake' will be the String, and then I can output that value and say "I now have a cake {cake}" . So this program will tell us "I now have a Chocolate Mousse cake". So, in this example, Rust moves ownership of this String from the 'cake' variable in the 'bake_cake' function to the 'cake' variable in the main function. A return value allows us to persist a value even though the function is concluding or ending. This 'cake' variable is the owner of the String, and if we didn't return the String, 'cake' would go out of scope and it would be responsible for deallocating this text on the heap. But because we are providing a return value, we are preserving the string. We are providing this string as the return value, which is the output that we give back to the calling function: in this case, main. So this is the inverse of what we learned about in the previous lesson. In the previous lesson, we showed how ownership moved from a calling function's variable to a parameter in the invoked function. This is moving ownership from a value in the invoked function back to the calling function. It's completely okay that 'cake' goes out of scope because ownership will move to this 'cake' owner, this 'cake' variable which happens to have the same name, but that's totally fine. Ownership will move from this 'cake' variable to this 'cake' variable. As a quick reminder, we can simplify the 'bake_cake'  function further and implicitly return the String. So of course we can first do this. Just simply write 'cake' without a semicolon on the last line. That will make it the return value implicitly. But then furthermore, we can just get rid of the 'cake' local variable and write this code. So 'String::from' -- we make sure to get rid of that semicolon. So now this String becomes the return value. The same principle applies. It's a little bit of a nuanced area because we can say there's technically no owner of the String right here on line #7, but we are still preserving it and returning it back to the main function, at which point the 'cake' variable becomes the owner, and the 'cake' owner is responsible for deallocating the memory. If we never save this to a variable... For example, if I simply did 'bake_cake'  in this situation, then we would return a String. There would be no owner to take ownership of it, and thus it would be deallocated automatically at this point. So Rust is still going to be careful, even though technically there's no name, so there's no owner. But the same expected principles are going to apply. The deallocation of that heap memory will happen as expected, but again, in our first example, 'cake' simply becomes the owner of this returned value.
