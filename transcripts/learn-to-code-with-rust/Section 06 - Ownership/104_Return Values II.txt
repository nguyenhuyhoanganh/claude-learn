# Return Values II

So by now, we know that if we pass a String type or any owned type into a function, Rust will move ownership to the corresponding parameter in the function. And this ownership feature can often prove challenging because if we want to keep reusing the String, we have to remember to keep returning ownership back to the calling function. We have to keep returning the Rust out of these functions. So let me show you an example that will demonstrate how this can quickly become challenging. Let's say that I'm modeling the cooking of a recipe. So my main function is going to invoke several helper functions that are going to add some kind of ingredient to my recipe. For example, I'll have an 'add_flour' function here, and then afterwards I can have something like an 'add_sugar' function, etc.. we're going to build up a cooking recipe. So in 'add_flour', I'm going to accept a parameter called 'meal' which will be of type String. And all I want this function to do is to concatenate some text content to the end of the String. So here I can call the 'push_str' method. And we're going to provide a step of the recipe here. Like 'add_flour'. In order to call the 'push_string' or 'push_str' method and mutate this String, I need to make sure that I make my parameter mutable with the 'mut' keyword. And I'm only going to write out one example here. But let's imagine that my program will have many functions like this. So we'll have an 'add_sugar' function, an 'add_salt' function, an 'add_eggs' function, etc. all of which will accept a mutable string and concatenate some content to the end of it. Now in the main function, I'll declare a variable called 'current_meal' and I'll initialize it to an empty String. I'll use the 'new' function this time around instead of 'from'. I'm starting with an empty string with no content, and what I'd like to do is invoke 'add_flour' and pass in 'current_meal'. This should be 'add_flour'. And then what I'd like to do is to keep invoking follow up functions like 'add_sugar' and 'add_salt', and keep passing in the current meal or the current recipe that I have. So this design is quickly going to prove problematic. Let's talk about why. When we call 'add_flour' and pass in this String, we are going to transfer ownership to the 'mela' parameter. When the 'meal' parameter goes out of scope at the end, it's going to deallocate this String. It's going to clean up this text on the heap. So we're actually going to lose that content completely because we are transferring ownership to the 'meal' parameter. The only way that we can preserve this String value, this content, and keep it alive is to send it back, which means we have to provide it as a return value here. This allows me now to receive that return value, and then I have to save it to a variable still, because if I don't, then there's going to be no new owner on line #3, and then the memory will once again be deallocated. So in this example, let's say I just want to reassign it to 'current_meal'. I can use 'current_meal' here, and this will require me to make 'current_meal' mutable, because now I'm reassigning a value. So I have to make this mutable like so. And then furthermore... Here, I forgot to specify that I will have an explicit return value of a String like so. And now we're going to have this design where every time we transfer ownership to a new function, for example, this hypothetical 'add_sugar' function, I'll need to make sure that 'add_sugar' will return the String back to me as its return value, so that I can keep reassigning it back each time. And this approach, as you might imagine, will quickly become cumbersome. Every function that accepts a String will have to return it to avoid deallocating that memory. So even a simple function that accepts a String to print it. It doesn't even have to mutate it. It just needs to use it for something like printing. Even a function that accepts a String for non-mutation operations will need to return it to keep giving it back to the caller to ensure that ownership is moved from the parameter back to a variable in the original calling function. Imagine that we have a function that accepts multiple parameters, each of which is an owned value. Maybe we have a function that accepts two Strings. Well, now we have two new owners, the two parameters, and their respective values will be deallocated when those parameters go out of scope, unless we return all of them back to the original function. And since we need to capture multiple values now, we need to start introducing data types like tuples that can store multiple values inside of them, because we need to give all of those values back to the calling function. So as you might expect, this approach that we're seeing here on the screen, this is technically valid, but it's not ideal. It's very frustrating because we have to keep returning a value back. Right? And that will be true for every owned value. So this approach is really not scalable. So we're going to figure out a way to solve this problem more elegantly in Rust in the follow up section with something called references. We'll talk more about that in the very next section.
