# Scope and Ownership

Earlier in the course, we learned about blocks and scopes. A block is a region of code that is created by a pair of curly braces. We can see an example of a block here. In our main function, the block begins on line number 1 and it ends on line number 3. We also learned about scopes. A scope is the boundary or region within a program where a name is valid, and scopes are directly connected to blocks. A function like main is one example of a Rust construct that creates a block, and that's because the main function body has a scope. That scope serves as the boundary for its variables, so variables declared in the main function, such as 'age', will live only as long as the main function does. At the end of the main function, when the block ends, the variables will go out of scope and become invalid. So next let's talk about how blocks and scopes apply to the concept of ownership. Every Rust value has an owner, and that includes both values on the stack and values on the heap. When we assign a value to a variable, the variable becomes the owner of the value. In this example, 'age' is the owner of the value 33. The owner is who is responsible for cleaning up the data. And how does the owner know when to clean up the data from either the stack or the heap? The answer is the owner knows to clean up the data when the variable goes out of scope, which is when the block ends. When the variable goes out of scope, it is the owner who deallocates the memory for that value. It either pops the stack entry or it cleans up the heap data. So in this example, the 'age' variable goes out of scope at the end of the main function at the end of the block. So we can say the 'age' variable exists here. And then the 'age' variable goes out of scope here. And as the owner of the value 33, the 'age' variable is responsible for popping the stack entry for cleaning up the data or the memory that 33 occupied. We can technically create a block anywhere with a pair of curly braces, so I can declare another block right here in my main function, and inside I can declare another variable. Let's call this one 'is_handsome' and I'll assign it, of course, to the value. true. So once again, the 'is_handsome' variable only exists within this nested block. This block creates its own nested scope within the main function. 'is_handsome' is not going to exist after the block concludes because 'is_handsome' goes out of scope here. So the 'is_handsome' variable is also the owner of the Boolean value on the stack. A boolean, much like an i32, is a stack entry. It's a fixed size, so when this inner scope concludes, the 'is_handsome' variable goes out of scope and, as the owner, it is responsible for removing the Boolean stack entry. We are not able to reference 'is_handsome' after that inner scope ends. We can see the violation here. "cannot find value 'is_handsome' in this scope". And that is because at this point the stack entry has been cleared, so the value is gone and the variable has gone out of scope. Now the 'age' variable still exists because we are still within its scope, which is the main function. So let's return back to a single function scope. I'll declare both the 'age' variable and the 'is_handsome' variable within the same scope. An i32 and a bool are both fixed size values, so they are stored on the stack and no matter which order I use them here... For example, I can output 'is_handsome' after 'age', but no matter the order, they are going to be cleared in a LIFO order from memory. Remember, LIFO is "last in, first out" and it is how stack data is cleared, so let's walk through the order of events. First up, the value 33 is going to be pushed onto the stack and the owner is the 'age' variable. Then, the value true is pushed onto the stack and its owner is the 'is_handsome' variable. We do a bunch of things with the variables and then we reach the end of the function scope. At this point, the owners have to clean up their respective values. And that cleanup, that clearing of stack data, occurs in LIFO order. The LIFO order means the true Boolean value, that stack entry, is removed first, right? And that is handled by its owner. The 'is_handsome' variable. Then, 33 is removed and that is handled by its owner, the 'age' variable. Both of the variables are out of scope, so at this point 'is_handsome' isn't validated. So 'is_handsome' goes out of scope, then 'age' variable goes out of scope and then the program is done. So to summarize Rust's rules for ownership and we've only explored them with stack data for now... But rest assured we will get to the heap in a lesson or two. Each value has an owner for these two values. The owner is a variable. It doesn't always have to be a variable, but every value has an owner, and a variable is one example of something that can serve as the owner. It is who is responsible for cleaning up that data. When the owner goes out of scope, the corresponding value is dropped, which means it is cleared from either the stack or the heap. All right.
