So we've talked about ownership in a very high level, but let me give you a more practical idea that we can take into future lessons. What is ownership? So every piece of data in your program is going to have what's called an owner. The term owner is just like the term in everyday life. You could be the owner of a house. You could be the owner of a car or the owner of a book or a computer. So the owner is the entity that owns the resource that is responsible for that resource. You, as the owner of your house are responsible for your house, right? So the owner is who or what in the Rust program is responsible for cleaning up a piece of data when that piece of data is no longer in use. So another way to think about it is the owner is who is responsible for deallocating, for cleaning up the memory that a value needs when it is no longer needed. So every value in a Rust program is going to have one owner. It's also important to note that that owner can change over the course of the program's execution, but there's only going to be one owner at a time. So just like in the real world, you can be the owner of a house, but then you can sell the house, and the house has a new owner. So who the owner is can change, but there can only be one owner at a time for each value. So what do we mean in a technical term for what owner represents? Well, the owner is usually going to be a name. For example, a variable is a name in our program. When we assign a value to a variable, the variable becomes the owner of that value. But a variable is not the only name in a program. For example, a function parameter is also a name, and thus a parameter can also be an owner. For example, when the function ends, the parameter is going to be responsible as the owner of deallocating that argument's memory. And ownership is usually going to be names, but it's also going to extend to other entities. For example, composite types, which are types comprised of multiple elements. So for example, a tuple, an array are composite types that hold other elements inside them, and a tuple and array are considered the owners of their values. Ownership can even be thought of like a hierarchical diagram, in the sense that you can have an owner of a value, and that value can be an owner of other values. So a variable assigned to a tuple can be the owner of that tuple. But then the tuple owns the values inside that collection, inside that composite type. And that can continue many levels or layers down. So this, I understand, can be very complex. And we've talked about it at a very high level and abstract level. But as we get into the code, we're going to reintroduce these ideas in practice with lots of code samples. Hopefully, the key takeaways here are clear. And that is that ownership is Rust's solution for solving memory problems, for making sure that you clean up memory when it is no longer needed. Different languages have adopted different strategies for solving those problems, and they each had their own trade-offs. The language either had to sacrifice speed or safety.
