# References and Borrowing

Every Rust value has one owner at a time. The challenge comes when multiple parts of the code need to reuse a value for certain types, like numbers. It is lightweight to create a full copy, but for other types on the heap, it means creating a duplicate of a value which is going to occupy some chunk of memory. We saw an example of that in the previous lesson with the 'clone' method that forced a full duplicate. But there is another way. What we can do instead is to create a reference. A reference allows the program to use a value without moving ownership. We describe this action of creating a reference as borrowing. So just like in the real world, borrowing means we ask the owner to lend us something, and then we use it, and then we promise to give it back to the owner when we're done using it. So with borrows, we never take ownership. If I borrow your car, I don't become the owner of the car. I just use it temporarily. Then, I give it back to you and you remain the owner throughout the entire process. Now, technically speaking, a reference is an address to the original value in memory. So if I ask to borrow your car, you'll probably give me the address where I can find it, the address where the car is stored. And I'll follow that address to use your car. That's exactly what a reference is. It's just a address in your computer's memory where the original value is being stored. So we can actually store that reference, that memory address, in a variable in a Rust program. That way, we're not creating a copy of the original value. Rather, we're just storing the address that can lead us to the original value. And that reference itself is pretty cheap to store compared to making duplicates of that original data each time. So we can say that the reference is the noun. It's the entity that we are creating in our program and borrow is the verb. So to borrow in Rust means to create a reference to some value without taking ownership of it. So most of the time, we're going to be creating references to heap data. Stack data is generally pretty cheap to make a copy of. Heap data is generally more expensive as far as memory consumption. As it turns out, though, technically speaking, a reference can hold the address of a value on either the stack or the heap, so we can borrow a reference to a stack value. It's a lot less common to see this, but it is technically possible. So in order to do this, we use a special character and that is the ampersand ( & ). That is Shift + 7 on your keyboard. So this symbol, the ampersand ( & ) is what's called the borrow operator because it borrows another value. That means it creates a reference. So for example, if I have a variable, let's start out with a integer which is going to live on the stack. So I'll call this variable 'my_stack_value' and give it an arbitrary argument or value of 2. Below, I'll create a variable called 'my_integer_reference', and here I'll use that borrow operator, which is the ampersand ( & ) followed by my original variable, which is 'my_stack_value'. So what we've done here is we've taken the memory address where the value 2 is being stored. And we've saved that memory address to 'my_integer_reference'. Notice that the type of my integer reference is not an i32. Rather it's &i32, which can be read as a "reference to an i32". The way to read that ampersand is "an address leading to". So this is an integer. This is an address leading to an integer. It's a memory address where we'll be able to find a valid integer, that valid integer being 2. All right. Now again the cost of creating a full copy of the value 2 is pretty cheap. This reference, this storage of a memory address is also going to occupy some amount of memory. It's probably going to be either comparable or even more than the memory required for an integer. And that's why Rust simply makes copies of stack data. It's just not that expensive. Where you're going to see the syntax more often is with heap data. So down below I can declare a variable. Let's call it 'my_heap_value'. And here let's create a String using the 'from' function. Let's do something silly in here like "Toyota". Down below, I'll create a 'my_heap_reference' variable. And it's going to be the same syntax. We're going to begin with the borrow operator which is an ampersand ( & ). We want to borrow something which means store a memory address or in other words, use something without taking ownership of it by just simply asking for its existing memory address. And what we want to create a borrow of is 'my_heap_value'. So in this situation, we are not cloning the original string. We're simply storing the heap memory address where that String exists. 'my_heap_value' remains the owner of this String. 'my_heap_reference' is actually the owner of this reference. And this reference, you can think of it like a totally separate value and also like a totally separate type. A String type is not equal to a reference to a string (&String). That's a totally different type, right? In the real world, a house is a different type of thing from an address to a house. Let's imagine that address is written on a piece of paper, right? That piece of paper with the address is a different idea and a different type from the house itself. It's the exact same principle here. You can think of the String as the actual house here. That's the actual concrete value on the heap. And this is storing the memory address on a piece of paper called 'my_heap_reference'. Other than that, the exact same principles are going to apply. So at the end of this function, the variables are going to go out of scope and they're going to be cleaned up. So 'my_heap_reference' is the last one on the stack. It's going to be cleaned up. It is not the owner of this String. It is only the owner of this reference. So that's going to be cleared. Then, 'my_heap_value' is the owner of the String. It will deallocate that heap memory. And then the same principle will apply for 'my_integer_reference' on the stack, and then my stack value on the stack as well. I also want to point out that you'll often hear the words reference and pointer used interchangeably. A reference is an example of a pointer. It's called a pointer because the address that a reference stores points to a memory location where the original value lives. You can think of the reference as like an arrow that is pointing to the original location where the data is being stored. Now, technically speaking, there's a small semantic difference between the words reference and pointer. A reference is a type of pointer. We can call it a subcategory of pointers in Rust. A reference is guaranteed to point to a valid value for the life or existence of that reference. In comparison, a plain pointer in other languages does not have that guarantee. So what this means is Rust will guarantee that 'my_heap_reference' is going to point to an address in the heap that is guaranteed to have this String, that is guaranteed to have a valid value. And, in other languages, you can actually run into problems where that's not the case. So just to distinguish again in real world terms, a reference is like an address to a house that is guaranteed to still be standing. To still be useful. Right. A pointer is like an address to a house that may or may not be there anymore. So a reference is safer. It's stricter because it's a pointer that is guaranteed to point to a memory location that has to have a valid value. So hopefully you're starting to get a sense of the problems that Rust is solving once again. In other languages, it is possible to work with a pointer that leads you to a memory location where the value is no longer being stored. Where it's been, say, deallocated. So you have an address to basically, let's say an empty lot where there is no more house anymore. So when you have a pointer and it points to a memory address where the value or the data has been deallocated, that creates the potential for bugs. In Rust, if you have a reference like this, the compiler will guarantee that the value at that memory address will be valid. The String will always exist. It will always be present as long as the reference 'my_heap_reference' exists. You might hear a terminology that expresses this, and that is "references must never outlive the referent". The referent is the original value and the reference is the pointer pointing to it, pointing to the original value. So that statement reflects that principle in Rust that we just described, and that is that the address to a value, the reference must never outlive the existence of the value. Rust is trying its hardest to make sure our programs are safe and reliable. All right. So hopefully that makes sense. And with that I will see you in the next lesson.
