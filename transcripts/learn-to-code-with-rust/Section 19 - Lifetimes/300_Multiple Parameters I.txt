The lifetime elision rules are insufficient to infer the relationships between the lifetimes of the parameters and the lifetime of the return value, and that is because there are multiple possibilities. And I want to show you some examples in this lesson. So first up, we can clean up some of our previous code. In fact all of the code right here, we can clean up as well as all of our code in 'main'. Let's keep things super simple and just return 'first' here and notice that Rust will not compile this code. And if we hover our mouse over the violation, it will tell us missing lifetime specifier. That means we need a generic lifetime annotation and the message reads: "This function's return type contains a borrowed value, i.e. a reference, but the signature does not state whether it is borrowed from first or second". Once again, there are multiple possibilities in the way that either 'first' or 'second' or both of these parameters could relate to the return value. So yes, the function's body is clearly returning the 'first' reference, so we know that the return reference's lifetime is connected to the referent of the 'first' parameter's lifetime. But remember that's not how the compiler operates. It looks at this function signature independently. This is the contract. And then it's going to confirm that the code in the body of the function lives up to that contract, to the promise that we make right here. As far as parameter types and as far as lifetimes, we have not provided the contract for the borrow checker to verify, and thus it is going to refuse to compile. Once again, the purpose here is for the borrow checker to validate that we have no dangling references, that we have no references to non-existent data, and there can be multiple different types of situations whenever you have multiple reference parameters where the returned reference is related to either one of those multiple references, or potentially both, and this is just an example with two of them. When Rust sees that, it needs to understand the relationships between them in your signature here, so that it can validate that the body of the function lives up to that promise in its code, that the implementation honors the expected connections between the lifetimes of the parameters and the references, so that Rust can guarantee that there is no dangling reference.
