# Multiple Lifetimes

When we declare a struct, we can define multiple lifetimes. That enables references to be connected to different lifetimes, to different periods of existence. Once again, I personally believe that this design can sometimes add more complexity that may not always be beneficial, but again, sometimes it's needed and you may see it from time to time, so I want you to be exposed to the syntax. So let's say that we define a TravelPlan struct. So right here I'll define a TravelPlan. And immediately I'll derive my Debug trait implementation above. And let's say that my TravelPlan will have two fields called 'from' and 'to', where we're starting from and where we're headed to. And both of those are going to be string slices. So I'll declare 'from' as a string slice and 'to' as a string slice. Since our struct is storing references, the borrow checker needs to establish the lifetime contract between the struct and its references, so we can use a single generic lifetime like 'a and mark both of our references with it, and this means that the lifetime of the TravelPlan struct must live within the overlapping lifetime of the referents of 'from' and 'to'. So if the lifetimes are different, as a reminder, the borrow checker will pick the smaller one, or equivalently, the overlapping one, the one where it can guarantee that both of the references are valid. So let me show you. Let's let's say we start out with a single lifetime here of 'a, and mark both of these as having lifetime 'a. All right. Now our code compiles. That is a longer lifetime than the one belonging to the 'to' variable, which only lasts until the end of the nested scope. But Rust is going to pick the overlap or the smaller lifetime of the two as the concrete lifetime that is filling in for generic lifetime 'a. So that means the borrow checker is assuming that the TravelPlan struct can only live as long as the 'to' referent right here. This is to's lifetime. Now, technically speaking, if we return the 'from' field specifically, that is not a dangling reference, right? Because the 'to' field will be a dangling reference because that is a field referring to this thing. But 'from' is a field that happens to be a reference that's getting its data from the 'from' variable right here. And that lifetime is still valid at the point that we want to print out 'plan'. There is no dangling reference as long as we return the 'from' field right here. But because we have bound ourselves to a single lifetime right here, the borrow checker has chosen this lifetime and erred on the side of safety and said: "I can't allow you to print this out". So we have stricter requirements that are trying to play it safe, and the borrow checker is assuming the possibility of a dangling reference even though one technically does not exist. So now let's add multiple lifetimes, and that will communicate to the borrow checker that the lifetimes of the 'from' and 'to' fields can be different. So for example here I'll declare a second lifetime. Once again the name is up to us. I'll just do 'b and then I'll declare the 'to' field as having lifetime 'b. And all this declares is that these two references are allowed to have different lifetimes. So now notice that our code is going to compile. Take a look. We now have Portland printed right here. So the key difference here is that Rust is able to figure out that this 'from' lifetime and this 'to' lifetime are different, and it doesn't have to pick one to play the role of the single lifetime that we saw in the previous example. Rust understands that the 'from' lifetime right here will be the concrete lifetime for generic lifetime 'a, and the 'to' lifetime right here will be the concrete lifetime for generic 'b. And since it understands they're different and it understands the associations of the fields, it knows that if we return 'from' here, it knows that 'from' is connected to this lifetime, and thus it does not represent a dangling reference. Rust was not forced to adopt the smaller or the overlapping lifetime to pick just one. So it's almost like TravelPlan is connected now to two different lifetimes depending on which field we are referring to. So the 'to' field is still going to become invalid after the end of this scope, because it's referent of the 'to' variable is going to be cleaned up. Its lifetime will end. And since 'plan' fully fits in within the lifetime of 'from', all this code is is valid. All right. We can in fact swap the 'a and 'b assignments right here in the struct definition. The key takeaway here is simply by declaring two different generic lifetimes, we enable them to be different. It's the exact same idea as with generics. When we have one generic of type T and we mark two things with it, we are saying that those two things must both be of type T, and similarly, if we just declare one generic lifetime, we're saying 'from' and 'to' must be connected to that single generic lifetime 'a and Rust thus has to choose some concrete lifetime, and it chooses the safer one of the smaller one. But as soon as we add two generic lifetimes and allow our references to not have to have the same one, then the borrow checker understands that it can associate the 'from' variable's lifetime with the 'from' field and the 'to' variable's lifetime with the 'to' field, and sort of track those simultaneous coexisting lifetimes as they exist simultaneously within the TravelPlan struct.
