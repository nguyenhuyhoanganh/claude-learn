# Invalid Lifetimes I

In the previous lessons, we saw examples of valid lifetimes. Let's now explore the opposite scenario. The program will not compile if the borrow checker sees an invalid lifetime, which is caused by a dangling reference. A dangling reference is a reference to data that no longer exists. It means the lifetime of the reference has exceeded or outlived the lifetime of the value it is borrowing. So in real world terms, the address has outlived the house. So let me show you an example of a dangling reference. We'll begin by declaring a 'cities' vector consisting of three Strings. So here I'm going to add a String of London. Let's also add a city of New York and finally Barcelona. So the 'cities' variable is the owner of the vector, and the vector is the owner of the three String elements. Below, I'll declare another variable called 'favorite_cities' and this will be a slice. So we're going to borrow a slice to the first two elements of the 'cities' vector. So as a reminder, for that we use our reference operator to borrow. We provide our vector, then our square brackets, and then the index positions that we want to pull from. So I'm going to start at index 0 and pull up to but not including index 2. So start at 0, pull up to 2. So that's going to capture this. And this is a slice. But a slice is still a reference. It's just a reference to a portion or a fragment of the original data. This 'favorite_cities' slice is dependent on the 'cities' vector existing. So I can of course print out 'favorite_cities' right here. I'm going to add my Debug formatting to do that. There we go. And output that we're going to see the first two strings of London and New York. So as a contrived example, let's use Rust's built in 'drop' function to deallocate the heap memory for the vector. This will also invalidate the 'cities' variable. So after the declaration of 'favorite_cities', I'll call 'drop' and I'll pass in 'cities'. This will force the end of the lifetime of 'cities'. The name is invalidated, but more importantly the data is deallocated. The memory is cleared from the heap. Right? So now even though we see the compiler error here, the dangling reference is right here on line #10. 'favorite_cities' becomes a dangling reference because it is a reference to memory that has been cleared, that has been deallocated. The referent, in other words, the original source of the reference, the source of data, that being 'cities', is now illegitimate, it is invalid. Therefore, we are trying to reference data that no longer exists. That is a dangling reference. The reference of 'favorite_cities' is trying to outlive the referent which is 'cities'. So of course we're going to see right here: "borrow later used here". We are using the borrow even though the data that it is borrowing no longer exists, we can accidentally create a dangling reference in certain situations if we return a reference to a value that no longer exists. Let me show you an alternative of this code. Let's say that I create a variable here called 'some_cities', and 'some_cities' will be assigned to the evaluation of a block. This is valid Rust code. We can have a block of code execute, and whatever is the final output of that block is what we'll assign to 'some_cities'. So say that I take my 'cities' vector and drag it into here, and then I take the reference part of 'favorite_cities'. So just this portion right here, and I'm going to return it from my block. And then I'm trying to return a slice, which is a reference to the first two elements. This is also invalid code. The reason is because when this block concludes, the 'cities' vector will automatically be deallocated because the 'cities' name will go out of scope. The lifetime of 'cities' ends at the end of this block, and we are trying to return a reference to a portion of 'cities', but 'cities' will be gone by the time this block is done. So whatever is remaining here in this reference, if we were to assign it to 'some_cities', it would be a dangling reference. It would be a reference to data that no longer exists. So once again, the reference's lifetime tries to outlive the lifetime of the referent that it is borrowing from. So now you can see the code does not compile and it says right here: "borrowed value does not live long enough". So the borrowed value, which is this slice right here, does not live long enough to be within the lifetime of the 'cities' value. And that's the constraint that the borrow checker is enforcing. So perhaps the alternate way that I can state this is the borrow lives too long. The reference and its lifetime outlives the lifetime of the 'cities' referent that is the base of that reference. And that is the problem. Now, these examples are somewhat contrived, because you're usually not going to write code like this that will force you into this error state. But as we'll come to see throughout the section, when we start dealing with function boundaries, when we start passing references into functions and receiving references as return values from functions, it becomes a lot harder to reason about and validate that these kinds of rules about dangling references are met, and that is where the borrow checker will keep us honest and make sure that we are not violating these kinds of rules that we are demonstrating in these more simplified examples. Remember, every time you have a nested block, you have a separate execution environment. You have a separate chunk of code running in this isolated sandbox. Whenever you invoke a function from another, it's a very similar idea. You have this separate sequence of code that is executing to then conclude and give you back something. And it's very important that what it gives back to you, if that is a reference, follows the exact same rules. That that reference is not accidentally pointing to data that is no longer valid, that no longer exists, that is no longer stored in memory, right?
