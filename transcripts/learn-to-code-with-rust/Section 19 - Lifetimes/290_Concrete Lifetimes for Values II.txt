# Concrete Lifetimes for Values II

So let's walk through a few more examples of lifetimes. As you may recall, Rust supports nested scopes through the use of curly braces. So for example, here in the body of the 'main' function, I can create another block with another set of curly braces. This is legitimate and it's somewhat of a contrived example. But we see these kinds of nested blocks all the time. For example, an if statement creates the same kind of nested block, and thus this creates its own nested scope. Another example is a function call that creates the equivalent of a nested scope. It's a distinct execution environment, a distinct area or section of the code. So inside this nested scope we can define another variable. Let's call it 'b' and I'll assign it to a value of 2. So the lifetime of 'b' is not the 'main' function, but rather it is the inner scope. The lifetime of 'b' starts right here when the value starts existing, and then it ends right here at the conclusion of the inner scope. When the variable goes out of scope and the value of 2 is cleared from that location in memory. So we cannot of course use the value of 'b' right here, because 'b' is no longer in scope. Or another way that we can describe it is 'b' is no longer alive. Its lifetime has ended right here. It is no longer valid or legitimate as a name within our program. So as I mentioned in the previous lesson, lifetimes are often connected to scopes, but they do not necessarily have to be connected. So here is an example of where a lifetime can end before a scope ends. One example is when Rust transfers ownership from one name to another. That movement will mark the end of a lifetime as well. For example, if I have a 'c' variable set to a String, let's say something like "Winter". And this can be of course any type that does not implement the Copy trait. And on the next line I'll create another variable of 'd' and assign it to 'c'. And as we know, we cannot use 'c' after line #9 because 'd' is the new owner of the String. So we can say that the lifetime of 'c' ends when 'd' takes ownership of the String. 'c' becomes invalidated, 'c' is no longer alive, it is no longer legitimate. So the lifetime of 'c' starts when this value moves into its location in memory. And that's going to consist of both the heap data as well as the stack entry that holds the pointer to the heap data. But when we assign it to 'd', the lifetime of 'c' ends with that movement. We can technically say, the scope of the 'c' variable is technically to the end of the main function, right? If this line was not present, 'c' would go all the way until the end of the main function. Its lifetime would be this region of code, and that is corresponding to the end of the 'main' function scope. And here the lifetime ends for a a different reason or at a different place, right? It's not related to the scope that the 'c' variable is declared within. It is related to the operation that we are performing here, which is the movement. So 'c' is no longer valid after the move. And so it is no longer living, so to speak. Its lifetime is over. And another example is if we pass ownership over by passing in our value into a function, in that case, ownership will move from the variable to the parameter of the function. So similarly, if I take a function in Rust like 'drop' and I pass in the 'c' variable. The ownership of the value creates the end of the lifetime of 'c'. So we can say once again that the scope of 'c' is technically the 'main' function, but its lifetime is over right here. Yes, we can say line #9, and I will continue to sometimes say the line numbers to provide clarity, but I'd like for us to think about it less in terms of line number and more about areas of code. If we had, for example, 100 lines of code in between this line and this line, the lifetime of 'c' is not measured in line numbers. It's not measured in seconds or minutes. It's just the section of code or the region of code that the value is alive or legitimate. It is legitimate starting here, and it stops being valid right here when ownership moves, and thus the lifetime of 'c' ends. So the lifetime can be related to the scope and usually is. But it doesn't have to be. That is the key takeaway of this lesson. With that I will see you in the next one.
