# Lifetimes and Referents

So to kick this lesson off, I want to clarify and repeat that the lifetime syntax here does not create a coupling between the returned reference and the 'items' reference. Rather, it creates a coupling between the returned reference and the original referent that 'items' is a reference to. Whatever is the original data source that 'items' is a reference to, that's what the return value will be connected to and must live within. So this return reference is separated or decoupled from 'items' as soon as the function is done running. There are no dependencies between them, and I want to prove to you that that is the case by adjusting the code in our 'main' function. So what I'm going to do is here instead of assigning the return value of this function to the 'two_cities' variable, I'll instead declare an execution block. So here's my opening curly brace and here's my closing curly brace. And make sure to end that with a semicolon. So as a reminder, when Rust sees an equal sign, it always evaluates the right hand side first. And if the right hand side consists of a block, Rust is going to execute the block. And then whatever is the final value that is produced is what it's going to assign to the variable on the left. And that is very similar to how a function works. So first things first, here I'm going to get rid of this semicolon. And then just to make things a bit more explicit I'm going to take this reference that we create inline. And I'm going to assign it to a variable because then it's going to be easier to reason about the reference and its scope. So here I'll declare a variable. Let's literally call it 'cities_reference'. And using the borrow operator I'll create a reference to my 'cities' vector. This is the exact same thing as we have on this line, except we are assigning it to a name. And then I'm going to pass in 'cities_reference' into my function. Now let's take a look at this. We have a block. We have a nested execution environment and a separate scope. The 'cities' reference, that variable is declared within this block. So when the block scope ends, 'cities_reference' will be cleaned up. So its lifetime is this region of code. 'cities_reference' will no longer exist after this block is done. We're going to use it as the basis to create a slice from some data source, return that slice and assign it to 'two_cities'. So if 'two_cities' and its slice, this return value right here, were coupled to 'cities_reference', then this would be a dangling reference because it would be a reference to a reference, and more specifically, a reference to a reference that is going to be cleaned up at the end of the scope. But the slice returned here is not connected to the original reference. Whether we look at it as 'cities_reference' here or the 'items' parameter here. Rather, the return value is coupled to the referent from which the 'items' parameter came, or equivalently, in this example, the return value is coupled to the referent of 'cities', because that's where 'cities_reference' took its reference from. And that is how Rust knows that 'two_cities', despite the fact that it was derived right here, is connected to the lifetime of 'cities' and must be completely contained within the lifetime of 'cities'. Here is the 'cities' region of code. Here is its lifetime. 'two_cities' kicks things off right here and fully lives within the lifetime of 'cities' up until the last point that it's used, which is technically here. So this is its correct lifetime due to non-lexical scope, but regardless, its lifetime is fully contained within the 'cities' lifetime. So the code compiles. That just goes to show you that the original reference that formed the basis of the 'items' parameter no longer exists after line 14, but we use that as the basis to create a slice, a borrow of some fragment of the original data. By using this as our starting point to get to the original data and take a fragment or portion or slice of that original data source, but then once the function is done, the return value is decoupled from the parameter. But using the lifetime specifier, we have declared that for some generic lifetime 'a that 'items' comes from or that 'items' is derived from, in this case, that concrete lifetime filling in for 'a is the lifetime of 'cities'. We now connect the returned reference to that referent's lifetime, to the original data source's lifetime from which the parameter reference comes from. A little bit of an important nuance, but one that is important to understand as far as understanding how this lifetime syntax works and what the compiler and the borrow checker are going to allow and prohibit. So to summarize, the returned reference here will never become a dangling reference because it will always point to valid data. And that is a slice or some portion of the original referent, which in this example is 'cities'.
