# Invalid Lifetimes II

So let's explore a few more examples of invalid lifetimes or, alternatively, of dangling references. So I've returned back to the code from the previous lesson. I have a 'cities' vector, and then a slice to the first two elements of that vector assigned to 'favorite_ cities'. 'favorite_cities' is a slice, but a slice is a type of reference. Here's another way that I can invalidate the 'cities' variable, thus ending its lifetime and thus making the reference a dangling one. For example, say I reassign 'cities' to a new variable of 'places' like so. The principles of ownership apply, which means 'places' becomes the new owner of the vector on line #8. Therefore, when I am trying to take a reference or a slice of 'cities' on line #9, that 'cities' name no longer exists. It is no longer alive. The lifetime of 'cities' starts here and ends right here. Therefore, I am intrinsically going to create a dangling reference, a reference to data that no longer exists on line #9. This is invalid and the code will fail to compile. Now let's see what happens if I try to drag this line up one like so. So this code is still not going to compile, but for a different reason. So here we are taking a reference. We are taking a slice. And then after that reference is valid, we are trying to then reassign ownership or move ownership from 'cities' to 'places'. The problem is at this point 'favorite_cities' is a reference that is borrowing and thus we are trying to change ownership in the middle of a borrow. Let me expand this right here and show you: "the borrow of 'cities' occurs here". That is when we create the reference. Then we move out of 'cities' here. We move ownership from 'cities' to 'places'. Now by itself that is not a problem. The actual problem really occurs on line #10. And that is because we are trying to use the reference. At this point on line #10, it is a dangling reference because 'favorite_cities' was a reference to the 'cities' name or variable or vector, and that is no longer the owner. The 'cities' lifetime has ended and 'favorite_cities', the reference, its lifetime is now outliving the lifetime of the 'cities' vector. Right? So one way that we can fix this problem is by moving line #10 one line up. And let me explain why that is going to work. Remember, when it comes to the lifetimes of references, Rust now applies non-lexical scope. That means that the lifetime of a reference ends at the last point that it is used. In this scenario, the last time that 'favorite_cities' is used is line #10, so Rust needs to guarantee that there are no dangling references for the entire duration of the 'favorite_cities' reference, and it cannot guarantee that because the referent of 'cities' becomes invalidated on line #9. So line #10 is invalid. I can show you that if I comment out this line, the code now becomes valid, because Rust recognizes now that the last point that the 'favorite_cities' reference is being used is line #8. So because of non-lexical scope, the lifetime of the 'favorite_cities' reference begins and ends on the same line. So the lifetime of 'favorite_cities' concludes after line #8, and that means it is fully within the lifetime of the 'cities' referent, which at this point will last until line #9. So this is the existence of the lifetime of 'cities'. You can see me highlighting it. We can clearly see that line #8 fully lives within that highlighted region of code. In comparison, if line #19 comes back in, that line #10 is outside the confines of that shaded block, it is trying to outlive the lifetime of the referent, of the borrowed data. Now, if I move this line up, the lifetime of 'favorite_cities' is expanded a little bit. The lifetime of 'favorite_cities' now looks like this. So lines #8 and #9. Once again, it is not going to go until the end of the 'main' function scope. That is because of the introduction of non-lexical scopes for the lifetimes of references. So the lifetime of 'favorite_cities' is this region of code, and thus it is completely fine to reassign 'cities' to 'places' on line #10, because the reference to 'cities' is no longer needed after line #9. It basically ends right here, so this becomes totally valid. So the 'cities' lifetime starts here, ends here. 'favorite_cities' lives entirely within it. The reference's lifetime is completely contained within the referent's lifetime, within the original data source's lifetime. And then the lifetime of 'cities' ends right here. The lifetime of 'places' starts right here. And then immediately afterwards, the lifetime of 'places' ends when the 'main' function concludes. There are no dangling references here, so this is a valid program that does compile.
