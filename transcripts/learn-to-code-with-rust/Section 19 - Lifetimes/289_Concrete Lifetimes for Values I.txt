# Concrete Lifetimes for Values I

Welcome to the next section of the course, which is all about lifetimes. This is one of Rust's most difficult features, so I'll do my best to introduce the topic step by step. One reason why it's challenging to teach lifetimes is because the term often refers to different ideas. For now, I'd like us to think about a lifetime just like we think about it in human terms. A lifetime describes how long something is alive, which means functional, valid, useful. The same principle applies to any value in Rust. The lifetime of a value refers to how long it is valid within the code. Valid meaning capable of being utilized, so lifetime is not something that we measure in minutes or seconds. It's more about the areas of code or regions of code where a value is alive, which once again means valid or capable of being used. Here's another slightly more technical definition of a lifetime. A value's lifetime is the time during which a value exists at a particular memory address. We can say that a value is alive for that section of code corresponding to its occupation of that single memory address, so the lifetime of a value starts when it is moved into a location in memory, and the lifetime of a value ends when it is dropped or moved from that location, when the memory is cleared. Okay. Lifetimes are often connected to the idea of scope, but they do not necessarily have to be. It's always easier to begin by thinking about scope though, so let's start there. As a reminder, a scope is defined as the region of code between a pair of opening and closing curly braces. Scope is an easier concept to reason about because we can see it visually in our source code. So in our 'main' function, for example, we create a block with this pair of curly braces and that creates a scope, right? The contents of the 'main' function live within that scope, that region of code. So if I declare a variable within the 'main' function, let's just call it 'a' and assign it a value of 1. We can say that the lifetime of the 'a' variable starts right here. We can technically say line two, but I generally don't like to think about line number. I like to think more about the logical area of the code. So for example, if we had a whole bunch of lines before the existence of 'a' and a whole bunch of lines after the existence of 'a'. The importance is not in line two or line seven. It's the more obvious takeaway that 'a' starts being alive right here, where it is declared, this is where its lifetime begins. This is the point where it is valid, where the name of 'a' has some legitimacy within the program. 'a' does not exist here. Its lifetime starts to exist right here at its declaration, and then its lifetime ends when the main function ends. Rust will reach the end of the function scope, which means the 'a' variable will go out of scope and thus its lifetime will end. It will no longer be alive. 'a' has no significance after this closing curly brace. So this right here we can think of as the lifetime of 'a'. Okay, so let me introduce a bit more complexity into the picture. When we are describing the lifetime of this a variable, we often use the term concrete lifetime. The word concrete means defined, literal, specific. It is the opposite of abstract or generic, which means more hypothetical or existing as a premise rather than as a realized thing. So what I mean by concrete is the lifetime of the 'a' variable is clearly defined. We can see it, we can understand it, we can reason about it, and Rust can understand it. It is the exact same lifetime every time the program executes. It's just this region of code. It's not a hypothetical lifetime that can change. It is a concrete region of code where the 'a' name is valid, where it is alive. So the Rust compiler understands this concrete lifetime, this region of time or region of code where 'a' is valid. And the reason it is able to do so is because the 'a' variable is contained within a single function. So it's very easy to follow the lifetime from its creation to its end, which is also the end of the scope. Rust can clearly see where the a variable comes into existence, when its life begins, and when its life or lifetime ends, right? Now, this is not always going to be the case when we're going to start to cut across multiple functions. When we start passing around data from one function to another, that's where lifetimes are really going to be increasing in complexity. That's where most of the confusion lies, where we start going into separate function scopes and seeing how lifetimes apply there. So a lifetime at the end of the day is a construct that exists strictly for the compiler. It has no runtime representation. It doesn't affect the logic of your program when it's running. Lifetime is just a compiler recognition of the aliveness, so to speak, of any value. When does the value become alive? When does the 'a' variable become legitimate? When is it useful? It basically starts from its declaration, the beginning of its lifetime, all the way to the end of its lifetime, which in this case is the end of the function scope. All right. So some of these ideas are probably familiar, but we're going to increase the complexity of this concept of lifetimes as we progress through the next lessons in the section. So lots of fun complexity up ahead. And with that I will see you in the next lesson.
