One of the common use cases for a box smart pointer is a recursive data structure. Now, we previously talked about recursion in the course. Recursion is when a function calls itself. As you might guess, a recursive data structure is one in which you store the structure itself. So you can imagine a struct that has a field that is the exact same struct, and this can continue multiple levels or layers down. A struct can contain a field that is itself, and then that nested struct can contain a field which is itself all the way, potentially until infinity. So in recursive functions, we solve that infinite recursion problem of a function continually calling itself forever with what's called the base case, which is a condition that forces the termination of recursion. Now, when dealing with recursive data structure, a box effectively solves that exact same problem. It allows the compiler to not have to worry about a data structure effectively recursing forever and taking up infinite memory. Right. A box will very elegantly allow us to solve this problem, because the box's entry on the stack is always going to be of a fixed size, even if the heap data is subject to variance. So perhaps the most common recursive data structure is the linked list, which the rust book calls a cons list. Let's take a look at what it looks like. So a linked list is a data structure that consists of a linear collection of connected nodes. And the word node in this situation just means an individual unit of data. Each node stores a value as well as a link or connection to the next node in line. So you can think of the link as just an arrow pointing to the next node. Note there's different ways to model or represent this linked list idea in code, as we'll come to see in the editor. So unlike arrays or vectors, the nodes within a linked list are not going to be stored contiguously in memory. And that word contiguously just means right next to each other. So rather these nodes can be spread out across many different parts of memory, across many different areas of the heap, with each node simply pointing to the next one pointing you to the next address. So the nodes within a linked list are still going to be connected, in the sense that you can go to one and use its arrow, or its pointer, or its link to get to the next node in line, the next node in the list. But they're not going to be connected necessarily in the memory of the computer, in the actual hardware, just connected in the sense of tying into one each other within the broader linked list. So I want to provide a real world example of something that we could model as a linked list. Just to give you a more concrete idea of what this could be used to build. So imagine that we were building a music playlist. Each playlist entry consists of a song with information about itself, maybe the artist or the name of the song, the year, the genre, etc. so we can think of the song as the node here, the individual unit of data. And in addition to these songs entry, each song in the playlist could also hold the link to the next song within the playlist. The thing that's supposed to play after it, right? There is a connection to the next node, to the next song, to the next piece of data. Inline song one could direct you to song two, and song two could direct you or link you to song three. Each node can inform you about the next node so that you can navigate to it. So maybe one track could complete playing and then you could follow its link to the next song, i.e. the next node, and then play that song and you can repeat that logic navigating across the songs, or equivalently, navigating across the nodes in the linked list until you get to the end, which is the song that doesn't have any more links to the next song, and that tells you you've reached the end of the linked list. All right. So the question, as always, is how do we model an idea like this in rust?
