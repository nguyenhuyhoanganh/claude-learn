# Vector Capacity Behind the Scenes

In this lesson, I want to show you an inside look on how vector capacity works behind the scenes. Every vector has a capacity. The capacity is the maximum number of elements that the vector can contain. Every time we add an element to the vector, we get closer to that maximum capacity, and there is the possibility that we eventually need more space than the capacity has room for. When that happens, Rust is going to find a new, larger location on the heap that has increased capacity. It's going to move all of the previous elements over there and then add the new one as well. The old memory is going to be deallocated because it no longer holds the data it used to. Now this all happens behind the scenes, so we don't have to worry about it, but it's important to understand that this is the reason why Rust wants to prevent multiple mutable references existing at the same time, and that is because some modification to the vector, such as adding an element, may actually move all of the elements in memory to a different position. And I want to show you that example in this lesson. So what we're going to do is we're going to use a special constructor function that is available on the 'Vec' type. And it is called 'with_capacity'. So this function returns a new empty vector. But we can specify the capacity. In other words, the number of elements that this vector can store. So I'm going to initialize it with a capacity of 4. In the real world this function can be helpful if we know the exact number of elements our vector will contain, but for example, cannot populate it until runtime, right? So at this point, Rust does not have to move anything to a new heap location, because the existing heap location from the beginning had room for 4, right? And generally when you have to move to a larger heap location, that requires some amount of effort, which is where the potential slowdown in your program occurs. When I use the word slowdown, I don't mean that it's going to be anything visible or noticeable in your program. I'm just saying that's the point where the computer has to expend extra memory and effort because it needs to find a larger, greater space with more capacity and then move all of the old elements over. So here is where the danger comes with mutable references. If we have a mutable reference that, for example, calls the 'push' method like it does here, this in fact expects a mutable reference that has the capacity to move data from an old memory location to the new memory location. The one with a capacity of 8. But if we have any other reference, mutable or immutable, that is still pointing to the old memory location that had a capacity of 4, then it will have a dangling reference. It will be a reference or an address to a place in memory where the data is no longer living. A place where the data is absent, right? Because it's moved to the new place with a capacity of 8. And that is why Rust prohibits more than one mutable reference to a value at a time. Because as soon as there's the potential for mutation, there is the potential that mutation will move memory around. And thus anything that was dependent on the old memory may now be out of date. And that, of course, will lead to technical bugs and undesirable behavior in your program. So hopefully you enjoyed this behind the scenes look. This is how vector capacity works behind the scenes.
