As a heap allocated data type, a vector follows the same rules of ownership that we've previously explored throughout the course. For example, if I take my 'pizza_toppings' variable and assign it to a new variable, say 'delicious_toppings'. Similarly, when we borrow a reference to a vector, the borrow checker will enforce the standard borrowing rules. Recall, for example, that if we have a mutable reference to a value, we cannot have any other reference, whether it be mutable or immutable. At the same time, you may also recall that we can have any number of immutable references at the same time. So with mutable, it is one mutable, and then you're done. With immutable, it's any number. Multiple immutable references are safe because each borrow knows that the data that it is referencing is guaranteed to not change. For that same exact reason, we cannot have multiple mutable references because one of them might reference data that will be changed by the other mutable reference. It is unstable and Rust is all about security and safety. Now, whenever we insert or remove an element anywhere in the vector, behind the scenes that may require new memory allocation on the heap. Sometimes Rust will move or copy the elements to a new area in the heap. It's is sort of equivalent to moving goods in a warehouse. Perhaps your vector will reach its full capacity and Rust will move it to a new area of the heap where it can store, say, twice as much capacity. This is not necessarily going to happen on every mutation, but it will happen from time to time on some operations. So in that scenario, a reference to an element could find itself accidentally pointing to deallocated memory. Rust has to be extra careful to ensure that there are no invalid references throughout the program, that there are no references pointing to a memory address where the value is no longer present.
