# Section Review

Congratulations on reaching the end of another course section. As always, let's take a few moments to review everything that we learned. This section focused on vectors. A vector is a collection type that stores homogeneous elements in order. Homogeneous means of the same data type. So a vector is very similar to an array, but the key difference is that a vector can grow and shrink in size. It can add elements and remove elements, and the way that that is handled is the vector is stored on the heap because that area has the open space, so to speak, to reallocate and to move data around. So each element in the vector is assigned an index position and that reflects its place in line its order. The index, as always, starts counting from 0. So the first vector element is assigned index 0. The second is assigned index 1, and so on. So Rust's official vector type is 'Vec' with a capital V, and that type has one generic which represents the type of the stored elements. So you can create a vector of many different types. For any given vector, the types must be the same, but you can have a vector of booleans, then a vector of integers, than a vector of custom structs, so that generic represents the type of the internal elements. It's a perfect use case for a generic because you keep the external container type, the vector collection type, while still enabling the flexibility for it to store any other type within it. So how do we create a vector? The first option is the 'new' constructor function that is found within the 'Vec' namespace. So we write the type, then the double colon, then the 'new' function and invoke it. It's the exact same standard as with 'String::new' for example, and that function requires a manual type annotation, which you can provide either with the variable definition or with the turbofish operator. And the reason the compiler needs that is because it doesn't know by default the kind of data that an empty vector will be storing. How could it possibly know the type? Now, one thing that we perhaps saw or didn't see is that if you write any code that inserts an element into the vector, then the compiler can infer the generic type. So if you create an empty vector, that code will not compile. But if you create an empty vector and then, for example, call the 'push' method and add something. Well, now the compiler can figure out the type of the generic, the type of the data that the vector is storing, and then the code will compile. As an alternative, we have the 'vec!' macro. That is all lowercase and, as all macros, it ends with the exclamation mark. Then you put the square brackets, not parentheses, but square brackets. And in there you can pre-populate your vector, separating all your elements with commas and then spaces for readability. Okay, so once you have your vector, you have this collection type that can grow and shrink. So here are some very common methods for doing those mutation operations. The 'push' method appends an element to the end of the vector, so it adds it to the end. The 'insert' method allows you to add an element, but add a specific index position, so that allows you to add an element to the beginning, which is called prepending. Or you can 'insert' an element right in the middle of the vector. You provide the index position to the method and then the actual value to insert inside. We also have the 'pop' method, which attempts to remove the last element from the vector, and it returns an Option enum, and that Option enum may have a 'Some' variant or a 'None' variant. The 'Some' variant will store the last element that was just removed, and it will store a 'None' variant if there was no removal because say you have an empty vector, right? That's why the 'pop' method doesn't return the value itself. That's not guaranteed. It returns an Option enum. The 'remove' method removes an element by an index position, and this one is a little bit different. It actually gives you back the element. It does not return back an Option, and this one panics at runtime if the index is invalid, meaning it doesn't actually exist. All right, so we can both read and write vector elements. So for reading we use square brackets. And then we can extract a vector element by its index position. The familiar rules of ownership apply. So if a type implements the Copy trait and you index into a vector and assign it to a variable, the full value will be copied over and there is no risk. However, if a type does not implement the Copy trait, for example, a String or one of your custom structs by default. In that case, ownership has the potential to move out of the vector to the new owner of the variable, and the compiler will generally prohibit that, because then it leaves the vector in this weird spot where it may have ownership over some of its elements, but lose another one of its elements to an external owner. And the general Rust standard is that a collection type or a composite type should be the owner of all of its nested data, and vectors are no exception. So if the type cannot be copied because it does not implement the Copy trait, rather than moving ownership, you want to use the borrow operator, the ampersand ( & ), to create a borrow right? That doesn't take ownership away. It just takes the memory address of the value inside the vector so that the vector retains ownership. There's also the 'get' method for reading. That accepts an index position, and it returns an Option enum once again containing either a 'Some' variant or a 'None' variant. The 'Some' variant will store a reference to the value, while the 'None' variant represents the idea that the index was invalid, right? You can also borrow a slice. As a reminder, a slice is a subcategory of a reference. It represents a reference to a fragment or portion of a collection type, literally like a slice of something. Right. So we provide the ampersand, the borrow operator ( & ), then the value, then square brackets, and then the range representing the lower bound, and then the upper bound that we want to extract to. Once again with the dot dot syntax ( .. ), the upper bound is exclusive, which means we're going to pull up to that index position, but not actually include the element at that position. Finally, we can write new vector elements or replace existing vector elements. So for example, to overwrite, we use square brackets to target an index position. That is the exact same syntax as reading. But this time around we provide an equal sign. And then the new value to replace the original one with on the right hand side of the equal sign. Once again, the familiar rules about references continue to apply. So for example, Rust will permit one mutable reference to the vector at a time, and that is to prevent an unfortunate situation where you have multiple references and both may attempt to overwrite data at the same time, or one may overwrite data while the other one does not expect it to change or expect its location in memory to change. So basically one mutable reference at a time. Once you have a mutable reference in your code, the compiler will prohibit any other type of reference from existing at the same time in your program. No coexistence. Once the existing mutable reference is no longer used in the code, then you can declare a new mutable reference. But they cannot coexist. They cannot be alive at the same time. As far as immutable references, there is no risk there because none of them can modify the data and thus cannot move it to to a different location in memory, and thus Rust permits any number of immutable references to the vector or to any owned value at a time.
