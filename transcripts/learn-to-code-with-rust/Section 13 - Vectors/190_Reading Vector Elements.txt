# Reading Vector Elements

In this lesson, we'll learn how we can read one or more of a vector's elements. Just like with an array, we can access a vector element by its index position, by its order in line. We can either access the element by value, or we can borrow a reference to the element with the borrow operator, the ampersand symbol ( & ). And to make things even more complicated, when we borrow or when we access a value, the way that that operates will depend on the type of data that is stored in the vector, and whether or not the type implements the Copy trait. So let's take a look at all of the variations in this lesson. I have my vector of 'pizza_diameters' from the previous lesson. This is a vector of integers which do implement the Copy trait. They live on the stack and it is easy to make copies of them. Let's also declare a vector of heap allocated Strings. So I'll declare three variables here. I'm going to call them 'pepperoni', and I'll assign this to a String on the heap. And I'll provide a starting value of "Pepperoni". And I'll do the same thing for a 'mushroom' variable. And then I'll do the same thing for a 'sausage' variable. And I'm going to place these three Strings within a vector on the very next line. So here I'll declare a new variable called 'pizza_toppings'. I'll provide my vec! macro. And then within my square brackets, I'll populate 'pepperoni', 'mushroom' and 'sausage'. So this will be a vector of heap allocated Strings. Now when we declare a String variable inside the vector, what happens is that ownership moves from the previous owner, the variable, into the vector itself. The same rules will apply to any kind of heap data, not just Strings. A vector, just like any container in Rust, will own its elements. Therefore, Rust moves ownership from the respective variable names to the vector itself, and then the vector is owned by its owner, which is 'pizza_toppings'. So then the 'pizza_toppings'. variable goes out of scope. It cleans up the vector, and the vector is the owner of its internal data, which is the Strings. And it cleans up those Strings on the heap as well. And to prove this to you, I can show you that after we move our variables into the vector and move the Strings to be more specific, I cannot simply print out something like 'pepperoni' or any one of my other variables because it has been moved. You can see we're trying to borrow for the println! macro a moved value of 'pepperoni'. So now these three variables on lines 4 through 6 are invalid after line number 7. So let's begin by accessing a value within 'pizza_diameters'. So right here I'll declare a 'value' variable. I'll provide my vector. And just like with an array, I'll provide a pair of square brackets. And then the index position of the element I want to pull out. Let's say I'm targeting this number 12 here. it is in the third position, so it has an index of 2. Since the index starts counting from 0. Now if we do this, the result we get will depend on the type of data within the vector. In this case we have an i32 which implements the Copy trait. In that scenario, Rust will create a full copy of that value for the variable. So in this case, if I print out 'value', we're going to see the number 12. But more importantly than that, we have created a copy of the 12 integer from the 'pizza_diameters' vector. So 'pizza_diameters' remains the owner of these 4 integers. And when we access it like this, we simply create a full copy because the type of an i32 implements the Copy trait. Let's take a look at what happens if we instead replace this with 'pizza_toppings'. Now you'll see the compiler is not going to be happy, and that is because a heap allocated String does not implement the Copy trait. So a move like this would force us to move ownership of one String from out of the vector into its new owner of the 'value' variable. And Rust generally doesn't like that, because that means that the vector is in this weird state of partial ownership, where it owns the 'pepperoni' String and the 'mushroom' String, but has lost ownership over the 'sausage' String. So in this scenario, the code will not compile. We're going to see cannot move out of the index of the vector. Move will occur because the value has type String which does not implement the Copy trait. So of course, in order to be able to access some heap allocated data that does not implement the Copy trait, we instead create a reference. So I'm going to change this variable to 'reference'. And we provide the exact same syntax here on the right. The name of the vector plus the square brackets. But we provide the borrow operator ( & ) so that we create a reference. We create a memory address where we store the memory address of the String at index position two. This "Sausage" string. But we don't actually create a copy of the String and the 'pizza_toppings' vector maintains full ownership over the original data. So if I run this, we are going to see "Sausage". But keep in mind that the 'reference' variable is not a String, it is a reference to a String. It is a ref String ( &String ). And when I output the reference with my println!, Rust will dereference the memory address that is being stored to get to the original "Sausage" String. By the way, we can actually borrow values that are copied. So for example, I can absolutely provide 'pizza_diameters' here and this code will work as well. This is a little bit less common because integers are so cheap to copy that it's generally easier and safer to just create a full copy each time rather than borrowing a reference to this integer value, but the same rules apply in the scenario because 'pizza_diameters' never loses ownership over its internal data, the numbers within the vector. The executable program will panic at runtime if we access an index that does not exist within the vector, and this is true whether we access it directly or whether we try to borrow a reference. We cannot borrow something that does not exist, and we cannot make a copy of or take ownership of something that does not exist either. So for example, here, I'll change this back to 'value'. It's interesting because the compiler can identify this error if we are working with an array, and that is because the compiler knows that the array length is fixed and it will always stay the same. The reason it cannot make the same guarantee for a vector is because a vector has the ability to grow or shrink over the size of this program. So it is possible that there could be some lines of code here. For example, line #8 that expands the 'pizza_diameters' vector to have 200 elements. And if it does, then line #9 would be valid. With an array, the compiler has the guarantee of a consistent length. With a vector, there is no guarantee of a consistent vector length, so rust cannot guarantee that index position 100 doesn't exist. We talked about borrowing references to elements within the vector. Another final thing that you can do with a vector, just like with an array, is borrow a slice.
