# The RefCell Type

So now that we've covered cell, let's move on to the complementary RefCell smart pointer. The reason we choose one type over another comes down to what we are protecting access to. The cell type works great for values that implement the copy trait, like integers and booleans. However, other types like structs or strings or vectors, heap types in other words, those can be large and expensive to copy. When we are working with heap data, it is common to borrow a reference to read those values and a mutable reference to write to them. It's often cheaper than making a full copy of the original value. We've seen this idea play out many times throughout the course. So the same principle is going to apply to the interior mutability pattern. How do we borrow a mutable reference to a portion of an immutable value so that we can modify it without making a full copy? The RefCell type from the Rust standard library implements the interior mutability pattern, but using mutable references. The RefCell type maintains ownership over its data, but it provides methods to borrow a mutable reference to the internal state, even though the larger type is declared as immutable. So the cell type from the previous lesson gets and sets values on an immutable value using copies, so no references are needed. In comparison, this new RefCell type gets and sets values by using mutable references on the immutable value. So this pattern, once again, breaks the standard conventions of Rust. Rust generally favors single ownership and the declaration of either a fully mutable or a fully immutable value. So these ideas that we are covering are almost like cheat codes that escape out of the traditional restrictions of Rust if you need them. Now there's one important note I want to make here. Rust is going to enforce the borrowing rules for this new RefCell type at runtime. In other words, when the program actually executes, not at compile time. So in other words, the program may compile just fine, but it may still panic at runtime, it may still run into an error if we break the rules of references. We are choosing to opt into this risk when we choose the RefCell smart pointer. We are explicitly choosing to opt out of the compile time checks. For example, the check of having only one mutable reference at a time. And so the burden falls on us, the developer, to make sure that we are honoring Rust's borrowing rules within our code because the compiler will no longer catch us. I'm going to show you that example in a few minutes from now. The acceptance of this risk may be necessary because the Rust compiler can sometimes be too strict in the sense that it can reject a program that is actually valid from a memory perspective. So to summarize, the Rust book states the RefCell type is useful when you are sure that your code follows the borrowing rules, but the compiler is unable to understand and guarantee that. Because the RefCell type allows mutable borrows checked at runtime rather than at compile time, you gain the permission of being able to mutate the value inside the RefCell even when the RefCell itself is immutable.
