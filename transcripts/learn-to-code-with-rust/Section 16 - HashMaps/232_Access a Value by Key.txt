# Access a Value by Key

In this lesson, we'll learn two ways that we can access a value by its key. The first option is to use a pair of square brackets that contains the key. So for example here, I'll declare a 'value' variable on the right hand side. I'll provide my 'coffee_pairings' hash map from the previous lesson. Then a pair of square brackets, and then the key that I want to extract. In this case, our key is a string slice. Say I target "Flat White". And if I print out the value of 'value' below, we're going to get the corresponding value for the key of "Flat White". And that is going to be "Almond Milk". Now this approach is fine, but unfortunately if the key does not exist, this will cause a panic at runtime. So for example, if I search for a non-existent key like "Cappuccino", we're going to get a runtime error. You can see right here "no entry found for" that specific key. So it's always, Rust has other approaches that are designed to be a little bit more safe. One option, an alternative, is a method called 'get. So here what I'm going to do is call a method called 'get' and pass in similarly the key whose value I want to extract. Now notice the difference here. Rust is going to return an Option. Remember an Option enum has two variants: 'Some' and 'None'. The 'Some' variant's associated data in this case is going to be a reference to the value if the given key exists. Now, the reason that that Option is always going to store a reference is because it's going to avoid accidentally taking ownership over the value that you are extracting. Imagine, for example, that we had hash maps of regular heap Strings rather than string slices. If we were to extract a value and then stuff it into the Option in the 'Some' variant, that would unfortunately move ownership out of the hash map for a value that is still technically inside it. So just like when we tried to access things inside a vector or an array. Rust doesn't want to give you partial ownership, so it wants to make sure in this scenario that the 'coffee_pairings' hash map maintains full ownership over its contents. Therefore, the 'get' method will always return a reference to the value. In this case, our value is a string slice, which is already technically a reference to that section of the executable binary where that hard coded text is being stored. That's why we see this interesting syntax of a reference to a string slice, which is almost like a reference to a reference. Right. And on top of that, it is an Option that is wrapping all of that in the 'Some' variant. That's why we're not simply able to output value below, because it does not implement the Display trait. So we have an Option. And one really cool method that we may not have covered before is called 'copied'. If you look at the IntelliSense on the right, what this method does is it converts an Option storing a reference to some type T to an Option storing that actual type T by making a copy of the actual content, of the actual stored content that that reference is pointing to. Now in this case we have a reference to T, which itself is a reference, a string slice. So what this will do and you can pay attention to the the type of value right here, right now we have a reference to a reference. If I change this to 'copied' now we're going to get an Option storing an actual string slice representing the actual value. Now it's still wrapped in an Option, so if you want to extract it from the 'Some' variant, assuming you get that, you can call a method like 'unwrap' or 'expect'. Another fun option is 'unwrap_or'. And remember this method takes a value representing the fallback to fall back on. And this is a good idea because if you have a value for a key, you're going to pull it out of the Option. Otherwise, you can provide a reasonable fallback. So for example here I can say "Unknown" or "Unknown Milk" ,whatever I want to provide in case of emergency. So now we can output 'value' because we finally are going to pull out some string slice from my original Option. And in this scenario "Cappuccino", the key does not exist. So we're going to fall back to "Unknown Milk". But the key takeaway here is we do not have the runtime panic that we saw with square brackets. It's a little bit more verbose, but it allows us to avoid any kind of issues when the program runs. And then of course, if we provide a key that does exist, now we're just going to get the corresponding value of "Almod Milk". We're going to get that string slice. But the 'get' method returns a reference to that string slice. Then we make a copy of that string slice, basically making a copy of the reference to the original place in the binary. And then we have this fallback which we are not going to need in this circumstance. And that value is going to be the actual original value of "Almond Milk". So as always, a lot of this can get pretty verbose and challenging. But the good news is all of these things exist because rust wants to keep us safe, wants to make sure that we don't accidentally take ownership, wants to make sure that we account for the scenario that a key does not exist, and wants to make sure that we account for the scenario that we can fall back to something if a value cannot be extracted. So a lot of these things, even though they add more code to the program, do really help us write safer code. All right. So that is two ways that we can extract a value from a hash map using its key.
