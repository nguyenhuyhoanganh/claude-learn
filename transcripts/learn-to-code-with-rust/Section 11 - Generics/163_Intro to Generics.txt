# Intro to Generics

Welcome to the next section of the course, which is all about generics. We briefly introduced this topic way back, but now let's dive into it with much greater depth. A generic is a type argument. In other words, a generic is an abstract placeholder type that stands in for a future concrete type. I know that's a mouthful, so let's talk through it step by step. Let's consider functions and parameters. A function's parameter is a name or a placeholder for an eventual value. The argument in this example function called 'add_5', we have a 'value' parameter. We don't know what the argument or arguments will be for the 'value' parameter. 'value' is just the name that we assign to an expected input. Parameters are powerful because of their flexibility. We can write names for future inputs and write procedural code that utilizes those inputs without knowing all of the future concrete values that will be passed in. This function is made more powerful because it's flexible. It supports any future i32 value. A generic is a very similar idea, but the generic is a placeholder for a type, not a value. A generic is like a parameter, but for a type like i32 or String or bool. In the dictionary, the word "generic" means not specific, and that's actually very fitting. The reason that Rust calls it a generic type is because it's not a specific type yet. It's a placeholder for a future specific type. Let's define the simplest, silliest function that we can that will allow us to introduce the idea of a generic. So I'm going to define a function called 'identity'. It's going to accept one parameter called 'value'. And all that is going to do is return the 'value' parameter as the return value. Very simple example, but it will allow us to demonstrate the point. Of course, the Rust compiler is unhappy with this code because it does not know the type of 'value'. Well, what should the type of 'value' be? Let's say I need this 'identity' function for a current problem at work that involves an i32. So I can define the type of value to be an i32, and then also annotate my return value as an i32 as well. So this fixes my current problem. But one issue is that this function will only work for i32s. Say tomorrow that I need the exact same 'identity' function functionality, but for a Boolean. I want a function that's going to accept a Boolean parameter and return that Boolean value. Well, unfortunately this 'identity' function is required to take an i32, so I cannot reutilize it, so I can try declaring another function. Perhaps I'll call it 'identity_bool'. And now I can again declare a 'value' parameter. This one will be of type 'bool'. It will return a Boolean and that Boolean will be the 'value' parameter. And then just for the sake of consistency, since I'm being more specific here with this function name, maybe I'll update this one to be 'identity_i32'. Well, we still have our original problem. Say that tomorrow I want the same logic, but for a floating point and then the same logic for a custom struct and then an enum. Technically speaking, I may want this function to be able to operate on any type in the world, because it's pretty simple. You just accepts a parameter and returns it. You can even see in the code for these two functions that the implementation code in each function body is the exact same. These functions are near identical. They perform the exact same logic. The only problem, and the only reason why they're forced to be different is because we're bound by these types, the i32 and the bool. We are constricted and limited because we have hardcoded specific types. That's not necessarily always a problem. Sometimes we know that a function will only accept a given type, and that's what it's made for. That may be the only type it needs to be able to work with, but in this scenario it is disadvantageous because we have coupled or connected the 'value' parameter to a concrete type that cannot be any other type. If only there was a way that we could abstract away this type, not make it so specific, but make it more general, more non-specific, more generic. Generic types are going to enable us to solve this problem pretty elegantly. So here's what we're going to do. We're going to declare a function called 'identity'. This will be the function that's going to solve all of our problems. Immediately after the function name we're going to declare a pair of angle brackets. That is the less than ( < ) sign. And then the greater than sign ( > ). All right. Inside these angle brackets, we're going to define a name for a generic type. The name we write within the angle brackets is up to us. You can think of this as a name for a parameter but that parameter represents a type, not a value. The common community convention is to call this generic type 'T', and to write it in a capital letter, like this. 'T' is just short for type, but again, this name is completely up to us. It can be 'Nonsense' if we want it to be. So we're going to call it 'T'. So what this syntax does is it tells Rust: Imagine there's some type called 'T' that you'll know about when the function is invoked. This function is not being invoked yet. So you don't know what type 'T' is. You don't know all the possibilities that type 'T' could be, but 'T' will be a future type. So we have this generic non-specific abstract type that we've called 'T'. Well, now that we have a name of 'T' for that type, we can use it to annotate the parts of our function. We can use this type 'T' to declare the parameter type and the return value type. So here I'll declare my regular parentheses for my parameters and my curly braces for my function body. We're going to accept a 'value' parameter, and I'm going to annotate its type as being of type 'T'. Do we know the concrete type that is going to be 'T' in the future? We do not. We're just saying for some abstract type 'T', for some generic type 'T, that can be a variety of different types in the future that we cannot predict, for some type that we've called 'T', we're going to have a 'value' parameter that will be of that type. And then I'll provide my annotation for the return value type. I'll provide the exact same 'T' for my return value type. So what this is saying is regardless of what type 'T' is the 'value' parameter and the return value must be the same type. We don't know the specific type, but whatever it is, these two are now related. Whatever value's type is going to be, that's the exact same type that the return value of the 'identity' function will be as well. Right. And so now in the body, we can just write our regular code of 'value'. And I want to clarify as well, the reason that we need these angle brackets is to declare that generic type and to give it a name called 'T', because otherwise if we just wrote 'T' by itself, Rust would think that 'T' is a concrete type, like for example, a struct that is literally named 'T', or an enum that is literally named 'T'. In this case, 'T' is not a specific type. 'T' is just a name that is coming from this name that we chose here. So if we wanted to call this 'Nonsense', that's totally fine, but then this would be 'Nonsense' and this would be 'Nonsense' as well. This is the generic name for a future type. 'T' is just the common community convention because it stands for type. So now that we have a wonderful 'identity' function that uses a generic type, we are good to remove this former code. So at this point we've covered everything we need to do within the code editor. But I do want to transition now to Wikipedia to show you some additional information. Remember from the start of the lesson that we talked about the inconvenient part about defining multiple functions that did the same thing but declared different type parameters. We had one 'identity' function with an i32 argument and another one with a bool. And we talked about how generics allow us to solve for that problem in code. Well, as it turns out, when the Rust compiler builds our final executable, what it does is exactly that. Or perhaps the process in reverse. It looks at our generic function, and it looks at all of the invocations of that function. And then it declares its own multiple versions of that function. So for example, for our 'identity' function, if we have an invocation with an i32, a f64, a String, a bool, a 'DeliSandwich', Rust will create a separate function for each one of those types. So in the final executable, there is no actual concept of generics. Rust will use the generics in our code to create the equivalent independent functions. We get all the benefit as developers. Rust takes care of that monotony of basically doing what we manually did at the start of the lesson. So that process of expanding a generic function to the multiple equivalent functions with specific type declarations based on the invocations, based on the uses of them, is called monomorphization. Pretty complex computer science term. You can see here on the official Wikipedia page, it says: "In Rust, monomorphization is a compile time process where polymorphic functions are replaced by many monomorphic functions for each unique instantiation". Kind of complex terminology here. But that's basically what it's doing. So you can see here this example is very similar to our own. There is an 'id' function that is equivalent to our 'identity' function. It accepts a generic 'T' It declares the parameter to be of type 'T', the return value to be of type 'T', and then returns the value, without the 'return' keyword in our case. And here in the main function, there is an invocation with an integer and then with a string slice. So after monomorphization, this becomes equivalent to two separate functions, one for an integer and one for a string slice. And if we had three other types or values of three other types being used with specific invocations of this 'id' function, Rust would create the equivalent function declaration for the final executable. Basically, Rust takes care of that boring heavy lifting and writes code that is very similar to the manual code that we wrote ourselves at the beginning of the lesson. But with generics, we don't have to write that code ourselves. We gain the benefit of even more flexible functions, more versatile functions that can deal with a greater variety of types. Right. We are not bound or limited or constricted to having to declare only one type. We can use a variety of different types and have the exact same logic within the function body.
