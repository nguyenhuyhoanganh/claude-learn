Congratulations on reaching the end of another course section. As always, let's take a few moments to review everything that we learned. This section focused on generics. A generic is an argument for a type. It's a type argument. In other words, it's a placeholder type, an unrealized type that will be a placeholder for a future concrete type, or perhaps multiple future concrete types. So I like to say that a generic is to a type what a parameter is to an argument. It's a stand-in that can play the role for a future value without having to define it explicitly. Concretely. Generics enable reusability by not coupling any of these constructs like a function or struct or enum, to a single specific hard coded type, so we can declare a type using a generic. And now we have a lot of flexibility in future types utilizing it and substituting for that generic placeholder. So what's the syntax look like? We declare a generic with a pair of angle brackets. That's the less than sign and the greater than sign (>) and some name. Usually, we use the capital letter 'T' if there's only one generic type. If not that, we usually have pretty short names for our generic types, but it's completely up to the developer. If we have multiple generics, we separate them with a comma and a space. Also important to note that multiple generics enable multiple future types to substitute for both of those generics, but multiple generics do not mandate that the future types must be different. Rather, they enable the future types to be different. So here are a couple of use cases of where we might use generics. So we have this type 'T' and we use it wherever we want this type 'T' to play the role of some future type. For example, in a function definition, 'T' can represent the type of the parameters and or the return value. We are not coupling or hardcoding an exact type like an i32 or a bool. We are defining some generic type 'T'. The word generic literally means not specific. That's where the name comes from. It's some non-specific type 'T', but now, because we have a name for that non-specific placeholder, we can use it to define the associations. For example, if a parameter has the same type 'T' as the return value of type 'T', then the compiler can validate that the parameter and the return value be of the same type at the point of invocation, even with varying types substituting in for that generic type 'T'. Similarly, in a struct definition, 'T' can represent the type of one or more fields. Now you can validate that multiple fields are of the same type, but have the exact type vary at the moment of struct instantiation. In an enum definition, 'T' can represent the type of the associated data belonging to some variant, and there's many more use cases beyond that. Finally, we talked about how we define methods within 'impl' blocks for types that use generics. So the generic type, say 'T', is intrinsically coupled to the definition of a type. In other words, a struct with a generic type 'T', its type definition from the compiler's perspective includes that generic. We can't separate ourselves from that generic. Thus, the 'impl' keyword requires that we provide a concrete type or a generic type for that main type 'T'. Now we can hard code a specific type like an i32 in that 'impl' declaration, which will allow us to declare methods for only that specific type. So if we declare i32, those methods will be declared for situations where the type 'T' is of type i32. Usually what you want is the ability to define methods for any type 'T', and for that we use this special syntax where we declare our own generic, 'T' in this example, after the 'impl' keyword, so that we can reuse that name 'T' after the declaration of some type. Right. The reason we do that is because if we did not do that, then Rust would look for a concrete type 'T' within those angle brackets after 'SomeType'. So it starts to think that 'T' is an actual name within your program, such as the name of a struct or enum that is playing the role of the original generic type 'T'. That's not what we usually want. We want: "For any type 'T', please declare these methods within the 'impl' block", and that's why we use that syntax where we need a generic type 'T' declared after the 'impl' keyword, so that Rust can understand that type 'T' is the type 'T' that we are declaring these methods for on some type. That's probably one of the most confusing parts of this section, but hopefully the benefit there makes sense.
