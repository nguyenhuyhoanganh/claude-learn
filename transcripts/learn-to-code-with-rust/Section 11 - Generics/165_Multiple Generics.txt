# Multiple Generics

In this lesson, let's explore a few variations on generics. First up, we are welcome to combine a generic type and a concrete type in our function parameter declarations. For example, above main, I'll declare a function called 'make_tuple' and this function will accept two parameters. Let's call them 'first' and 'second' for now, and all it's going to do is return a tuple consisting of 'first' and 'second'. So let's declare a generic type 'T' in angle brackets, as always right after the function name right here. And I will declare the type of the first parameter to be the generic type 'T', which enables flexibility in future invocations. But the 'second' parameter I can declare to be a hard coded type. Let's pick an arbitrary type of an i32. And then I also need to provide my return value. So here I'll provide my arrow syntax and provide a tuple return value that will store an element of 'T' in the first position and then an element of type i32 in the second position, and that should do it. So here in main, I can show you a sample invocation of 'make_tuple' and pass in whatever type I want for 'first', maybe a string slice like "hello", and I am bound to have a second parameter of type i32. So here the compiler will hold me responsible. So if I pass in "world" right here, that is going to be a violation because we do not match the expected type here. In fact, let me add a semicolon here so we can see the exact error right here: "expected in i32, found a string slice". And if I bring this back to an integer like 5, that should work. Ok. We are also welcome to reuse the same generic type for multiple parameters. For example, I can update the 'second' parameter here to be of type 'T' as well. That will require me to update my return value here as well. So now I will return a tuple of two elements, both of which will be of type 'T'. It's important to note that with this syntax we are adding an extra constraint. We are mandating that the 'first' and 'second' parameters be of the same type. It's a generic type, so each invocation of the 'make_tuple' function can choose a different type for type 'T', but each invocation must provide an identical type for the 'first' and 'second' parameters. So once again we're going to have a violation right here. Because Rust first sees a string slice and thinks that the type of 'T' is a string slice. Therefore, the type of the 'second' parameter must also be a string slice, and instead it's getting an integer so it's not happy. And if I were to reverse the order here, Rust now sees the reverse. It sees a 'first' parameter value of an i32. So it assumes that type 'T' will be played by an i32 and says if 'T' is an i32 and the 'second' parameter must be of type 'T', then 'second' must be an i32. But instead it's getting a string slice. So we can invoke 'make_tuple' with two integers or two string slices, or two booleans. Any two values as long as they are of the same type. But we cannot invoke it with a combination of types because that violates this requirement of the generic. This is type 'T', which is a single type that we are requiring for both of the parameters. We can also declare multiple generics within the angle brackets. So let me show you that syntax. We're going to separate our generics with a comma and then a space for readability. So I'm going to add a comma here and a space. And I'll add another generic named 'U'. Once again, the names of the generics are up to us. But a popular community convention is to use sequential alphabetic characters. 'T' is popular for a single generic because it stands for type, and then 'U' is popular as a second name because 'U' comes after 'T' in the English alphabet. But again, that name is totally up to us. So here I'll once again vary up my syntax. My first parameter will stay of type 'T' and my second parameter will be of type 'U', and I'll update my return tuple to similarly hold two elements. The first one of type 'T', the second one of type 'U'. So now you'll notice this code will now compile. So this declaration enables two different types to fill in for our two generics. In this case, an i32 fills in for the generic 'T', and a string slice fills in for generic 'U'. And if we were to reverse these around, the code would continue to compile as well. It's important to note that this syntax is not requiring that 'T' and 'U' be different types, they're simply opening up the possibility for 'T' and 'U' to be different types. Whatever Rust sees in the 'first' parameter, in this case an i32, will fill in for 'T', and whatever Rust sees in the 'second' parameter will fill in for 'U', and then Rust will enforce the constraints that we've placed here with the expected return type of the tuple. I want to show you that if I invoke 'make_tuple' with two values of the same type. For example, here are two i32s in a row. This is also valid. The generic syntax above is declaring two generics, but there is no obligation that they must be different just because we have two generics. We just have two placeholders. Okay, you can think of it like two mad libs, two blank spaces that we are filling in. So when Rust sees this code it says: "Okay, what is the type of 'T'? It's an i32 which I can figure out from the type of the 'first' parameter. What is the type of the generic 'U'? In this scenario, it's going to be an i32. So Rust knows that 'T' and 'U' are both filled in concretely by the i32 type. And then it's going to enforce this constraint that the return tuple must be an i32 followed by an i32. But in this case, it's simply filled in by two different generic types. So once again this syntax is not requiring two different types, but it is opening up the possibility of having two different types. That's where the flexibility comes from. All right. So just to show you a couple more examples, here I am providing let's say Boolean and let's say a float. Totally valid even though there are different types. And here I am providing a Boolean and a Boolean, in which case now true. and 'second', or equivalently generics 'T' and 'U' are both of the same type of 'bool' in this example. And once again, all of these functions are going to compile because the real important thing is Rust is validating the relationships between the generics, the parameters, and the return values. Right. The fact that we have two simply creates the potential for two placeholders, two future concrete types to fill in later at the point of the invocation of the 'make_tuple' function, and they can be of the same type or different types. That's in comparison to the previous syntax we had, where we only had one generic type 'T', and we used that for both parameters. That does create the constraint that both parameters must be of that same type 'T'. So these syntax options you have to be careful with because they do create different constraints and requirements.
