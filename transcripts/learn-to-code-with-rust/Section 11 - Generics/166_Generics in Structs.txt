# Generics in Structs

In the previous lessons, we applied generic types to function parameters and return values, but there are other use cases for generics in Rust. For example, we can add a generic type to something like a struct. For example, let's declare a struct called 'TreasureChest' and this struct will hold two fields. I'll declare a 'captain' field, which will always be a String. And then I want a 'treasure' field, and I want this value to be a bit more flexible. We can have a variety of different treasures in the real world. Right? So how can I make this a dynamic type? Once again, we can utilize generics. After the struct's name, we're going to provide the same angle brackets. And then we'll provide our generic types. So I'll declare one generic type called 'T'. It's the same idea here. That generic type is up to me, and I can name it whatever I want. And then I'll declare the type of the 'treasure' field to be of type 'T'. So what I'm saying here is this: "Hey Rust, imagine there's going to be some future type 'T'. We can't predict all of those options in advance, but a future type called 'T', and that type 'T' is going to be the type of the 'treasure' field." So I don't know at this moment when I declare the struct all of the possibilities of what the 'T' type could be. But that is precisely what gives this definition its flexibility and its versatility. Now, 'treasure' is not hard coded or coupled to a specific type. It has the flexibility to be a variety of different types in the future, including types that we may not even know exist yet, right? 'treasure' could now be a future struct, a custom struct that we haven't even declared yet. So this is more flexible in a sense because it can handle many different future types. So to demonstrate this, let's create some struct instances within main, and we're going to vary up the type of the 'treasure' field. For example, here I can declare a 'gold_chest' and provide my 'TreasureChest' struct. For my 'captain' field, I have mandated that that must be a concrete type. That must be a String, so I can provide a string here like "Firebeard". But I have a bit more flexibility with my 'treasure' field. So let's start off with something like a string slice. I'll declare that in double quotes here and declare a treasure of "Gold". And now I have a valid struct. Notice here, in the inference that we have our struct name 'TreasureChest'. Then, within the angle brackets, we have the concrete type that is filling in for the placeholder of 'T' that we provided here. 'T' is the generic. It's the non-specific type that we do not know in advance. Here the ref str ( &str ), the string slice, is the concrete type that fills in for 'T', and Rust can infer what 'T' is going to be because of the initial value assignment for 'treasure'. This is a string slice, so Rust understands that 'T' must be a string slice. Here's another example with a totally different type for the 'treasure' field. I'll declare a 'silver_chest' and this will be a 'TreasureChest'. Once again, 'captain' has to be a String. So let's do something like "Bloodsail". And then for my 'treasure' field this time around, I'm going to go with a heap allocated String. So 'String::from' and let's say this is a "Silver" chest. Well once again this code is valid. This will compile. We have a 'TreasureChest'. But now the type of the 'T', the concrete type for the generic 'T' is a String, but it gets even more versatile than that. For example, one more time I'll declare a 'TreasureChest' instance. Let's call this our 'special_chest'. And here we'll do a 'TreasureChest' once again with a 'captain' that must be of type String. Let's call it something like "Bootyplunder". And then for 'treasure', that field, I'll do something even more different. Let's do something like an array of string slices so it doesn't even have to be a scalar type like it is here. And here. We can now provide a collection type like an array or perhaps a tuple, right? Or another struct or an enum. It gets really versatile. So here I can have something like "Gold" and "Silver" and "Platinum". We now have a 'TreasureChest' with three string slices. And all of these examples are completely valid, right? You can see right here the code will compile. In fact, very quickly I can add my Debug Implementation here and then print out each one respectively. So here I'll provide my Debug syntax and provide 'gold_chest'. Here, I'll provide 'silver_chest'. And here I'll provide 'special_chest'. And you can see all of the variations. Here is "Gold" as a string slice, "Silver" as a String on the heap, although its visual representation in Debug format is the same. And then here is 'treasure' as an array of string slices. And that's not even scratching the surface of all the possibilities, right? So that's how generics help us out is. They enable this kind of flexibility where we don't need to declare three different 'TreasureChest' struct types, one supporting a string slice or a reference, another with a string, another with a array. We can declare a single data type that contains internally a generic to enable the flexibility, to enable reusable code like this. All right, that's all there is to cover in this lesson.
