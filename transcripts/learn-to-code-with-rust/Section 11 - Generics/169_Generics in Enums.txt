# Generics in Enums

So, as you might have guessed, we can apply generics to various types in Rust. And in this lesson I want to show you an example with an enum. So here I'll declare a new enum called 'Cheesesteak'. And once again the syntax is going to be the exact same. We'll provide our angle brackets and then declare a name for our generic type. And we plan to use our generic type to represent the type of some value within an enum. So here I'll call my generic type 'T'. This name is up to us. And then I'm going to provide my curly braces and my enum variants. So I am not obligated to use my type 'T' in every enum variant. It's up to me. So for example, let's say we'll have a 'Plain' variant that will have no associated data and then I'm also going to have a 'Topping' variant. And this 'Topping' variant will be a tuple variant where we're going to store one piece of associated data with the topping, which is basically what that topping is going to be. And I'm going to make the type of that associated data for the 'Topping' variant to be of type 'T'. All right. Let's take a look at how this is going to work in main. I can practice creating a whole bunch of cheesesteaks. For example, I can start with a 'Cheesesteak' and say that my variant will be 'Topping'. Well, if I need to use the 'Topping' variant, I need to provide a piece of associated data which I can provide within parentheses. This was what we covered in the enums section of the course. So here say I provide a string slice. My topping will be "mushroom". Well, now Rust will infer the type of 'T' to be a string slice, a ref str ( &str ). So, for example, if I assign this to a variable like 'mushroom, you'll see right here the type will be a 'Cheesesteak'. It is the enum. But then we see the concrete type for the generic type 'T'. So the concrete type for 'T' here is a ref str, a string slice ( &str ). Here's another example. I can declare an 'onions' variable. Once again, I'll have a 'Cheesesteak' with a 'Topping', and this time let's provide a heap allocated String so I can either do 'String::from' or, as an alternative, I can take my string literal and invoke the 'to_string' method on that. And that is going to give us a heap allocated String. Notice here that the type of 'T', the concrete type of 'T' for this variable is now the heap allocated String. Here's another example. Let's say I have a 'topping' variable and this one will be another heap allocated String. Let's take "bacon" and call 'to_string' on it. So now I have a String. And on the next line, I'll declare a 'bacon' variable set to a 'Cheesesteak'. And I have to choose one of the variants. Let's do 'Topping'. And this time around my type of 'T' is going to be a reference to a String ( &String ). So I can take a reference to my 'Topping' string on the line above. So this is itself totally different from what is on line #8. The concrete type for 'T' here is not a string slice, it's not a string, it's a reference to a String ( &String ). That's how specific we can get here. All right. Now let's see what happens if we try to use the 'Plain' variant here, which does not have any associated data. So I'll declare a variable called 'plain' and then try to use 'Cheesesteak::Plain'. You'll notice that this code will not compile. And the reason is even though we're using 'Plain' here, this enum is declared with a 'T' generic type. And Rust doesn't know what that type 'T' is going to be, right? It says I don't know. Consider giving 'plain' an explicit type right where the type for type parameter 'T' is specified. Technically speaking, yes, there is no topping associated here, but imagine that this was a mutable enum and we wanted to, or a mutable variable rather, and we wanted to assign it to a new variant. Well, in that scenario, the compiler can't keep you honest. So we have to declare the type 'T' even if we're not utilizing the 'Topping' variant yet. So the way we do that is in this example, we have to explicitly annotate the type. So I'll do a colon, write 'Cheesesteak', which is not enough by itself. Then I'll provide my angle brackets and specify the concrete type to use for the generic type 'T'. And let's say I pick String in this example. So now our code will compile. And let me show you an example of where Rust will hold us accountable if we change to a different variant. Let's say I make this variable mutable with the 'mut' keyword. So I can now reassign the 'plain' variable to another 'Cheesesteak' variant. So say I want the 'plain' variable to now be a new variant of topping. Well, now the kind of topping I provide here must be of type String, because I declare the type of the generic type 'T' to be a concrete String type right here. So if I provide something invalid like a string slice, this is a different type, right? You'll see here "expected String. found a string slice, a ref str". This is a different type compared to the type that we declared here and promised the Rust compiler that we would honor. That's why this declaration is important because it affects future code, and that's why the compiler needs to know what 'T' is going to be. Even if we start out with the 'Plain' variant that doesn't utilize 'T', because there's the potential for this variable to change into a 'Cheesesteak' variant that does require 'T'. Rust needs to know from the beginning, both for memory reasons and to keep us responsible, and to allow the compiler to check for violations, it needs to know what type 'T' will be, because it cannot figure it out from the initial 'Plain' assignment, and thus we declare it here. And then Rust is able to validate our code moving forward. In these examples, we did not need to provide the manual type annotation, because Rust could infer the type of 'T' based on the initial assignment of the value that lives within the 'Topping' variant. Right here, we know we have a string slice because we're using the 'Topping' variant. Rust says 'Topping' has a value of type 'T'. You're giving me this string literal and the type of that is string slice. So I know that 'T' must be string slice for this variable. It cannot do the same thing here, which is why we have to manually annotate the type in this example. So I can fix this by calling the 'to_string' method. And now our code will compile just fine.
