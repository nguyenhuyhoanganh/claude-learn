# Collecting User Input with read_line Method

In this lesson, we'll learn how to collect user input from the command line when we run a Rust program. So now we're going to be able to accept some input from the user, which of course can then influence what the program does or how it runs. So to begin, as a reminder, Rust includes what's called the Standard Library, which is a collection of modules built into the core language that assist with developer productivity. So the standard library is a collection of pre-built tools, things like functions and structs and enums that help with everyday operations. We can technically refer to these names from the top level of our program if we use the full prefix, the full path into the standard library, and the module where a given name is located, but the more common convention is to utilize the 'use' keyword at the top of our file to bring in the specific names that we want to use within the current file, and that allows us to not have to write out the full prefix. Whatever is the last name that we provide to 'use' will be brought into the current file's namespace. So that can be a struct, an enum, a function, or a submodule within the larger module. So at the very top, I'm going to add 'use'. And we're going to start with our standard library which is 'std'. And then inside, I'll use the scope resolution operator ( :: ). Inside, there is a submodule we want called input/output which is abbreviated 'io'. That is short for input/output. And this 'io' submodule includes various functionality for dealing with input and output, in other words, data coming into our program and data leaving our program. The user's entry that we're going to collect when the program runs is data that is coming into our program. That is why the functionality is part of the 'io' input/output submodule. So this 'io' module which I can reference right here now, inside there we're going to have access to a function called 'stdin'. So I can provide again the scope resolution operator ( :: ) and access a nested function within that submodule called 'stdin'. And I'm going to invoke that function. That function is going to return a struct also called 'Stdin' but with a capital 'S'. We don't have to worry about too much about what that struct is doing, but it is that struct that is going to include its own method called 'read_line', and the 'read_line' method is going to read or in other words, gather a line of user input. So we'll be able to ask the user to type out a value. And then when the user presses Enter, that's how Rust knows that the user is done typing. The line has terminated or concluded when the user presses the Enter key and Rust will gather whatever the user has typed. So I'm going to invoke 'read_line' here. And this is where things are going to get a little bit interesting. So what the 'read_line' method accepts, as we can see from the 'buf' parameter there in the IntelliSense, is a mutable reference to a heap String. We need a heap String because we don't or can't predict the content that the user will write, right? It could be one character or five characters or 50 characters. We need the type of string that supports dynamic content, and for that we need the heap allocated capital 'S' String. And what this method expects is a mutable reference to that String, just so it doesn't take ownership over it. We don't want to take ownership away, because it is the original String that the 'read_line' method will write to through the use of the mutable reference. So here's what that looks like. I'll declare a variable here called 'name', and I'll create an empty heap allocated String with the 'new' constructor function. Now another important detail is because I'm going to provide a mutable reference to this String right here, I need the original 'name' variable to be marked as mutable, so that it is capable of changing, even if that change is going to be done through a mutable reference being passed to 'read_line'. It is the 'read_line' method that is actually going to perform the mutative operation. But I need to tell Rust that mutation is allowed by making this mutable. Okay, so here I'm going to pass in not 'name' because that would be passing in the String. Not a reference to the name, because that would be an immutable reference. And there's no way to write or mutate the original String. Rather, I want a mutable reference to my heap allocated String represented by my 'name' variable. Now, by itself, this is going to prompt the user, and it's going to be really confusing because the user is not going to have any kind of direction on what to do. So what we should do is right before I'm just going to use println! to explain to the user what I need from them. So I'm going to say something like: "What is your name?" All right. And that should do it. So let's take a look at how this program runs currently. And then we'll adjust it to improve it a little bit more. So I'm going to run this. You can see right here: "What is your name?" I can type in something like "Boris". Press Enter and the program ends. So we are collecting the user's input but we're not doing anything with it. Well let's now utilize it to give feedback back to the user. Now the actual String that is going to contain the contents that the Terminal or Rust is going to write to is our original 'name' String. So we can actually use 'name' immediately after assuming everything works and say "Hello". And then I'll interpolate the value of 'name', which at this point should have the contents written to it based on what the user has entered. So I will run this again. I'm going to enter "Boris" and we're going to see "Hello Boris". And if I run this again and provide a different name like "Pierce", we're going to get "Hello Pierce". So now we have these beautiful dynamic programs that can react to the user input. Now there's a couple of optimizations we can make with this program. Right now Rust is unhappy because technically speaking, what the 'read_line' method returns is a Result enum variant. Remember, the Result enum represents an operation that can create an error or a success state. You may recall there are two variants. There are the 'Ok' variant, and then there is the 'Err' variant which will hold the error value. Now the 'Ok' variant in the success state of this Result enum is not actually going to hold the user's entry or the String in other words. Rather, it's just going to be an entry of the number of bytes that has been collected. So the length of the user's entry or the number of bytes they have input. Usually that's not particularly helpful information. We have what the user has collected or provided in our 'name' String already. That's what we see right here. Rust is just unhappy because we're not really utilizing the Result, and we're not covering both of the possible variants of the enum. So there's a couple of things we can do here to make Rust a little bit happier. The first is given that we have a Result variant, we can call the 'expect' method here. As a reminder, that is equal to the 'unwrap' method. It's going to try to extract a value. Not that we want to necessarily extract the number of bytes that the user has entered, but in case we failed with collecting the user input, we can at least try to extract the bytes and then provide some helpful error message for the user in case that is unsuccessful. So in case this line of number #6 fails, I can provide an error message like "Failed to collect input from the user". And that's one way that we can deal with that Result enum that we get back. And even better approach is to handle both of the variants, 'Ok' and 'Err', with the 'match' keyword. So what I can do instead is get rid of 'expect'. And then what I'm going to do is use 'match' right here. Remember, 'match' forces us to account for every possible variant of an enum, and an enum is what's going to be returned by the 'read_line' method. So I'll provide my curly braces here, and the compiler will tell us you need to provide an arm for both the 'Ok' variant and the 'Err' variant. So for example, I can say for the 'Ok' variant, if I wanted to extract the associated data here, this value would be the amount of bytes again that we collected. We don't really care about that, but if you want it, it's available in order to indicate to Rust that I do not care about this associated data, and I don't want to give it a name. I can simply use an underscore ( _ ) here instead of providing a name for that associated data. And then I can provide my arrow syntax to specify what to do with this 'match' arm. And that seems like a perfect place to put my println! So if we successfully get the user's input, which will be indicated by the 'Ok' variant of the Result enum, we're going to run this path of logic, this branch of execution. But now the advantage of this approach is I can also target my 'Err' case. And that will provide me with its own separate type of data, the actual error message. I can provide that associated data with a name like 'error' or 'message', whatever you want, and then utilize that name within my operation here so I can println! something here and say "There was an error" and then interpolate the value of error right here. And that is a little bit more of a stable program. It looks like this was 'message'. So that's my mistake here. There we go. So once again let's run this program. And it's going to say "What is your name?" I'm going to write "Boris". And everything is working as expected. Now there's one little gotcha that is in our example. Notice that I enter "Boris" and then I print out "Boris". But then I have this additional line, this empty line being printed as well. So as it turns out, when the user presses Enter, that does terminate the collection of input. But that Enter press also accidentally represents a new line character, a line break, and that is being captured. So in this example, Rust is not just collecting "Boris", it's actually collecting "Boris" with a line break and that is why it's printing "Boris" and the line break immediately afterwards. Then the program concludes and that's where our Terminal picks up. In other words, we have this additional unnecessary character at the end, the line break, and thus it just keeps adding an extra line each time that we ask the user for input. So if we were to keep asking them for various pieces of information, it might be a little bit awkward because there's going to be a random line break interspersed throughout their contents. So one really simple thing that we can do here is I'm going to move this 'name' to being a argument to my println! macro. From the previous lesson, we learned the 'trim' method, and the 'trim' method removes white space from both the beginning and end of a string. And this can be really helpful, not just because it's going to remove the newline character, but also because it's going to remove things like extra spaces that the user added at the end of their input, or an extra space at the beginning. 'trim' is going to remove all of that, and we're going to print that final string slice, which is just going to be the actual content that the user provided. So now notice when I run this file I'm going to get "Boris" and it's going to say "Hello, Boris". And now it's not going to print that extra new line because we have trimmed it in this println! for line number #7. And of course, if you wanted to save that, you would assign 'name.trim()' to its own variable, or perhaps overwrite the original 'name' variable right here, it's up to you. And then you would be able to reuse that cleaned up trimmed string. All right. So that is a quick introduction to using the 'read_line' method. Once again you bring in your 'io' submodule, input/output. If you don't want to use the 'use' keyword, you have to type this out before 'io'. So it would be 'std::io::' etc. It can get pretty verbose, so most people prefer this approach. Within the submodule, we have our 'stdin' function which returns a 'Stdin' struct. We can assign that struct to a variable. There's no need to do so because we really need the 'read_line' method on it. We invoke that immediately and pass in a mutable reference to a heap allocated String. Then, whatever the user provides is what is going to be written to that string. And then since this 'read_line' method returns a Result because it could technically fail, the recommended approach is to handle both of those Result variants, the 'Ok' variant representing a success, a properly collected user entry, and the 'Err' variant representing some kind of failure. So now this program will work regardless of the situation that we encounter. All right. So that is a quick introduction to collecting user input with the 'read_line' method.
