# A Brief Discussion on Enum Memory

So just a quick point on enum memory. We know that an enum can have multiple variants with different types and different amounts of associated data, and that data can in turn require different amounts of memory. So you might be curious, how is Rust going to deal with these potential inconsistencies in the required memory for a given variant? So what Rust is going to do is it's going to choose the enums memory allocation based on what the largest variant requires. For example, a pointer to a String occupies 24 bytes on the stack. The heap itself is going to store the text data, but the stack is going to store a pointer to that heap data, that address, and that address is going to occupy 24 bytes. So for the CreditCard and DebitCard variants, we can say that that means that they would require at least 24 bytes of memory to store the associated String. However, there are two Strings in the PayPal variant, so this enum variant would require at least 48 bytes, 24 bytes per string, right? 24 * 2. So because these two are 24 and this variant would require 48 bytes, Rust will choose the largest memory size: in this case 48. And it's going to choose that because that is what is needed to support all of the variant possibilities. So that way if we declare a variable like 'my_payment_method', and then we reassign it to something that requires more memory, Rust will already have that dedicated memory, let's say 48 bytes from this assignment to support that scenario where we get a new assignment that supports or requires the largest amount of required data, and Rust will not need to reallocate any memory, because from the very first initial assignment, it's going to request that maximum possibility. So we can say that Rust is supporting perhaps what we can call the worst case scenario, which is the largest possible required size for any variant, right? It's important to note that the total size of the enum in memory is not necessarily going to be just the sum of all of the associated values' memory sizes, so that's a good place to start when reasoning about it. But under the hood, Rust also needs to store the actual variant name like PayPal or CreditCard. And sometimes it also performs other optimizations. So that's to say this 'PaymentMethodType' variable is not necessarily going to require exactly 48 bytes just because it has 2 strings, but it's going to allocate at least 48 bytes because that is the variant with the largest memory requirements, right? Day to day, you don't need to worry about whether something is on the stack or the heap. You don't need to worry about the exact memory that it's going to occupy. You don't even need to worry about optimizing for every byte because again, computers are very fast today. But it's just good to know that behind the scenes, Rust cares about all this stuff and is taking all of these additional steps to ensure you have an efficient program on your hands.
