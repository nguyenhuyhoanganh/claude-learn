The word enum comes from the word "enumerate", which means to list off every option one by one. So in technical terms, an enum is a Rust type that represents a set of possible values a set of limited finite values. Each possible value is called a variant. So we begin with the 'enum' keyword followed by its name in PascalCase. That means capitalizing the first letter of every word and then curly braces. Inside that block, we declare our variants, separating each one with a comma and then usually a line break. And those are our limited options belonging to that enum, to that category. By default, our custom enums do not implement the Copy trait. so the regular ownership rules apply. So there's actually different ways that we can declare those variants. And those ways differ in how they're going to store any associated data. Associated data is data or information that belongs to that variant. For example, a tuple variant stores one or more pieces of data based on order or position. It's called a tuple variant because it resembles a tuple. You can almost think of it like a tuple being attached to a specific variant. In that variant definition, within the block, we provide our parentheses and then these sequential types of the data. The beautiful part about a tuple or a tuple variant is that the data can be of different types, so you can bundle together different pieces of information all on one variant. It's also important to know that your variants can store different data in different formats. They are not obligated to have to be identical. They can differ. And so you can declare one variant that stores these three pieces of information as a tuple variant, and another one that stores 5 pieces of information as a struct variant. And that's totally fine. So when we actually create the enum instance from the blueprint, we provide parentheses at the point of instantiation. And then we provide the expected number of sequential values. And they must match the declared types in our variant declaration. We also have the complementary struct variants. They similarly store data but based on field name rather than position, so they resemble structs. You can think of a struct variant as a variant that stores a struct of associated data. So in the variant definition we use curly braces instead of parentheses. Inside the associated block, we declare the fields and their associated types. Then when we create the enum instance, or more specifically the variant, we provide curly braces again. And then the concrete values for those fields that must match the declared types. So the syntax for both the variant declaration and the instantiation will differ depending on whether you have a struct variant or a tuple variant. You can also have an empty variant that has no associated data at all, and that's totally fine as well. An enum is often going to be paired with the 'match' keyword. They work really well together, because the 'match' keyword will validate that every possible enum variant is accounted for. So if you have a dynamic variant that you cannot predict in advance, you can combine it with a 'match' keyword and ensure that you declare an associated code block or at a minimum, a value to produce for every possible variant. The compiler will prohibit the program from compiling if you do not cover every possible scenario. So it's a very exhaustive check. Now, a 'match' pattern can also extract the associated data from a tuple variant or a struct variant directly within the block. And you can get really nitty-gritty here, because you can even match against a specific variant with a specific piece of associated data. So you can have a lot of different possibilities being handled within this single construct with the validation of the compiler. You also have, for example, the underscore ( _ ) catchall character that will always match. There's lots of different ways to work with the 'match' keyword. It's a pretty comprehensive but powerful feature in the Rust language, and very often paired with your enums. Like structs, enums can define their own methods. A method is just a function that lives on an instance. It's a command. It's an action that it can take based on its data. We use the exact same syntax. We use the 'impl' keyword followed by our enum, and then a block that stores all of our methods. Our methods are declared like plain functions, except they accept 'self' as the first parameter. And that will represent either the owned enum value or a reference to it, which allows us to avoid ownership by borrowing. Methods can also define additional parameters after 'self', and we can pass those in during invocation. We never have to pass in the argument for 'self' because that is done automatically. So hopefully you can see the similarities between structs and enums as far as method definition. Obviously there are different types with different use cases, but rust strives for consistency with elements like this. So hopefully it's starting to to click as far as the syntax. All right.
