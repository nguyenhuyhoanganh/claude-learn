# The match Keyword V - match with Exact Value

In a match arm for an enum, we can match against not only a variant, but a variant with a specific value, with a specific piece of associated data. It's actually remarkable how precise and granular we can get with this syntax. So let's start by declaring an enum. I'm going to call it 'Milk'. And I'm going to have two variants of milk. There's going to be a 'Lowfat' variant which will have an associated fat percentage that I can represent as a single sequential i32. So here I'm using the tuple variant syntax to store one piece of positional data, a number, and then the other variant is going to be 'Whole' milk and it will have no associated data. So let's define a method for the 'Milk' enum using the 'impl' block. So 'impl Milk' followed by my curly braces and our method will be called 'drink'. This time around, for the sake of variety, let's allow the 'drink' method to take ownership over the enum instance. So I'm going to provide 'self' and that means whatever instance the 'drink' method is invoked upon, that instance will be passed in to 'self', to the parameter. Thus, unless we return 'self', we're going to transfer ownership and thus not be able to use the enum instance after the 'drink' method is done. That will be okay in this scenario. So once again, as a reminder, this syntax is totally fine and it is equivalent to either writing an explicit type of 'Milk' here. That's what 'self' will be, an instance of the 'Milk' enum. Or we can also do capital 'S' 'Self', which is an alias for 'Milk' anyway. Or this syntax right here is the exact same thing. It's a shortcut. So then I'll declare my curly braces and within the body once again we'll use the 'match' keyword and compare 'self' with all of the possible arms in here. So this is where the magic happens. For the first arm, for the first pattern, I'm going to match against 'Milk' and the 'Lowfat' variant. But notice this syntax. I'm going to add a parentheses and provide the value 2. So this is an even more specific match. This will only match if 'self' represents not just the 'Lowfat' variant, but a 'Lowfat' variant that is storing an associated data value of 2 for this i32. So if it is a 'Lowfat' variant, but with any other number besides 2, it will not match. So this is super precise, right? So here I can provide my regular block after the arrow and say something like .. oops, that's going to be a println! here. We're going to say "Delicious, 2% milk is my favorite". Now notice here that if I add my 'Whole' variant as my match arm and provide a corresponding println! like "You've got the whole milk". Notice that when I save, the compiler will still be unhappy, and that is because we have not covered all of the possible cases of what 'self' could be. Right. There is a possibility that 'self' will have no matches, because we have not covered the 'Lowfat' variant for any other i32 in existence, right? 'Lowfat' with 1 is not covered. 'Lowfat' with 5000 is not covered. Right. So here it's going to tell us you have not been exhausted. You have not covered all of the possible patterns. And it's telling us, starting from the minimum value of an i32 all the way to the maximum value of an i32 has not been covered. Right? So in order to satisfy the compiler, we need to add one more 'Lowfat' variant that is more general and can capture any number here. So I can do that by providing the name here for our given percent of fat. And now I'm going to have a 'match' arm that will capture all of the other possible values for i32 and I'm going to have this i32 available with the 'percent' name so I can println! and do something like "You've got the lowfat" and then I'll interpolate "{percent} percent". Here "You've got the lowfat 1% version". This is totally arbitrary. So now our compiler is happy. Another thing to note is this general one must come after the more specific match, because if I declare them in the opposite order, the 'Lowfat' variant with a value of 2 will actually be unreachable. And that is because this first pattern will match any 'Lowfat' variant in the world, including a value of 2, right? This will match when the percent is 2, and the match statement will only look for the first match, so all 'Lowfat' values will be matched here. So Rust will never get to evaluating this pattern for a 'Lowfat' variant, right? Thus, we need to make sure we first check for 2, and then only if the associated data is not 2 do we check the next option, which is a 'Lowfat' variant with another value for this i32, right? And this covers all of our scenarios and Rust is happy. So now all that remains is actually invoking this 'drink' method within 'main'. So just to show you a few examples. I can start with a 'Lowfat' milk. Let's start with something like 1 and invoke the 'drink' method. So when this runs, Rust is first going to compare 'self', which is this instance right here with this pattern. It's going to see: "Yes, it is low fat, but the number 1 does not match the number 2". So the associated data condition is not equal. So this pattern is not met. At which point Rust compares that to this. Now there is a match because percent here is general enough to cover the value of 1. And thus we're going to get "You've got the lowfat 1 percent version". Now, if I have a 'Lowfat' variant specifically with the value of 2, now we're going to match on the very first pattern right here. And now we're going to get this println! "Delicious, 2% milk is my favorite!". And then finally if we have 'Whole' that does not have any associated data. So I can just invoke 'drink' directly. And we're going to get the third option which is "You've got the whole milk!" All right. So this is how precise that Rust can get in its match statements. It can literally target not just a variant but a specific value within that variant. And so you're matching can get really, really precise.
