# Introduction to Apache Kafka

Hi everyone. In this lecture, I will make an introduction to Kafka. As mentioned previously, I will use Kafka in the implementation of SAGA, Outbox, and CQRS patterns, and keep the domain events in Kafka to trigger domain event listeners. Let's see the high level architecture of Kafka. Kafka brokers are the servers that forms a cluster and serve to producers and consumers to insert and reach data. Having multiple brokers in a cluster is important for high availability because with multiple servers Kafka can replicate the data on different nodes and increase resiliency of the system. Kafka has the concept of topic. Which is a logical data structure that consists of partitions, and partitions are the smallest physical storage unit that holds to data. As mentioned, some data can be replicated on different partitions, on different Kafka brokers to increase resiliency, this is achieved using the replication factor property. For example, if Kafka cluster has three brokers and replication factor is three, then the same data will be replicated on three different partitions, on three different nodes, and this will provide a strong resiliency. Producers writes data at the end of a partition and consumers reach the data from the start of a partition and keep an offset with an ID to continue from the offsets in case of restarts. Consumers achieves to read the data from the offset using a consumer group concept. So a consumer belongs to a consumer group and a consumer group will not reach the same data more than once. Instead it'll keep reading the new data, using the offset. One thing to note here is that if you create a new consumer group with a new identifier you can read the data again from the start of a partition. Kafka has two important features. One is the resiliency. As mentioned, resiliency is achieved using a replication factor and duplicating the same data on different partitions on different broker knots. The second important feature is the easy scaling. You can have parallel consumer threats up to the partition number in a topic. That means if you create a new partition, you can create a new consumer and consume the data with a new threads concurrently. Finally as mentioned, the data is inserted as an append-only lock into the partitions, and once inserted, the data cannot be changed or updated, so it is imitable. Since it inserts data to do end of a partition, it is fast. There is no need to search the place to be inserted, and if you want to see a final state of error records, you can get the history and calculate the latest state. Or you can use a K table using Kafka streams and hold to latest states in a table like structure and query it anytime. All right. Let's also discuss the other components that are used in running Kafka. Currently in production applications, Kafka still requires Zookeepers to manage the cluster and hold to metadata. There is key IP 500 mode that allows to use one of two Kafka brokers as the orchestrator. This will allow removing Zookeeper dependency, but it is still not in the production ready state. There is also Schema Registry components that helps to use a strict schema while producing and consuming data. This will prevent errors on producer and consumer sites, forcing all sites to use the shared schema. It basically provides a mechanism to manage and share the schemas between the producers and consumers. In the first call, producers send the schema to do schema registry and get an ID. Then producer uses this schema to serialize the data. If you use Arrow, this will be our italization and it'll send this data with the ID to the Kafka broker. Then a consumer will reach the ID and the serialized data and get the schema from the schema registry by querying it with the ID, and it simply deserialize the data using this schema. As you see here there is a local cache on both producer and consumer sites, so instead of querying this camera registry each time again and again, producer and consumer will actually cache the results and use this cache to obtain this camera. This will prevent making a network call each time you produce or consume data. All right. After this introduction, in the next lecture let's run a Kafka cluster using Docker.
