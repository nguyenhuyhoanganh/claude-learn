# Implementing Kafka model generic module

All right, let's go to Kafka model module. Here, I will create the Kafka model classes and I will use Avro schema type while creating these classes. Let's first go to pom.xml file and add our dependency. In the pom.xml file of Kafka model, I will also add avro-maven-plugin I will use this plugin to create the Avro Java classes from the Avro schema files. As you see, the source directory is src/main/resources/avro, so the Avro schema files will be here, and the output directory is source main Java, so the generated Avro Java classes will be in this package. In the executions, you see generate-sources phase and the goal is set as schema. It is configuration when you run Maven install commands. It will create Avro classes during the generate-sources phase. Finally, here you see that stringType sets to Java string and decimal logical type is enabled, so that I will be able to use decimal type for the price fields. Now I will go to this source directory, resources, Avro, and create four Avro schema files with AVCS extension, payment requests and response, and restaurant approval request and response. Remember, I have created four Kafka topics and, accordingly, here I have four schema files. Let's see the content of this schema files. in the payment request file. I have the namespace, com.food.ordering.system.kafka.order.avro.model. This will be the Java package name. The name is PaymentRequestAvroModel and this will be the Java class name. In the fields, I have id with type string and LogicalType uuid. And our LogicalType is an Avro primitive or complex type with extra attributes to represent a derived type. So actually, Avro doesn't have a UUID type, but to mark this field with the correct field, we can use this logical type. In the end, this will be a Java string and the values still need to be validated in the client code that uses this Avro schema type. Then I have sagaId, customerId and orderId. All these fields are strings and has UUID logical type. The price fields of type bytes and the logical type is decimal. Our requires to use bytes type to hold a decimal value, as you see here. I set the precision as 10 and set scale as two, so I will have prices like 10.75 or 200.50. As you see, this is aligned with the implementation of the order domain logic. Remember, I used scale two in the Java with decimal values. For createdAt field, I use a long type with logical type, timestamp-millis. And for payment order status, I use enum Avro type and I need to give a name as payments order status and use symbols with an array. These are actually the enum values. Similarly, in the payment response Avro schema file, I have the same namespace and payment response Avro model for the Java class name. Then I have id, sagaId, paymentsId, customerId, and orderId fields which are string types with logical type UUID, and I have similar price and created at fields as in the payment request object. I have an enum type payment status here. And finally, to hold a list of strings for failure messages, I use Avro type array and use an inner items object with type string. In the restaurant approval requests, I have a similar structure, as you see here, with id, sagaId, restaurantId, orderId as UUID types, and I have RestaurantOrderStatus enum type. For products, I have an array type. It's an inner object named Product and with ID and quantity fields. As you see, these are simply the mapped fields to Java classes used in the order domain logic. Additionally, I have the same price and createdAt fields here. Finally, in the restaurant approval response schema file, I generate restaurant approval response Avro model class with id, sagaId, restaurantId, and orderId. Then I have created at fields, order approval status, enum type, and the failure messages string array. Great, now, if I run Maven install commands for Kafka model module, it should create the Java Avro models from the Avro schema files. You see that the Java classes are created in the Java folder with the package that I set in the schema file. I see some compiled time warnings. Let's reload Maven so that IntelliJ will see the Avro dependencies. All right, I will continue with Kafka producer module in the next lecture.
