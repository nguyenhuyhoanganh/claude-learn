# Introduction to Outbox pattern

Hi everyone. I will make an introduction to Outbox Pattern in this lecture. Outbox Pattern uses local ACID transactions to create consistent distributed transactions. It will complete SAGA in a safe and consistent way. In SAGA pattern, with a long running transaction, you will have a local data store transaction and also we'll have the events publishing and consuming operations. If you just first commit to database transaction and publish, if the publish operation fails, SAGA cannot continue and you'll leave the system in inconsistent state. Instead, if you first published the event and then try to commence database transaction, things can even go worse. The local database transaction can fail. In that case, you would have already published a wrong event which you should never have published. Remember, that I have first completed local database transaction and then published to event. But as mentioned, this published operation can fail because of a problem in service in KAFKA or in network communication. To resolve this issue, we need to combine SAGA with Outbox Pattern to obtain a consistent solution. I will be using pulling Outbox Table with a scheduler and keep the state of SAGA Outbox and order in the Outbox Table for each microservice. In Outbox Pattern, you don't publish events directly. Instead, you keep your events in the local database table called Outbox Table. This table belongs to the same database that you use for local database operations, so that you can use a single ACID transaction to complete your database operations in the service and the insertion into the Outbox table. Therefore, I will be sure that the event is created automatically within the local database using ACID transaction. After this, you will complete the Outbox Pattern by reading the data from the Outbox Table and publishing the events. For this, there are two approaches, pulling the table data, or change Data Capture approach. Each will listen transaction logs of the Outbox Table. In both case, you should do the implementation to be sure that you don't miss the events in the Outbox Table and they are safely published into the message pass. As mentioned previously, I will use pulling Outbox Table approach and handle possible failure scenarios in the following lectures. Using the Outbox Table, I will keep track of SAGA and order status for each operation. Also, I will use Outbox Table to ensure idempotency and to prevent data corruption in case of concurrence operations. I will apply optimistic logs and database constraints using the Outbox Table as you will see in the following lectures.
