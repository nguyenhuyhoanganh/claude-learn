So how does optimistic locking works? When you read data from database you'll get a version column with a value. Initially it'll be zero. Then after running some processing logic when you want to update the original data it'll check the version fields from database. If the version is different that means some other transaction has updated this data. If the versions are the same, the original transaction will update the data and increment the version by one. As you see, I first get the payment Outbox object at the start of the process methods. This returns order payment outbox message with the current version defined in the database table. If it is any records, the version is zero. And during the update of all the payment Outbox message using these same methods the version integer fields is incremental and the changes will be committed before returning from the methods. Now imagine two threads enter the process methods both read the same outbox message with the same version and both pass this if condition because both as the outbox object which started SAGA status and they both come to do payment outbox helper save methods. with optimistic, lacking with aversion field and these two threads try to update the same row simultaneously. One of them will get the lock and do the update and the other one will wait till the first one commits. When the lock is released, second thread gets lock but the version will be incremented in that case by the thread one and for thread two it'll not be the same version that it got when it first fetched the data here. In that case, I will get an optimistic lock exception and the operation of the second stretch will be rollback. The downside of using optimistic locking is this rollback operation. If you have too much collisions there will be more rollbacks which is not good for performance. But with less collisions, like in our case I would expect only small amount of collisions here it'll perform better than pessimist lock which will lock the row with a select for update manner and it'll even prevent reading the data from another transaction. Not that for monitor operations, I would still recommend using pessimistic locks or constraints but for most of the other operations optimistic locking is fine.
