# Refactoring Order domain layer: Adding Outbox models & Updating ports

All right, let's continue with the changes of order service domain layer for outbox pattern. I will first go to order-replication-service module and then I will create a new package, outbox. Here I will create two sub-packages; model and scheduler. In the model package, I will create payment and approval packages. And then in the payment package, I will create OrderPaymentsOutboxMessage class. In this class, I will simply model the fields of the outbox message in the domain layer. I will add Getter, Builder, and AllArgsConstructor Lombok annotations, and then it's id and sagaid, UUID fields. Then I will let two ZonedDateTime createAt, processedAt, then I will add the two string fields, type and payload. Type will be the constant name of saga such as order processing saga. The payload is a string here and it'll actually be the JSON representation of the domain events. So for this one, I will create a JSON mapper class just after finishing this class. And I add SagaStatus, OrderStatus, and OutboxStatus and types. To use OutboxStatus, of course I need to add a dependency to do neve outbox module here in the order application service. So I will open Pam XML file and add the outbox dependency in the dependency section. Finally, I will have the version fields, which will be an integer. As I mentioned, I will use this field to version data rows to use in optimistic locking. Now I will create Setter methods for processedAt SagaStatus, OrderStatus, and OutboxStatus cause those are the fields that I will set later when the outbox message is processed. In the same payments package, I will also create OrderPaymentsEventPayload class. This will be the JSON representation of the domain events for payments. I will add the same Getter, Builder, and AllArgsConstructor annotations, then I will add orderid and customerid string fields and the BigDecimal price fields, ZonedDateTime createdAt fields, and finally, string paymentOrderStatus fields. I will add JSON property annotation to these fields. And for that, I need to go to Pam XML file and add spring.boot.starter JSON dependency. Then I can use JSON property annotation in all fields here in this class. As I mentioned, I will create a JSON object from this order payments event payloads and set this as a stringed value to the payload fields of the OrderPaymentOutbox message. Similarly, I will go and create OrderApprovalOutbox message class. This will be similar to the OrderPaymentOutbox message. I will let the same Lombok connotations and then add the same fields and Setter methods. And I will create OrderApprovalEventsPayload class. Again, I will let Getter, Builder, and AllArgsConstructor annotations. In this payload class, I will have orderid, restaurantid, price, createdAt, and restaurantOrderStatus fields. Also, I will have a list of products here. And for this, I want to keep the product ID and quantity together. So I will create another class OrderApprovalEventProducts. It's same Lombok annotations and with two fields; id string and quantity integer. I will let JSON property annotation to both fields. And then in the OrderApprovalEventPayload class, I will use this OrderApprovalEvent product in the list of product fields. Finally, I will add the JSON property annotations to all fields in this payload class. As in the payment to outbox message in this OrderApproval message class, I will use the JSON string representation of OrderApprovalEventsProduct in the payload field. I will come to the scheduler package later as it will require to use the port definitions. So let's first go and create the output ports in the ports package. Remember that output ports are nothing but interfaces to be implemented in the infrastructure modules. And the domain layer, we'll simply use the interfaces and inject them at runtime. In the output repository package, I will create PaymentOutboxRepository interface, and I will add save methods with parameters OrderPaymentOutboxMessage and return orderPaymentOutboxMessage. Then I will create findByTypeAndOutboxStatusAndSagaStatus methods with type outboxStatus and sagaStatus VarArgs parameters. These three dot means it's a VarArgs parameter and it can take more than one sagaStatus values. And I will create findByTypeAndSagaIdAndSagaStatus methods with type sagaId and sagaStatus VarArgs parameters. Finally, I will create deleteByTypeAndOutboxStatusAndSagaStatus methods with type outboxStatus and sagaStatus VarArgs. You will see why and how I will use these methods shortly. And I will create ApprovalOutboxRepository interface and add the exact same methods only the parameter and return types will differ a bit. I will use OrderApprovalOutboxMessage instead of PaymentOutboxMessage. Then I will go to outputs message publisher payments package and create a new output ports, PaymentRequestMessagePublisher. In this interface, I will add a single method, publish, and use OrderPaymentOutboxMessage as the first parameter. As a second parameter, I will pass a MyConsumer interface, which is a functional interface, comes with Java 8. It basically accepts two parameters and doesn't return anything. It accepts the parameters as generic types. I will use OrderPaymentOutboxMessage and outboxStatus for the two parameters for this BiConsumer interface. In the implementation, I will have a methods that takes these two parameters and return void, and then I will simply pass that methods definition and let it be called in the published method. So why do I need that? Because I want to update OutboxStatus as completed or failed. depending on the result of these published operation. This published methods will be implemented in the order messaging module with an adapter. It will use Kafka Producer. And only in that adapter I will know that if Kafka Producer send methods successfully sent the data or not. Remember that Kafka Producer send method is an asynchronous methods and it uses a callback methods to be called later. When I send this BiConsumer as parameter to the publish methods, I will be able to call it in the Kafka Producer callback methods. Remember that Kafka Producer callback methods handles failure and success cases. I will simply call the accept methods of BiConsumer in those failure and success methods and update the outboxStatus in the local database. Stay tuned for the implementation. I will do that in the following lectures. Similarly, in the restaurant approval package, I will add RestaurantApprovalRequestMessagePublisher interface and create published methods with OrderApprovalOutboxMessage and BiConsumer parameters. For the generic types of these BiConsumer, I will use OrderApprovalOutboxMessage and outboxStatus. As mentioned, I will implement these output ports in the order messaging module in the next lectures after completing the order application service changes. Actually in the end, I will not need these orderCreated, Canceled, and PaidMessagePublishers because I will use this OutboxMessagePublisher for each type of events and separates them in the outboxMessage object using the payload object, which is the domain events and it has the paymentOrder status for PaymentOutboxMessage. And for ApprovalOutboxMessage, it has a restaurantOrderStatus to make this separation. So I will delete this separate event publishers here. Before returning to scheduler package implementation, I will go and update OrderSagaHelpers with a new method, orderStatusToSagaStatus. Here I will simply pass an orderStatus parameter and return a sagaStatus to get a sagaStatus and save it in the outbox table. I will use a switch statement and map the orderStatusToSagaStatus. For an order in PAID status, I will have a sagaStatus.PROCESSING because if an order is paid and requires an approval, it is in the middle of saga processing. If an order is approved, that means saga is completed successfully. So I will set the status as SUCCEEDED. For a canceling order status, I will set the sagaStatus as COMPENSATING, cause remember that a canceling order status is set when orderService publishes an orderCanceled event to be processed by the payment service and rollback can compensate the payment changes for that order. For a canceled order status, I will set COMPENSATED saga status because if an order is canceled, it is already rollbacked and compensated from the previous steps. Finally, for the default case, I set the saga status as started here. Actually this will match to the PENDING order when it is first created. Great, let's continue with the implementation of scheduler package in the next lecture.
