# Updating Order Service database schema and config for Outbox Pattern

Hi everyone. In this lecture, I will update order service to use Outbox pattern. First, I will add and commit my changes to GIT repository using, git add and, git commit commands. And then I will create a new branch. Before outbox, I will use, "git checkout -b" commands to create the new branch. Now, I will switch back to the master branch using, "git checkout master" command. So anytime you can go to before outbox branch, and compare the changes that you will do for the outbox pattern. Now first I will go to Saga module in infrastructure. And add saga status enum. I will let: started, failed, succeeded, processing, compensating and compensated options. I will use these saga status enum objects to hold hold the saga status in the outbox tables. And I will create a new module, Outbox, under infrastructure module. And create a new package, com food ordering system outbox. Here, I will create a new enum outbox status with values: Started, completed, and failed. Then I will add this new dependency to do base palm XML file with project version. Now I will go to order service. And first I will change to inits SQL file, in the order container resources folder. Here I will like to create statement for outbox tables. Now remember that in order service I have three events, order created, order canceled, and order paid. The first two events, order created and canceled are used to publish a message to do payment request to page and they will trigger payment service. And the third one, or the paid events is used to publish a message on a restaurant approval request topic and it will trigger restaurant service. So, here actually I have two types of events. One is for payment service and the other one is for restaurant service. It's outbox pattern. I will persist the events to a database table. But, if I keep all these three events in the same outbox table, I will be putting unrelated events in the same place. So, to keep the concepts segregated, I will use two outbox tables here in the order service. One is for payment service and one is for restaurant service. Now I will create two new enum types first to using the outbox tables. First one is saga status type with the possible saga status values as in the Saga status Java enum type. And I will create outbox status with the same possible values of the outbox status, Java enum type. Then I will create payment outbox table. Here I have ID and saga ID, UU ID fields. And then I have created and processed times with the times stamp type. Then I have a string type field here which will hold to type of the saga. Notice that I have currently only one type of saga, which is order processing. Then I add payload fields with jsonb type. So, I will keep the event data as a json payload in this field. Not that this means I need to serialize event objects to json when I put in the outbox table. And, I need to de-serialize it on the consumer side. Then I have outbox status, saga status and order status using the enum types. Order status will be one of the values of order status Java enum type. Saga status will be one of the values defined in the Saga status Java enum type. And the outbox status will be the overall status of outbox operation, which is defined in enum outbox status in Java, as you see here. Finally, I have the version field here, which is an integer. I will use this field for optimistic locking as you will see shortly. Then I have the primary key for ID fields here. And then I will create two indexes. First one is an index on type, outbox status, and saga status. I will query outbox table using these fields. So, it is better to have an index on those fields. You will see why I need these shortly. And I will also add a unique index on type, saga id and saga status fields. So, I will expect that as saga of any type must only be in a single status. These indexes will make more sense when I start implementing changes. Now similarly, I will create restaurant approval outbox table. As you see, I have the same fields. I have the primary key on ID, and then I will have the same indexes. First is on type outbox status and saga status. And the second one is a unique index again on type, saga id and saga status. Then in the application YML file I will add two configuration values. Outbox scheduler fixed rate, and outbox scheduler initial delay. Under the prefix order service. I will set 10,000, which is 10 seconds. And I will use this ten second rate for the scheduler implementation. So, I will pull the outbox table for each ten seconds for this demo. On production, you probably want to use this value less than ten seconds, depending on the processing time of a cycle operation. Ideally, these rates shouldn't be more than two seconds. Great.
