# Refactoring Payment domain layer: Updating Message listener implementation

All right, let's go to payment request helper class. First I will inject two more fields here, order outbox helper and payment response message publisher. I will let these fields to the current constructor to inject them. In persist payments methods, after persisting TB objects, I will call order outbox helper save order outbox message method. For the first parameter, I need an order advance payload object so I will add a new method payment events to all the event payload in the payments data mapper. And create an order advance payload object from the payment event. I will use Builder and set payment id, customer id and order id, price, createdAt, payment status and failure messages. Then I will call this new mapper method here to pass the first parameter of save order outbox message. For the second parameters, I will use payments event, get payments, get payment status methods to get the payment status. Then I will pass outbox status as started, and finally pass the Saga id using UUID from String method. This will persist a new outbox message and the order outbox scheduler will process this message using the scheduled process outbox message. As you see, after processing the message outbox message is updated. In case of successful response from Kafka I will set outbox message status as completed. I will update the messaging module in the coming lectures for that. Now here in the persist payment methods I will cover a failure scenario to make the application more resilient. Remember that if I have completed outbox message for a Saga id, this means that the message sent to Kafka using the payment response Kafka topic and an acknowledgement received. After that, the payment response Kafka topic will be consumed by order service to get the payment status. If order service somehow failed to process this payment response, it might ask for a payment again for the same Saga id. In that case, if I see an already completed outbox message I should not process the payment again. Instead, I will assume that the published payment message is not processed by the order Service so I will send it again. For this, I will create a private method here publish if outbox message processed for payment. Here I will pass payment request and payment status as the parameters. In this method I will call get completed order outbox message by Saga id and payment status methods with the Saga id and payment status. I will get an optional order outbox message object as a response here. If this optional object is present, I will publish the order outbox message using payment response message publisher which is the publisher interface that I have injected here. But for this publisher, I need a second parameter which is the outbox callback. Remember that I have used this update outbox message methods in order outbox scheduler. So I will use a method reference to use these methods in the publish method. And I will return true, and otherwise I will return false. Now I will call these methods at the top of the persist payment methods. If I get a true response, I will log an inform message and just return from these methods. This way, I will simply republish the outbox message to let order service about the payment status in case order service could not get or process the payment service response previously. Similarly, in the persist cancel payment methods, I will call the same publish if outbox message process for payment methods. At this time, I will pass payment status as canceled. If I get a true result, I will log and return as in the persist payment method. Then after the database persist operation I will call order outbox helper save order outbox message methods, and persist an outbox message. I will pass the order advance payload object and get it from the payments data mapper method, payment events to order advance payloads and pass payments status, outback status as started and the Saga id. Remember that in order service, in the order payment Saga class I had optimistic locking checks using the version field and I had also uniquely constraint checks for the approval outbacks in the same transaction. Here, I don't have an update for the outbox message so actually I cannot use optimistic locking. Optimistic locking can be used for concurrent updates of an existing database record. Here I only insert a new outbox message object so I will only use a unique constraint violation to prevent two threats, processing and operation and inserting the same outbox message at the same time. For this, I already have the unique index definition in the schema SQL in payment container. This index is on type Saga id, payment status and outbox status as you see here. Great, so I have completed the payment service domain layer changes for the outbox pattern. Let's update the payment data access with outbox adapter implementation in the next lecture.
