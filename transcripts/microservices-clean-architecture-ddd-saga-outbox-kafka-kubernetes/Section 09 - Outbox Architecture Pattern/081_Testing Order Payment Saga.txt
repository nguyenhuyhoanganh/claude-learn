# Testing Order Payment Saga

Hi everyone. In this lecture, I will write an integration test for order payment saga. For this, I will go to order container module and add Spring Boot starter test dependency in the pom.xml file. In this integration test, I will use SQL files to initialize some data on Postgres database. Therefore, I will go to test resources folder and create a SQL folder and then put two SQL files to use in the integration test, OrderPaymentSagaTestSetUp.sql and OrderPaymentSagaTestCleanUp.sql. In the SetUp.sql, as you see, I insert an order and the related order item and address objects. Then I insert a records to payment outbox table for a new order so old status values has the initial states as you see here. In the CleanUp.sql, I delete the records that I used in the test from orders and payment outbox tables. Note that when I delete the order table, order items and address tables will be deleted automatically because of the cascade relation between these tables as you see here. Now I will go to test folder and create a package, com.food.ordering.system order service domain. And I will create OrderPaymentSagaTest class. I will add Spring Boot test annotation and set classes property as OrderServiceApplication class. Note that this is the Spring Boot main class for order service. With this Spring Boot test annotation pointing to the OrderServiceApplication class, I aim to start the Spring Boot context in my test like I am starting the application. And I will add SQL annotation and set OrderPaymentSagaTestSetUp in the classpath. Similarly, I will add another SQL annotation and add the CleanUp.sql file, and this time I will set the ExecutionPhase as AFTER_TEST_METHOD, so this CleanUp.sql will be executed after each test method. Please note that the setup SQL uses the default ExecutionPhase which is BEFORE_TEST_METHOD, so it will be executed before each test method. Finally here, I will add SLF4J annotation to use logging in this class. Now I will autowire OrderPaymentSaga field, and also autowire PaymentOutboxJpaRepository field. And I will create the final fields for saga ID, order ID, customer ID, payment ID, and price. First, I will create a method, testDoublePayment with test annotation. In this method, I will call orderPaymentSaga.process method. And for the parameter, here I will create and call getPaymentResponse method and get a PaymentResponse object. Note that this is the response object that comes from payment service to the order service with an event. I use PaymentResponse builder and set the fields using constants that I defined. Also I set the random ID, and set created it using Instant.now method here. And finally, as you see, I set the empty failureMessage list. As you see, I set the paymentStatus as COMPLETED here, so it says successful response. Great, then I will call orderPaymentSaga.process method with the PaymentResponse object. And I will do that two times. I will call the process method with a PaymentResponse object that has the same saga ID. It will simulate that the first thread runs the process, and the second thread only comes after first thread returns from this process method, that is, after the transaction is committed. Remember that with this scenario, I would expect the second method will return with this if block and get an outbox message with saga ID already processed message in the logs. Let's run this test. Indeed the first method called process the outbox message, and the second method called it's already processed error message in the logs. Great, let's write more tests for concurrent access to the orderPaymentSaga. Remember that I have optimistic locking control on payment entity with the version annotation. And also I have a unique index control on payment and approval outbox tables as you see here. These two checks running the process method. For now I will remove the unique indexes from the approval outbox table and payment outbox table so that I will see the optimistic locking exceptions in my test clearly. I will create a new method, testDoublePaymentWithThreads. And I will put test annotation here and create a thread and run OrderPaymentSaga.process method. For the parameter, I will call the getPaymentResponse method. As you see, I use the lambda inside the thread constructor which is actually a runtime implementation of runnable interface. Runnable interface has no parameter and has void return type, so as my lambda definition here. No parameter on the left side of the lambda and no return statement on the right side of the lambda. This will only run the process method on the right side of the lambda. Then I will create another thread and call the process method. Now I will start the two threads and then I will call join method on both threads. Join method will block the calling thread which is the main thread that calls the method until the thread whose join method is called has completed. So by calling join method for both threads, I will be sure that both threads will be executed before the main thread exits this test method. This way, I call the process method from both threads almost at the same time. I will add 12 statements to the method for this InterruptedException. And finally, I will add an assertion here. For this, I will create a new method, assertPaymentOutbox, because I will reuse it later. In this method, I will call PaymentOutboxRepository, find by type and saga ID and saga status in method and get PaymentOutboxEntity. I pass the order saga name, saga ID, and processing saga status in a list here. And I will use assertTrue method to check if the paymentOutboxEntity object is created. Now if I run the test with thread, it will pass, so the outbox message is saved with saga state processing. Let's also check the logs to see if optimistic lock exception occurred. As you see, I got object OptimisticLockingFailureException for one of the threads, but the other one does the job because I got my outbox object with the processing saga state in the assertion method. You can also use CountDownLatch instead of thread join method. Let's write a similar test using a latch. I will create another test method, testDoublePaymentWithLatch. Here I will create a CountDownLatch with count two. CountDownLatch is a synchronization construct that allows one or more threads to wait until the set of operations being performed in other threads completes. And I will create two threads here and run the process method as in the previous test method. But this time I will use a try/catch/finally block and catch OptimisticLockingFailureException and log and error message. And in the finally block, I will count down the latch, then I will do the same for the second thread. Now I will start both threads and then call CountDownLatch await method. The await method looks on to the current count which is 2.0 due to invocations of the CountDown method. Since I have count two, this will wait until both threads complete it. So I force the two threads to run almost at the same time again. Here I've also added the 12 statements to the method for the InterruptedException. Now I will do the same assertion here and check if my PaymentOutboxObject is created. Let's run the test. As you see, the test is passed, so one of the threads is already inserted in the data in the outbox table with saga state processing. And if I check logs, I see that the OptimisticLockingFailureException has occurred for thread two. If I run it again, this time thread one might get optimistic locking. It doesn't matter as long as one of the threads does the job, and the other one is roll backed, which is the aim of using optimistic locking here. All right, we have tested order payment saga for concurrent access, and test the optimistic locking. I will continue with payment service refactoring in the next lecture to use outbox pattern. So I will see you in the next lecture.
