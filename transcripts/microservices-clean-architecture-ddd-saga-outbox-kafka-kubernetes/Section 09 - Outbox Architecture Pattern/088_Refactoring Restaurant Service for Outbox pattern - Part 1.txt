# Refactoring Restaurant Service for Outbox pattern - Part 1

Hi everyone. In this lecture I will refactor restaurant service for outbox pattern. This will be almost the identical changes with the payment service. Therefore, to prevent being too verbose I have already updated restaurant service here and now I will review when I explain them. You can download to source codes for these changes in the resources section of this lecture. Now first in the restaurant container module in init schema sql file, I have edit outbox status type. Remember, it could be edited by other services as all of them uses it. So I first drop it if it exists, then I recreate it. And also here I created order outbox table and this is almost the same table as in the payment service. Here is a difference, I have approval status and in the indexes I also use approval status. In the application yaml, I have added fixed rate and initial delay as 10 seconds. This is the same config as in the other services as you see. Remember I use these values to configure this scheduler. Then I will continue with restaurant data access module. Here I have a new package, outbox and five subpackages. In the entity package, I have order outbox entity for table order_outbox. This is again very similar to the entity class in payments data access. Here I have approval status instead of payment status. The rest is the same. I have the same Lombok and JPA annotations and I have the fields for the database table order_outbox. To use the outbox status, I edit the outbox module dependency to the pom xml file of data access module and I have order outbox not found exception in exception package, which is a runtime exception. In the mapper package, I have order outbox data access mapper class with two methods, order outbox message to outbox entity that creates an order outbox entity from the order outbox message, and the other method's order outbox entity to order outbox message to create an order outbox message from the entity. In repository, I have order outbox JPA repository with repository annotation and I extend JPA repository with order outbox entity and UUID types. Here I have three methods find by type and outbox status, find by type and Saga id and outbox status, and finally delete by type and outbox status. And in the adapter package, I have the adapter implementation order outbox repository impl. Here I have component annotation and I implement order outbox repository, which is the output part in the restaurant application service module. Here I inject two fields, order outbox JPA repository and order outbox data access mapper. And here I have the implementations for the overwritten methods. In save methods, I call JPA repository save methods and use order outbox data access mapper to convert outbox object to entity and also entity to outbox objects for the return type. In find by type and outbox status, I call order outbox JPA repository find by type and status method and return an optional list of order outbox message. And again, I use order outbox data access mapper to convert JPA entity to outbox objects using the order outbox entity to order outbox message method. As you see I throw order outbox not found exception in case approval outbox cannot be found. In find by type and Saga id and outbox status method, I call order outbox JPA repository find by type and Saga id and outbox status method and get an optional order outbox message object using the type Saga ID and outbox status parameters. And finally, in the delete by type and outbox status method, I used the corresponding JPA repository method to delete the completed outbox status objects. After data access module, now I will go to the restaurant application service module. First I have the outbox saga and spring boot starter json dependencies edit to the pom xml file. Then in the ports package, in output subpackage, I have order outbox repository interface with four methods. Save find by type and outbox status, find by type and Saga id and outbox status, and delete by type and outbox status. Remember that this interface is implemented with the order outbox repository impl adapter in restaurant data access module. Now in the message publisher package, I have restaurant approval response message publisher interface. I have a publish method here with parameters order outbox message and BiConsumer with order outbox message and outbox status. Generic types is BiConsumer parameter is for callback method to update outbox status in the local database after getting a response from the message pass, which is Kafka here. This is another output port and it is implemented in the messaging module. I will come to the messaging module shortly. Note that I had two publishers previously for order approved and order rejected conditions. But with outbox pattern, I have a single publisher and the status will be in the parameter order outbox message here in the restaurant approval response message publisher. Next I have a new package outbox and two subpackages, model and scheduler. In model package I have order event payloads, which holds to fields that I need in the events payloads. As you see here, I use json property annotation on the fields here because this class will be converted to a json representation text. Then I have order outbox message with the required fields for an outbox message. The payloads string field will be the json representation that I just mentioned using the order event payload class. Then in the scheduler package, I have order outbox helper spring components. Here I have order outbox repository and object mapper fields that are injected using constructor injection. First I have get completed order outbox message by Saga id outbox status method here and this is used by the publish if outbox message process method in the restaurant approval request helper and this is to publish a message again if order service asks to do so. Then I have a method to get an order outbox message by outbox status. As you you see these method is called from schedulers to find the outbox messages by status. The order outbox scheduler needs started outbox messages to process. On the other, cleaner scheduler needs the completed ones to delete. Delete order outbox message by outbox status method is called from cleaner scheduler as you see here. Then I have save order outbox message method and this is called to persist an outbox message in the restaurant approval request helper after domain logic runs. And the update outbox status method is used as a callback method to update the outbox status after Kafka returns a response. As you see it is the second parameter to the publish method. The second parameter is a BiConsumer functional interface. Save method is called by save order outbox message and update outbox status internally and it calls to order outbox repository save method to persist the outbox message into database. Finally, create payloads simply creates a json representation from order events payload object using object mapper write value as string method. In all public method, I have the transactional annotation just to be sure a transaction is started for those database operations. Now in the order outbox scheduler class, I have the usual Slf4j and component annotations and so I implement outbox scheduler interface from outbox package. I have two fields injected here, order outbox helper and restaurant approval response message publisher. And on the process outbox message methods, I have transactional and scheduled annotations. For scheduling, I set the fixed rate and initial delay properties from the application configuration. In the implementation of process outbox message methods, I just call order outbox helper, get order outbox message by outbox status method and get the outbox messages in started state. And if I got some outbox messages here, I log an info message using the identifier of the messages. And for each message, I called response message publisher publish methods and pass the order outbox message and the methods reference for order outbox helper, update outbox status. As you see this update outbox status method is used to update the outbox status and I call it when Kafka returns the response. Finally, I log an info message here. Then in the order outbox cleaner scheduler class I have the same Slf4j and component annotations and I implement a outbox scheduler interface. I have a single field injected here, order outbox helper. And on the process outbox message method I have the scheduled annotation for midnight. So these methods will run every day on midnight. I also have the transactional annotation here. And in the implementation I call order outbox helper, get order outbox message by outbox status method. And for the outbox status I pass completed to get the completed outbox messages. If I find completed messages, I log an info message and then call order outbox helper delete methods to delete those messages. Finally, I log an info message and finish this method. All right.
