# Refactoring Order domain layer: Updating Order Approval Saga

Hi everyone. Let's finish the order service domain layer refactoring with the OrderApprovalSaga. First, I will remove this OrderCancelledPaymentRequestMessagePublisher as I don't use the publishers anymore. Then, I will remove the second and third parameters from the SagaStep interface. Remember, I have updated the interface to use only one perimeter, T. And I will make the return types void for both process and rollback methods. Then, I will add three more fields here and inject them. PaymentOutboxHelper, ApprovalOutboxHelper, and OrderDataMapper. Now in the process method, I will call the approvalOutboxHelper getApprovalOutboxMessageBySagaIdAndSagaStatus method with SagaId and with PROCESSING SagaStatus and get an Optional OrderApprovalOutboxMessage. Here, I use PROCESSING status. Because SagaStatus set to PROCESSING before triggering approval phase, as you see here. It is done in the process method of order payments saga And the order is paid, SagaStatus sets to processing and save into order approval outbox table. If orderApprovalOutboxMessageResponse.isEmpty, I will log an info message and return. The same reason is valid here and duplicate messages come from Kafka, one of them won't be necessary to run, so I eliminate that message. Then, I will get the OrderApprovalOutboxMessage from the optional objects. And then, I will create approveOrder method and call it with response parameter. And I will move these codes into these method, this will return another orders. Then, I will get the SagaStatus from the order status using the OrderStatusToSagaStatus method of orderSagaHelper. And then, I will call the approvalOutboxHelper save method. For the parameters, I will create getUpdatedApprovalOutboxMessage method with orderApprovalOutboxMessage, OrderStatus and SagaStatus. And simply update the orderApprovalOutboxMessage with process time and new status variables for order and saga. Then, I will return the orderApprovalOutboxMessage and use it in the same method. Similarly, I will call paymentOutboxHelper save method and create getUpdatedPaymentOutboxMessage method with SagaId, OrderStatus and SagaStatus parameters. In this method, I will get the OrderPaymentOutboxMessage using PaymentOutboxHelper, getPaymentOutboxMessageBySagaIdAndSagaStatus method. I will pass the sagaId and PROCESSING saga state. If there is no message prompts in processing state, that is a system error, so I will throw an OrderDomainException here. Otherwise, I will get the outbox message and sets the process time using the ZonedDateTime with the UTC zone. And sets the orderStatus and sagaStatus and then return the OutboxMessage. Now in the rollback method, I will call the approvalOutboxHelper, getApprovalOutboxMessageBySagaIdAndStatus method. It's SagaId and PROCESSING SagaStatus is in the process method. This will return an Optional OrderApprovalOutboxMessage. And if this is empty, I will log an info message and return. As I explained previously, if this object is empty, it will imply that the rollback operation is already completed and the duplicate message comes after that. Then, I will get the ApprovalOutboxMessage object and then create and call rollbackOrder method with RestaurantApprovalResponse parameter. And then move these codes into this new method. Then, I will call order saga helpers, OrderStatusToSagaStatus method and get the SagaStatus from the OrderStatus. And then, I will call the ApprovalOutboxHelper save method and update the outbox object. For the parameter, I will call to getUpdatedApprovalOutboxMessage method and get the updated object is in the process method. Finally, after updating the ApprovalOutbox object, in this method, I need to create a new payment outbox object with the orderCancelledEvent because here I got a rejected order from restaurant approval service and I need to trigger an event for payment service to rollback the payments changes. For this, I will call paymentOutboxHelper savePaymentOutboxMessage method. The first parameter to this method requires an order paymentEventPayload. For this, I will create a new method in OrderDataMapper, OrderCancelledEvent to OrderPaymentEventPayload, and convert OrderCancelledEvent object to OrderPaymentEventPayload object. Here, I will simply set customerId, orderId, price, createAt and paymentOrderStatus. For the PaymentOrderStatus, I set CANCELLED here because the event is an OrderCancelledEvent. Then in the rollback method, I will call this new mapper method pass the first parameter of savePaymentOutboxMessage. Then I sent the other parameters for this method, OrderStatus, sagaStatus, and OutboxStatus. As you see, for the outbox, I sent STARTED because this is a new outbox object. Then, I will set the saga ID with the UUID fromString methods reading it from the restaurantApprovalResponse object. Please note that similar to the process method, in this rollback method, to prevent duplicate updates, first, I checked if the message is already processed by reading the ApprovalOutboxMessage object from database. This check will be successful if a thread is already returned from these methods, it means the changes are already committed. In that case, a second thread will not find a processing saga because I set the SagaStatus to compensating in this method. Here, OrderStatus is CANCELLING, so the corresponding SagaStatus will be COMPENSATING. In case two threads of duplicate messages come to the method at the same time, I have an optimistic locking here. Again, similar to the process method. I will have the version fields in approval entity with version annotation which will enable optimistic locking. Let's say two threads try to commit to the changes after reading the same data. Save it version zero. Since the operation is an update operation, only one of them will get the right lock on database objects and commit to the changes. This will increment the version by one. Only then, the second thread will get the lock. And then, it will compare the version of the object, it is red at the start of the method with the current version, which is one. Since the version's mismatch because the origin of version is zero and now it is one, the persistent provider will throw optimistic locking exception, and the changes of the second thread will be roll backed. Finally, there is also a unique index on payment outbox table is in the approval outbox table. The unique index is on type, saga_id and saga_status, so it will be not possible to insert the same data into the payment outbox table even if there was no optimistic lock checks.
