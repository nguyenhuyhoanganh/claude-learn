# Refactoring Payment Messaging module for Outbox pattern

Hi everyone. Let's update the payment messaging module to use outbox pattern. I will go to payment messaging module and create payment events Kafka publisher class. I will delete the previous three publishers because they are using the events directly. However, now I only use the outbox message and encapsulates the event type in this message. In payment event Kafka publisher class, I will let sl4j annotation to create a log variable automatically and use component annotation to make this class as spring managed bin. And I implement payment response message publisher interface, which is the publisher output port in the payments domain layer, as you see here. I override the publishment out here from the payment response message publisher interface. Now if I look at the publisher implementations in the order service, I have two implementations in the order service, one for payment and one for restaurant approval. But here I need only one which will publish the response to the order service. The implementation will be similar to the order service implementations. I will add four fields, messaging data mapper, Kafka producer with string and payment response avro model generic types, payment service config data. I will use this config data to read Kafka topic names from configuration. And finally, I use Kafka message helper from Kafka producer. Then I inject these fields with constructor injection here. In the published methods, I will call Kafka message helper get all event payloads methods with payload string and order event payloads class type, and it will return me an order event payload object. Then I will assign sagaID to a local variable getting it from the order outbox message object and I will log an inform message. I will go to the data mapper class and remove the three methods that I used with the events directly, because now I don't use them, as I mentioned, and I only have an outbox message. Then I will create an E method here order events payloads to payment response avro model. Here I will create a payment response avro model object from the order events payload object, and I will pass the sagaID also as the parameter here in this methods. I will use avro model, new builder methods and set a random ID for this new message, and then I will set the remaining fields from the parameters of these methods. I will set four ID fields, saga, payments, customer, and order. Then I set price, created ads, payment status, and finally, the failure messages. Now I will call these order events payloads to payment response avro model methods in the published methods, and get a payment response avro model object. Then I will call Kafka producer sent methods with parameters, payment response, topic name, sagaID, payment response avro model, and with the call back. For our call back, I will use Kafka message helper, get Kafka callback methods and pass again payment response topic name, then payment response avro model, and order outbox message, and then the outbox callback. Then for the last two parameters, bypass the orderID and then the avro model name as a string parameter. Remember that these outbox callback methods is called after getting acknowledgement from Kafka in the Kafka message helper class. So I only update the outbox table when I get a response from Kafka and I am sure that the message is reached to Kafka, then I will log an info message and then I will use a try catch block and catch generic exception and log an error message here. Now I will do a final change in the payment request Kafka listener class. Remember that in order service listeners, I catch the optimistic logging failure exception, and prevent reading a duplicate message, because this optimistic logging comes when it duplicate message comes. Remember that here in the payment messaging, I have a unique constraint on the outbox table to prevent duplicates. As I mentioned, I cannot use optimistic logging as there is no records yet to update. So here I will catch data access exception. To be sure, I only prevent retrying the unique constraint error. Here I will add postgres dependency in the payment messaging module pom.xml file. And then I get the root cause of the exception here, and check that exception and SQL state is not null, and I will check if the SQL state is the postgres unique violation state. As you see, there is an enum PSQL state class and it has all the states, so I use unique violation value from this enum. In case this is a unique violation, I will log an error message and prevent retrying the processing of this message. Otherwise, I will throw payment service exception so that these Kafka listener methods can retry to process the message. Remember that in order service messaging module, I have catched the order not found exception also. Here I can also have similar exception, payments not found exception for the persist canceled payment methods, as you see here. I will change this exception to payment not found exception, as it fits better here. Then I will catch this here and log an error message and I will not propagate it, so this Kafka listener methods will not retry to process a message if there is no payment, which shouldn't be the case for a correct saga flow. All right, we have completed the payment service changes. Let's write a test in the next lecture to test the double payment processing, and see if we gets this unique constraint violation exception.
