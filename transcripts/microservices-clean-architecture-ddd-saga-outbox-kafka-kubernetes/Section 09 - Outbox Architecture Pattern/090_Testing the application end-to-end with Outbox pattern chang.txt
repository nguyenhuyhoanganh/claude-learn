# Testing the application end-to-end with Outbox pattern changes

Hi everyone. In this lecture, I will test the application end to end. For this, I will send a request from Postman to the order-service and observe the logs, Kafka topics and database tables. Let's first start Zookeeper using docker compose. And then I will start kafka-clusters. Again, using docker compose, with docker compose -f common.yml -: f kafka_cluster.yml up command. I will not start the init_kafka.yml file because I already created the Kafka topics in the previous lectures. If you want to start with fresh data, you can run init_kafka.yml file which will delete and create the topics. Also, you may clean the volumes folder for Zookeeper and kafka-cluster to erase all previous data. Now, I will start customer-service, order-service, payment-service and restaurant-service in IntelliJ. These four services will start the springboard applications and also will reset the database schema, as I have the init_schema and data_sql files in the application configuration as you see here. Now, I will go to Postman and send a post request to order-service using a wallet input JSON request. As you see this is the same JSON request that we have tested, before implementing outbox. Let's send this. Then I will get the tracking ID as a response. Now I will go to the get end points and query the order with the tracking ID. First the order will transit into the paid state and then to approved state. As you can notice it takes around 10 seconds to change the states here because I set the outbox schedulers rate to 10 seconds and I am currently using outbox pattern to complete this side of flow. Now I will go to logs. In the order-service, I see the creating order message in the OrderController. Then order is initialized in the OrderDomainServiceImpl class and then it is saved in the order, CreateHelper and in the PaymentOutboxHelper class, I see that the PaymentOutboxMessage is saved into database and then a response is returned to user with a CreateOrderResponse object. As you see, here we just have persisted to order created message into outbox table and returned to user. There is no event fired until these moments. Now in the PaymentOutboxScheduler, the scheduler will find this outbox message. As you see it says, one OrderPaymentOutboxMessage is received and it is ready to send to Kafka. It reuses OrderPaymentEventKafkaPublisher to publish this events to Kafka and I can see the message in the logs of the KafkaProducerImpl class. Here the payload is created with an OrderPaymentEventPayload object and the OrderPaymentOutboxMessage is sent to Kafka. This outbox message includes the payloads along with the other information like ID, second ID and status informations. Remember, once I get a confirmation from Kafka broker I will update this outbox message as completed. In KafkaMessageHelper logs, I see that I get acknowledgement from Kafka. I understand that with log, received successful response from Kafka. 'Cause this only prints if Kafka producer returns as successful message and in that case I update the outbox message as completed. As you see from the logs of update outbox status in the PaymentOutboxScheduler. Remember this, these update outbox status methods sends to publisher as a callback methods, as a second parameter and it only executes when Kafka returns acknowledgement with the own success methods. At this point, since the message is produced in the Kafka, I should see this message in the payment-service, Kafka listener. Let's switch to payment-service logs. Indeed in PaymentRequestKafkaListener, I see that order payment request is received and the payment is initialized in the PaymentDomainServiceImpl. Then an OrderOutboxMessage is saved in the OrderOutboxHelper class. This outbox message is again persisted into local database this time to the payments database and the scheduler, OrderOutboxScheduler reads this message and sends to Kafka, as you see in the logs of OrderOutboxScheduler. It uses PaymentEventKafkaPublisher to send the message. And in the logs I see that the outbox message is sent and when kafka-cluster returns acknowledgement, the OrderOutboxMessage is updated as completed. This message is meant to trigger order-service to continue the cycle operation. So let's switch to the order-service to see if it gets this message. In the PaymentResponseKafkaListener, I can see that payment response is received and the order-services started to process successful payments. It uses OrderPaymentSaga and updates the order with paid status and updates the payment outbox message with the new status information. At this point, order status is paid and the corresponding saga status is processing. You can see the order status to saga status conversion in these methods, in OrderSagaHelper class. Now the order is updated as paid and the next saga step should be an approval from restaurant-service. For this, order-service creates and separate the outbox message, this time for approval. I can see this in the ApprovalOutboxHelper class logs and if approval outbox message is saved. After this message is persisted, the approval scheduler will be able to find this message in the database and indeed in the RestaurantApprovalOutboxScheduler class, I see that OrderApprovalOutboxMessage is received. It is published using OrderApprovalEventKafkaPublisher class and in the KafkaProducerImpl I can see the message is printed. This time order approval event payload class is used to hold two payloads, as you can see here. Once the OrderApprovalOutboxMessage is sent to Kafka and kafka-cluster returns successful message, order approval outbox table status is updated as completed. As you can see in the logs of RestaurantApprovalOutboxScheduler. Now this should trigger restaurant-service, because it listens this restaurant approval events. So I will switch to restaurant-service docs and indeed I can see the approval request message in the RestaurantApprovalRequestKafkaListener logs. As you see in logs of RestaurantDomainServiceImpl, order is approved. And then OrderOutboxMessage is persisted into restaurant-service local database using OrderOutboxHelper class. The OrderOutboxScheduler receives this message and use RestaurantApprovalEventsKafkaPublisher to send two approval events to Kafka. So a new OrderOutboxMessage is sent to Kafka... And again, the status of this message is updated as completed, once kafka-cluster returns successful message. Remember I set the outbox messages as completed because I have separate schedulers to clean the completed messages from outbox table. This will keep the outbox table small to achieve better performance. Finally, order-service will listen the response from restaurant approval service. So let's go to order-service docs one last time. As you see in the RestaurantApprovaResponseKafkaListener class, I got the restaurant approval response and the order is approved in the OrderDomainServiceImpl class. At this point, approval outbox and payment outbox messages are also updated with the latest statuses. Now the order is approved and the saga is completed. Not that no more outbox messages will be required after that because the saga is completed after getting the approval for order. Now, if I check the order database in pgAdmin console, I will see that the order is approved. Also in the payment to outbox table, I will see the completed outbox message which saga status succeeded. I see a similar completed message in the restaurant approval outbox table here. Remember, these messages will be deleted with the cleaner scheduler. In production, it would also be required to archive this data to another table for future investigations of the outbox messages. In the payment database. I see that the credit entry of customer is reduced to 300 and in the credit history table, I see the 200 debit row, which corresponds to the recent order. The order outbox table has the completed outbox message and also the payment status is completed, as you can see here. Finally, in the restaurant schema, I see the approved order in the order approval table and also I can see the completed outbox message in the order outbox table with the approved status for approval status column. And let's open Kafka tool and check the messages on Kafka topics. For example, in the payment-request topic. I will get the last message and get the key. The data is in .hex formats and I will use an online websites to convert this .hex to .text. As you see, the key is the saga ID, which has the same value of the saga ID column in the outbox table in database. If I convert to value, I will also see the values of the ID. Since the value is in overall serialized formats, here the texts are not encoded and not directly visible, as you can see. To see it, I need to deserialize this message using our deserializer. My Kafka consumers has this ability, so I can see the values in the services. You can also use kafkacat and use it as a consumer to check the data in any Kafka topic. Let's use kafkacat for restaurant approval request. I will use kafka cat -c -b, localhost 19092 and -t restaurant-approval request. Here, -t, is used to pass the topic name. As you see, I can see the messages on this topic using kafkacat commands. Now let's cover some failure scenarios. I will do that in the next lecture.
