It was required to make this class transactional because I wanted to persist database changes here, and then publish the domain events that these methods returns. So if I look at the color methods, create order, there is no transactional annotation but now things are changed. The idea of using outbox table is to have a single assets transaction for local database operations and for outbox table. So I need to use transactional annotation in the create order methods, so that it'll create a single transaction and persist the changes to local database and then insert into the outbox table with this same payment outbox message methods. Because of that, I will add transactional annotation here in the create order methods. Here as you see, this create order and persist order methods are public methods. Otherwise supreme cannot create a transaction for these methods. Actually, these classes order, create commands handler and order create helper are in the same package. So I could remove the public modifier and use package private modifier. However, by default, Supreme uses supreme proxy AOP and all AOP functionality provided by Spring, including transactional annotation, will only be taken into accounts if the call goes through the proxy. That means the annotated method should be in walked from another bean. Here I meet this requirements because I call order create command handler bean from another bean for replication service in pull, as you can see. However, there is a second requirement in Supreme AOP, which is to call a public method. Otherwise, transactional annotation is not taken into account. So I used public access modifier here. Now a new transaction will be created before running this methods and it'll be committed before return. So all the database operations inside these methods including persist order and saving outbox message will run in a single asset transaction which was the main target of using outbox pattern. Note that, you may now remove the transaction annotation in the persist order methods, but also you can keep it because in your transactional annotation we'll simply use the alter transaction by default since the default propagation method is required in spring. So if there is a transaction it'll use the existing transaction otherwise it'll create a new one. And because of that keeping the transactional in the inner methods is okay. So in the end, this create order and persist order methods will run in the same single unit software. In case I call persist order operation from other methods, keeping a transactional notation here is safer although currently I only call persist order from the creator order methods.
