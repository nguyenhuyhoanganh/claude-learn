# Implemeting Domain Events in Order Service domain layer

Alright, let's continue implementing order domain logic with domain events. As you see in the design, I will create three domain events: OrderCreatedEvent, OrderPaidEvent, and OrderCancelledEvent. Let's first create OrderCreatedEvent. I will implement the domain event interface from the common domain module, and pass the order as the generic type. Remember, this DomainEvent is the marker interface to mark the class as a DomainEvent. And also to mark the entity class using the generic type, and I will have the Order and ZonedDateTime fields. I will not create a window for this event object as it has only two fields. So let's create the constructor and also at the getter methods. Similarly, I will create OrderPaidEvents implements domain events with order generic type and I will use those same structure with the OrderCreatedEvent. Also, for OrderCancelledEvents I will implement domain events with order generic type and use order and createdAt fields. Here I want to keep the domain event classes separated, as each class represents a different event. However, here we have a code duplicate. Although it's just defining two fields and getter methods, but still we can get rid of from this code duplicate using inheritance. I will create a new class order events and implement domain events with the order generic type and copy the code from one of the events to here. I will make this order event class abstract as I don't want it to be created. Now, if I extend order event from OrderCreatedEvent and call those super class constructor, I can actually get rid of the fields and getter methods. I will do the same for the OrderPaidEvent and OrderCancelledEvents, to prevent code duplicate. Right now, I will complete this domain core module with the domain service implementation. First, I will create order domain service interface in the com food ordering system order service domain package. I will let validate and initiate order methods that takes order and restaurant entities as parameters and return OrderCreatedEvent. This methods will call the required business methods from the entities to validate and initiate an order. Then I will create payOrder methods with order parameter. This method will return an OrderPaidEvent. Third method will be approveOrder, which will take order parameter and have void return time. Next method is cancelOrderPayment with order and failure messages as parameters and will return OrderCancelledEvent. And the final methods is cancel order, with again order and failure messages parameters with return type void. At this point, I want to clarify some points. First of all, here you see that I return to domain events from the domain service. That means the event firing process will be on the caller service, which will be the application service as you will see in the next lectures. This is an approach that I prefer for domain events handling process so the events will still be created in the domain core either in entity or in domain service. However, the event firing will be in the application service. I do this because before firing an event the underlying business operation should be persisted into the database because if I fire an event and persist operation phase later, I will end up with an incorrect event, which would have never been fired. So why didn't I fire an event in the domain service or entity? Because if I want to fire events in the domain core I need to persist the business logic results in the domain service or entity. Since I want to persist operations before event firing. However, as I mentioned I prefer to delegate the repository calls to the application service to prevent doing unnecessary job in the domain core module, which should only focus on business logic. The domain has no knowledge about event publishing or event tracking. It only creates and return the events after running business logic Application service will decide when and how to raise the events. You may have seen different approach when it comes to the domain events handling process, such as firing the event in the domain entity or in the domain service. However, I prefer to create and return the domain event from the domain core module and delegate to event firing process to application service because of the reasons that I mentioned. A second thing to mention here. Where should I create the domain events, in entity or domain service? Naturally, domain entities are responsible to create the related events as they can be directly called from the application service because in Domain-Driven Design, using a domain service is not mandatory. As mentioned, domain service is required if you have access to multiple aggregates in business logic or you have some logic that doesn't fit into any entity class. However, here I also follow a personalized approach and always integrates a domain service in front of the domain. So my application service will never talk to entities directly. Because of that, I can safely move the event creation into the domain service. With these things in mind, let's implement the domain service. I will start doing that in the next lecture.
