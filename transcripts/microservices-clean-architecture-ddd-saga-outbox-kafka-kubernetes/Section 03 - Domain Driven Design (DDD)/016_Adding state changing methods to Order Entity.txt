# Adding state changing methods to Order Entity

Now as you see, I have four additional public methods that I decided on the design. These methods are the state changing methods to change the state of an order during order processing. So basically, these methods will help me to create a simple state machine to validate the previous state and apply the next state. Let's check these states and the transitions on the project diagram. When an order first initialized, it is in the pending state. Then it will go to the payment service. Payment service can return two response, payment successful or payment failed. If payment is successful, order should transit into the paid state. So in the pay method implementation, I should first check if the order is in pending state. If not, throw an exception. And then, I will set the order status as paid. Let's implement the approve method next. If payment returns successful and order status set as paid, this paid order is sent to restaurant approval. If approval is successful, order should go into approved state. For this case, I first need to check if order is in paid state. If not, throw an exception. And then, set the status as approved. Next method is initCancel. Let's check the project diagram again. If the restaurant approval fails, order is in still paid status, right? In that case, to create a consistent application, order service need to inform payment service to rollback the payment operation. In that case, I should set the order status as canceling and sent a cancel request to the payment service. Please note that I will cover this scenario while implementing SAGA pattern as this is an example of compensating transaction. So what should be the current state for initCancel operation? It should be in the paid state, as the payment should have been done already. If this not the case, I will throw an order domain exception here. Then I will set the order status as canceling. Finally, the cancel methods. For this one, order could be in two different states. First one is pending state. If the order is sent to payment service and payment failed, I should set the order as canceled. And in that case, the current order status will be pending. There is another state that could lead to canceled state. That one is the canceling state as mentioned in case of approval is failed, order is set as canceling and the payment service is called for rollback operation. Then payment service completes the rollback for the payment, order service should set the order status as canceled. So I will set canceling status as the precondition for cancel operation. If the current state is not correct, I will throw an exception as I did in the other state changing methods. And in the end, I will set the order status as cancel here. For the cancel and initCancel methods, I also want to obtain the failure messages from the other services. Remember, for this purpose, I have edit the failure messages fields in the order entity. So, I will get the list of string failure messages as parameter and update the failure message list with these messages. Let's create update failure messages methods for that and call it after setting the status. I will do the same for cancel method. And for the update failure messages method, I will check both parameter list of failure messages and the order objects field failure messages. If both are not null, I will add the parameter messages to the orders messages list. Let's also filter the empty messages here. So I create a stream from the message list and filter the empty ones and collect it to a list in the end. If the orders failure message field is null, I will directly assign the parameter into it. So I will hold to history of failure messages in the order entity for audit purposes and also to return to client when order status is queried using the get end point. Great.
