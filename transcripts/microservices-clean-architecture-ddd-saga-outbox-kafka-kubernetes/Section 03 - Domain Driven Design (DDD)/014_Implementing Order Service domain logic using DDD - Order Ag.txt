# Implementing Order Service domain logic using DDD - Order Aggregate Root

Hi everyone. Let's continue with the order service domain logic implementation. Now I will go to order service-domain-core, and as you see here I have a dependency to do common-domain-module. This will be the only dependency that I'll adds to this core domain module, as it is just to use some common domain classes. Now, I will create a new package com.food.ordering.system.order.service.domain. Then I will create 4 sub packages; entity, valueobject, event, and exception. Great, let's create the first entity object. I will create a new class named, Order. This will be my AggregateRoute for order process. So I will extend the AggregateRoute abstract class from the common-domain-module. If Intelligy cannot recognize the dependency to the common-domain-module, please click on the Maven reloads. As the generic variable, I will use orderId here. So the ID property of the AggregateRoots will be set as order ID, and it'll be inherited in the order class. Then I will add the fields that we have defined while designing this order entity. Let's check the design that we have done in the previous lecture. First, I will add CustomerId, and then add RestaurantId. Remember both these value objects are defined in the common-domain-module. Then, I will add DeliveryAddress. For this one, I need a value objects named StreetAddress. Let's create this in the value object package of order Domain core. I will create a new class, StreetAddress, and add four final fields. ID, street, postalCode, and city. Then I will create the constructor with these four fields and sets them. Then I also add Getters methods for each fields as they will be required for mapping this data in and out of the domain. Finally, I will override HashCodes and Equals methods using the three fields without ID because ID is not important to check equality of an address as this is a value object. I have put ID here just to pass a random ID to the data layer as I will persist the address information in a separate relational table, as you will see, when I implement the data access layer of order service. Now I will return to OrderEntityClass, and import the StreetAddress. The next field in OrderAggregate is price, and I will use money value object from common domain for this. Then I need a list of order items, so I need to create OrderItem entity here. I will create OrderItem class under entity package. For this one, I will extend base entity because it's an entity but not an aggregate route. For the ID fields, I need a value object to define the OrderItemId. So let's create it here in the value object package, I create OrderItemId class, and extend BaseId, and use Long for the generic type. The uniqueness of order item is only importance in the aggregates, so I don't need a UID field here. Having a long value starting from one will be enough. Then, I will add OrderID fields to have a reference to order in the order item. I don't make this field final because these fields will be updated later during business logic. After that, I will need a ProductEntity in the order item to match the item with the real product. For this product entity, having the name and price is enough in this context. So I will create a Product class in the entity package, extend based entity with ProductID as the generic type. And I will add string Name and money Price fields. I will create a constructor with all three fields; productID, name and price. And call the super class setId methods to set the productId. Then I will create the Getter methods for name and price fields. That is enough for this entity for now. One thing to notice here is that I don't need to override HashCode and Equals methods because they're already overwritten in the base class, and it only compares the identifier of the entity. Remember, for entities, we should have a unique identifier, so that's why I use this unique ID in the Equals and HashCode methods. Our return to OrderItem entity now, and next fields in the order item will be integer quantity, and then I will add price and subtotal fields using money value objects. Here, quantity multiplied by price must be equal to the subtotal. Let's create the Getter methods for all fields as they will be needed by Mappers. I will then create a Builder using the Intelligy InnerBuilder plugin, so that it'll be easier to create the object fluencly instead of using a constructor with many parameters. So please go to the plugins in Intelligy, and install InnerBuilder plugin. This plugin will create a Builder pattern as described in the Joshua Bloch, Effective Java, book. I will choose Builder in the generate menu, then I will create it with the final fields, and I will also choose to create the static Builder methods. It cannot use the generic typeOrder itemID to set the baseId, so I just need to replace the ID with the order itemId in the builder. And I will set the super method setId using builder.orderItemId, in the private contractor. As you see, the contractors is private, so we need to use Builder to create these objects. We cannot use the Constructer anymore because private constructors cannot be reached outside of the class. As you see here, there is this static Builder methods also to create a Builder object. I will simply rename this to use Builder as the name directly to make it simpler. Since this module is the core-domain-module, I don't want to pollute this with any dependency, and want to keep my entities and value objects independent even from any framework or library. So instead of adding Lombok dependency, which has annotations to create the Builder pattern, for example, I decided to create it using Intelligy plugins. Also, with this way, we will see the constructor and Builder code directly, it is not hidden as in the Lombok autogenerated code, and if I want to add any validation during the business object creations, I can do that here. In some other modules, like in the infrastructure modules, I will still use Lombok to prevent Boilerplates Java codes. However, for core logic, I don't prefer that. Great, now, I will return to order entity, and import the list class for order itemId list. Next fields in the order entity is trackingId, which will be a simple value object that extends baseId with UUID generic type. I will return this ID to the client so that the client can query the OrderStatus using the get endpoints that I will provide. Then, I will add the OrderStatus using the NM type that I have defined in the common-domain-module. Finally, I will let the failure messages as a list of strings. As you see, these three fields are not final because I will set them during business logic after creating the order entity, so I cannot make them final. Next, I will create the Getter methods for each field. As you see, I'm not creating the Setter methods here although this is not an immutable class. Instead, I will use methods with well defined names for state altering operations. Now, I will again create a Builder using the InnerBuilder plugin. I will replace the ID with orderId in the Builder manually as I did in the OrderItem entity. Then, I will use super class setId methods to set the OrderId. Finally, I will rename the NewBuilder methods to Builder. All right, so now I can start the critical business rules for order processing. I have Order, OrderItem and ProductEntities which are the entities in the Order Processing Aggregate as you can see here. Now, let's look at the design diagram that we have created, and summarize the critical business rules. In OrderEntity, I will have public methods as you can see in the design; validateOrder methods, bin-validate initial order status, total price and item prices. InitializedOrder will simply initialize default values. Pay methods will check if status is pending, and update the status as paid. Approve methods will check if the status is paid, and update as approved. initCancel methods, we'll check if status is paid, and update as canceling. And finally, the cancel methods check if the status is canceling or pending, and update is canceled. To validate and initialize the order, I will also make use of order item and product entities. I will complete that details during implementation. So let's start creating, and implementing the implementation methods of order processing in the next lecture.
