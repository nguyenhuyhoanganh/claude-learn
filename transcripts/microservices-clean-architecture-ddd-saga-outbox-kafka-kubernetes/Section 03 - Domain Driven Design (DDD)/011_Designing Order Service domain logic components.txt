# Designing Order Service domain logic components

Hi everyone. In the next lecture I will start implementing the domain logic of order service using the tactical domain driven design patterns. But first, let's design the core logic here and we can implement that design easily. I will create the order processing aggregate. First of all, I will create an order entity class and make it the aggregate rules. So I will use the order entity to ensure the business environments. Let's think which fields should we need in an order entity. First, I will add the identifier of the order with an order ID fields. As mentioned previously, I will use value objects to hold to fields to bring context, to do values. So if order, order id, I will create an order ID value object and hold an UUID field inside this. Let's create a separate space for value objects and show the order ID class there. Since a customer will create this order I will also add customer ID field. For this field, I will again create a value object and hold a UUID field. Then I need to relate to order with the restaurant that the food will be sent. So I need also a restaurant id. This will be, again, a value object with an UUID field. Then I need to delivery address for that one. I will define a street address field and creates another value object for that. In street address, I will define four fields UUID, id, string street street string post code, and finally string city. Next, I need to keep the price of the order and for that I will use another value object named money. Inside the money value object I will keep a big decimal amount field. Then I will have the list of order items so I will need another class order item and this order item will be another entity. Let's put to relation arrows for order and order item to do order processing aggregate. Here in the order item I will add first order item ID fields as a value object. For this, I will create the order item ID value object. Then I will let order ID fields to relate the order item with the order. The third fields in the order item class will be product fields to relate the product information with the order item. This product class should be another entity as it represents a business object with a unique identifier in product entity. I will put string name and money price fields in the order item. I will also add integer quantity, money, price and finally money sub total fields. So basically quantity multiplier by price should give the sub total for an order item. Great, now I can return to aggregate route order. After adding order items I will also add a tracking ID using another value object. This tracking ID will be used to query the order status so we won't need to expose the internal order writing field. I will use UUID for the tracking ID value object. Then I will add order status value object into order entity. This one will have pending date approved canceling and canceled values, so I will use one of those status values to define the current status of an order. Looks like using an an Java type will be a good fit for this order status object you will see in the implementation section. Finally, I will add a list of string into the order entity to keep the failure messages. This will be helpful to collect the failure messages from other aggregates during business logic and return to the caller service. Great, apart from this, to complete the business logic I will also need two more entity from other aggregates customer and restaurant. For customer aggregates I will have a single entity customer and I will only have a customer ID field. I will just use this to check if customer exists or not so I don't need to add any other fields here for now. Then I will create restaurant entity also in the order service core domain. This one will be another aggregate route and I will use this to get the information about products and use that in the business logic of an order operation. I will create the restaurant entity which is the aggregate route. Here I will need restaurant ID value objects. I will again use UUID fields as the value for this value object. Then I will have a list of products entities to define the available products in a restaurant. As you see here we use a shared product entity in order aggregate and restaurant aggregates in the business logic. Finally, I will have a boolean active field just to check if restaurant is active to complete the order or not. Now finally, I will define the possible domain events that can be generated in the order service. When a client triggers an order process operation I should create an order created event. When I create this event the order status will be in the pending state as it is the first step in order process. In this event, I will keep order object as a reference so I have a reference to order entity, and also I keep created at field which type launch date time not that for zone's state time, I don't create a value object because it is actually a value object that is defined in the JDK as you see here. So I can use it directly as a value object. Then I will create order paid event. This event should be fired when a payment is completed for an order, so the order status will be paid in this case. Again, I will either reference to order entity and also add zone date time to keep the creation time for this event. Finally, I will also add order canceled event. This event should be fired if payment fails or the approval of to order fails during restaurant approval. I will use the order entity and the creation time fields using zone date time as I used in the other order events. I will color the different aggregates and also do value objects and domain events to make this separation visual better. Let's put the relation for the restaurant here also. Now finally, I will also write down the domain logic methods for order entity. Validates order, initialize order, pay, approve, in it cancel, and cancel methods. So I will first validate and initialize an order in pending state. Then I will call state changing methods for order processing and the order is paid. I will call pay methods, and when it is approved I will call the approve methods. If there is a cancellation first I will set the state to init cancel And then finally cancel the order using cancel methods. Right, I didn't go into the implementation details here and just define the basic objects and the business logic methods for order service domain core. Let's start with the implementation and the details in the next lecture.
