# Implementing Order Application Service - DTO classes

Hi everyone, let's continue with implementation of order application service module. I will go to this module and first add the required dependencies. This application service module will use the domain core, so I will need other domain core and also common domain dependencies. Additionally, as I mentioned in this layer I will handle data validations and transactions. For validation purpose, I will add Spring Boot Starter Validation dependency. And to use transactional annotations of spring, I will add Spring TX dependency. As you see, as opposed to the domain core module, here I started making use of framework abilities to make the development easier but I do this only on the auto level in the application service, not in the domain core, which has the core domain logic. And I will create a base package, com food ordering system order service domain. I will start creating the sub packages, first package is DTO to hold to data transfer classes. Here I will create three sub packages, create, track, and message. Under create package, I will create create order command class. This object will have the required command information to create an order, an application service will ask this object from the clients of domain layer. I will use Builder and all our constructor annotations from Lombok and also use Getter annotation to add the gutter methods for the fields of these objects. Builder annotation of Lombok will create a Builder object to create the object fluently, and all our constructor is required to use this annotation. Remember, in the domain core, instead of using Lombok I created the Builder class manually because I wanted to reach each quote clearly to be able to add some checks during object creation, besides, I wanted to make the domain core independent of frameworks to some level. But here in the one layer above in the domain model I can use these Lombok annotations to get rid of some boilerplate Java codes as I won't write any logic here during the creation of DTO objects, they are just data transfer objects. I will add five fields here, UUID customerId, UUID restaurantId, Bigdecimal price, list of order items and order address. For each field, I will also add NotNull annotation from Spring validation library to prevent setting null value for these fields. For the order item and order address I will create two more classes. In the order item, I will have the same Lombok connotations and have UUID productID, integer quantity, BidDecimal price, and BigDecimal subtotal fields. Again, I will add NotNull annotation for each fields as I don't want them to be set as null. Then I will create order class. After adding Getter, Builder and all our constructor Lombok connotations, I will add street, postal code and city fields with string type and I will add NotNull annotation. Here you can also apply some more validation checks using validation annotations. For example, I will add max size check for each field with maximum size of 50 for the street and city and maximum size of 10 for postal code. Now after completing the create order command, let's also create the create order response. So the client will send a create order command to get a create order response as a response object. In this class, I'll use same Lombok connotations, Getter, Builder, and all our constructor. Then I will let three fields, UUID order tracking id, order status and the string message field. I will use NotNull annotation for each field again. Here as you see, I reuse the order status class from the common domain module for this response object. Under track package, I will create track order query class. The clients will use this to query the latest state of an order, I add the same Lombok connotations here and add order tracking id UUID fields with NotNull annotation. And I will create track order response class with the same Lombok connotations. And here I have order tracking id UUID and order status fields. I also have a list of strings to return the failure messages to the clients. Here I use NotNull annotation for order tracking id and order status. But for failure messages, I will not use it because it can be null in case there is no failure. The last package for DTO classes is the message package. Here I will create two classes, first one is payment response. This will hold the response that return from the payment service to the order service. I will use the same Lombok connotations again here, and then I will create the fields. I will start with string id field, then I will add a sagaID field. We will use a sagaID in the messages between the services so I am adding it here, you will see how we will use it in the next sections. I also add order id, payment id, and customer id. Then I add price BigDecimal field and add CreatedAt fields with Java instant type. Here I also need to return the payment status which can be completed, canceled, or failed so these are the states that can return from the payment service. For that, I will create a value object in the common domain module. So I create an Enum type payment status with completed, canceled, and failed values. Finally, I will add a list of string failure messages in the payment response. Second message response is for order approval, so I create restaurant approval response class and then add ids, sagaID, order id and the restaurant id fields and I will add createdAt fields using Java instance type as in the payment response. Again, similar to the payment response, I need to use an order approval status this time here so I create order approval status value objects in the common domain module. Here I will add approves and rejected values for this Enum type. Finally, I will have a list of string for failure messages also in the restaurant approval response. All right, let's continue with mapper class implementation in the next lecture.
