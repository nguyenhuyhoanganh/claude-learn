# Introduction to Clean and Hexagonal Architectures

Hi everyone. In this lecture, I will make an introduction to Clean and Hexagonal Architectures. Basically, by separating the layers and putting the domain layer on the center of the software, will lead to a clean architecture. This can be achieved by creating a dependency rule that leads to only allow, pointing inwards towards the domain layer. For this, we can use Dependency Inversion Principle and Polymorphism to emerge any dependency relation. In the next lecture, I will design the components of the first microservice, order service and show how to apply these principles. In the end, you will have an easily testable software, that is independent of any external element. Clean Architecture also explains the details in the domain logic and dimensions about Entities to implement a critical business rules. And Use Cases to implement the application specific business rules. In the end, Clean Architecture can be taught as an umbrella that covers the concepts of Hexagonal Architecture and Onion Architecture, by adding the details about the core domain logic. All these architectures concentrate on isolating the domain layer and making it the most independent and stable components. The details will be just interchangeable plugins for the domain layer. To explain the component relations, I will now go into the Hexagonal Architecture details. Hexagonal Architecture is also known as Ports and Adapters. The main idea is to divide the software into two main parts, insights and outsides. The insights will be the domain layer that holds the business logic. These parts will be developed first, and it'll not depend on any other layer. So it should be the most independent and stable layer as it is the heart of your software. The outside will include all the dependent layers such as API that is called by end users, databases that is used to persist the results of business logic, a message queue or event store to send notifications to other systems, an external service that needs to be called from the business layer, or even any framework that is used in the software such as Spring Framework. All of these outside parts are not actually your software. They should be behaved as plugins to your software. So the main principle of Hexagonal Architecture is to isolate the domain from any of these dependencies. It'll end up with easily testable applications with isolated business logic, from the infrastructure and data sources. Hexagonal Architecture is invented in 2005 by Alistair Cockburn. He described it as allow application to equally be driven by users, programs, automated tests or batch scripts. And to be developed and tested in isolation from its eventual run-time devices and databases. Here you see two types of adapters. Adapters are the interchangeable components. Primary Adapters are the ones that use the core logic that is in domain layer. They use the input ports to call the implementations that are defined in the domain layer. While the Secondary Adapters are implemented in the external modules like database or message queue. In this architecture, user input is processed by one or more Primary Adapters and passed to the core logic and the core logic interacts with this secondary adapters only. Then output of core logic. We return to the end user, using Primary Adapters again. Realize that we use interfaces on input and output integration, and Dependency Injection is used to pass the implementation of the secondary adapters to the core logic and Primary Adapters to the outside such as API. There are numerous advantages of using Clean and Hexagonal Architectures. First of all, you should understand that it is good for mainly long lasting applications. It'll allow to leave as many options open as possible for as long as possible. With such applications, you will realize that you always need to adapt for new technology changes to keep your software in a good shape. As mentioned, these changes has nothing to do with your business logic. For example, today you may use a relational database. Tomorrow you may want to adopt for another relational database or even to a no SQL database. In this case, by keeping your business logic separated you will be able to easily change your data source. In a traditional layered architecture. Say with three layers, user interface, business and data layer. It would have all of our dependencies points in one direction. Each layer above depending on the layer below. So in that case, your business layer will depend on the data layer. This will prevent changing the data layer without touching the business layer. With Clean and Hexagonal Architecture, all dependencies will point to the business layer making the business layer independent of any other dependency. In the coming lectures, I will start writing our first microservice using this Clean Architecture. Then you will see how ports and adapters will help to reverse the dependencies and make the business logic independent. I will be using Dependency Inversion Principle to make this happen. With Dependency Inversion Principle and Polymorphisms, any source code dependency can easily be inverted and the low level modules like the data source layer will be plugins to high level modules like business logic. In the next lecture, I will use a diagram to explain this dependency inversion on the first microservice, which is order service. With Clean Architecture, you will be able to delay the implementation decisions of all dependencies. And can just implement your business logic without thinking any limitations of any data source or framework. You can even test your business logic completely by simply marking the dependencies. Apart from that, as mentioned, you can replace any adapter implementation without touching to the business layer. And you can maintain each layer separately without affecting other layers. It'll also allow to separate development and deployments of different layers and modules. Furthermore, the separated layers are naturally easier to understand because each of them focuses on its own logic. When I count all these advantages, you might think, is there any disadvantage of using these architecture? In software development, every solution has pros and cons. With Clean or Hexagonal Architecture the price you need to pay is writing more code. Sometimes you even need to duplicate some codes like having different data transfer objects for different layers to represent some data. Yes, you will write some more quotes but it'll pay you these efforts by having a fully maintainable and easily testable application. So your application should be independent of frameworks user interface, database, and external services. Conforming to these simple rules is not difficult and it'll save you a lot of headaches going forward. In Clean Architecture, the core business logic is implemented in the entity objects. Entities consist of the Critical Business Rules of the system. For example, prior to creating an order, what do you think the state of the order, checking that the total price is correct or checking if the order is in stock, are the critical rules that need to run before placing an order. One layer of all the Entities, you will have Use Cases which handles the use cases of a system by orchestrating the entity objects. Use Cases harmonizes the Entities by calling them in the correct order and to achieve the Critical Business Rules. Besides the critical rules, there could be some application specific business rules such as having a discount on an item temporarily or checking if a user doesn't exceed it. And allow daily purchase limit. These type of rules should be implemented in the use cases. At this point, I also want to briefly mention Domain Driven Design next to Clean Architecture. In the next section, I will cover Domain Driven Design in detail while implementing the domain layer of the services. Here, what I want to show is that, the high level approach is the same in Clean Architecture and Domain Driven Design. Both has a domain layer isolated in the core of the system and attaching the lower level dependencies into it, such as user interface, database, and external services. However, there is a slight difference in the domain core itself. In the Clean Architecture we have Entities which are the core domain elements and keep the enterprise business rules. One, they will hire. You see the Use Cases that keep the application business rules. Use Cases are responsible to orchestrate and call the Entities as per the use cases requirement. In Domain Driven Design, on the other end, we still have the Entities that have the core business rules but this time it has an additional Aggregate and Aggregate root concepts. An Aggregate root is the main entity that orchestrate the core business rule of the current context. This context is called as Bounded Context. An Aggregate is a group of business objects which always needs to be in consistent states. Therefore, we should save and update Aggregates as a whole inside a transaction. An Aggregate root is a class which works as an entry point to our Aggregate and all business operations should go through the root. This way, the Aggregate root will make sure that the Aggregate is in a consistent state. One layer above the Entities, this time in the Domain Driven Design we have domain services. This can be taught as the equivalent of Use Cases if we compare with Clean Architecture although conceptually they are not the same. In the domain service, you should have the business logic that spans multiple Aggregate roots so that they can be implemented in a single Bounded Context. A domain service can also include a business logic that doesn't fit to an entity naturally. Additionally, there is application service concepts in Domain Driven Design. Application service will expose the required business layer methods to the outside using parts, and these parts will be implemented in the domain layer itself. In the application service we can also have the data mappings, validations and transaction management. Basically, application service should be responsible to make any data adapter calls and gather the data to pass into domain service and Entities. Remember, domain service and Entities has the core business logic and they instill these things, like gathering data, mapping the data or validating the data. Those are the responsibility of application service. As you see, there's a slight difference on the implementation of domain logic between Clean Architecture and Domain Driven Design. I will be using Domain Driven Design concepts and namings when I implement the domain logic of the two microservices in the implementation sections.
