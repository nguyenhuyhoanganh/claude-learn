# Container module: Adding spring boot starter class and config

Hi everyone. As a last module to order service, I will implement the order container module and complete the order service. Let's go to order container module, and first, I will update the Palm XML file to add Spring Boot starter dependency. This is is required, because I will have this Spring Boot Main class in this module, and it'll start the Spring Boot application for the order service. I will also add Spring Boot maven plugin to create a runnable jar file for this microservice and also to create a Docker image during maven install command using the build-image call of spring boot maven plugin For the image name, I will use {project.groupid}/order.service and project version. Now I will create the base package for this module. Comfort Ordering System Order Service Domain and then I will create order service application class. I will let Spring Boot application annotation with ScanBase packages com food ordering system. This annotation will mark this class as the Spring Boot application. The ScanBase packages property is important when working with multiple modules. With this property, any package on the other modules in this account as long as it starts with com food ordering system as the package name. Then I will add the static void main method and call spring application run method to start the service. As you see, I sent the order service application class, and arguments as the parameters to this run method. Here, I also need to add two more annotations. First one is entity scan annotation, with base package, com food ordering system, order service data access. This one is required for a multi-module application and here I set a strict package name, so only the entities, that sits on this package will be scanned as JPA entities. Finally, I will let enable JPA repositories annotation and set base packages again. So any JPA class that sits under this package, will be scanned as a JPA repository and I will create another class, Bean configuration. I will mark this class with configuration annotation so this will be a spring-managed configuration Bean. Then I will add order domain service method with return type order domain service, and here return a new order domain service impl object. I will put Bean annotation on these methods. So what does these methods do? Remember, in the domain core, I haven't added any spring dependency. So the order domain service, is not marked as a spring Bean in the domain core module. But I still want to use the order domain service as a spring bean and injected to the order application service module. To use this order domain service as a spring bean, I need to register it as a Bean. And I'll do this here in this Be Configuration class. So when this Spring Boot application starts, it'll register the order domain service as a spring bean, although I don't have a dependency to the spring on the order domain core. Then I will let application yml file, and at the configuration data. Here, I set the HTTP server port as 8181, and then set the log level as back for the base package. Then I set the names of to four Kafka topics, payment request and response, and restaurant approval request and response. As you see here, I use order service as the prefix for this topic names. Then here, I'll set the spring JPA and data source properties. First, I will set open-in-view property to false. This property will disable open session in-view which forces the persistence context to stay open. So that the view layer can trigger the proxy initialization. This will keep a database connection open for a long time which would have really bad effects on database performance. It's enabled in spring by default, so I set it to false here, to prevent this behavior. Then I have show-sql, true. Which simply will show each SQL on the locks which is good for the back purposes. As you see, I set the postgresql9 as the database platform, and the hibernate Dialect. Then I set the connection URL using local host, with default port 5432 and with the Postgres database. For the current schema, I used order here. So I will create a schema called, "order" in the Postgres default database. Here you also see Binary Transfer and rewrite batched inserts through properties. With binary transfer, the data will be transferred from Postgres server to JDBC driver in Binary form. So it'll be transferred faster as this will eliminate the need for conversion like converting a number from their text representation to their Binary representation. With the rewrite batched inserts property, I will increase the batch insert performance, by rewriting the batch inserts to use multi-values. That means, it'll use a single insert statement with multiple values instead of using multiple insert statements which will increase the insert performance. And this string type on specified property, will tell JDBC driver to send all strings untyped. I use this to use UUID fields, and to prevent string checking on UUID type on Postgres. You see the database username and password here. This password should be encrypted. You may change how to encrypt your secrets and also to change how to externalize your configuration at the same time. You can have a look at my other course, Events Driven Microservices, Spring Boot, Kafka and Elastic search. Here, I will leave the password as plain text, just to focus on the main concepts on this course. Then I set driver class to org Postgresql driver, and set platform to postgres. You see that I have an init-schema.sql file here. I will create it after finishing this application yml file. With initialization mode always, init-schema file, will run each time I start the Spring Boot application. Remember, I have created three configuration classes in the Kafka config data module. Kafka config, Kafka producer config, and consumer config. Each class has different prefixes. Here you can see that, I use these prefixes and set the properties for Kafka brokers, Kafka producer and consumer. For Kafka config, I set Bootstrap servers which sets the broker addresses in the Kafka cluster. I use local host for host name, and use the port that I exposed in the docker compose file of Kafka cluster. Then I set schema registry url, which is local host with port 8081, as you see in the docker compose file of Kafka cluster. Here I also set number of partitions and the replication factor to three. Remember that, with three partitions, I can run three concurrent Kafka consumers and scale better. And with replication factors set as three, I can have better resiliency because it'll keep the replicated data in three different partitions. In three different brokers. Remember, I have three brokers in Docker Compose definition of Kafka cluster as you can see here. For Kafka producer config, I set key serializer class as string serializer. Because my key will be the string representation of order ID. And for value, here I use KafkaAvroSerializer, which is a class in Confluent library. Remember that, I have created the Avro models in the Kafka model module to send data to Kafka in AvroSerialized form. For the compression type I use snappy here. The compression options that Kafka supports are, Gzip, Lz4, Zstd, and Snappy. Among these options, Snappy gives a good balance of CPU usage, compression ratio, speed, and network utilization. For example, jzip will compressed more, but it'll be slower and Lz4 will compress less, and it'll be faster. But in that case, network bandwidth will be higher. Acknowledge property is set to all here. That means the Kafka producer, will wait acknowledgement from each broker, before confirming the produce operation. If you use acknowledge one, a confirmation from the target broker that gets the requests from the producer clients will be enough. And with acknowledge zero, producer will not wait any confirmation from the Kafka brokers. As you can imagine, this will lead to a non-resilient system. So keeping the acknowledge all is a best practice. For page size, Here I use 16 kilobytes which is the default value. And also, here I have a boost factor to allow increasing the batch size. This batch size, will be used to send the data in batches from producer to Kafka Brokers. Linger-ms is used to add a delay on producer, before sending the data. This makes sense when there is a light load on producer. With light load, producer will send data to broker, even if the batch size limit is not reached. So by using a delay with this linger-ms property, you can increase the batch size so you can increase the throughput on the producer side. Request-timeout is the timeout value, that producer will throw a time out error, in case no response comes from the Kafka broker. And finally, here I set the retry count to five. That means, it'll retry five times in case of error on the producer side, right? Let's continue with the Kafka consumer configuration explanations in the next lecture.
