# Messaging module: Adding Mapper and Config Data

Hi everyone. In this lecture, we will implement the order messaging module. As you can remember, I have completed the generic Kafka modules in the previous section. In the messaging module, I will use that generic modules while implementing the adapters for the publisher output parts of the order domain layer. Also, here I will create the Kafka listener implementations to be used by the domain layer. Let's first set the required dependencies. I will need Kafka producer, consumer, and model dependencies. As usual, I want to add them to the base POM.xml file, with project version, but they're already added, as you see here. Now, in the order messaging module, I will add Kafka producer Kafka consumer, and Kafka model in the dependencies section. As you see, the order application service is already there, since we will implement the output parts, that are interfaces, from the order domain layer. I will create a base package, com food ordering system order service messaging, and create three sub-packages: publisher Kafka, listener Kafka, and mapper. Let's start with mapper class. -: I will create order messaging, data mapper class, and mark it component annotation. First methods I will add here is order created events to payment requests Avro model. These methods will return payment request Avro model, and take an order-created event parameter. Here, I will create a payment request Avro model object to send it to Kafka. First, I will get the order object from the order created event. Then, I will use new builder methods of payment request Avro model class, and set ID with a random UUID, and then, set an empty string for the saga ID for now. I will fill this value when we implement saga pattern in the coming sections, and then set customer ID, order ID, and price from the order object. Then, I will set created at field, and finally, the order payment status. The order payment status represents the possible status values to send from the order service to payment service. Here, I will set it as pending. Another possible value is canceled state. Remember, when an order is filled at the restaurant service, I need to call the payment service to roll back the operation, and in that case, I will have a canceled status for the payment. So, I also create order canceled events to payment request Avro model methods to create a payment request Avro model object from the order canceled event, and this time, I will set the payment order status as canceled. Next, I will create a configuration data class for order service, which will map the complete data into a Java class. I will use this to get the target Kafka topic names. For this, let's go to the order application service module and create the order service conflict data class in that module. I will use data Lombok connotation, and use configuration, and configuration properties annotations, and use order service prefix. So, this class will lot the configuration data from the order service prefix, from a configuration file, like from the application YAML file. I will create four string fields: payment request topic name, payment response topic name, restaurant approval request topic name, and restaurant approval response topic name. As you remember, I will use four Kafka topics to communicate between the microservices using domain events. All right, let's continue with the publisher implementations in the next lecture.
