# Messaging module: Adding Publisher implementations

Now, I will go to Publisher Kafka package and create Create Order Kafka Message Publisher class. Here, I will implement order created payment request message publisher interface from the order domain layer, which is an output port, in hexagonal architecture terms. I will use component annotation and make this publisher class as spring pin, and also, I will add SLF4J annotation to create a SLF4J log variable automatically. Here, I will create three final fields: messaging data mapper, order service config data, and Kafka producer with string and payment requests Avor model, generic types. Remember, this Kafka producer is the interface that is implemented with a generic approach in the Kafka producer module. Now, I will inject these three fields using constructor injection. In the publish methods, I will get the order ID as a string variable, and then, log an info message. Then, I will create payment request Avor model object by calling messaging domain mapper, order created event to payment request Avor model methods, and send the order created event as the parameter here. And I can call Kafka producer send methods and pass payment request topic name as the first parameter to the send methods. I will read it from the configuration class that I just created in the order application service module. So, this topic name will come from the configuration. Then, I will send order ID as the second parameter. This will be the key of the Kafka data, and, as the value, I will pass the payment request Avor model object. Finally, I will pass a callback methods to get the results later asynchronously. So, I will create get Kafka callback methods, with payment request topic name and payment request Avor model parameters. Here in these methods, I will return a listenable future callback object, and use send result generic types with string and payment request Avor model, which are the types of TN value in my Kafka message. I will override on failure and on success methods. In the on failure methods, I will log an error message, and in the success methods, I will log an info message, including order ID and Kafka metadata information, like topic, partition, and offset. These methods seems to be only logging information for now. However, when I implement saga and outbox patterns, the importance of these methods will increase, and I will be refactoring this code to obtain a highly resilient system. Stay tuned for that. After sending the message to Kafka, I will log an info message, and then catch the generic Java exception to log an error message, in case of an error during Kafka send operation. Then, I will create cancel order Kafka message publisher class, and implement order canceled payment request message publisher interface from the order domain layer. I will again add component SLF4J annotations for this class, as in the create order Kafka publisher class. I will have a similar implementation, so I will copy it from the create order Kafka message publisher class, but I will have the order canceled event as the parameter of the publish methods. And I will change this log message, and call the order canceled event to payment request Avor model methods in the messaging domain mapper to create a payment request Avor model from the order canceled event. I will use the same get Kafka callback methods. So, let's move these methods to a common helper class to reuse it from each publisher class. So, I will create order Kafka message helper class, and add components and SLF4J annotations. Then, I will create get Kafka callback methods here with public access modifier, so that I can reach it from other publisher classes. Then, I will call these methods from both publisher classes. In create order Kafka message publisher, I will delete the private get Kafka callback methods. Then, I need to create a need field for the order Kafka message helper, and inject it. And then simply call the methods from the helper class. I will do the same for the cancel order Kafka message publisher. Finally, I will create a pay order Kafka message publisher class, and implement order paid restaurant request message publisher interface, from the order application service module. I will have the same component and SLF4J annotations. This publisher will publish the data to another Kafka topic, so it will be slightly different than the order create and cancel publishers. Here, I will inject three fields again, messaging data mapper, Kafka producer, and order service config data. For the Kafka producer, this time, I use restaurant approval request Avor model as the Kafka message type, because I will send the data to restaurant approval request, Kafka topic, which will expect a type of restaurant approval request Avor model. In the published methods, I will get the order ID. Then, I need to create a restaurant approval request Avor model object from the order paid event. To do that, I will create a new methods in the mapper class, order paid event to restaurant approval request Avor model. And then, I create this restaurant approval request Avor model object from the order paid event object. As you see, I set the restaurant order status as paid for this request object, because I will call the restaurant approval only when the payment is completed, and the order status set as paid. And again, I set an empty string for the saga ID for now, here, and I will fill this value when we implement the saga pattern in the coming sections. Now, I will call these methods in publish methods, and get the restaurant approval request Avor model. Then I will call Kafka producer send methods, and for the topic name, I will use restaurant approval request topic name. For key, I will send order ID, and for value, restaurant approval request Avor model. As I did in the other publishers, I will create and send a callback methods. This time, I need to use restaurant approval request Avor model as the generic message type in the callback methods, so I cannot reuse the same methods here. Let's make this get Kafka callback methods, a generic methods to reuse it also from this order paid event publisher. For this, I will create a generic variable, T, in this methods and replace the payment requests Avor model with this T in all places. I will rename the parameters as request Avor model and response topic name to make them generic in the names. And then, I will add a new parameter, order ID string, and use it in the log info message. Finally, I will also add a string, request our model name parameter, and use it in the log error message. Now, in the pay order message publisher, I will inject this helper, and call to get Kafka callback method. I will pass the topic name, request Avor object, order ID, and the restaurant approval request Avor model string value. Then, I will log an info message. And then, I will use a try-catch statement to catch the generic exception here, and log an error message in case of exception occurs. Now, I need to change also the other publishers to use the generic Kafka callback methods. In create order publishers, I will send order ID and payment requests Avor model string parameters to do get Kafka callback methods. Then, in the cancel order Kafka message publisher, I will again send order ID, and this time, send payment requests Avor models string as the fourth parameter. Great, I have created separate publishers for each type of domain events. Although the publish method implementations look similar, it is wise to keep them separated in different publisher classes to easily maintain and change each publisher separately. And for common operations, like the Kafka callback methods, I still use a common helper class. All right, after creating the publisher implementations, let's continue with the listener implementations in the next lecture.
