# Container module: Explaining kafka consumer properties

Hi everyone, let's continue with the Kafka consumer configuration explanations. I set key deserializer to string deserializer and value deserializer to KafkaAvroDeserializer. In the consumer implementation, to consume the serialized data, I need to define the correct deserializers to read key and value. The key is the string representation of order id and value is the Avro models defined in the Kafka model. As you remember, we have used Avro own data type to hold to data in the Kafka topics. When I put to data on Kafka topic it was actually serialized into Avro data formats. So to be able to consume this Avro data I need to define the correct deserializers, and here it is the generic Kafka Avro deserializer from Confluence library. Consumer group id property. This property ensures that a Kafka consumer doesn't start from beginning each time while consuming a Kafka topic. Instead, it'll continue from the last read item. As you remember, to do that, a Kafka consumer holds an offset value. This offset is matched with a consumer group using the unique id. For example, if you make this consumer group id a random value, what would happen each time you restart your Kafka consumer service? Since an offset is matched with the group id it will not see any offsets with new randomly created consumer group id so each time you will read the data from the start. This might be a use case if you really want to read the same data again and again, but mostly it's not preferred. And to prevent the application, a specific id is used for this property consumer group id. As you see, I used two different consumer groups for payments and restaurant approval. Auto offset reset property. With this property, if there is no offset remains in the Kafka server, you say that you want to start reading from the beginning of a partition. So when you read a Kafka topic first time, if you set this property as earliest, it'll start reading from the beginning of a partition, which is the preferred behavior most of the time. If you set this property as the latest it'll reset the offset to the latest records, but in that case, you can only read the new data that comes after you start your service. Specific Avro reader. Since we use Avro data type while holding the data on Kafka we have to set this specific Avro reader key property as true in the Kafka consumer config. Bench listener. Bench listener property allows to consume the data in batches instead of consuming them one by one. As you remember, I set this property in the Kafka consumer config spring bin. You can also see the other properties that I set into the Kafka listener container factory. Auto startup. If this property is set as true, Kafka consumer will start consuming data immediately. If this property is set as false, the Kafka listener will not start automatically. As you see, I set this is property in the Kafka consumer spring bin, and the value is true. Concurrency level property will creates multiple threats if it is set to more than one. Here I set it as three, which is equal to the partition number and it is required for maximum concurrency and higher throughput. Because it's partition three, we can have at most three consumers as I mentioned previously. If you create more than three consumers it'll be idle until you add another partition. Session time outs milliseconds property sets the time out for heartbeat threats and specifies the amount of time between that broker needs to get at least one heartbeat signal from the consumer. If broker doesn't get a signal in this timeout interval it'll mark the consumer as dead, and it will remove it from the consumer group. The default value for this property is 10 seconds. Heartbeat interval milliseconds property sets the frequency of sending heartbeat signals by the consumer. So if I set this as three seconds, which is the default value, then for every three seconds the consumer will send a heartbeat signal to the broker. It is recommended to wait for missing some heartbeat signals before marking the consumer as dead because a network can fail temporarily that's why I set the heartbeat interval to one third of session time out milliseconds here so that it will try three times before timing outs and before consumer will be removed from the consumer group. Max poll interval milliseconds property is for user threats. If message processing logic is too heavy it might take more time than the time interval. In that case, coordinator will mark the consumer as dead and it'll leave the consumer group and coordinator will trigger a new round of rebalance to assign partitions to do other available consumers. So it is important to set this marks poll interval property according to the processing time requirements of your application. Max poll records property sets the maximum records to fetch in each poll. That means if I set this property as 500 then a consumer who fetches the data it can fetch 500 records at maximum at a time. Max partition fetch bytes. This is the maximum bytes that can be fetched in each poll, so this puts another limit on the consumer. For example, if you set the max poll records as 500 you may expect 500 record each time. But if this 500 record holds more bytes than the limit defined in this max partition fetch property you cannot get 500 records at a time. Here I set it as one megabyte, but you also see another property to boost these value. So you can use this property to increase these limits and tune your consumer according to your environment and data. And finally, poll time out milliseconds property. When a consumer tries to fetch data and if there is no data on the Kafka topic it'll wait for some time and block the client codes. This property sets these time outs on the consumer while fetching the data. So if I set this value as 100 it'll block on the poll methods for 100 milliseconds and wait for the new records. If you set this time out value too large it'll block your client code for a long time so your threat will be blocked instead of doing some real work. On the other hand setting this value too small will cause CPU stall because in your polling logic you will have a loop, and if poll timeout is set to very small value your while loop will run very frequently and it'll use your CPU resources. So it is again important to tune this value and set accordingly. Great. Let's finish order service with the Init schema SQL file. I will add this file in the next lecture.
