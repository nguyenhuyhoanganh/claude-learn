As mentioned in Debezium documentation, to use Postgres in change data capture we basically need to enable logical replication. This means we need to replicate the data written in the transaction log of Postgres. As I mentioned in the previous lectures the transaction log of Postgres is called write ahead log. So we need to replicate the content of the write ahead log. And while doing that we need to decode the content that will be understood by the client of this replication streaming which is Debezium here. Logical decoding is the process of extracting all persistent changes to a database table into a coherent easy to understand format which can be interpreted without detailed knowledge of tool databases internal states. Previously there was Wal2Json and decoderbufs pluggins which are used to decode the content of write ahead log to JSON or protocol buffers respectfully. These plugins were required to be installed and pointed in the PostgreSQL configuration file. However, starting with Debezium 0.10 version Debezium supports replications streaming using pgoutput which is supported after PostgreSQL 10. This means that a logical decoding output plugin is no longer necessary and changes can be emitted directly from the replication stream by the connector. Now I need to describe what is a replication slot in PostgreSQL. A replication slot is for logical decoding such as wal2json or pgoutput, and it is used by Debezium. In the context of logical replication, a slot represents a stream of changes that can be replayed to a client in the order they were made on the origin server. Each slot streams a sequence of changes from a single database. As mentioned in the Postgres documentation multiple independent slots may exist for a single database. Each slot has its own states allowing different consumers to receive changes from different points in the database change stream. For most applications a separate slots will be required for each consumer. So to summarize, replication slot of Postgres is the final destination of the transaction log that will be read by the consumer. If I draw the relation between the right ahead log, the output plugin, the replication slot and the consumer, When the data is changed in a row in a Postgres table that change is recorded in the write ahead log. Then if logical decoding is enabled for each data manipulation such as insert update or delete, the logical decoding translates the data manipulations using an output plugin. As mentioned, I will use the default pgoutput plugin here. The output plugin simply changes the records from the write ahead log format to the plugin's formats which is JSON in the pgoutput plugin. Then the decoded data is written into replication slot and from there the consumer can read this data to be used in the downstream components. So the plugin that I will use will be the pgoutput plugin and the consumer will be Debezium source connector here. The replication and logical decoding in PostgreSQL provides an efficient way to stay up to date with data changes in your Postgres database We write ones to the reliable Postgres log then use that data in multiple consumers for different purposes such as with Debezium source connector to use with outbox pattern. Here, instead of a pull model where each component queries Postgres at some time interval, we use a push model where Postgres notifies the other applications for each change. So this will be a base for change data capturing implementation of outbox pattern which will work in near real time thanks to this push model as opposed to the pull model that is used in the pulling the outbox table implementation. Here an important thing to keep in mind that in case of postgres restart, a slot may resend the changes so it works with at least one semantic and the consumer needs to handle this situation which is handled in Debezium connector. However, after getting the data from slot the Debezium client will use a Kafka producer to send the data to the target topic and in case there is a network issue in the acknowledgement at that point, the data can still be sent twice or more to the Kafka topic, so it's still working with at least one semantic with Debizium connector. Therefore, I will keep in mind this in implementation and use the deduplication of the same messages in Kafka consumers, as we did similarly in the pulling the outbox table implementation.
