# Introduction to Change Data Capture

Hi everyone In this section, I will introduce change data capture approach to use it in the outbox pattern implementation as an alternative to the previous pulling the outbox table implementation. First of all, what is change data capture? Change data capture is an approach to get the database events in near real time by using database transaction logs. So it uses a push method instead of waiting and pulling in some time interval. Thanks to this push method approach, it has lower overheads and more close to real time. So it reads the database changes from transaction log, which is called Write Ahead Log in Postgres, and these logs are actually nothing but the data manipulations that are done by each transaction running on the database engine. Basically, every insert, update, and delete operations are written into transaction logs in the filesystem for recovering the data back to a consistent state in event of some failure while it is writing information to disk. Writing to transaction logs is fast, because no ordering or database constraints are in place in this log, as opposed to the real database table files. To implement change data capture, I will use Debezium open source platform. Debezium provides Kafka connectors to write the data into Kafka and also provides source connectors for various databases such as Postgres, which is the database that I use in this course. So I will simply add debezium/connect docker image into my Kafka cluster docker_compose file and run the Debezium connector to send data to Kafka. After running the connector, I will register a Postgres source connector to start listening transaction logs of the outbox table in Postgres. So if you look at how change data capture with Debezium works, each insert, update, and delete on a database table are inserted into an append-only log on disk on all databases. Debezium listen these row-level changes and captures changed data, and then sends this data to Kafka using Kafka connector. So instead of pulling the table and consuming CPU, here it listens the transaction logs on disk and acts when there is a new data on the logs file. This way, it creates realtime streaming solution with a push approach. If you remember the outbox pattern implementation, we will be replacing the schedulers written in Java using Spring Boot scheduled annotation, and instead use Debezium Kafka connector. with PostgreSql source connector.
