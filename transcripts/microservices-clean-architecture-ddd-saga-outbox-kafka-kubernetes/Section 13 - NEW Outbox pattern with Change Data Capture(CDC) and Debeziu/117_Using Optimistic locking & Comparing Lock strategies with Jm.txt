# Using Optimistic locking & Comparing Lock strategies with Jmeter load test

Hi everyone In this lecture, I will run the JMeter load test using optimistic locking instead of pessimistic locking. Remember that in the previous lecture, I have used Lock annotation with lock mode type, pessimistic write On the credit entry JPA repository, find by customer Id method. This was required because I fetch a customer credits and histories in the same transaction and do some business logic checks using those values. So, fetching the credit entry and history should be atomic while sending multiple requests using the same customer ID simultaneously. To use pessimistic locking, I simply apply a select for update query which will lock all the transactions that are trying to select data from this table for the same customer ID. So I serialize the transactions and run one by one to overcome the race condition here. There is another option to accomplish the correct results which relies on optimistic locking. Optimistic locking doesn't get a lock on the first select but relies on comparing the version of the row during commit operation with the row that is fetched in the first place. For this, it requires a version integer field to make the comparison. So this version field is updated in each change to the row and if the version is changed between the select and update of the row, an optimistic locking exception is thrown. If the versions are the same, the operation will be completed successfully by committing the transaction. So when one of the transactions acquired the update lock, the other ones will be blocked at that moment and the transaction with the update lock will compare the current row version with the version that is fetched previously. If they are equal, update will be performed and, otherwise, an optimistic locking exception will be thrown. In case of an optimistic lock exception, we can just retry the operation hoping that there will be no concurrent update in the second try. So let's see this in action.
