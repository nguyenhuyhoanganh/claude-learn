In the previous sections, we focused on the implementations of different architectural microservices patterns and we sent the requests one by one to the order service for happy flow and for failure scenarios. So if I come to the possible unique constraint exception here, when can this happen? Here we have a list of input objects. Each of them handled one by one in this forEach loop by calling the applicationService method as you see here. Here we have a transactional method and we actually save and commit the results into database after returning from this method. So consider in a list of three objects We finished the first two of them and inserted to outbox table records. And in the third one we got an exception that is not handled here in the listener. In that case, the exception will be propagated to the caller and this will cause not committing the Kafka consumer offsets for all the items in the inputs lists. In that case, when this listener poll the next set of inputs, it'll actually read the first two items that are already processed and saved to the outbox table. Then it'll give a unique contraint exception in that case. And if I don't catch and eliminate the message here, it'll keep reading that message from Kafka topic because the message offset will not be committed as a result of unhandled exception. So by catching unique constraint exception and not doing anything, I will make sure the same message will not be read again and again because the offset will be committed after returning from the listener method, when no exception is thrown because Kafka consumer offsets are only committed after returning from this received method that is annotated with KafkaListener annotation. So the offset will be committed to Kafka for all the records in the input list only after returning from this method. And if I got an exception and do not handle it here for any record, supreme will simply keep committing the offsets for old items in the list. This will cause to read the same items again in the next poll from the Kafka consumer. Remember, Kafka consumer maintains an offset value to keep track of the last read item. So in happy flow it reads the items, process all of them. And after returning from the receive method it'll commit offsets for each item. But again, in a failure case, it'll not commit offsets for any of the items in the list. And if this happens in the forEach loop after processing some records, that processed records will not be committed to Kafka and will need to be reprocessed. So I will catch data access exception here and handle a unique constraint violation case. I will get the similar catch implementation from PaymentRequestKafkaListener class. To use PSQLState, I will add PostgreSQL dependency here in the pom.xml file. A second option here would be using a listener with a single item instead of a list. This decision actually depends on the possibility of getting an exception in processing the lists. If there is less chance of getting an exception, it's better to keep a list of inputs for better throughput. However, if we keep getting lots of exceptions, then it'll be costly to reprocess and get unique constraint exception for the messages and eliminating them. So here I will keep the list of messages and catch the exception because I don't see high chance of getting the exception here. In PaymentKafkaListener, I will consider a scenario where the other option getting a single item in the listener will make more sense. Stay tuned for that.
