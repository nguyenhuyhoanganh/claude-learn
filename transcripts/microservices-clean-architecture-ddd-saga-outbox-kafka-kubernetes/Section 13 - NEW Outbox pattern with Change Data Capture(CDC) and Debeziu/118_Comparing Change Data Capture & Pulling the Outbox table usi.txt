As you see, the outbox pattern is significantly slower with pulling the outbox table when compared with the change data capture approach. Even if you lower the scheduler rates from 500 milliseconds to a lower value, it'll create some duplicate and retry operations, as a I mentioned before. So no real performance gain we can get from that. We can actually see the unique constraint violations in the logs, even with 500 millisecond scheduler time interval. So if you make it a lower time interval, multiple schedulers will possibly get more same messages from the outbox table, causing more unique constraint violation and more retries, which will cause the system to run slower. These results were expected actually because change data capture provides a solution close to real time with a push approach, instead of keep pulling the table with a scheduler. The pulling the outbox scheduler implementation doesn't scale well, as we see when the concurrent transaction size is getting bigger. Now, here we can actually do some more improvements for better performance in outbox pattern. For example, for pulling the table, the outbox table can be partitioned to increase throughput. If we partition the table with a column, and set each consumer instance to read from that partition, we can actually divide the data among instances. This will also prevent reading the same message from different instances of services, because each message will be dedicated to a single instance, thanks to the partition. So there will be no unique constrained exceptions that will slow down the processing, because of retries, as we experienced with thousand concurrent requests in Jmeter load test. Also with partitioned table, we will truly run each partition in parallel by running N number of consumer instances; where N is equal to the partition number on the outbox table. Then if we have N number of partitions on Kafka topics as well, we can run each partition in parallel end to end. A better option can be using multiple outbox tables for each instance of a service. This can be used for both pulling the table, and change data capture approach. In pulling the outbox table, each instance will create data on its table, and consume and process it. In change data capture, we can create debezium connectors for each outbox table that is running for each instance. In that case, for postgres, we need to set the max slot size equal to the number of outbox tables, as mentioned before. Remember, this can be set in the Postgres configuration file. Actually, this is the only way to create some parallelism with change data capture. Because as I mentioned before tasks max property cannot be more than one, and there is a sequential read for the transactional log of a table, as you can see here for Postgres. So it is actually better to have multiple outbox tables instead of using a single table, with different aggregate types, And for better performance and for better distribution of work, using different outbox tables per instance of a service can be an option. Again, multiple connectors in Postgres require more replication slots. This will create a more complex architecture, so it should be chosen if that performance improvement is really necessary.
