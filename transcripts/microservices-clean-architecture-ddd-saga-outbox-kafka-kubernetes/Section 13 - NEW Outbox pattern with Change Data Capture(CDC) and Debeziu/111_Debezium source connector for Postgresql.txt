# Debezium source connector for Postgresql

Hi everyone, in this lecture, I will create the Debezium Postgres source connectors. I will go and open Postman and create my first connector request. I will use localhost 8083 port, which is the port that Debezium connector is running, and I will use connectors URI with Post method. As the JSON body, I will use the following content. Please note that you can get this JSON body as well as the required config changes of Postgres in the resources section of this lecture, I also provided the final source code with change data capture implementation in the last lecture of this section. Here I give the connector name as order-payment-connector. As you see, I use Debezium Postgres connector for the connector class. Here tasks.max is set to one, and actually this cannot be more than one with any Debezium database source connector. Specifically for Postgres, it is mentioned here as you see that is natural because the data changes of Postgres are written sequentially to write ahead log and replicated to a slot as mentioned and then it's read by the consumer again sequentially. So with a single connector, we cannot have enough parallelization for better performance. For concurrent processing, we need to create multiple connectors that reads from different slots for different tables. And since I already have four outbox tables, I will actually use four different slots and four different Debezium connectors for each outbox table, I will touch to this tasks.max property and possible concurrent processing in change data capture implementation of outbox pattern in the implementation part in the coming lectures. Alright, so I have the database host name, port, user and password, and the database name and the server name here. As you see, I just used host.docker.internal for the host name. This is because I run the connector in Docker and I use the Postgres running on my laptop to reach the Postgres running on the host platform from the Docker container, I just need to provide host.docker.internal as the host name. Then I have table.include.list as order.payment_outbox here. So this connector will listen the payment outbox table in order schema, which is one of the outbox tables in the order schema. Here I specify the topic.prefix as debezium, and this is mandatory in Debezium Connect 2.2 version. I might also use schema include lists to list in all tables in a schema. Then I have tombstones.on.delete set to false here. This means if a record is deleted, the tombstone event will be discarded. A tombstone event is just a marker that the row is deleted. So before physically deleting a record in Postgres, a marker is set on the record. And for this, a new event with key and with null value is created. Usually this event is not required by the consumer so I just ignore it here. Then the slot.name property set to order_payments_outbox_slot. This is the slot that I explained in the previous lecture. So each connector will have a dedicated slot that the data will be written from Postgres transaction log and be read by the connector. If you deploy multiple instances of Debezium Postgres connector, you must sure to use distinct replication slot names. Remember I used max_replication_slot four in the Postgres configuration, so I will have enough slots for all four outbox tables in the project. So if you need more connectors with different slots, we need to adjust the max slots in the Postgres configuration and restart Postgres. Then I have plugin.name as pgoutput here. As I mentioned, I will use the default replication plugin of Postgres, which is pgoutput after Postgres 10 version. So specifying the plugin name is enough here. And remember I didn't set any library name in the Postgres configuration file for this purpose. As mentioned, if I used another plugin such as wal2json, I had to install it and set it in the Postgres config file. Now let's see the Debezium connector in action. Before creating the connector, I will run the zookeeper and then the Kafka cluster docker compose file, which has the Debezium connector container. Let's send the connector request. I can list connectors using get endpoint localhost:8083/connectors. I can also delete the connector using delete endpoint by giving the connector name, but I will not delete it now. Then I will run the order service to create the outbox table using the init schema SQL file which runs automatically during startup when I run the order service. Now in the PG admin console, I will insert a record into this table. But before running this insert, let's open Kafka UI. As you see, I have a Kafka UI docker container in the Kafka cluster compose file. Here I specify the bootstrap servers to connect to my local cluster. Great, let's insert the data now in the PG admin console. Here I first create UUID extension to use UUID generate method then run this INSERT statement. I provided this INSERT statement in the resources section of this lecture. As you see in Kafka UI, the topic named debezium.order.payment_outbox is created automatically by the Debezium connector after I insert the data in Postgres. Remember I set the topic.prefix as debezium, and the rest of the topic name comes from schema plus the table name. Now, if I check the Debezium connector topic, I will see that it produced a message.
