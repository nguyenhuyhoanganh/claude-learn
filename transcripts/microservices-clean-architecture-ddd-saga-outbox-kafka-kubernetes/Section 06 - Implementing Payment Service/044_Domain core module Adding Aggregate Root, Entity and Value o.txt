# Domain core module: Adding Aggregate Root, Entity and Value objects

Hi everyone In this section I will create the payment service. Please note that this implementation of payment service and the implementation of restaurant service in the next lecture will be similar to the order service following clean and hexagon architectures and applying domain-driven design concepts. If you are confident about these concepts, you may prefer to skip the payment service and restaurant service sections and continue with section eight, that is with saga pattern. You can get the source code payment service and the restaurant service in the first section of the sections or can get it by cloning the GitHub project as explained in the lecture five providing the source code lecture I'll create the payment service module under food ordering system. Let's first create all the sub modules and then start implementing payment domain module. I will delete the source folder and then create four sub maven modules in payment service payment domain payment data access payment messaging and payment container. As in the order service domain module I will delete the source folder and create two sub modules in payment domain module payment domain core and payment application service. Great, so let's start with the payment domain core module. I will add the common domain module as a dependency in the POM xml file. Remember that this was the only dependency to add into the core domain module and it includes the base classes and interfaces such as aggregate root and base entity. Then I will create a base package com food ordering system payment service domain. Then let's create four sub packages, entity, value object, event and exception. Let's start with entity package and create the payment class. I will extend aggregate root from common domain module and use payment ID as the generic type for ID replacement. So I need to go and create a value object payment ID in the value object package here. I will extend base id, which type UUID. Then in the payment class I will add three final fields order id, customer id, and price. For price I use Money value objects. Then I'll add two more fields payment status and created at. As you see, the payment status can be completed, canceled or failed. As I did in the order entity classes, here I had the getter methods for the fields. Then I will use inner builder plugin and create a builder for this payment class. I will replace the ID generic type with payment ID in the builder implementation as I did previously with order oriented classes. Then I will add initialize payment method and set payment ID with a random UUID. Here I will change the access modifier to public for payment id value object constructor and then set the created at field with current time in UTC zone. Then I will add validate payment method and pass the previous failure messages as parameter. Here I will just check the price and if it is not greater than zero I will add a new message to the failure list. Finally, I will add update status method and set a new status to the payment status field. Then I will create another entity called credit entry and extend base entity with credit entry id. Again, here I will create this value object credit entry id in the value object package. I will extend base id, which type UUID I will make the constructor public in this value object. Now in the credit entry class, I will import credit entry ID and then add final customer ID fields and total credit amount fields with money value object. I will add getter methods then I will use inner builder plugin and create a builder. Again, I will change the ID to credit entry ID and use set ID method in the constructor as I did previously for the builder implementation. Also, I will change the new builder methods name to the builder. Let's also change the name of this method in the payment class. So I will name this as builder. Then in the credit entry class I will add credit amount method takes a money value object as parameter and add this value to the total credit amount. Similarly, I will add subtract credit amount method and subtract value from the total credit amount. A final entity here will be credit history. I will extend base entity and use credit history ID as the generic type, so I will create credit history id value object. Again in this value object I will extend base ID with UUID generic type and create a public constructor with UUID parameter. I call the super class constructor with the UUID value here. Then I will add three final fields here, customer ID amount and transaction type. For transaction type I will add an new value object with an ENUM type and with debit and credit options. Then I will create the getter methods and add the builder using the inner builder plugin of IntelliJ. Again, I will replace the ID with credit history ID in the builder and call setId method in the private constructor to set the credit history id. Then I will rename the static new builder method as builder. As you see, I didn't extend credit history and credit entry from aggregate root. Instead, I used base entity. Actually, you can think this credit entry and history as separate aggregate roots. For example if you create a rest API here to top up credits for a customer so they can act independently from a payment. I will not implement this API to top up customer credit here and instead initialize the data from an SQL file. But still, I kept these entities separate to emphasize that they don't necessarily be only included in a payment operation. Let's don't forget to import the UUID in credit history id. All right, after completing the entity and value objects I will continue with exception and domain events in the next lecture.
