# Domain core module: Implementing Payment Domain Service

Now I will create payment domain service interface. Here I will have two methods. First one is validate and initiate payments. It will return a payment event and takes parameters, payments, credit entry, credit history list and failure message list. The second method I want to add is validate and cancel payments. It's same return type payment event and with the same parameters. Let's create the payments domain service input class. I will implement payment domain service interface and override the methods. I will also mark this class with slf4j annotation to use a log variable automatically. Now in the validate and initiate payments methods implementation, I will call validate payment methods on payment object and pass the failure messages as parameters. Then I will initialize payments. And then I want to validate to credit entry. For this, I will create a new method, validate credit entry, and pass payments, credit entry and failure messages as parameters. Let's implement this validate credit entry methods. Here I will check if payment price is greater than the total credit amount of credit entry, and in that case, I will log on error message, and add a new failure message to the failure message list. Because here the price of the payments cannot be greater than the total credit amount of credit entry, which is the total credit amount of a customer. As you see, instead of drawing an error I am accumulating the failure messages into a list. And in the end, I will have all the failure messages to be returned from the payment service to the client. Next, I will create subtract credit entry method and pass payments and credit entry parameters. In these method, I will simply subtract the payment price from the credit entry. Then I will create a new method, update credit history, with payments, credit histories and transaction type debit. In these method, I will add a new credit history record to the list of history objects. Here the transaction type is debit because the amount of the payments will be subtracted from the customer's total credit. Finally, I will create and call a new method, validate credit history and I will pass credit entry, credit histories and failure messages as parameters. In this method, first, I will get the total credit history using a stream on credit histories and filtering it with transaction type credit. Then I will map reduce the amount and get the total of to credit history as a money value object. Similarly, I will get the total debit history. This time I will filter debit transaction type. Actually, it'll be better to create a new private method here and use it to get the credit and debit history total amounts. So we will have less code by using this common method. If the debit total is greater than the credit total, I will log an error message and update the failure messages. And finally, if the total credit amount of the credit entry is not equal to the total debit minus total credit, I will again log an error and add a new failure message. With these crosschecks, I validate if the payment objects are in the correct state. And basically customers should have enough credit to be able to complete the payment, and the historical records of credit must be greater than the debit. Then if the failure message list is empty, I will log an info message and set the payment status as completed and then return a payment completed event. I will pass payment in current time in UTC zone as parameters. Here payment completed event requires a failure message list parameter. However, I will not have any failure message for a completed event. So let's remove the failure message list from the constructor, and instead send an empty list to the super constructor. If the message list is not empty, I will log a message, and set the payment status as failed. Then I will return payment failed event object with payment, current time and failure message list. Let's delete this return statement, as I don't need it anymore. Here for this UTC string, remember that I had created a constant, in the order domain, but I need it also here in the payment service. So let's move it to the common domain module, and use it from each service. For this, I will create a new class domain constant in the common domain module. And add UTC static final field with public modifier. I will also add private constructor to the domain constants class, so that this class will only serve for static fields. So I cannot create an instance of this class because of this private constructor. Now I will use this new constants from order domain service implementation, and from payment domain service implementation. In the validate and cancel payment methods, I will call validate payments methods on payment object, and create and call add credit enter method, with payments and credit entry parameters. This time, I will use add credit amount method on credit entry object to add the price make into the credit amount. Then I will call update credit history method, and this time I will use credit transaction type, because this will top up a credit record into the history. Because here the payment is getting canceled. Then again, if the failure message list empty, I will log an info message and set the payment status as canceled. And then return a payment canceled event. I will pass payment and current time in UTC zone as parameters here. Again, I will remove the failure message list from the payment canceled event constructor, and send an empty list called failure messages will only be needed with failed payments. If the failure message list is not empty I will log a message here and set the payment status as failed. Then I will return payment failed event object with payment, current time in UTC zone and failure messages. All right, payment domain core implementation is completed.
