# Application Service domain module: Adding Mapper, Config and Ports

Hi everyone. Let's continue with the payment application service module under payment domain. Here I have a typo, this module should be named as payment application service, as in the order service So I will rename this module. I will update the payments pom.xml and use the new name. Also, I will update the payment application service pom.xml file to set the artifactID as payment application service. Here I will add payments domain core as a dependency. I need to add this dependency to the base pom.xml file with project version so that I can use it here without two version. Then I will let common domain dependency. Remember that this application service will serve to do outside of domain and will delegate the calls to the core domain module. Then I will add springboot starter validation to use spring validation, and spring tx to use the transactional annotations. And I will create the base package com food ordering system payment service domain. Then I will create submodules, config, exception, mapper, dto. Finally, ports package. In the conflict package, I will create payment service config data class, and use data configuration and configuration properties annotations, similar to the order service config data class. Here I will use payment service prefix for configuration so it will match the configuration data of the application yaml file with the fields in this class. Here I will add payment request topic name and payment response topic name fields for this configuration class. And in the exception package, I create payment application service exception class. I will extend domain exception from common module as in the other domain exception classes. I will use this payment application service exception from the payment messaging module. Now in the mapper package, I will create payments data mapper class. I will add component annotation. I will come back and write mapper methods here as in the mapper classes in the order service. This class will simply be my factory class that will create the domain objects from the input objects and create the output objects from the domain objects. Then I will go to the dto package and create payment request class. I will add getter, builder, and all args constructer annotations. As you know, these are the lombok connotations that I use for other dto classes also. Getter will create getter methods. Builder will create a builder pattern, and all args constructor will create an all args constructor which is required to use the builder annotation. Here I will add do payment request fields. ID, sagaID, orderID, and customerID. These are the string fields. And I will have big decimal price, instance created at, and payment order status. For this one, I will go and create payment order status value objects using an enum type in the common domain module. Here I will have pending and canceled options. In payment request, I will only add settle methods for the payment order status because I will need to update the status based on the result of the business logic on payment domain module. Let's continue with the ports. As you remember, these are nothing but interfaces that needs to be implemented With adapters. I will create two packages, input and output. Remember that there are two types of ports in hexagon architecture, input and output. I will start with input ports and create a package, message listener. Here I will create payment request message listener interface, and add complete payment and cancel payment methods. As you see for both of the methods, I use payment request object as a parameter. Then I will go to output package and create repository package. First, I will create payment repository interface. Here I will have save methods. This will take a payment parameter and return a payment. Then I will add find by order ID methods with UUID parameter and return an optional payment. I will also have credit entry repository with save methods, with credit entry parameter, and the same methods will also return a credit entry. Then I will add find by customerID methods and find a credit entry of a customer by customerID and return optional credit entry. Finally, I will add credit history repository interface. I will have a save method to save the credit history and return the saved object, and also I will have a find by customerID method to get an optional list of credit history objects for a customer. Finally, I will create message publisher package in the output package. Here, I will create payment completed message publisher interface and extend domain event publisher from common domain. As the generic type, I will use payment completed events. Similarly, I will create payment canceled message publisher interface with generic type payment canceled events for the domain event publisher. And finally, I will create payment failed message publisher with payment failed events for the domain event publisher. Now I have completed the ports. As you remember, I will implement the output ports in the infrastructure modules. For repositories, I will use payment data access module and for message publishers, I will use payment messaging module, similar to the implementations in the order service. But for the input ports, I need to implement them here in the payment application service, because it'll be called with domain events from the order service. So let's continue with the implementation of input ports in the payment application service in the next lecture.
