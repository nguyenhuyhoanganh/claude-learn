After updating dependency versions, I will also update Kafka version to the latest one and then remove Zookeeper dependency to use the new craft mode, which allows to run a Kafka cluster without using zookeeper. All right, first I will create a new branch named update to Spring Boot 332, which is based on 315 branch. I will update the pom.xml file with the new versions. As you may know, we hold all versions in a single place in this project, so updating the versions in a single place is easy here. First I will go and update parent Spring Boot version 332 in the base pom.xml file in the properties section. I will also update Maven compiler version as 313 zero Mockito version as 512 zero spring Kafka version as 322, and Kafka Avro serializer version as 770. Then finally our version as 112 zero. These are the latest versions for each dependency. Let's load Maven changes and build the projects. Now I will run Maven clean, install commands and see if the build is successful As you see, the build is successful. So let's continue. Now let's update the Kafka Docker version and then remove zookeeper dependency by using the Kafka craft mode. First, in the environment file, I will use the current latest Kafka docker version for confluent docker image, which is 770. Then I will delete zookeeper docker compose file. And then under the volumes folder I will also delete zookeeper as we won't need it anymore. Now in craft mode I need to generate cluster ID and then format the storage directory with this cluster ID. For this I have two executable files here. Those are runnable files and they will be referenced from the Kafka cluster Docker compose file. As you see, the generate cluster id file uses random Uuid module to create a unique ID and the check cluster id file weights this ID to be created in the temporary directory, and then updates the storage directory with the cluster ID, which is a required step in the craft mode of Kafka. In the Kafka cluster compose file, I have schema registry and three brokers as you see here. Then I also have Kafka Generator, Kafka UI and init Kafka containers. Kafka generator is also an instance of confluent Kafka Docker image, and it uses the generate cluster ID file to generate the cluster id. Then in the Kafka broker containers, we run a command to run check cluster ID executable file to format the storage with the generated cluster ID. In craft mode, we have some additional environment variables for each broker. Let's look at them one by one. Kafka process roles defines the role of this broker. As you see, for each broker we used controller and broker. That means any of the brokers can be the controller of this cluster, while the rest of the containers will only be the brokers. The controller will simply lead the Kafka cluster, taking the role of Zookeeper, which is removed in the craft mode. As I mentioned before, then I have Kafka controller Quorum waters here, which stays the brokers that can be included in voting to find the controller. Again, I used all brokers as the waters here. When having three brokers, it is fine to use each broker as a candidate for controller role, and also use each of them as the voter. In case of more brokers, you may want to change this and use less amount of waters and controller candidates, which can speed up the process of choosing the controller. Here, Kafka log directory is points to the craft logs, and its volume is also mapped in the volume section. As you see, I already mentioned about these commands, which runs the check cluster ID shell file to be able to run Kafka cluster in the craft mode safely. I have the same Neve environment variables in each broker as you see. I moved to init Kafka container inside this Kafka cluster file. If you look at the previous version on this project, the init Kafka was a separate file. However, we can just keep it here as a container so that we will have only one docker compose file to run, as we already removed the zookeeper docker compose file. So I will delete the init Kafka compose file as we will not need anymore. Finally, I have the Kafka UI container here, which has a nice user interface to be able to inspect the Kafka cluster brokers topics and the data. Great. Let's try to run this Kafka cluster file. I will open a new terminal window and navigate to the infrastructure docker compose folder, and then run Kafka Cluster using the docker compose command. I will use cat commands to see if the cluster is created. Then let's use Kafka UI dashboard on localhost 90 zero zero to see if the cluster and topics are created. Remember, the init Kafka container should create the topics when this single docker compose file runs. All right, everything looks good here. Great. Now let's run the services. First I will run the customer service, then order service, then payment service. And finally restaurant service. First let's create a customer using customer Rest endpoint using localhost 8184 endpoint. I will use postman and send the Post request using the JSON body to create the customers. I have the JSON bodies in the repository under the JSON files folder. Now I will send a Post request to order service Rest endpoints which runs on 8181. Here I send customer ID and restaurant ID, address, price and the items information. First I see that the order is in pending status. It should go to paid state and finally in the approved state I should see it if there is no error. All right.
