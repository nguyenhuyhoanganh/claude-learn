# Deploying Confluent Kafka to local Kubernetes using cp-helm-charts

Hi everyone. Let's run Kafka on Kubernetes. I want to use Confluent Kafka with Schema Registry, and currently the easiest way to use Schema Registry with a Kafka cluster, is using Confluent Kafka operators for Kubernetes. For production, it is a paid service by Confluence. However, for proof of concepts and to use in test and development environments, we can still use cp-helm-charts project. This is an open source, unofficial Confluence Kubernetes solution. To easily use the cp-helm-charts locally, I will simply clone the project into my local repository. For this, I will create a new project, food-ordering-system-infra. I will delete the source folder here as I will not write any source code, and then I will initialize this project as a Git project, using git init command. Now I'll create a new folder, helm, and open this folder in Terminal, and I will use git clone commands and clone the cp-helm-charts into this helm folder. Now, to run these charts I need Helm. Here is the installation steps for Helm. I will simply use brew install command to install Helm on my Mac machine. Please install it according to your operating system. Then I will run helm install command and give a name to my Kafka helm clusters, like local-confluent-kafka, and then specify the cp-helm-charts directory. Then for version I set 0.6.0. As you see, this command is mentioned here in the cp-helm-charts GitHub page. Again, as you see, it runs and also suggests some commands to test the cluster. Here also, an example, Kafka clients, to connect Kafka from a client pod. First, I will run kubectl get pods command, and be sure that all the components run correctly. I will be sure that I see running status for all pods. Now I will create this Kafka client deployment, and create the topics. For this, let's create (indistinct) YAML file, for Kubernetes, in the infra project. I will create kafka.client.yml file, and put the content of this file as suggested. As you see, the client is a pod here. I have the apiversion:v1, which is the first stable version of Kubernetes, and as the metadata, I have the kafka-client as name, and I use default namespace. The namespace allows different projects, teams, or customers to share a Kubernetes cluster. So when I use default namespace, this pod will be able to communicate with the other containers in the default namespace. Note that the cp-helm-charts will create Kafka cluster in default namespace, by default. Then I have this spec definition for containers. Again, I set the same name for containers, kafka-client, and then I set the Docker image name, which is cp-enterprise-kafka, with version 6.1.0. Then as a command, I run sh, which invokes the default shell, and uses its syntax, -n flags. -: c flag, means to execute the following commands, which is here exec tail, for the /dev/null directory. I will use kubectl apply command to create a new pod for this container. However, first, I need to make an update on PodDisruptionBudget YAML file. With Kubernetes version 1.25, PodDisruptionBudget is not available in the policy/v1beta, but instead it is available in policy/v1. So please open PodDisruptionBudget YAML file under charts/cp-zookeeper/templates folder and change policy/v1beta to policy/v1. Now I will run kubectl apply -f kafka-client yml command. This will create a new pod that includes a container with the cp-kafka-docker-image. If I run kubectl get pods command, I should see the new pod is running. Then I will go into this pod using kubectl exec command. I will use -it option, give the name of the pod, kafka-client, and use /bin/bash as the shell. Here it says to use a double dash in the new version, so it will be simply this command. Inside the Kubernetes pod, I will run the required commands to create the Kafka topics. Let's write the first commands to create the customer topic, which is required in customer and order services, as you can remember. I will type kafka-topics--zookeeper, and give the zookeeper host name and port. As you see in the locks of cp-helm-charts, I need to use this host name, local-confluent-kafka-cp-zookeeper-headless, with port 2181. Then I set the topic name, "customer" and use create option, and then set partition and replication factor as three. I will also add, -: - if-not-exists flux. As you see, the customer topic is created. Similarly, I will create the other kafka topics, payment-request, payment-response, restaurant-approval-request, and finally the restaurant's approval response. Remember that these topics are required in our microservices. Let's also run Kafka topics list commands to see the list of topics. I will again use ZooKeeper, with host name local-confluence-kafka-cp-zookeeper-headless, and with 2181 port. I will create a new file here. Create topics sh. To delete and create these five topics, I will need these commands when I deploy to Google Clouds so it is good to have them in this file. I simply use double dash delete flag with "if-exist" condition, and then delete the all five Kafka topics. Then here I add the create commands for each Kafka topic. Actually, here, let's make the ZooKeeper host parametric so that I can reuse this file with Google Cloud. I will use Stellar one for the zookeeper host name, so this file will accept the zookeeper host name as the first parameter. Now I have the Kafka cluster up and running in Kubernetes, and it includes the required Kafka topics. Finally, if you want to stop and remove the Kafka cluster you can simply use helm uninstall commands, with the name of the cluster. If I run kubectl get pods commands after running uninstall commands, I see that all pods are terminating. Let's also delete the Kafka client's deployments using kubectl delete commands, and pass the deployment file kafka-client-yml. Alright, after having the Kafka cluster running on Kubernetes, in the next lecture I will run the microservices on the same local Kubernetes clusters. So I will see you in the next lecture.
