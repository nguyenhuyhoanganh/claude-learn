Hi everyone. Now, I will deploy the microservices into local Kubernetes cluster. Let's first, go to helm folders and deploy the Kafka clusters using helm-install command. I will give the cluster name as local-confluent-kafka and set the folder name, CP-helm-charts, with version zero six zero. If I use kubectl-get-pods command, I should see the pods in running state. Okay, I will open another terminal window on the main directory of the project, and then run kubectl-apply-minus-f-application-deployment- local-YML command. Let's check with kubectl-get-pods command. All right. Here I got some errors. Let's check the logs using kubectl-logs command for one of two services. As you'll see here, I got an incompatibility on the compile and target Java versions. I cannot run a Java application with a version that is older than the compiled version. As you can remember, I have the Maven compiler plugin, which is set to Java 17, so I compiled my code with Java 17. Also, remember that I create my docker images using Spring Boot Maven plugin with build image goal, and this docker image actually constructs my runtime version for Java. When I check the plugin documentation, it says it uses compiler's plugin configuration, or the Maven compiler targets property. Apparently, it cannot pick up the correct Java version from the Maven compiler plugin, so I will add Maven compiler targets property into the property section of the base POM XML file. Then, I will run Maven-install command again. Meanwhile, I will delete the application deployment using kubectl-delete command in the info project. Indeed, this time, Spring Boot Maven plugin uses JDK 17 to create the docker image, as you see here. So this time, I should get the correct Java version, 17, for run time, and is the Java version of the compile time also. After creating the docker images again with the correct Java run time, let's run kubectl-apply-minus-F-application- deployment-local-YML command. This time, I got all the services with running status, as you can see. Let's test the application using Postman. First, I will add some customers using the customer service post API. I will add customers user underscore one, and use the UU ID that is used in the payment service data in its file. And then, I will go to order service customer table. As you see, I can see the customer here also in the order service schema. And remember, this order service customer table is updated asynchronously using CQRS pattern. Now I will send an order. Let's open the Postman top for order service. I will use local host eight one eight one, and send the same requests that we have used before. I got the tracking ID. If I query the get endpoint using this ID, first, I will get the order in pending state, then it'll go to the paid state, and finally, it is approved, as you can see, so the whole saga flow run successfully. I can go and check the logs in Kubernetes pods also. I will run kubectl-get-pods commands, and get the pods name of the order service, and then I will use kubectl-logs ALT name. You can also use minus-F option here to follow the logs. As you see, in the order service logs, the order is first created in the local database, and the event is saved into outbox table, then the outbox event is published to Kafka with the first saga step, which triggers payment service, and when payment is completed I get another event in Kafka, this time, for order service. So the order service got the payment completed event and then updated the order as paid, and proceeds to the next saga step. It publishes a paid event into another Kafka topic, and restaurant service gets these events and approve or reject the order. Here, it is approved, and the new event is published into another Kafka topic. Finally, the order service gets this order approved event and completes the order with approved status. As we did previously, you may also check the Postgres database using PGadmin, and Kafka topics using kafkatool, or kafkacats to get better understanding of the exchange events and the results.
